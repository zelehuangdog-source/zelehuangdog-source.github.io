> **摘要**：垂类 Agent 构建知识库时，最常见的做法是把所有领域知识不加区分地编译进同一套存储管道。本文提出：领域知识按性质分为四类（关系型、事实型、规则型、隐性型），每类有天然适配的存储载体（图、向量、Skill、模型权重），Agent 通过各载体透出的描述信息自主路由，按需调用。不写死管道，不预设检索链路。

---

#### 一、垂类 Agent 的建设点

当前各大厂商已经提供了通用 Agent（如 OpenAI Codex、Claude Code），它们基于大模型封装了 ReAct 循环、工具调用、多步规划、代码执行等通用能力。现在流行的构建垂类agent的方式就是基于这些通用agent，针对自己的垂直领域构建专业化的垂类 Agent。垂类 Agent 的差异化在以下五个建设点：

| 建设点 | 解决的问题 |
|--------|-----------|
| 领域知识 | Agent 懂什么 |
| 领域工具 | Agent 能操作什么 |
| 工作流设计 | Agent 按什么流程执行 |
| 评测 | 怎么衡量 Agent 做得好不好 |
| 反馈 | 怎么让 Agent 越来越好 |

五个点里，**领域知识是地基**。工具再强，不懂业务就是瞎操作；流程再完善，知识不对就是在错误的方向上高效运转。

但"领域知识"三个字说起来简单，落地时最常见的做法是：开一个向量库加一个图库，把领域知识不加区分地同步编译进去，查询时通过图收敛、向量增强之类的策略做检索。

看起来很完善，但问题在于——**所有类型的知识被揉在了一起**。垂类领域的知识不是一种东西，硬塞进同一套存储和检索管道，要么装不下，要么用不好。

本文专讲：垂类 Agent 的知识库该怎么建。

---

#### 二、知识不该揉在一起

工程领域有个共识：不同性质的数据用不同存储。交易流水用 MySQL，会话缓存用 Redis，全文搜索用 ES，实时指标用时序数据库。没人会把所有数据塞进同一个 MySQL 然后靠查询策略去适配所有场景。

但到了 Agent 知识库建设，这件事反而被忽视了。领域文档、实体关系、规则说明往往被编译进同一套管道，靠检索策略去适配所有类型的问题。

这就像把交易流水、用户画像、实时日志全写进 MySQL，然后靠索引优化和查询技巧去硬撑——能跑，但每种数据都用得别扭。

**垂类 Agent 尤其不能这么干。**

举个例子：同样是"订单"领域，外卖订单、酒店订单、打车订单的知识结构完全不同：

- 外卖订单：关注配送链路拓扑、骑手调度规则、超时判定逻辑
- 酒店订单：关注房态库存关系、取消政策规则、价格日历计算
- 打车订单：关注路径规划图、计价规则引擎、供需匹配模型

如果把三个领域的知识全灌进同一个图 + 向量的混合管道，检索时就会互相干扰——Agent 问"超时订单怎么判定"，向量检索可能把酒店的取消超时和外卖的配送超时混在一起返回。

垂类的意思就是：**一个领域一个知识库，且同一领域内，不同性质的知识也要分开存储。**

---

#### 三、四种知识，四种载体

知识管理领域有多种分类方式——Polanyi（1966）区分 explicit/tacit，Nonaka & Takeuchi（1995）扩展为 explicit/tacit/procedural/declarative。这些分类面向的是"知识的认知属性"，不直接回答"用什么技术载体存"。

本文从**工程落地**的视角出发，按"什么载体能最自然地承载这类知识"重新划分为四类。这不是学术定论，而是一种面向 Agent 系统建设的实用分类：

| 知识类型 | 本质特征 | 存储载体 | Agent 调用方式 |
|---------|---------|---------|--------------|
| 关系/结构型 | 实体间的连接与拓扑 | 图数据库 | 遍历查询，查询本身即答案 |
| 事实/文本型 | 非结构化的描述、解释、经验 | 向量库 | 语义检索 + LLM 理解 |
| 规则/过程型 | 确定性流程、硬约束、判定条件 | Skill（过程知识包） | 按需加载指令，确定性执行 |
| 隐性/经验型 | 专家直觉、模糊判断 | 模型权重（Fine-tuning） | 内化在推理过程中 |

**Agent 如何灵活调用这四种载体：**

每种载体向 Agent 透出一段描述（第五节详讲），Agent 根据用户问题的性质，自主决定调哪个、调几次、什么顺序。不写死管道，不预设调用链路。

一个问题可能只命中一种载体，也可能需要串联多种。比如"这条核心链路下周能不能变更"：
1. 调图 → 确认链路拓扑和影响范围
2. 调 Skill → 判断是否在封版期内
3. 调向量库 → 检索历史类似变更的经验教训
4. 综合给出结论

**与常见落地方式的区别：**

GraphRAG 等框架本身并非只有一条固定管道——Microsoft GraphRAG 有 Local/Global 模式，LlamaIndex 有 Router Query Engine，LangChain 有 Agentic RAG pattern。但在实际落地中，大多数团队的用法仍然是：query 进来，图收敛一下，向量增强一下，拼成 context 丢给 LLM，每次走全套。本文批判的不是框架能力，而是这种**不区分知识类型、一条管道硬撑所有场景**的常见落地方式。

分类载体的做法是**Agent 自主路由**——不同性质的问题走不同的路径，该查图就只查图，该调 Skill 就直接调 Skill，不需要每次都过一遍完整管道。更精准，更高效，也更容易维护和扩展。

#### 四、为什么必须分开——逐类举例

##### 1. 关系/结构型 → 图数据库

**场景**：Agent 需要回答"OrderService 挂了，哪些服务会受影响？"

这个问题的答案藏在拓扑里：

```
(FrontEnd)-[:CALLS]->(OrderService)-[:CALLS]->(PaymentService)
                                    -[:CALLS]->(InventoryService)
                                    -[:CALLS]->(NotificationService)
```

一次图遍历，沿着 CALLS 边往上游走，立刻拿到所有受影响的调用方。**查询本身就是答案**，不需要 LLM 做任何理解和推理。

**反例：如果把调用关系存进向量库会怎样？**

你得把"OrderService 调用 PaymentService"写成一段文本，切成 chunk，embedding 之后存进去。用户问"OrderService 挂了影响谁"，向量检索靠语义相似度去捞——可能捞到一段提到 OrderService 的故障复盘文档，但那是历史经验，不是实时拓扑。而且三跳、四跳的间接依赖，向量检索根本发现不了，因为那些 chunk 里可能压根没出现"OrderService"这个词。

**一句话**：关系型知识的价值在"连接"，不在"描述"。图天然表达连接，向量只能表达相似。

---

##### 2. 事实/文本型 → 向量库

**场景**：Agent 需要回答"竞业协议中，离职后多久内不能加入竞对公司？"

答案藏在一段法律条文里：

> "竞业限制期限不得超过二年，自劳动合同解除或终止之日起算。用人单位应按月向劳动者支付经济补偿，补偿标准不低于劳动者离职前十二个月平均工资的30%……"

这段知识的价值不在"什么连着什么"，而在**文字本身的含义**。你需要 LLM 去理解"不得超过二年"和"自解除之日起算"的语义，才能给用户一个准确回答。

**反例：如果把法律知识建成图会怎样？**

你可以建一个图：`(竞业协议)-[:包含条款]->(期限条款)-[:规定]->(不超过两年)`。但这只抓到了结论，丢掉了上下文——"补偿标准不低于30%"这个关联条件、"自解除之日起算"这个起算点、各地司法实践的差异解释，全部丢失了。法律知识的价值恰恰在那些**需要上下文才能正确理解的细节**，抽成三元组就变成了断章取义。

**一句话**：事实型知识的价值在"内容"，不在"结构"。向量保留完整语义，图只保留骨架。

---

##### 3. 规则/过程型 → Skill

**场景**：Agent 需要判断"PaymentService 这周三能不能上线变更？"

这个判断有一套硬规则：

```
输入：service_name, change_date
判断逻辑：
- 查日历：本周是否为封版期 → 是 → 禁止
- 查 SLA：该服务是否 4个9 且无回滚方案 → 是 → 禁止  
- 查窗口：距离变更日不足 7 天且未提前报备 → 是 → 禁止
- 以上均不命中 → 允许
输出：允许/禁止 + 具体原因
```

条件满足就是满足，不满足就是不满足。封装成 Skill，Agent 调一次拿到确定性结论。

**反例：如果让 LLM 自己判断会怎样？**

你把规则写进 prompt："封版期内禁止变更，4个9服务需要回滚方案……"。LLM 可能：
- 算错日期（今天周一，周三是不是7天内？LLM 做日期计算出错率很高）
- 漏条件（prompt 太长时遗漏某条规则）
- 无法查实时数据（封版日期每个季度都变，写在 prompt 里就是过时信息）

确定性逻辑交给确定性执行，不要让概率模型做 if-else 的活。

**一句话**：规则型知识的价值在"确定性"。Skill 执行一次永远对，LLM 推理十次可能错三次。

---

##### 4. 隐性/经验型 → 模型训练

**场景**：Agent 需要判断"PaymentService 对 BankGateway 是强依赖还是弱依赖？"

你第一反应可能是：写几条规则不就行了？

```
尝试写规则：
- 有降级方案 → 弱依赖？
- 调用量占比 > 80% → 强依赖？
- 在核心链路上 → 强依赖？
```

但实际情况是：
- PaymentService 有降级方案（异步重试），但 BankGateway 挂超过 5 分钟用户就开始投诉——**按方案是弱，按体感是强**
- 调用量只占 30%，但那 30% 全是真金白银的支付——**按量是弱，按业务影响是强**
- 问三个架构师，可能给出三个不同答案，而且**都有道理**

这就像"给一篇文章打分"。你可以列规则：字数够不够、结构清不清晰、有没有错别字。但文章好不好终究是一个整体感知，规则只能覆盖很有限的维度。真正的判断力来自读过大量好文章和烂文章之后形成的**直觉**。

技术上：用大量专家标注的"强弱依赖判断案例"做 Fine-tuning，让模型内化这种模糊判断。模型学会的不是几条规则，而是专家在各种边缘情况下的判断倾向。

**反例：如果用 Skill 硬编码规则会怎样？**

你写了一套规则，覆盖了 60% 的 case。剩下 40% 全是灰色地带——有降级但降级不够快、调用量不高但影响金额大、不在核心链路但关联了核心链路的上游……每发现一个新 case 就加一条规则，规则越来越多，互相冲突，最后维护成本比训练模型还高。

**一句话**：隐性知识的价值在"判断力"，规则写不尽的灰色地带，只能靠模型内化。

#### 五、串联：让 Agent 知道该找谁

四种载体分开存了，Agent 怎么知道某个问题该调哪个？

靠每种载体向 Agent 透出的描述信息。Agent 不需要知道里面存了什么具体内容，只需要知道"这个载体能回答什么类型的问题"。

| 载体 | 透出什么 | Agent 据此判断 |
|------|---------|--------------|
| 图 | 完整数据模型（节点类型、边类型、属性、示例查询） | "这个问题能通过拓扑遍历回答吗？" |
| 向量库 | 知识覆盖范围（有什么主题 + 不覆盖什么） | "这个问题需要文档知识吗？这个库里有吗？" |
| Skill | 每个 Skill 的 name + description + when_to_use | "这个问题需要确定性判断吗？哪个 Skill 对口？" |
| 模型训练 | 无需透出——已内化在推理中 | 模型自动运用，不需要显式调用 |

**图透出数据模型**：

```
节点：Service(name, appkey, sla_level), Database(name, type)
边：CALLS(qps, timeout_ms), READS(table_name), DEPENDS_ON(type)
示例：MATCH (s:Service {name:'OrderService'})-[:CALLS*1..5]->(d) RETURN d
```

Agent 看到这个，就知道"下游服务有哪些"该来找图。数据模型本身也体现了为什么要用图而不是 MySQL——同样查五跳下游，SQL 要写递归 CTE 嵌套五层，图数据库一行 `[:CALLS*1..5]` 搞定。跳数越深差距越大，不只是写法简洁，是可读性和查询性能的双重差距。关系型数据库能存关系，但不擅长**遍历**关系。

**向量库透出知识范围**：

```
覆盖：协议迁移指南、故障复盘报告(247篇)、架构评审规范
不覆盖：实时监控数据、服务拓扑关系
```

Agent 看到"不覆盖服务拓扑关系"，就不会拿着"OrderService 下游有谁"这种问题来向量库碰运气。

**Skill 本身就是描述**：

Anthropic 的设计里，每个 Skill 启动时只加载 name + description（约 30-50 token）。Agent 扫一眼描述清单就知道有哪些确定性能力可调用，匹配时才加载完整指令。这套渐进式加载机制天然就是按需路由。

**模型训练的知识是内置的**：

不需要描述透出，不需要显式调用。模型遇到"强弱依赖"这类模糊判断时，自动从训练权重中调用内化的判断力——就像你不需要"查阅"自己的阅读品味，读到一篇文章自然就知道好不好。

**本质**：描述透出 = 给 Agent 一张能力地图。地图越清晰，路由越准确。

#### 六、完整案例：一次变更评估的知识路由

用户问 Agent：**"PaymentService 要从 HTTP 切到 gRPC，下周三能上线吗？"**

Agent 的思考和行动过程：

**第一步：理解问题涉及什么**

这不是一个单一类型的问题。它同时涉及：影响范围（拓扑）、变更规则（确定性判断）、迁移经验（文档知识）、风险评估（模糊判断）。

**第二步：调图——确认影响范围**

```
MATCH (s:Service {name:'PaymentService'})<-[:CALLS*1..3]-(upstream) RETURN upstream
```

结果：OrderService、FrontEnd、MerchantService 三个上游直接依赖 PaymentService。协议切换意味着所有调用方都要适配。

**第三步：调 Skill——判断时间窗口**

```
check_change_permission(service='PaymentService', date='2026-06-04')

→ 禁止。原因：PaymentService 为 4个9 SLA 服务，变更需提前 14 天报备，当前仅剩 7 天。
```

到这里已经有了明确结论：下周三不能上。但 Agent 继续补充信息帮用户做完整决策。

**第四步：调向量库——检索迁移经验**

检索"HTTP 切 gRPC 注意事项"，命中知识库中的《服务通信协议迁移指南》和两篇历史迁移复盘。关键信息：
- 需要灰度期至少 3 天，新旧协议并行
- 历史案例中 InventoryService 切协议时因超时配置未同步导致 P1 故障

**第五步：模型综合前三步信息，给出结论**

模型不需要额外调用任何载体，直接基于前三步拿到的事实（拓扑、规则判定、历史经验），综合组织成用户可直接决策的回答：

> 下周三不能上线。原因：
> 1. SLA 服务需提前 14 天报备，当前仅剩 7 天，不满足窗口要求
> 2. 影响 3 个上游服务（OrderService、FrontEnd、MerchantService），均需适配新协议
> 3. 建议：先完成报备流程，预留至少 3 天灰度期，参考 InventoryService 迁移复盘中的超时配置问题提前排查

---

**这个案例体现的核心逻辑**：Agent 没有走一条固定管道，而是根据问题的复合性质，依次调用了图（拓扑）、Skill（规则）、向量库（经验），每一步都命中了最合适的载体，最后由模型综合所有事实给出结论。如果所有知识都塞在同一个 GraphRAG 管道里，这种精准的分步路由是做不到的。

---

#### 展望

本文聚焦于"知识该怎么分类、用什么载体存"这一核心问题。以下是尚未展开但同样重要的方向：

**扩展性**：当知识量级从百级涨到万级，每种载体都会碰到瓶颈——图的节点爆炸与遍历性能、向量库的语义空间拥挤与检索精度下降、Skill 的规则膨胀与冲突管理、模型训练的标注成本与领域漂移。如何在不改变架构原则的前提下做水平扩展，是工程落地的下一步。

**路由准确性的评测**：Agent 路由错了怎么办？需要建立评测体系——跑一批标注好"该调哪个载体"的 case，度量路由准确率，反向优化各载体的描述质量。


**知识的生命周期管理**：知识不是静态的——链路拓扑每天在变、规则每季度更新、文档持续积累。每种载体的更新机制、一致性保障、版本回溯都是待解决的问题。
