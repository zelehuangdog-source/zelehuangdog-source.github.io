> **摘要**：GitHub 构建了名为 Qubot 的内部分析智能体，让任何员工都能用自然语言查询数据仓库并在几秒内获得答案。其核心架构包括用户界面（Slack/VS Code/CLI）、联邦式上下文层和双查询引擎（Kusto + Trino）。最关键的发现是：结构良好的上下文层不仅提高准确性，还能将返回正确答案的速度提升三倍。文章还介绍了用于部署前回归检测的离线评估框架，以及 Qubot 如何成功实现从集中式支持到自助服务的转变。

大型数据和分析组织往往很难真正实现数据和洞察的自助化。过去几十年里，行业一直试图解决这个问题，但基本没有成功，而现在 AI 给了我们一种可信的方式来实现这一目标。

以 GitHub 的规模，为数十个产品团队提供专属分析支持是一项挑战，因此许多团队不得不自行解决这个问题。虽然产品和工程团队可以利用大量有价值的产品遥测数据来做决策，但要弄清楚该用哪个数据模型、哪种粒度、哪些过滤条件，然后编写查询并验证结果——如果没有数据分析师的支持，这一直都很困难。

Qubot 应运而生，这是我们内部由 GitHub Copilot 驱动的分析智能体。Qubot 让任何 Hubber（我们对 GitHub 员工的称呼）都能用自然语言对 GitHub 数据仓库中的任何数据模型提问，并在几秒内获得答案。

Qubot 不是一个报表工具，也不是仪表盘的替代品。相反，它面向的是探索性问题，比如"哪个用户群在这个功能上的留存率最高？"或"上周哪个产品对推动这个指标的贡献最大？"Qubot 的维护成本为零，并且帮助团队快速上手他们可能不熟悉的数据集。

在这篇博客中，我们将介绍 Qubot 是如何构建的、它经历了哪些变化，以及我们学到了什么。

#### Qubot 的工作原理

架构由三个主要组件组成：用户界面、上下文层和查询引擎。

##### 用户界面

Qubot 可通过 Slack、VS Code 和 Copilot CLI 访问。Slack 界面不需要任何配置，而且是 Hubber 们首选的协作工具。当有人在 Qubot Slack 频道中发布问题时，系统会生成一个 Qubot 实例，作为运行在 github.com 上的 Copilot Cloud Agent（云智能体）。答案直接在 Slack 中提供，用户可以与他人分享结果，也可以在线程中迭代以演化或细化问题。所有结果还会作为 Markdown 报告存储在 Pull Request 中，用户可以参考它来微调查询或用于仪表盘。

Qubot 也可在 VS Code 和 Copilot CLI 中使用，适合希望将体验更紧密集成到工作流中的用户。只需一条命令即可将 Qubot 安装为插件，之后它就可以在 VS Code 或 Copilot CLI 的任何 Agent 会话中使用，与用户配置的其他自定义智能体、技能和工具并存。

##### 上下文层

我们的数据仓库包含不同策展阶段的数据：原始事件（Bronze，铜层）、规范化的事实和维度（Silver，银层）、以及为特定业务场景策展的数据集（Gold，金层）。上下文层以联邦方式构建，知识针对数据类型进行定制。

- 对于 Bronze 数据，我们有产品团队贡献的遥测上下文，包含 schema 信息和元数据。
- 对于 Silver 数据，我们有查询示例、使用指南、必需的过滤条件等，由数据和分析团队维护。
- 对于 Gold 数据，我们有业务规则和指标定义，由拥有这些数据集的团队贡献。

我们还利用 ETL 管道系统性地用额外信号和衍生元数据丰富上下文层。上下文在运行时通过 GitHub MCP Server 加载，从上下文层获取数据。

##### 上下文智能体

上下文层不断用持久化在多个仓库中的新知识进行丰富。在 GitHub，我们主要使用 Markdown 编写文档，所以不需要对接多种不同的工具。

我们通过一个上下文智能体简化了联邦式上下文贡献。团队可以通过标准化模板或引用包含相关上下文的仓库来贡献内容。智能体随后会将这些信息摄取、组织并规范化为一种结构化格式——根据我们的评估，这种格式已被证明对 Qubot 有效。

##### 评估框架

上下文层或智能体配置的每次变更都会在发布前进行评估。当有人想用新知识丰富上下文层时，可以提交一个 Pull Request。新上下文会经过离线评估框架，该框架衡量响应的准确性、找到正确答案的延迟，并在回归问题到达用户之前捕获它们。

用于在结构化测试用例上评估 Qubot 的基准测试框架包含三个组件：

- **测试用例**：一组精心策展的提示数据集，包含已知正确答案、基准 SQL 和元数据（领域、难度）。
- **自动化运行编排**：一个脚本，自动使用 GitHub CLI `gh agent-task create` 将每个测试用例作为 Agent 任务启动，运行多个并行试验，轮询完成状态，并保存详细的 JSON 结果。
- **统计聚合**：一个报告脚本，读取保存的结果并计算每个测试用例的指标：完成率、准确性和耗时（平均/最小/最大）。

端到端流程是：定义测试用例 → 每个用例运行 Qubot N 次 → 收集结果 → 聚合统计 → 比较配置。

##### 查询引擎

Qubot 通过 MCP Server 连接到 Kusto 和 Trino——这两个查询引擎支撑了 GitHub 大部分分析工作负载。我们开发了 Trino MCP Server 的自定义实现，而对于 Kusto，我们部署了 Fabric RTI [MCP Server](https://learn.microsoft.com/en-us/fabric/real-time-intelligence/mcp-overview) 的本地版本。Kusto 速度快，非常适合对近期事件数据的探索性查询。Trino 则处理复杂关联查询和更深层的历史分析。

Qubot 不会强制用户知道该用哪个引擎，而是默认使用 Kusto，当问题需要时自动切换到 Trino。

#### 变化与收获

Qubot 在 GitHub 内部得到了广泛采用，数百名热情用户运行了数千次查询。Hubber 在数据和分析 Slack 频道中提出的问题数量大幅减少，因为现在他们可以更自主地探索数据，只在遇到复杂问题时才寻求帮助。它还让那些从未敢涉足数据仓库的 Hubber 也能获取他们做决策所需的数据。这也是我们提供多种界面（Slack、Copilot CLI、VS Code）的原因之一——Hubber 技术能力很强，但我们希望提供一个零门槛、零配置的选项。

我们很快发现，上下文层是增强 Copilot 推理能力、打造专家级分析智能体的关键。在实验中我们发现，结构化且精心策展的上下文不仅让 Qubot 更准确，还能让它返回正确答案的速度提升三倍。这对分析工程学科有深远影响，因为它使这类工件成为数据建模中的一等公民，而不是事后补充。

Qubot 是中心辐射（Hub-and-Spoke）模式成功执行的罕见案例。它减轻了数据和分析团队的压力，因为产品团队拥有其产品表面的遥测数据，业务团队拥有其 Gold 数据的定义。Qubot 像一个引力场，将所有分散的知识集中到一个可以惠及整个 GitHub 的单一工具中，激励合作团队为 Qubot 做贡献，而不是创建局限于自身领域的多个工具。
