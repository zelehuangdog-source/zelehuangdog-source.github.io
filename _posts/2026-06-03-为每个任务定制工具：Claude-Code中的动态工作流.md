> **摘要**：本文介绍了 Claude Code 中新发布的「动态工作流（dynamic workflows）」能力——Claude 可以为手头的任务即时编写专属的执行框架（harness）。默认的 Claude Code 框架在单一上下文窗口中同时承担规划与执行，这在常规编码任务上很高效，但在长耗时、大规模并行或高度结构化的对抗性任务上会暴露出三类失败模式：智能体偷懒（agentic laziness）、自我偏好偏差（self-preferential bias）和目标漂移（goal drift）。动态工作流通过编排多个拥有各自独立上下文窗口的 Claude 实例来从结构上规避这些问题。作者系统梳理了六种可组合的常用模式（分类路由、扇出汇总、对抗验证、生成过滤、锦标赛、循环至完成），并给出迁移重构、深度研究、事实核查、排序、规则遵循、根因调查、规模化分诊等丰富用例，以及与 `/goal`、`/loop` 配合、设置 token 预算、保存分享等实操建议。核心提醒：工作流会消耗更多 token，要审慎判断何时真正需要更多算力。

上周，我们在 Claude Code 中发布了动态工作流（dynamic workflows）。现在 Claude 可以即时编写自己的执行框架（harness），为手头的具体任务量身定制。

虽然默认的 Claude Code 框架是为编码而构建的，但它对许多其他类型的任务同样有用——因为事实证明，很多任务都和编码任务相似。不过，确实存在某些类别的任务，我们必须在 Claude Code 之上构建定制框架才能达到峰值表现，比如研究（Research）、安全分析、智能体团队（agent teams）或代码审查（Code Review）。

工作流让你能够动态地创建这些框架，使 Claude 能够在 Claude Code 内部原生地解决上述所有问题以及更多问题。你还可以与他人分享和复用这些工作流。

在本文中，我会分享我在工作流上的初步体验和心得，帮助你充分利用它。

话虽如此，最佳实践仍在发展中！动态工作流往往会消耗更多 token，所以要仔细思考何时以及如何使用它们。

#### 示例提示词（Example prompts）

在深入技术细节之前，我想先给出一些示例提示词，帮你打开关于工作流可能性的思路：

- "这个测试大概每 50 次运行才失败 1 次。建立一个工作流来复现它，提出多个理论假设，并在 worktree 中对抗性地测试它们。`/goal` 在某个理论成功之前不要停。"
- "用一个工作流，遍历我最近的 50 个会话，挖掘出我反复做的修正，把那些重复出现的转化成 CLAUDE.md 规则。"
- "用一个工作流，翻遍过去六个月 Slack 里的 #incidents 频道，找出那些反复出现、却没人提过工单的根因。"
- "拿我的商业计划书，跑一个工作流，让不同的智能体分别从投资人、客户和竞争对手的视角把它批得体无完肤。"
- "这是一个装着 80 份简历的文件夹，用工作流为后端岗位给它们排名，并复核前十名。用 AskUserQuestion 工具来面试我，以建立一套评分标准（rubric）。"
- "我需要给这个 CLI 工具起个名字。用一个工作流头脑风暴出一堆候选，再跑一场锦标赛选出前三。"
- "用一个工作流，把我们代码里的 User 模型全部重命名为 Account。"
- "遍历我的博客文章草稿，用一个工作流对照代码库验证每一条技术声明，我不想发布任何错误的东西。"

#### 动态工作流如何运作（How dynamic workflows work）

动态工作流会执行一个 JavaScript 文件，其中包含若干特殊函数，用于生成和协调子智能体（subagents）：

![图像]

动态工作流还包含标准的 JavaScript 函数，比如 `JSON`、`Math` 和 `Array`，用于处理数据。

特别值得了解的是，动态工作流可以决定每个智能体使用哪个模型，以及子智能体是否在自己的 worktree 中运行——这让 Claude 能够选择所需的智能水平和隔离程度。

如果一个工作流被中断（例如因用户操作或退出终端），恢复会话时工作流能够从中断处继续执行。

#### 为什么需要动态工作流（Why dynamic workflows）

当你让默认的 Claude Code 框架做一个任务时，它需要在同一个上下文窗口里同时进行规划和执行。对许多编码任务来说，这非常有效，但在长耗时、大规模并行和/或高度结构化的对抗性任务上，它有时会失效。

这是因为：Claude 在单一上下文窗口中处理复杂任务的时间越长，就越容易陷入以下几种特定的失败模式：

- **智能体偷懒（Agentic laziness）**：指 Claude 在一个特别复杂、多环节的任务尚未完成时就停下，在取得部分进展后就宣告任务完成——例如在一次安全审查中只处理了 50 项里的 20 项。
- **自我偏好偏差（Self-preferential bias）**：指 Claude 倾向于偏爱自己的结果或发现，尤其是在被要求对照评分标准来验证或评判它们时。
- **目标漂移（Goal drift）**：指在多个回合中对原始目标的忠实度逐渐流失，尤其是在上下文压缩（compaction）之后。每一次摘要总结都是有损的，像边界情况要求或「不要做 X」这样的约束细节可能会丢失。

创建一个工作流，通过编排多个各自拥有独立上下文窗口、目标聚焦且彼此隔离的 Claude，有助于对抗这些问题。

#### 动态工作流 vs 静态工作流（Dynamic vs static workflows）

你以前可能用 Claude Agent SDK 或 `claude -p` 创建过静态工作流，来协调多个 Claude Code 实例协同工作。

但因为静态工作流需要适配所有边界情况，它们通常更通用、更泛化。而有了 Claude Opus 4.8 和动态工作流，Claude 现在已经足够智能，能够为你的具体用例编写量身定制的执行框架。

#### 使用动态工作流时的实用模式（Helpful patterns）

你只需让 Claude 创建一个工作流就能开始使用，或者使用触发词「ultracode」来确保 Claude Code 创建一个工作流。

但建立起对动态工作流运作方式的心智模型，会帮助你理解何时使用它们，以及如何通过提示词来引导 Claude。

以下是 Claude 在构建工作流时可能使用并组合在一起的几种常见模式：

![图像]

##### 分类并行动（Classify-and-act）
用一个分类器智能体来判定任务类型，然后根据任务路由到不同的智能体或行为。或者，在最后用一个分类器来决定输出。

##### 扇出并汇总（Fan-out-and-synthesize）
把一个任务拆分成许多更小的步骤，对每个步骤运行一个智能体，然后汇总这些结果。当步骤数量很多，或者每个步骤都受益于自己干净的上下文窗口（这样它们之间不会相互干扰或交叉污染）时，这种模式特别有用。汇总步骤是一个「屏障（barrier）」——它会等待所有扇出的智能体完成，再把它们的结构化输出合并成一个结果。

##### 对抗验证（Adversarial verification）
对每个生成的智能体，再运行一个单独生成的智能体，对照评分标准或判定标准来对抗性地验证它的输出。

##### 生成并过滤（Generate-and-filter）
针对某个主题生成大量想法，然后通过评分标准或验证来过滤它们，去除重复，只返回质量最高、经过检验的想法。

##### 锦标赛（Tournament）
不是去分割工作，而是让智能体在工作上互相竞争。生成 N 个智能体，每个都用不同的方法尝试同一个任务。然后由提示词或模型用一个评判智能体进行两两对决（pairwise）式的评判，直到决出胜者。

##### 循环至完成（Loop until done）
对于工作量未知的任务，循环生成智能体直到满足某个停止条件（不再有新发现，或日志中不再有错误），而不是固定执行若干轮。

#### 用例（Use cases）

要创造性地思考何时以及如何让 Claude Code 制作动态工作流。我发现，工作流有时在非技术性工作上甚至更有用。

![图像]

##### 迁移与重构（Migrations and refactors）

Bun 就是用工作流从 Zig 重写为 Rust 的。你可以在 Jarred 的 X 帖子里读到更多关于这是如何完成的细节。

关键在于把任务分解成一系列需要逐个处理的步骤，例如调用点（callsites）、失败的测试、模块等等。为每一处修复在 worktree 中分出一个子智能体来做这次修复，然后让另一个智能体对抗性地审查，再合并它们。可以考虑告诉智能体不要使用资源密集型的命令，这样你就能最大化并行，而不会耗尽机器资源。

##### 深度研究（Deep research）

我们在 Claude Code 内部发布了一个深度研究 skill（`/deep-research`），它使用了动态工作流。具体来说，它扇出网络搜索、抓取来源、对抗性地验证它们的声明，并汇总成一份带引用的报告。

但你做这类研究不止可用于网络搜索。例如，可以让 Claude 从 Slack 的上下文中编写一份状态报告，或者通过深入探索代码库来研究某个功能是如何运作的。

##### 深度验证（Deep verification）

![图像]

另一方面，如果你有一份报告，想要核查并溯源它引用的每一条事实声明，你可能想生成一个工作流：让一个智能体识别出所有的事实声明，然后为每一条分出一个子智能体来详细核查。你还可以让一个验证智能体去检查溯源子智能体，以确保它的来源质量过硬。

##### 排序（Sorting）

![图像]

你可能有一个列表，想按某种你认为 Claude Code 擅长评估的定性指标来排序，例如：按 bug 严重程度排序的支持工单。但如果你试图在一个提示词里排序 1000+ 行，质量会下降，而且也塞不进上下文。取而代之的做法是：跑一场锦标赛、一条两两比较智能体组成的流水线（比较式判断比绝对打分更可靠），或者并行分桶排名再合并。每一次比较都是它自己的智能体，所以由确定性的循环来维护赛程表，只有当前的运行顺序留在上下文中。

##### 记忆与规则遵循（Memory and rule adherence）

![图像]

如果你有一组特定规则，发现 Claude 总是遗漏或难以遵守（即便把它们放进了 CLAUDE.md），那就创建一个工作流，列出必须由验证智能体检查的规则清单——每条规则配一个验证者。创建一个「怀疑论者」人设的子智能体来审查这些规则、确保它们合理，将有助于避免过多的误报。

反方向也成立：从你最近的会话和代码审查评论中挖掘你反复做的修正，用并行智能体把它们聚类，对每个候选项做对抗性验证（这条规则真能预防一次真实的错误吗？），然后把幸存下来的规则提炼回 CLAUDE.md。

##### 根因调查（Root-cause investigation）

调试最有效的方式是提出几个独立的假设并测试它们，但如果你只用一个上下文窗口，Claude 会陷入自我偏好偏差。

工作流可以从结构上防止这一点：生成多个智能体，从互不相交的证据中产生假设。例如，分别为日志、文件和数据设置独立的智能体。每个假设随后都可以面对一组验证者和反驳者（refuters）组成的评审团。

这不只适用于代码。工作流可以用于销售（为什么三月销售额下降了？）、数据工程（这条流水线为什么失败了？），或任何复盘（post-mortem）演练。

##### 规模化分诊（Triaging at scale）

![图像]

每个团队都有一个支持队列、bug 报告，或某种人类无法完全处理的积压。

分诊工作流会对每一项进行分类、与已经在追踪的内容去重，然后采取行动。这可能意味着尝试修复，或者上报给人类用户。

分诊工作流的一个实用模式是「隔离（quarantine）」。这意味着禁止那些读取不可信公开内容的智能体执行高权限操作，这些操作转而由负责对信息采取行动的智能体来完成。

把分诊工作流与 `/loop` 搭配，就能让 Claude 持续不断地做这件事。

##### 探索与品味（Exploration and taste）

工作流在探索一个问题的不同解法时很有用，尤其是当它基于品味时（比如设计或命名），并且会从一套评分标准中受益。

试着让 Claude 探索一堆解法，并给一个审查智能体一套「好解法长什么样」的评分标准。当审查智能体认为已经满足标准时，任务就完成了。解法也可以基于评分标准通过锦标赛来排序或选取。

##### 评估（Evals）

你可以为特定任务运行轻量级评估：在 worktree 中分出独立的智能体，然后再分出比较智能体，对照评分标准来比较并给具体输出打分。例如，对照某个特定标准来评估并改进你创建的某个 skill。

##### 模型与智能路由（Model and intelligence routing）

创建一个针对你的任务调优过的分类器智能体，由它决定使用哪个模型。当你的任务会涉及大量工具调用、并且在执行前先做研究有助于识别出最适合该工作的模型时，这会很有帮助。

例如，「解释 auth 模块是如何工作的」这个任务的最佳模型，取决于 auth 模块里有多少文件以及代码库的形态。一个分类器智能体可以做这项研究，然后根据任务的预期复杂度路由到 Sonnet 或 Opus。

#### 何时不要使用动态工作流（When not to use）

工作流是新东西。虽然有许多用例它能创造出超额的成果，但并非每个任务都需要它，而且它可能最终消耗显著更多的 token。

最好是创造性地使用工作流，以你以前没有尝试过的方式去推动 Claude Code。对于常规编码任务，试着问问自己：它真的需要更多算力吗？例如，大多数传统编码任务并不需要一个由 5 名审查者组成的评审团。

#### 构建动态工作流的技巧（Tips for building）

**提示词（Prompting）**
为动态工作流编写详尽的提示词、运用我们上面描述的具体技巧，能产生最好的结果。

工作流不只是为大任务准备的。你可以提示模型使用一个「快速工作流（quick workflow）」。例如，你可以对某个假设创建一次快速的对抗性审查。

**与 `/goal` 和 `/loop` 结合**
当使用可重复的工作流时（例如分诊、研究或验证），把它们与 `/loop` 搭配以按固定间隔运行，并与 `/goal` 搭配来设定一个硬性的完成要求。

**Token 使用预算**
你可以为动态工作流设置明确的 token 使用预算，以限制一个任务消耗多少 token。你可以用类似「use 10k tokens」这样的预算来提示它，这会设定一个上限。

**保存与分享动态工作流**
你可以在工作流菜单中按「s」来保存工作流。你可以把它们签入 `~/.claude/workflows`，或者通过 skill 来分发。

![图像]

要通过 skill 分享它们，把你的 JavaScript 工作流文件放进 skill 文件夹中，并在 `SKILL.md` 里引用它们。为了获得更大的灵活性，你可能想提示 Claude 把 skill 中的工作流当作模板（template），而不是一个必须逐字运行的脚本。
