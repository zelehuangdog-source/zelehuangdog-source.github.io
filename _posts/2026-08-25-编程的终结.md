> **摘要**：作者由 Bun 1.4 的 Zig→Rust 重写切入——11 天、100 万行代码、6,778 个 commit、约 16.5 万美元的 token 消耗——指出「人手写代码 + 人逐行评审」的编程范式正在走向终结。作者结合亲身经历：给 Fable 下达需求与架构后，14/28 小时即得到端到端可用的 Iceberg 集成与边缘数据复制系统。Anthropic 和 OpenAI 的开发者已把关注点上移到系统、prompt 与验证工具层，只看结果不看代码。作者预测一两年内前沿智能将便宜到人人可全职使用，未来属于指挥 AI、搭建 harness 和验证体系的「软件工厂」操作者。

上周 Bun 1.4 发布了。这一版包含了把 Bun 从 Zig 重写为 Rust 的工作，据说新增了超过 100 万行 Rust 代码。虽然围绕语言切换，编程社区掀起了一阵风波，但我认为这次发布最重要的不是换了什么语言，而是这次重写是怎么完成的、规模有多大。这些细节，加上我自己的使用体验，以及即将到来的 AI 进展，让我相信：我们已经走到了「我们所熟知的编程」的终点。

我的意思是：靠人手动写代码、再由其他人逐行评审来产出可用软件这件事，正在走向消亡。至少，它会被 Agent（智能体）创造的可用软件洪流淹没——人只评审最终结果，不再看代码本身。我们拥有的软件会比以往任何时候都多，但其中大部分代码不会有人写过、甚至不会有人读过。

当然，随之而来的也会有一座「垃圾山」：满是 bug、毫无用处、粗制滥造的软件，不符合任何程序员的审美和追求。但同时也会有工程质量良好、真正解决实际问题的软件——只是从未被人类的眼睛逐行细看过。

这种软件产出的爆发，在 GitHub 官方博客关于 [8 月 17 日故障的文章](https://github.blog/news-insights/company-news/the-august-17-outage-and-the-work-ahead/)里的那张图上已经能看出来：

从去年开始，代码产出量出现了陡峭的指数式增长。我的推测是：其中大部分来自个人副业项目、公司内部的「秘密项目」（skunk works）或个人用户的仓库——也就是那些被视作「非关键」的东西。在大多数公司，让单个开发者在驱动业务的产品上多产出 2 倍，仍然存在巨大的组织摩擦，更别说 10 倍、100 倍了。

这些图里几乎所有的代码，都不是当前最前沿的模型产出的，而是几个月前的前沿模型产出的——也就是说，不是 Fable 5，也不是 GPT 5.6 Sol。

#### Anthropic 和 OpenAI 的开发者生活在近未来

读 [Bun Rust 重写的细节](https://bun.com/blog/bun-in-rust)，最大的亮点是：这次重写由一位开发者 Jarred Sumner 驱动，他使用的是 Fable 5 的预发布版本和近乎无限的 token 预算。他搭建了一套让 Agent 并行工作的 harness（执行框架），把 Zig 代码库翻译成 Rust。

在 11 天里，多个 Agent 产出了 6,778 个 commit，烧掉的 token 按 API 定价折算大约要 16.5 万美元。

我还记得今年 5 月初、上面那篇博客发布之前，这场重写引发的风波。当时它只是通过[一次合并](https://github.com/oven-sh/bun/pull/30412)暴露出来的，变更量显示 +1,009,257 -4,024。我被这个规模惊到了，并推测他们是用 Mythos 做到的：

> 我特别想知道这是不是用无限的 Mythos token 做出来的。这是我们其他人的「近未来」吗？还是说这就是当下、他们用 Opus 4.7 的 token 就做出来了？我赌是前者。所以这是今年晚些时候才可能实现的事情的一次预演。
>
> — [@pauldix，2026 年 5 月 14 日](https://x.com/pauldix/status/2055000108043837543)

我当时的使用体验是：我不认为 Opus 4.7 能做到这种事，所以一定是尚未发布的 Mythos，才让一次「真的能跑起来」的重写成为可能。

AI 写了 100 万行代码，然后在接下来的几个月里不断打磨，最终产出一个可靠、目前正运行在数百万开发者机器上的软件——这件事简直不可思议。你可以说「这没那么厉害，他们手里有个参照物（oracle，可直接对照验证的原始实现），从一种语言翻译到另一种语言本来就简单」，但我觉得这大大低估了整件事的意义。如果你能搭好一套验证体系、给出正确的方向，AI 就能产出一个高度复杂、高度精密的软件，并且能持续迭代，直到它真的能用。

如果你留意 Anthropic 和 OpenAI 的开发者最近几个月在 X 上的发言，会发现他们每人每周都会合入几十甚至上百个 PR，而且关注点已经上移到了更高的抽象层。这很合理：一个开发者不可能每周逐行细看几百个 PR 的代码，同时还要完成自己的工作。

如果把他们公开说的话当真，他们已经不再逐行评审每一个被合入的改动。他们把时间花在搭建系统、编写 prompt、构建验证工具上，让 AI 规模化、高速地产出软件。至少当他们谈论「loop」（改进循环）时，我是这么理解的。

他们身处一个拥有无限 Fable 和 Astra（OpenAI 下一代模型）额度的世界。他们活在我们这些「平民」大概一年后才会体验到的近未来里。他们用 AI 开发软件的体验，和站在场外等着每周 Fable 额度重置的我们，完全是两回事。

Bun 1.4 的发布让你得以一窥：当 Fable 级别的智能配上近乎无限的 token，会发生什么——大规模的软件交付，真的能用，而且在数百万个实际部署上得到了验证。

#### 来自一线的经验报告

说两件我最近的亲身经历。我的直觉感受是：Fable 和之前的模型有质的区别，就像去年 11 月底发布的 Opus 4.5 让人们感到的不同一样。它跨过了一个门槛：只需更高层级的指令和更少的监督，就能产出更多东西。我可以给它需求、架构和实现说明，它能在我不做任何干预的情况下，连续工作数小时，产出一个功能完整的第一个版本。

我的两个例子都还没在 InfluxDB 正式发布，是我在 fork 里新造的能力。我选它们就是为了看看新模型能做到什么程度。

第一个是 Iceberg 集成：让 InfluxDB 中的数据可以通过 Iceberg REST 访问，或者落到外部 S3 bucket 和 Glue catalog 上。这是一个复杂特性，需要：

- 启用该功能的 API 和 CLI
- Iceberg REST API 的实现
- 与 compactor（压实器）深度联动，在外部存储中生成 Iceberg manifest 和 Parquet 数据
- 生成 Iceberg manifest，或向 Glue 发起请求
- 在 InfluxDB 内实现 S3 API，用于非导出场景

这是几千行的实现和测试代码。我敲定了粗粒度的架构设计和需求，然后指挥 Fable 通过 sub-agent（子代理）干活、触发代码评审、并监督整个过程。14 小时后，它产出了一个能跑的版本。我接着让它用一个运行中的 InfluxDB 集群做端到端验证，外部客户端用 DuckDB 和 PyIceberg。它修了几个 bug，验证一切正常。

第二个例子是为 InfluxDB 打造一个边缘数据复制系统：多个独立的 InfluxDB 节点作为卫星节点，周期性地把压缩后的数据复制到一个中心 InfluxDB 集群。它定义了：

- 设置复制内容和频率的 API
- 访问上述功能的 CLI
- compactor 的更新：用于过滤、聚合、生成待复制的压缩数据，并跟踪哪些已上传、哪些还没传
- 边缘节点访问 catalog 信息的 API，供复制载荷使用
- 接收压缩数据块进入管线的 API
- 让整套系统可观测的指标和系统表

我列好架构，给出了用户体验应该长什么样的示例。我和 Fable 协作产出了设计，然后让它去实现，我充当监督者。28 小时后，它有了一个基本可用的实现。

接着我指挥它把系统部署到我们 AWS 里的测试基础设施中，观察指标和日志，边跑边修 bug。短短几轮迭代之后，它就达到了端到端可用的状态，而且几个月后的今天还在运行。我后来甚至让它顺手做了一个 UI，展示各节点之间的复制动作和数据传输速率——纯粹是因为，为什么不做呢。

当然，这两个东西目前都没有正式发布、没有支持承诺，也算不上我所说的「生产可用」软件。所以你可以套用很多人对 AI 的评价：它帮你更快地做出原型。但这么说其实低估了它。

原型就是能用的软件。而且原型的改进和测试，可以靠更多与 AI 的改进循环继续推进——它不是靠人类代码评审变好，而是靠使用和测试变好。

这两件事我都是用每周的 Fable 额度和我的订阅做完的（中间还得等一周额度重置）。我没做到的，是把它放到云端、接上一个有无限 Fable 额度的改进循环。如果把最顶级的前沿 Agent 派出去 7×24 小时听我号令干活，每个月大概要烧掉几十万美元，我们付不起。

Jarred 用 11 天完成了 Rust 重写，但之后又让 Agent 持续改进了好几个月，才把它作为正式支持的版本发布。原型只是起点，Agent 同样能帮你交付迭代过、打磨过、加固过的生产级产品。

#### 我们这些编程平民的近未来

去年的这个时候，我们手里是 Opus 4.1 和 GPT-5。现在你用零头的价格就能买到更强的智能。去年 11 月底和 12 月初，我们迎来了 Opus 4.5 和 GPT 5.2。正是这两个模型，让每个 CTO 在寒假期间坐立不安：居然可以随口就造出功能和软件。

我预计今年 OpenAI 和 Anthropic 还会有一两个大发布。我最乐观的猜测是：OpenAI 的 Astra 会在 9 月某个时候到来，达到 Mythos/Fable 级别，而且很可能比 Fable 5 更强。

我预计对标 Opus 4.5 和 GPT 5.2 那种「跨过门槛」级别的 Fable 和 Astra，会出现在今年年底或明年初。

那种水平的模型智能和能力，将能为你的软件造出你能想到的任何功能。而且它能跑。而且它能帮你测试和验证。它的交付速度只取决于你多愿意接收代码。唯一的问题是：你想发布什么？你想维护什么？

到明年年底，这种水平的智能会便宜到我们大多数人都能全职使用它，就像 Jarred 当年能用预发布版 Fable 产出 Bun 1.4 一样。

再过一两年，我们将能广泛用上 token 产出速度快 10 到 100 倍、成本只要零头的系统。看看 [Cerebras C4 的发布](https://www.cerebras.ai/cs4)和 [OpenAI Jalapeño 的结果](https://x.com/firstadopter/status/2092266927377039838)。更快、更便宜的前沿智能触手可及的日子就要来了。

组织惯性可能意味着，还会再有十年：人手动写代码，同事逐行评审。很多（甚至大多数）公司会继续像从前一样开发软件。

但最高效的软件创造者，将不再以任何传统意义上的方式「编程」。他们会指挥 AI、搭建 harness 和「软件工厂」、构建 QA 和验证体系，以前所未有的速度交付能用的软件。

而我们将抵达这样一个节点：AI 写的、正在生产环境运行的软件，比人写的多。那就是编程的终结。
