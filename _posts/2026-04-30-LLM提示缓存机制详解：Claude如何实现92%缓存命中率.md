#### LLM 提示缓存机制详解

> 以 Claude 如何实现 92% 缓存命中率为案例

每当 AI Agent 执行一个步骤时，它都会将**整个对话历史**发送回 LLM。

这包括系统指令、工具定义，以及三轮对话前就已经处理过的项目上下文。所有内容每一轮都会被重新读取、重新处理、重新计费。

对于长时间运行的 Agent 工作流来说，这种冗余计算往往是整个 AI 基础设施中**最大的成本项**。

一个 20,000 token 的系统提示在 50 轮对话中运行，意味着 100 万 token 的冗余计算被按全价计费，却**产生零新价值**。而且这个成本会随着每个用户和每个会话不断累积。

解决方案就是**提示缓存（Prompt Caching）**。但要用好它，你需要理解底层到底发生了什么。

#### 静态上下文 vs 动态上下文

在优化提示之前，你需要理解什么会变，什么不会变。

每个 Agent 请求都有两个本质不同的部分：

- **静态前缀**：在各轮对话中保持完全一致——系统指令、工具定义、项目上下文和行为准则。
- **动态后缀**：随每轮对话增长——用户消息、助手响应、工具输出和终端观察结果。

这种分离正是提示缓存得以实现的基础。基础设施存储静态前缀的数学状态，使得后续共享相同前缀的请求可以完全跳过计算，直接从内存中读取。

理解了这一点，本文中的每个架构决策都会变得显而易见。

#### KV 缓存的工作原理

要理解缓存为何如此高效，你需要了解 Transformer 在处理提示时实际做了什么。

每个 LLM 推理请求有两个阶段：

**预填充阶段（Prefill）** 处理整个输入提示。它对上下文中的所有 token 执行密集矩阵乘法，构建模型的内部表示。这是**计算密集型**的，代价高昂。

**解码阶段（Decode）** 逐个生成 token。每个新 token 被添加到序列中，模型预测下一个。这个阶段是**内存密集型**的，因为它主要读取历史状态而非进行大量计算。

在预填充阶段，Transformer 为每个 token 计算三个向量：Query（查询）、Key（键）和 Value（值）。注意力机制使用这些向量来确定每个 token 与其他每个 token 的关系。任何给定 token 的 Key 和 Value 向量**仅依赖于它之前的 token**，一旦计算完成就永远不会改变。

**没有缓存时**，这些 Key 和 Value 张量在每次请求后就被丢弃，下一次请求从头重新计算。对于 20,000 token 的前缀，这意味着 20,000 个 token 的注意力计算完全不需要再次发生。

**KV 缓存**通过在推理服务器上持久化这些张量来解决这个问题，以 token 序列的加密哈希作为索引。当新请求带有相同前缀时，哈希匹配，张量从内存加载，这些 token 的预填充计算被完全跳过。

这将每个生成 token 的计算复杂度从 **O(n²) 降低到 O(n)**。对于在 50 轮对话中重复的 20,000 token 前缀，这是一个巨大的削减。

#### 经济账

定价结构使得这个架构决策变得如此重要。

- **缓存读取**：基础输入价格的 **0.1 倍**——每个缓存 token 享受 **90% 折扣**
- **缓存写入**：**1.25 倍**——存储 KV 张量需要 25% 的溢价
- **延长一小时缓存**：**2.0 倍**

以下是 Anthropic Claude 各模型的具体定价：

| 模型 | 基础输入 | 缓存写入 (1.25x) | 缓存读取 (0.1x) | 输出 |
|------|---------|------------------|-----------------|------|
| Claude Sonnet 4 | $3.00/MTok | $3.75/MTok | $0.30/MTok | $15.00/MTok |
| Claude Haiku 3.5 | $0.80/MTok | $1.00/MTok | $0.08/MTok | $4.00/MTok |

这套数学只有在缓存命中率保持高位时才有效。最好的生产示例就是 Claude Code。

#### Claude Code 的 30 分钟编码会话

Claude Code 完全围绕一个目标构建：**保持缓存热度**。

以下是一个真实的 30 分钟编码会话从计费角度的详细过程：

**第 0 分钟**：Claude Code 加载系统提示、工具定义和项目的 CLAUDE.md 文件。这个负载超过 20,000 token，由于每个 token 都是新的，这是**整个会话中最昂贵的时刻**。但你只需支付一次。

**第 1-5 分钟**：你开始下达指令，Claude Code 派遣 Explore 子智能体浏览代码库、打开文件、运行 grep 命令。所有这些被追加到动态后缀。但 20,000 token 的静态前缀现在以 $0.30/MTok 而非 $3.00/MTok 的价格从缓存中读取。

**第 6-15 分钟**：Plan 子智能体接收的是**摘要简报**而非原始结果，因为传递原始输出会不必要地膨胀动态后缀。它生成实施计划，你批准后 Claude Code 开始修改。每一轮都从缓存读取静态前缀，命中率攀升超过 90%，每次访问都重置 TTL 以保持缓存热度。

**第 16-25 分钟**：你请求修改，这意味着更多工具调用、更多终端输出、更多上下文累积在动态后缀中。此时会话已处理数十万 token，但**每一轮都从缓存读取了 20,000 token 的基础层**。

**第 28 分钟**：你在终端运行 `/cost`。没有缓存的话，按 Sonnet 4.5 费率计算，200 万 token 将花费 $6.00。在缓存效率达到 92% 的情况下，184 万 token 是缓存读取，总成本降至 **$1.15**。这是单个任务 **81% 的成本削减**。

| 指标 | 数值 |
|------|------|
| 总处理 token | 2,000,000 |
| 缓存读取 token (92%) | 1,840,000 |
| 全价计算 token (8%) | 160,000 |
| 无缓存成本 | $6.00 |
| 有缓存成本 | $1.15 |
| **节省比例** | **81%** |

这就是热缓存的样子。你只需为静态基础支付一次，之后每次读取几乎免费。动态尾部是唯一需要持续付费的部分。

#### 基于哈希的缓存的脆弱性

关于提示缓存，最反直觉的一点是：

> **"1 + 2 = 3" 命中缓存，但 "2 + 1" 就是缓存未命中。**

基础设施从头开始对完整 token 序列进行哈希。如果该序列中有**任何东西**发生变化——即使只是两个元素的顺序——哈希就会改变，整个前缀就会按全价重新计算。

这不是一个次要的实现细节。它是 Claude Code 中**每个工程决策都围绕其设计的核心约束**。

以下是在生产环境中实际导致缓存失效的案例：

- 注入系统提示中的**时间戳**导致每次请求产生唯一哈希
- **JSON 序列化器**在不同请求间对工具 schema 的键排序不同，导致前缀失效
- 会话中途更新的 **AgentTool 参数**清除了整个 20,000 token 的缓存

由此产生三条规则：

##### 1. 不要在会话中修改工具

工具定义是缓存前缀的一部分，添加或删除工具会使下游所有内容失效。

##### 2. 永远不要在会话中途切换模型

缓存是模型专属的，切换到更便宜的模型意味着从头重建整个缓存。

##### 3. 永远不要通过修改前缀来更新状态

Claude Code 不编辑系统提示，而是将提醒标签追加到下一条用户消息中，使前缀保持不变。

#### 应用到你自己的 Agent

无论你是使用 Claude Code 还是从头构建自己的 Agent，同样的规则都适用。

按以下顺序组织你的提示：

1. **系统指令和行为规则**放在顶部。会话中途不要更改。
2. **所有工具定义预先加载**。不要添加或删除。
3. **检索到的上下文和参考文档**放在接下来。在会话期间保持稳定。
4. **对话历史和工具输出**放在底部。这是你的动态后缀。

启用 Anthropic API 的**自动缓存**后，缓存断点会随对话增长自动推进。没有它，你需要手动跟踪 token 边界，而错误的边界意味着完全错过缓存。

##### 上下文压缩

当接近上下文限制时，使用**缓存安全的分叉**：保持相同的系统提示、工具和对话历史，然后将压缩指令作为新消息追加。缓存前缀被复用，唯一按新价计费的 token 只是压缩指令本身。

##### 验证缓存是否工作

监控每个 API 响应中的三个字段：

- `cache_creation_input_tokens` —— 写入缓存的 token 数
- `cache_read_input_tokens` —— 从缓存读取的 token 数
- `input_tokens` —— 未经缓存处理的 token 数

**缓存效率** = `cache_read_input_tokens / (cache_read_input_tokens + cache_creation_input_tokens)`

像监控系统可用率一样监控这个指标。

#### 核心要点

提示缓存不是一个你随手开启的功能，而是一种**你需要围绕其设计的架构纪律**。

核心思想很简单：组织你的提示，让静态内容位于顶部，动态内容在底部增长。基础设施对前缀进行哈希，存储 KV 张量，并在每次后续读取时给你 90% 的折扣。

但纪律在细节中：

- 不要在系统提示中注入时间戳
- 不要打乱工具定义的顺序
- 不要在会话中途切换模型
- 不要修改缓存断点上游的任何内容

Claude Code 展示了这在规模化时的效果——**92% 的缓存命中率和 81% 的成本削减**。如果你在构建 Agent 时没有围绕提示缓存进行设计，你就是在把大部分利润留在桌上。
