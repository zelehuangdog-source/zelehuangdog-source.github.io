在 Anthropic，代码量和部署速度都已呈指数级增长。我们的软件工程师人均每季度交付的代码量，是 2021 到 2025 年间的 8 倍。

我们的评审、监控以及其他安全流程必须随着这一提速而同步扩展，否则就会变成制造瓶颈的公式（[阿姆达尔定律，Amdahl's Law](https://en.wikipedia.org/wiki/Amdahl%27s_law)）。

我们的软件开发流程本身也发生了巨变。Claude 已经从编码助手演进为主要的创造者和评审者。如今，[Claude 撰写](https://www.anthropic.com/institute/recursive-self-improvement)了合入我们代码库约 80% 的代码。

超过一半的代码是由我们内部版本的 [Claude Tag](https://www.anthropic.com/news/introducing-claude-tag) 合并的，而人类工程师则专注于指挥方向、设定意图、并掌握最终审批权。

这意味着我们的安全团队必须防守一个快速膨胀的攻击面，并加固一条以非确定性（non-deterministic）、持续演进的智能体（agent）为核心的生命周期。在本文中，我将介绍保护软件开发生命周期（SDLC，Software Development Lifecycle）的一系列策略。

*（本文旨在与我们近期发布的* [*面向智能体的零信任（Zero Trust for Agents）*](https://claude.com/blog/zero-trust-for-ai-agents) *框架结合阅读；本文中的所有实现都运用了那个框架里的安全设计理念。）*

我们所要防范的威胁是具体的：一个被攻陷或被提示注入（prompt-injected）的智能体引入恶意变更；被智能体当作可信输入而摄入的供应链与依赖投毒（supply-chain and dependency poisoning）；以及那些更为常见、但如今以更高数量涌现的应用漏洞类别。接下来介绍的每一项控制措施，都至少对应上述威胁中的一种。

为了在不显著拖慢研发速度的前提下做到这一点，我们部署了几项总体策略，包括：

- 安全左移（Shifting security left），并与代码开发阶段完全融合；
- 使用硬性的访问与身份边界，来收敛爆炸半径（blast radius）；
- 在上线前后，结合自动化的确定性审查（deterministic reviews）与智能体审查（agentic reviews）；
- 在杠杆率最高的环节插入人工把关（humans in the loop）。

在本文中，我们将介绍在软件开发生命周期各个具体阶段所实施的安全流程，以及它们背后的核心原则。这些原则更为持久——因为随着模型能力的演进，安全团队必须不断重新审视、乃至重新发明自己的流程。

#### 不断演进的软件开发生命周期

Anthropic 内部自动化 PSR（项目安全评审）的流程。

我们的研发团队已经[详尽地](https://claude.com/blog/running-an-ai-native-engineering-org)介绍过他们软件开发生命周期的变化，因此在深入每个阶段之前，这里只做一个简短的铺垫。

从高层来看，我们的软件开发生命周期是被压缩的。它更多地由原型（prototype）和内部采用（dogfooding，吃自家狗粮）驱动，而非漫长的规划周期。创意来自组织的各个角落，传统角色（前端、后端、设计）之间的界限也变得模糊。评审和审批仍然有人类参与其中，但同时也由智能体循环（agentic loops）驱动。

尽管每个阶段都已被 Claude Code 和 Claude Tag 从根本上重塑和加速，但每个阶段的名称与目的，对于一个来自更传统组织的开发者来说，并不会显得陌生。这些是天然的关卡（gates），我们也把它们用作面向 AI 原生 SDLC 的安全流程的一部分。

#### 计划（Plan）

我们最早的安全自动化之一，是一个由 Claude Opus 驱动的、简单的 PSR（project security review，项目安全评审）Web 应用。它会摄入一份项目设计文档，并对照 [MITRE ATT&CK 框架](https://attack.mitre.org/)进行分析，以识别潜在漏洞并给出缓解建议。

我们已经显著增强了这个系统，将它连接到一个内部知识索引（knowledge index）上，从而在全组织范围的政策、过往决策和相关系统层面，提供更深入的上下文。

这让我们能更好地理解潜在风险，同时也能捕捉到 PSR 本身遗漏的信息。仅这一项实现，就为 AppSec（应用安全）团队节省了大部分时间。一旦我们确信 Claude 能够准确评估风险，我们就允许团队自行审批他们的项目——只要 Claude 判定该次上线的风险足够低。

在这里，我们可以看到面向 AI 原生 SDLC 的首批关键调整之一。PSR 最初的设计目的，是在漫长而昂贵的编码过程之前捕捉安全问题。在这一阶段抓住一个问题，能节省数月的重新开发时间。

如今，一个重大功能的多个原型可以在数小时内完成，这使得详尽的架构评审不再是那么关键的关卡。将我们的 PSR 应用连接到知识索引，能够捕捉那些原本可能被遗漏的上下文，同时又不制造不必要的减速带。而创建一个 Claude Code skill，则让 Claude 能够进一步「扇出（fan out）」，去捕捉散落在各处的额外上下文。

**持久原则（Enduring Principle）**：把安全智能体连接到组织上下文。随着规划周期的压缩，更有效的做法是把这些智能体带到上下文本就存在的地方——聊天线程、过往评审、代码库——而不是在那些可能已不再需要的阶段强行要求详尽的文档。无论如何，智能体都需要代码本身之外的上下文。
