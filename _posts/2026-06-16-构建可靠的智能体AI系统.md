> **摘要**：本文是拜耳公司 PRINCE（临床前信息中心）平台的详细案例研究，展示了如何在制药行业构建生产级智能体 AI 系统。文章提出了两个核心工程概念——"上下文工程"（为不同智能体阶段提供精准聚焦的上下文）和"框架工程"（围绕 LLM 构建编排、状态持久化、回退和可观测性脚手架）。系统采用混合检索策略（RAG + Text-to-SQL）、三层反思循环（流程反思、数据反思、草稿反思），以及向领域特定子智能体演进的层级架构，为企业级智能体系统的可靠性建设提供了极具参考价值的工程实践。

临床前药物发现本质上是复杂且数据密集的。研究人员面临着一个重大挑战：如何高效地访问和分析在这一关键阶段产生的海量信息。传统的基于关键词的搜索方法往往依赖于刚性的布尔逻辑，在面对临床前研究问题的细微差别和复杂本质时，常常力不从心。

大语言模型（LLM）的出现带来了变革性的机遇。通过将 LLM 的生成能力与信息检索系统的精准性相结合，检索增强生成（Retrieval-Augmented Generation, RAG）已经成为一种前景广阔的技术。这种方法有潜力彻底改变临床前数据访问方式，使研究人员能够用自然语言提出复杂问题，并获得基于专有数据的准确且上下文丰富的答案。

拜耳很早就认识到了这一潜力，并致力于探索这些技术如何解决临床前研究中长期存在的挑战。

在本文中，我们分享了这段旅程——拜耳对生成式 AI 的早期投资如何催生了 PRINCE，一个基于智能体 RAG（Agentic RAG）构建的智能体 AI 系统。这个案例研究探讨了将临床前数据检索从一个充满挑战的迷宫转变为直观对话体验的技术架构、工程决策和经验教训。

PRINCE 背后的许多工程决策现在可以通过**上下文工程**（context engineering）和**框架工程**（harness engineering）的视角来理解，尽管在系统最初设计时我们并未使用这些术语。上下文工程塑造了每个模型接收什么信息、不接收什么信息，以及上下文如何在研究、反思和写作等专门步骤之间流动。框架工程塑造了模型周围的脚手架：编排、工具边界、状态持久化、重试、回退、验证、反思循环、可观测性和人工审核。

虽然本文聚焦于技术架构和工程挑战，但我们发表在 Frontiers in Artificial Intelligence 上的论文更详细地涵盖了产品演进和商业影响。

#### 挑战：穿越临床前数据迷宫

拜耳的临床前研究格局，与许多大型制药组织类似，拥有多样化且庞大的数据阵列。这包括来自各种研究的高度结构化数据集，以及嵌入在研究报告、出版物和监管提交文件等文本文档中的大量非结构化信息。研究人员在有效访问和分析这些信息时经常遇到重大障碍：

- **数据孤岛**：信息碎片化地分散在众多不同的系统和存储库中，使得获取与特定化合物或研究相关的临床前数据的全面、整体视图变得极为困难。
- **有限的搜索能力**：传统的基于关键词的搜索引擎难以应对临床前术语和研究问题的复杂性和多变性，通常产生不相关、不完整或过于庞杂的结果。
- **耗时的人工分析**：从多个文档中提取特定见解或编译信息需要大量人工努力，将宝贵的研究人员时间从核心科学活动中转移开。

这些固有的挑战突显了对更高效、更智能、更集成的临床前数据检索和分析方法的明确需求。

#### 解决方案：PRINCE——一个演进式平台

为应对这些挑战，拜耳开发了临床前信息中心（PRINCE）平台。PRINCE 被构想为临床前数据的统一入口，最初专注于整合以前孤立的结构化研究元数据，并以"可搜索"的方式暴露它们。这一初始阶段允许用户应用高级过滤器，主要从结构化研究元数据中检索信息。

然而，拜耳有价值的临床前知识的很大一部分存储在数十年积累的非结构化 PDF 研究报告中。由于多年来的多次系统迁移，与这些报告相关的结构化元数据可能不完整、缺失，甚至包含错误的注释。关键的是，权威的"金标准"信息始终存在于已批准的 PDF 研究报告中。

生成式 AI 的出现，特别是 RAG，提供了解锁这些非结构化数据宝库的钥匙。通过集成 RAG 能力，PRINCE 开始将范式从基于过滤器的"搜索"工具转变为自然语言"提问"系统，使研究人员能够直接查询这些研究报告的内容。

这一演进反映了 PRINCE 经历的三个不同阶段：

- **搜索（Search）**：初始阶段专注于为数千份非临床研究报告创建统一入口，将来自各个临床前领域的多个内部数据孤岛整合为可搜索的格式，主要利用结构化元数据。
- **提问（Ask）**：此阶段引入了利用检索增强生成（RAG）的 AI 驱动的问答系统。这使研究人员能够通过自然语言提问，直接从非结构化数据中获取见解，包括历史报告中的扫描 PDF。
- **执行（Do）**：当前阶段将 PRINCE 定位为能够执行复杂任务的主动研究助手。这通过集成多智能体系统来实现，使平台能够处理复杂查询、编排工作流，并支持起草监管文件等活动。

从搜索到提问再到执行的有意识演进，代表了对行业在临床前开发中追求更高效率和创新需求的战略回应。通过为研究人员提供日益强大的工具来访问、分析和处理临床前数据，PRINCE 旨在实现更快的数据驱动决策、减少不必要的实验需求，并最终加速开发更安全、更有效的疗法。

#### 系统架构：构建可靠的智能体 RAG 系统

系统以交互式对话 UI 的形式运行，由强大的后端基础设施支撑。其架构专为处理复杂查询和交付准确、上下文丰富的答案而设计，使用 LangGraph 进行编排，并通过 FastAPI 应用提供服务。

图 1 提供了系统上下文——UI、后端、数据存储、LLM 回退和可观测性——而图 2 深入展示了系统如何协调其专门的智能体。

- **用户请求**：流程从用户通过基于 React 构建的对话式 UI 提交请求开始。
- **编排**：用户请求被路由到后端基于 LangGraph 的编排层。这个工作流引擎协调一个多阶段流程，依次经过澄清用户意图、思考与规划、进行研究（使用 RAG 和 Text-to-SQL）、验证数据完整性，最终通过 Writer Agent 生成响应。工作流包含刻意的暂停点和反馈循环，以确保在继续之前数据的完整性。（我们在后面的专门章节中探讨此智能体工作流的细节。）
- **数据检索和状态管理**：Researcher Agent 与一个全面的分布式数据生态系统交互：
  - 所有研究报告的向量表示存储在 OpenSearch 中，构成信息检索的核心知识库。
  - 经过各种 ETL 和协调流程处理的策划结构化数据通过 Athena 访问。
  - 智能体执行的状态被精心跟踪。在每个逻辑步骤（LangGraph 节点执行）之后，相应的状态使用 LangGraph checkpointer 持久化到 PostgreSQL 中。
  - 更广泛的应用级状态在 DynamoDB 中管理。
- 系统利用内部 GenAI 平台，这些平台托管来自 OpenAI、Anthropic、Google 和开源提供商的模型。这些平台通过统一的 OpenAI 兼容端点暴露所有模型，使得交换模型和为每个任务选择最佳工具变得容易。它们还管理控制平面，执行速率限制和其他防护措施以防止滥用。
- **弹性和错误处理**：健壮性是一个关键的设计原则，配备了多种回退机制：
  - 如果特定 LLM 失败，系统会自动重试请求几次，然后回退到替代模型或平台以确保服务连续性。
  - 为了从瞬态故障中快速恢复，重试在单个 LLM 调用级别和逻辑节点级别（即智能体计划中的整个步骤）都已实现。
  - 此外，智能体被提供错误的上下文，以便它们能够规划不同的轨迹或替代行动方案作为响应。
- **可观测性和评估**：整个系统被监控以确保性能和可靠性：
  - 通用系统健康状况和指标使用 Cloudwatch 跟踪。
  - Langfuse 作为主要可观测性工具，提供所有生产流量的详细追踪。这允许对问题进行深入调试。此外，评估数据集在 Langfuse 中存储和管理，使得分析性能分数和诊断特定故障变得更容易。评估使用 RAGAS 评估框架完成。实时流量评估每天进行一次，而数据集评估在对核心工作流、提示词或底层模型进行重大更改时进行。
- **最终响应**：一旦智能体处理了请求并生成了满意的响应，它就被发送回对话式 UI 呈现给用户。

贯穿这一架构的设计原则是**上下文纪律**。更大的上下文窗口并没有消除对每个智能体所见内容进行筛选的需求。在早期迭代中，将过多信息放入上下文会使系统更难操控，也更难评估。因此 PRINCE 避免将提示词视为包含所有可用信息的一个大容器。相反，不同阶段接收不同的上下文：思考与规划的规划上下文、Researcher Agent 的检索上下文、Reflection Agent 的证据上下文、以及 Writer Agent 的综合上下文。这减少了上下文污染，使系统更易于调试、评估和改进。

这些步骤确保系统能够通过利用精密的多智能体架构和多样化的强大工具和数据源，为广泛的复杂查询提供可靠且上下文相关的答案。

#### 智能体 RAG 系统

PRINCE 整合了一个智能体 RAG 系统（图 2）来处理需要多步骤、推理和与不同工具或数据源交互的复杂用户请求。这套设置使用 LangGraph 实现，编排整体工作流，并利用 Researcher Agent、Writer Agent 和 Reflection Agent 来执行特定任务。系统被设计为健壮且可靠的，配备了多种回退机制以确保即使某些组件失败，系统也能继续运行。

##### 澄清用户意图

澄清用户意图步骤充当抵御歧义的第一道防线。随着系统扩展到包括毒理学和药理学等多样化领域，简单的用户查询经常变得模糊不清，使得自动选择正确的工具变得困难。系统不是依赖于在所有数据源上进行代价高昂的试错，而是主动提出澄清问题来精确定位特定的领域或数据类型。

这确保了系统用必要的约束增强查询以定位正确的工具。我们还通过在 UI 中开发领域级选择来优化这一点，这将允许用户预先过滤有效的工具。为进一步减少摩擦，系统还提供 AI 辅助的数据源推荐：当用户没有选择任何数据源——或选择了多个但没有明确焦点时——模型分析用户查询背后的意图并建议最相关的来源。用户保留完全控制权，可以接受、调整或覆盖推荐，确保领域专业知识始终有最终决定权。这种"快速失败"机制可以防止在模糊查询上浪费执行资源，同时通过仔细调优，确保在意图已经明确时系统保持简洁不扰人。

从上下文工程的角度来看，这一步是工作流中的第一个组装决策：它在任何检索开始之前就约束了哪些工具、领域和数据源将在范围内，确保后续智能体接收的是一个聚焦的而非开放式的问题。

##### 思考与规划：流程反思

思考与规划步骤负责制定策略来满足用户的请求。这一关键组件为系统提供了一个专门的空间，在采取行动之前推理下一步——一种受 Anthropic Think 工具启发的技术。重要的是，这一步执行的是**流程反思**：评估智能体是否在向最终目标正确推进并处于正确的轨迹上，而不是评估数据本身。

在多步骤智能体工作流中，特别是那些涉及许多顺序动作的工作流中，流程反思是必不可少的。考虑一个场景：系统需要执行 50 个步骤来完成一个复杂任务。在每个节点，系统必须问：我是否以正确的方式执行这些步骤？我是否在按预期推进？当前轨迹是否通向用户的目标？思考与规划步骤提供了这种元认知能力，允许系统反思自己的工作流并相应地调整策略。

这个"思考空间"在涉及多个工具调用的场景中被证明特别有价值。当 PRINCE 最初开发时，它只有几个工具：一个用于基于 RAG 的检索，另一个用于 Text-to-SQL 查询。然而，随着我们集成更多数据源来扩展系统的能力，可用工具的数量显著增长。随着工具的爆炸式增长，一个固有的挑战随之而来：不同工具之间的关注点重叠和领域边界模糊。

例如，多个工具可能服务于相似但微妙不同的目的——查询结构化元数据与非结构化报告，或检索研究摘要与详细的实验数据。当面对属于相似领域但处理略有不同数据的工具时，LLM 有时会难以为给定查询选择最合适的工具。通过引入专门的思考步骤，系统可以明确推理哪个工具最匹配用户的意图，评估每个可用工具的特征，并做出更知情的决策。这种方法显著提高了工具选择的准确性。

除了工具选择之外，思考与规划步骤对于编排多步骤流程也是必不可少的。PRINCE 中的许多复杂查询需要一系列工具调用，其中一个工具的输出必须在确定下一步动作之前进行分析。例如，系统可能首先查询结构化元数据来识别相关研究，然后使用这些研究 ID 从非结构化报告中检索详细信息，最后综合这些发现。没有专门的流程反思空间，系统将尝试线性执行这些步骤而不评估每一步是否将其带向更接近目标。有了思考步骤，系统可以暂停、评估其在工作流中的进展，并智能地规划完成用户请求所需的后续工具调用。

##### Researcher Agent

Researcher Agent 充当系统的主要信息采集者。随着我们将新的科学领域接入 PRINCE，我们始终观察到数据落入两个主要类别：结构化和非结构化。虽然具体的实现技术可能因领域而异——例如，对药理学查询使用 Snowflake Cortex Analyst 进行 Text-to-SQL，而对毒理学使用其他更自定义的方法——但这些检索策略背后的基本原理保持一致。

随着 PRINCE 在多个临床前领域扩展，单个拥有扁平工具列表的 Researcher Agent 变得越来越难以管理。许多工具操作相似的概念——"研究"、"发现"、"化验"——但根据领域不同，指向不同的底层数据集、模式和监管解释。例如，当用户提到"这项研究"时，相关上下文可能是重复给药毒理学研究、心血管安全药理学包，或聚合质量数据表中的特定化验，每个都有自己偏好的信息来源。

为避免一个庞大的智能体同时处理重叠的工具和微妙不同的数据契约，我们正在积极将 Researcher 能力演进为**领域特定子智能体的层级结构**。在这个提议的架构中，每个领域智能体将拥有自己的工具集（例如，毒理学 RAG + 毒理学元数据 SQL，或药理学 RAG + 化验级 SQL），以及定制的提示词指令，编码该领域的数据模型如何工作、哪些表或索引是权威的、以及如何解释关键概念。我们预期这将保持职责的连贯性，减少意外的跨领域泄露，并使每个领域的检索行为更容易推理和测试。

为有效地从这个多样化的格局中获取见解，Researcher Agent 采用了专注于两种不同模式的混合检索方法：

- **检索增强生成（RAG）**：用于处理非结构化数据，主要是 PDF 报告。
- **Text-to-SQL**：用于查询存储在 Amazon Athena 中的结构化数据。

这种双策略使系统能够弥合叙述性科学报告和定量实验数据之间的差距。

在这个更新的愿景中，顶层 Researcher Agent 被设计为协调者而非单一的全知组件。给定澄清后的用户意图和 UI 中的任何明确领域选择，它将把查询路由到适当的领域子智能体，后者可以决定如何在自己的边界内组合 RAG 和 Text-to-SQL。这种模式旨在从用户角度保持"一个研究者"的简单性，同时在内部允许每个领域发展自己的工具、模式和检索方案而不破坏系统的其余部分。

##### 非结构化数据的检索增强生成（RAG）

鉴于拥有数千份临床前研究报告和其他非结构化文档的庞大存储库，RAG 对于通过将 LLM 响应基于这一特定知识库来提取相关见解是必不可少的。RAG 流水线包括一个全面的摄取流程和一个精密的查询时架构。

**摄取流程**：临床前研究报告，大多是跨越数十年的 PDF，通常包括带有复杂表格的扫描文档，首先被集中到 S3 数据湖中，并通过为此语料库调优的提取流水线。提取的文本被规范化为结构化 JSON，然后使用保留足够科学上下文同时保持块（chunk）对检索高效的策略进行分块。

每个块都用来自 Amazon Athena 的研究级和章节级元数据进行丰富（例如研究 ID、化合物、物种、给药途径、页码和父章节），这些元数据后来在 RAG 层中实现精确的元数据过滤。最后，这些注释的块被嵌入和索引到 Amazon OpenSearch Service 中，形成支撑对历史语料库和每日增量（新的或更新的报告到达时）的语义和元数据感知检索的向量存储。

**查询时 RAG 流水线**：当用户提交查询时，系统启动多阶段检索流程。这个流水线被设计为有效地从向量数据库中检索最相关和最可信的信息，以为 LLM 的响应提供基础。

为说明这个流水线，考虑示例查询："在研究 T123456-2 中是否观察到以下任何临床发现：竖毛、共济失调、眼睛半闭和稀便？"系统通过以下步骤处理此查询：

1. **关键词提取**：用户的自然语言查询首先由 LLM 分析。通过精心的提示词工程，模型被指示提取与我们文档语料库中的关键词搜索高度相关的关键词（例如 "piloerection"、"ataxia"、"eyes partially closed"、"loose faeces"）。

2. **元数据过滤器生成**：同时，LLM 基于查询生成元数据过滤器。例如，提取过滤器 `eq(study_id, T123456-2)` 以缩小搜索空间。这个过滤器是使用少样本提示词（few-shot prompting）动态生成的，向模型提供各种排列和组合示例，确保它能处理多样化的过滤请求。

3. **查询扩展**：为确保全面检索并考虑措辞和术语的变化，由一个更小、更快的模型执行查询扩展（多查询或查询重写）。这基于原始问题生成 n=5 个语义相似的查询。对于示例查询，这可能包括如下变体：
   - "研究 T123456-2 中报告的临床症状，包括鸡皮疙瘩、协调性缺乏、半闭眼睑或腹泻。"
   - "实验 T123456-2 中关于毛发竖立、步态不稳、眼睛未完全睁开或水样便的记录观察。"
   - "试验 T123456-2 中记录了哪些临床观察，特别是关于毛发竖起、平衡受损、眼睛部分闭合或软便的存在。"

4. **混合检索器**：从向量数据库（Amazon OpenSearch Service）的信息检索使用混合搜索方法，结合元数据过滤、语义向量相似性搜索（kNN）和基于关键词的检索。此流程执行如下：
   - **元数据过滤**：前一步生成的元数据过滤器（例如 `eq(study_id, T123456-2)`）直接应用于向量数据库查询。这基于在摄取过程中从 Amazon Athena 附加到块的结构化元数据预过滤搜索空间，确保只考虑与指定研究 ID（或其他相关元数据）相关的块。这将搜索空间从数百万向量显著减少到数十到数百的可管理范围，提高了效率和相关性。
   - **并行混合搜索执行**：对于 n=5 个扩展查询中的每一个，针对过滤后的 Amazon OpenSearch Service 向量数据库并行执行单个混合搜索查询。此查询同时结合语义向量相似性搜索（kNN）和基于关键词的搜索，利用 OpenSearch 高效的多向量和文本搜索能力。
   - **加权结果评分**：在每个并行执行的混合搜索中，对结果应用加权方法。语义搜索结果权重为 0.7，关键词搜索结果权重为 0.3，以平衡上下文理解和精确术语匹配。这个权重是通过实验确定的，以优化我们数据的检索效果。
   - **结果聚合和初始排名**：来自所有 5 个并行混合搜索执行的结果（相关块集及其加权分数）被聚合。所有搜索结果中的唯一块被汇总，并使用它们在并行搜索中的最高加权分数来确定初始排名。这一步基于这些聚合和加权分数初始检索较大的潜在上下文块集（k≈20）。
   - **重排序（Reranking）**：初始检索的块集（k≈20）然后使用重排序步骤进行精炼。交叉编码器模型（bge-reranker-large）评估每个检索块相对于原始问题的相关性，选择前 k=7 个最相关的块作为 LLM 的上下文。这个重排序步骤对于确保最相关的信息被优先用于最终响应生成至关重要，即使它们在初始语义相似性或关键词匹配中排名不是最高的。

5. **最终 LLM 提示词生成**：精炼的上下文（k=7 个块）然后与原始问题结合形成最终的 LLM 提示词。这个提示词被精心构造以引导 LLM 基于提供的上下文生成聚焦且准确的响应，最小化幻觉的风险。

6. **带引用的响应生成**：然后由最先进的推理模型处理最终提示词和提供的上下文来生成带引用的响应。LLM 综合上下文中的信息来形成连贯且准确的答案。关键的是，响应自动包含引用，链接回支持生成答案的原始文档中的特定块。

7. **监控**：整个查询时 RAG 流程，从初始查询到最终响应生成，使用 Langfuse 持续监控以进行可观测性、性能和质量分析。

##### 结构化数据的 Text-to-SQL

虽然 RAG 擅长非结构化数据，但需要对结构化数据点进行精确过滤、聚合或比较的查询更适合 Text-to-SQL。示例包括"给我 50 个在大鼠上进行的研究示例"或检索包括剂量组的特定数值化验结果。如图所示，Researcher Agent 可以智能地决定将此类查询移交给 Text-to-SQL 工具。

将自然语言问题转换为可执行 SQL 查询并检索结果的过程涉及几个关键步骤：

1. **查询分析和意图识别**：分析用户的自然语言查询以理解用户意图，并识别从结构化元数据中请求的特定数据点和过滤器。

2. **模式理解和相关模式选择**：为准确生成 SQL 查询，LLM 需要理解相关的数据库模式。对于大型复杂模式，只有与用户查询相关的必要模式组件被动态注入 LLM 的上下文中。这降低了模型的复杂性并提高了生成 SQL 的准确性。

3. **动态少样本提示词用于 SQL 生成**：将复杂的自然语言查询转换为精确的 SQL 方言（在我们的案例中是 Athena）对 LLM 可能具有挑战性。为解决这个问题，我们采用动态少样本提示词。一组精心挑选的示例，代表各种复杂查询模式及其在 Athena 方言中的正确 SQL 翻译，存储在向量数据库的单独集合中。基于用户的查询，使用向量相似性搜索从这个"语义层"中检索相关示例，并包含在给 LLM 的提示词中。这为 LLM 提供了上下文学习示例，引导它在正确的方言中生成准确的 SQL 查询。基于遇到的挑战持续添加新示例进一步提高了系统随时间的性能。

4. **SQL 查询生成和验证**：一个具有强大代码生成能力的模型，以相关模式信息和动态少样本示例为条件，生成相应的 SQL 查询。为确保 LLM 能准确处理结果并在后续综合中识别正确的行，某些基本列（如研究 ID 和研究标题）始终包含在生成的 SELECT 查询中。然后验证生成的查询以确保它遵守允许的操作（例如，只允许 SELECT 查询；为数据完整性和安全性明确阻止 DELETE、INSERT 或 UPDATE 查询）。值得注意的是，此过程的早期迭代包括一个 LLM 审查步骤来检查生成的 SQL 查询；然而，此步骤后来被移除，因为发现审查 LLM 有时会错误地将有效查询标记为错误的，在没有相应的准确性提升的情况下阻碍了效率。

5. **查询执行和结果限制**：验证的 SQL 查询在 Amazon Athena 的结构化元数据数据库上执行。为防止数据泛滥和管理响应大小，系统执行限制，每次最多获取 50 条记录。

6. **错误处理和迭代**：如果 SQL 查询执行成功，检索到的结果（最多到指定限制）被返回并集成到整体响应生成过程中。如果查询由于语法错误、模式问题或其他执行错误而失败，来自数据库的错误消息连同生成的查询和原始上下文被传回同一模型。LLM 分析错误和上下文来生成修正的 SQL 查询。这个生成和执行 SQL 查询的迭代过程在工具放弃并报告失败之前最多尝试 3 次，可能表明一个无法解决的查询或模型处理特定请求能力的限制。

##### Reflection Agent：数据验证和充分性

虽然思考与规划步骤提供流程反思，Reflection Agent 执行的是互补但不同类型的反思：**数据反思**。这一关键组件评估从各种工具检索的数据是否足够且相关以回答用户的问题——这与工作流本身是否正确进展是根本不同的关注点。

在多步骤智能体工作流中，这两种类型的反思服务于不同但同等重要的目的。流程反思（思考与规划）确保智能体采取正确的步骤并向目标适当推进。数据反思（Reflection Agent）确保通过这些步骤收集的信息足以满足用户的请求。两者都是必不可少的：智能体可能执行完全有效的工作流（好的流程）但仍然检索到不足以回答问题的数据，反之，可能有足够的数据但未能有效地通过工作流推进。

如研究工作流图（图 2）所示，在初始信息检索和"思考与规划"循环之后，当思考与规划步骤认为流程已经推进得足够好并准备评估数据时，Reflection Agent 被调用。Reflection Agent 通过将检索到的上下文与用户的原始查询进行比较并识别潜在的差距或缺失信息来评估收集数据的充分性和相关性。如果收集的信息被认为不足以提供完整的响应，Reflection Agent 会生成特定的后续问题，旨在获取必要的缺失信息。这些后续问题然后被传回思考与规划步骤，该步骤启动进一步的检索步骤以获得更全面的结果。这个由 Reflection Agent 生成的问题驱动的数据验证和后续信息检索的迭代过程，展示了系统基于初始结果细化搜索策略的能力。如果信息充足，工作流进入下一步。

##### Writer Agent：答案综合和格式化

一旦 Researcher Agent 从 RAG 和 Text-to-SQL 收集了相关证据，Writer Agent 负责将这些原始材料转化为呈现给用户的最终答案。它的工作不是"发现"新信息，而是综合检索到的上下文、遵守用户指令，并在生成过程中执行 PRINCE 的质量约束。

Writer Agent 运行有几条不可协商的规则。它必须将每个声明基于提供的上下文中，并将准确的引用附加回底层的块和研究 ID，因为在监管环境中可验证性至关重要。它还负责遵守用户级别的格式要求（例如表格、项目符号或特定的章节结构），并与临床前科学家使用的领域特定答案标准保持一致。

对于更复杂的响应——如多章节摘要或部分填写的监管模板——架构支持使用短内部审查循环来扩展 Writer Agent。在这种模式中，Writer 会先起草答案，然后审查步骤检查缺失的章节、不一致的表格或相对于原始问题的差距，并可能将有针对性的指令发回给 Writer 以修改特定部分。这种设计实现了一种专注于答案完整性和呈现的轻量级反思形式，补充了工作流早期 Reflection Agent 对数据充分性的关注。重要的是，这些监管起草工作流的所有输出都旨在接受专家审查；最终提交由合格人员撰写和批准。

这给了 PRINCE **三个互补的反思循环**：
- **流程反思**检查工作流是否在正确的路径上，帮助捕捉错误轨迹、错误的工具选择或糟糕的排序。
- **数据反思**检查收集的证据是否充分，帮助捕捉薄弱证据、缺失上下文或覆盖差距。
- **草稿反思**检查生成的输出是否完整，帮助捕捉缺失章节、不完整表格或综合差距。

这些智能体共同构成了一个实用的上下文工程模式。系统不是简单地不断向提示词添加更多信息。它在正确的时间将正确的上下文路由到正确的能力：思考与规划的规划上下文、Researcher 的检索上下文、Reflection Agent 的证据上下文、以及 Writer 的综合上下文。这体现在系统中的具体决策中：Text-to-SQL 步骤只注入与当前查询相关的模式组件，而不是完整的数据库模式；Reflection Agent 接收原始问题和收集的证据来评估差距，而不是完整的工作流历史；Writer Agent 接收带引用约束的策划块，而不是原始检索输出。从单体智能体到这种结构化工作流的转变意味着每个智能体可以被单独评估、调试和改进。

#### 在生产 LLM 系统中建立信任

建立和维护用户信任对于任何 AI 系统的成功采用至关重要，特别是在临床前药物发现这样的关键环境中，其决策具有重大影响。对于生产 LLM 应用，信任不仅仅是关于准确性；还关乎可靠性、透明度和用户验证所提供信息的能力。PRINCE 中集成了多种机制来实现这一点：

##### 透明度和可解释性

确保透明度和可解释性是 PRINCE 设计的关键方面，培养用户信任并使生成的响应能够被验证。系统整合了几种机制来实现这一点：

- **中间步骤和透明度**：鉴于工作流的迭代性质和生成最终答案可能需要的时间，保持透明度至关重要。系统在查询处理、信息检索和反思过程中执行的中间步骤，包括制定的查询和使用的工具，都显示给用户。这提供了对系统推理过程的可见性，允许用户跟踪到达最终答案所采取的步骤。此外，当识别到相关上下文（块）时，这些源材料的链接会在屏幕上呈现，允许用户准确看到哪些信息被入围并用于制定最终响应。

- **通过引用进行事实性验证**：系统通过强大的引用机制促进用户对事实性的验证。生成的答案始终伴随引用，引用参考原始源文档和结构化元数据。这些引用直接链接到向用户显示的上下文，使他们能够轻松验证响应中声明的准确性并将信息追溯到其来源。用户可以将鼠标悬停在生成响应中的任何句子上，以查看相应的引用，该引用提供指向 PRINCE 和源文档的链接，包括页码和用于支持答案该部分的报告中的确切引用。这种细粒度的引用级别显著增强了系统输出的可信度和可靠性，并简化了人工审查过程。

##### 评估

严格的评估是构建和维护可靠 LLM 应用的基础。PRINCE 的性能和可靠性通过两种类型的评估组合来评估：数据集评估和实时流量评估。

- **数据集评估**：每当对核心工作流、提示词或底层模型进行重大更改时进行，这些评估利用带有预定义参考答案的策划数据集，由主题专家精心准备并存储在 Langfuse 中。自定义评估脚本处理每个问题并将生成的响应与参考答案进行比较，产生定量指标如忠实度（答案被上下文支持的程度）、答案相关性（答案多好地回答了查询）、上下文相关性（检索块的相关性）、答案准确性（与基准真相的比较）和与参考的语义相似性（与参考答案的语义相似性）。鉴于系统的智能体性质，在不同工作流阶段应用适当的评估指标（类似于测试金字塔）至关重要，这是在评估整体端到端性能之外的补充。

- **实时流量评估**：作为批处理作业每天对来自实时环境的真实用户查询执行（没有预定义的参考答案），这些评估提供了对真实世界性能的宝贵见解。忠实度和答案相关性等指标仍然可以评估。实时流量评估对于监控系统行为、识别生产中的潜在问题（如幻觉）以及理解在多样化实时查询上的性能至关重要。

##### 监控

持续监控系统的性能和输出对于在生产环境中主动识别和解决问题至关重要。使用 Langfuse 等平台，我们持续监控 PRINCE 以识别潜在的偏差、错误或改进领域，确保系统响应的可靠性和安全性。

#### 弹性工程：错误处理和恢复

鉴于 PRINCE 中固有的多步骤工作流的复杂性，健壮的错误处理和恢复机制对于确保系统的可靠性和提供无缝的用户体验至关重要。系统被设计为能够在各个阶段从故障中优雅恢复，而无需完全重启整个工作流。

我们错误处理和恢复方法的关键方面包括：

- **状态持久化**：整个工作流图的状态被持久存储，使系统能够直接从失败的节点恢复执行。这通过将代表智能体通过工作流进度的 Agent State 存储在 Postgres 中来实现。应用状态的其他方面，如日志、中间步骤和引用，存储在 DynamoDB 中。这种状态的分离和持久化对于在有状态的智能体系统中实现健壮性至关重要。

- **内置重试**：系统在工作流的各个步骤配置了内置重试。如果特定步骤遇到瞬态故障，系统将自动尝试重新执行它预定义的次数，然后再发出更永久性的错误信号。

- **用户发起的重试**：除了自动重试外，用户可以选择通过界面手动重试失败的查询。当用户发起重试时，系统利用持久化的状态直接从故障点继续工作流，智能地跳过在先前尝试中成功完成的步骤。这显著改善了用户体验并节省了计算资源。

- **框架级支持**：错误恢复机制得到底层框架 LangGraph 的显著支持，后者为管理工作流状态和处理图结构中的错误提供了可靠的内置能力。这为构建弹性的智能体工作流提供了坚实的基础。

- **LLM 回退**：为增强可靠性并缓解与模型可用性或性能相关的问题，系统整合了自定义 LLM 回退处理。如果对主要 LLM 提供商或特定模型的调用在几次重试后失败，系统会自动回退到来自不同提供商的替代 LLM。这种机制对于维护系统可用性和响应性至关重要，特别是因为外部服务的平台停机超出了我们的直接控制范围。

这种全面的错误处理和恢复方法最小化了瞬态故障的影响，减少了用户从头重启复杂查询的需要，并通过避免成功步骤和 LLM 调用的冗余执行来贡献于成本和延迟节约，所有这些对于生产就绪的系统都是必不可少的。

这些机制是**框架工程**的实践。LangGraph 工作流充当智能体周围的控制层：它定义了哪个组件可以行动、可以使用哪些工具、工作流可以在哪里暂停、失败如何被重试、状态如何被持久化，以及系统何时应从研究转向反思再转向写作。这个框架使系统比不受约束的自主智能体更不不透明、更可靠。它为应用提供了清晰的恢复、检查、评估和人工干预的控制点。

#### 提升数据质量：命名实体识别和标注

Amazon Athena 中结构化元数据的准确性和完整性对于 Text-to-SQL 组件的性能和 PRINCE 内的整体数据可发现性至关重要。由于历史数据迁移和拜耳广泛运营历史中不同实验室和系统的不同标注实践，元数据有时可能不完整、缺失或不正确。

为应对这一挑战并持续提升结构化元数据的质量，我们开发了一个实用系统，采用命名实体识别（NER）直接从研究 PDF 中提取和创建准确的标注。这个系统被设计为读取临床前报告的文本内容并识别应在结构化元数据中表示的关键实体和相关信息。

该过程涉及：

- 处理研究 PDF 以提取文本并识别相关实体（例如研究 ID、化合物名称、物种、给药途径、剂量信息、临床发现等）。
- 基于识别的实体及其在文本中的关系生成结构化标注。

我们正在积极将这个实用系统集成到数据流水线中，以自动纠正和丰富 Amazon Athena 数据库中的数据。系统在生成准确标注方面的性能已经针对策划的数据集进行了评估，展示了有前途的结果。为管理这些标注到生产数据库的集成，我们正在开发一个评估系统，为每个提取的字段提供置信度分数。高置信度分数的字段将自动用于更新 Amazon Athena 中的相应条目。较低置信度分数的字段将被隔离并标记为人工审查和干预，在利用自动化的同时确保数据准确性。这种方法旨在持续提升结构化元数据的质量，使其成为 PRINCE 和其他下游应用更可靠的信息来源。

#### 旅程仍在继续：迭代开发

PRINCE 自 2024 年初开始对终端用户可用，智能体集成在当年晚些时候引入。这对于收集真实世界反馈和推动迭代开发至关重要。指导我们开发的一个关键原则是理解构建生产就绪的 LLM 应用是一个迭代过程；我们不会等到功能绝对完美才寻求用户反馈。相反，我们优先早期交付价值，并基于真实世界的使用持续优化系统。

在初始阶段，我们的焦点完全放在实现核心功能所需的准确性和性能上，即使这意味着承担更高的成本。我们认识到过早优化成本可能会损害系统的有效性并阻碍用户采用。只有在达到所需的准确性和性能水平后，我们才开始关注成本优化，确保效率的提升不会对用户体验或结果质量产生负面影响。

PRINCE 的开发遵循持续的迭代过程。用户反馈、持续的监控数据和来自专家科学家的见解被持续反馈到开发周期中，导致架构、检索技术、智能体行为和用户界面的优化，以提升性能、可用性，并最终产生科学影响。

#### 结论

在像临床前药物发现这样复杂的企业环境中构建生产就绪的 LLM 应用，是一段以重大技术和工程挑战为标志的旅程。PRINCE 案例研究表明，通过结合健壮的数据基础设施、像 RAG 和 Text-to-SQL 这样的精密信息检索技术，以及智能的多智能体编排系统，可以从庞大的、以前无法访问的数据存储库中解锁有价值的见解。

我们的经验突显了聚焦于可靠性工程的关键重要性，包括健壮的错误处理、状态持久化和 LLM 回退。此外，建立用户信任至关重要，这通过工作流中的透明度、通过细粒度引用实现的清晰可解释性，以及对系统性能的持续评估和监控来实现。

PRINCE 已经在增强拜耳的数据可访问性和研究效率方面展示了有前途的结果，改变了科学家与临床前信息交互的方式。这不是旅程的终点，而是迈向创建真正智能研究助手的重要一步。

PRINCE 的更广泛教训是，生产就绪的智能体 AI 不仅仅是关于更好的模型或更好的提示词。**可靠性来自于同时工程化模型所见的上下文和模型行动所在的框架。** 上下文工程帮助确保每个模型在工作流的正确阶段拥有正确的信息——且仅有正确的信息。框架工程帮助确保工作流保持有界、可观测、可恢复，并适合受监管的研究环境。

随着模型能力的提升，今天框架的某些部分可能会变得更薄或转移到原生模型能力中。但在企业研究系统中，特别是在信任、可追溯性和可审查性很重要的地方，对上下文、工作流状态、恢复、反思和验证的显式控制仍然是必不可少的。

我们希望这个概述为在受监管且数据丰富的领域中构建和将 LLM 应用投入生产所需的实际考虑和技术深度提供有价值的见解。
