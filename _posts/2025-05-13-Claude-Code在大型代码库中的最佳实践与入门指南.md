Claude Code 正在生产环境中运行，涵盖数百万行代码的单体仓库、历经数十年的遗留系统、横跨数十个代码仓库的分布式架构，以及拥有数千名开发者的组织。这些环境带来了小型简单代码库所不具备的挑战——无论是每个子目录的构建命令各不相同，还是遗留代码分散在没有共同根目录的文件夹中。

本文介绍了我们观察到的、在规模化场景下成功采用 Claude Code 的模式。我们使用"大型代码库"来泛指多种部署形态：数百万行代码的单体仓库、历经数十年积累的遗留系统、横跨多个独立仓库的数十个微服务，或以上的任意组合。这也包括运行在团队通常不会与 AI 编码工具关联的语言上的代码库，比如 C、C++、C#、Java、PHP。（在这些场景下，Claude Code 的表现通常超出大多数团队的预期，尤其是在最近的模型版本发布之后。）虽然每个大型代码库的部署都受其特定的版本控制、团队结构和累积约定所影响，但本文所述模式具有跨场景的通用性，适合作为考虑采用 Claude Code 的团队的起步参考。

Claude Code 以软件工程师的方式导航代码库：它遍历文件系统、读取文件、使用 grep 精确查找所需内容，并跨代码库追踪引用。它在开发者的本地机器上运行，不需要构建、维护或上传代码库索引到服务器。

早期的 AI 编码工具依赖基于 RAG（Retrieval-Augmented Generation，检索增强生成）的检索方式，通过对整个代码库进行向量嵌入，在查询时检索相关代码片段。在大规模场景下，这些系统可能失败，因为嵌入管道跟不上活跃的工程团队。当开发者查询索引时，索引反映的可能是数天、数周甚至数小时前的代码库状态。检索返回的可能是团队两周前重命名的函数，或引用了上个迭代已删除的模块，且没有任何提示表明它们已过时。

智能体搜索（Agentic search）避免了这些失败模式。当数千名工程师提交新代码时，无需维护嵌入管道或集中索引。每个开发者的实例都基于实时代码库工作。

但这种方式也有权衡：当 Claude 拥有足够的起始上下文来知道该往哪里找时，效果最好。这意味着 Claude 的导航质量取决于代码库的配置程度——通过 CLAUDE.md 文件和 skills 来分层提供上下文。如果你要求它在十亿行代码库中查找某个模糊模式的所有实例，上下文窗口会在工作开始前就耗尽。在代码库配置上投入的团队会看到更好的结果。

#### 驾驭体系与模型同等重要

关于 Claude Code 最常见的误解之一是，其能力完全由所使用的模型决定。团队往往关注模型的基准测试分数及其在测试任务上的表现。但在实践中，围绕模型构建的生态系统——即**驾驭体系**（harness）——对 Claude Code 性能的影响远超模型本身。

驾驭体系由五个扩展点构成——CLAUDE.md 文件、hooks、skills、plugins 和 MCP 服务器——每个都承担不同的功能。团队构建它们的顺序很重要，因为每一层都建立在前一层之上。另外还有两项能力——LSP 集成和子智能体（subagents）——作为补充。以下逐一介绍每个组件和能力的作用：

**CLAUDE.md 文件是第一步。** 这些是 Claude 在每次会话开始时自动读取的上下文文件：根目录文件提供全局视图，子目录文件提供本地约定。它们为 Claude 提供完成任何工作所需的代码库知识。由于它们在每次会话中都会加载（无论任务是什么），因此保持其内容聚焦于广泛适用的信息，可以避免它们成为性能拖累。

**Hooks 让配置持续自我改进。** 大多数团队把 hooks 视为防止 Claude 犯错的脚本，但它们更有价值的用途是持续改进。Stop hook 可以在会话结束时回顾发生了什么，并在上下文仍然新鲜时提出 CLAUDE.md 的更新建议。Start hook 可以动态加载团队特定的上下文，让每个开发者无需手动配置就能获得适合自己模块的设置。对于 lint 和格式化等自动化检查，hooks 以确定性方式执行规则，比依赖 Claude 记住某条指令能产生更一致的结果。

**Skills 按需提供正确的专业知识，而不会让每次会话都臃肿。** 在拥有数十种任务类型的大型代码库中，并非所有专业知识都需要在每次会话中出现。Skills 通过渐进式披露来解决这个问题——将专业化的工作流和领域知识卸载出去（否则它们会与上下文空间竞争），只在任务需要时才加载。例如，安全审查 skill 在 Claude 评估代码漏洞时加载，而文档处理 skill 在代码变更需要更新文档时加载。

Skills 还可以限定在特定路径下，这样它们只在代码库的相关部分激活。拥有支付服务的团队可以将其部署 skill 绑定到该目录，这样当有人在单体仓库的其他位置工作时，它就不会自动加载。

**Plugins 分发有效的实践。** 大型代码库面临的一个挑战是，好的配置往往停留在少数人手中。Plugin 将 skills、hooks 和 MCP 配置打包成一个可安装的包，新工程师在第一天安装该 plugin 后，就能立即拥有与资深 Claude 用户相同的上下文和能力。Plugin 更新可以通过组织内部的托管市场分发。

例如，我们合作的一家大型零售组织构建了一个 skill，将 Claude 连接到其内部分析平台，让业务分析师无需离开工作流就能拉取绩效数据。他们在面向业务部门大规模推广之前，就以 plugin 形式分发了它。

**语言服务器协议（LSP）集成赋予 Claude 与开发者在 IDE 中相同的导航能力。** 大多数大型代码库的 IDE 已经运行着 LSP，驱动"跳转到定义"和"查找所有引用"功能。将这些能力暴露给 Claude，就赋予了它符号级的精确度：它可以追踪函数调用到其定义处、跨文件追踪引用，并区分不同语言中同名的函数。没有 LSP，Claude 只能基于文本进行模式匹配，可能会定位到错误的符号。我们合作的一家企业软件公司在 Claude Code 推广前，就在全组织部署了 LSP 集成，专门为了让 C 和 C++ 的导航在规模化场景下可靠工作。对于多语言代码库，这是价值最高的投资之一。

**MCP 服务器扩展一切。** MCP 服务器是 Claude 连接内部工具、数据源和 API（它本身无法触达的）的方式。最成熟的团队构建了 MCP 服务器，将结构化搜索作为工具直接暴露给 Claude 调用。其他团队则将 Claude 连接到内部文档、工单系统或分析平台。

**子智能体将探索与编辑分离。** 子智能体是一个隔离的 Claude 实例，拥有自己的上下文窗口，接受任务、完成工作，然后只将最终结果返回给父级。驾驭体系就绪后，一些团队会启动一个只读子智能体来映射某个子系统并将发现写入文件，然后让主智能体带着完整的全景信息进行编辑。

##### Claude Code 扩展层一览

下表总结了每个组件的功能、加载时机，以及我们常见的误区：

| 组件 | 是什么 | 何时加载 | 最适合 | 常见误区 |
|------|--------|----------|--------|----------|
| CLAUDE.md | Claude 自动读取的上下文文件 | 每次会话 | 项目特定约定、代码库知识 | 把应该放在 skill 里的可复用专业知识塞进去 |
| Hooks | 在关键时刻运行的脚本 | 由事件触发 | 自动化一致性行为、捕获会话经验 | 用提示词代替应该自动运行的事情 |
| Skills | 针对特定任务类型的打包指令 | 按需，在相关时 | 跨会话和项目的可复用专业知识 | 把所有东西都塞进 CLAUDE.md |
| Plugins | 打包的 skills、hooks、MCP 配置 | 配置后始终可用 | 在组织内分发有效的配置 | 让好的配置停留在少数人手中 |
| 语言服务器协议（LSP）* | 通过语言特定服务器提供实时代码智能 | 配置后始终可用 | 符号级导航和类型语言的自动错误检测 | 以为它是自动开启的 |
| MCP 服务器 | 连接外部工具和数据 | 配置后始终可用 | 让 Claude 访问其本身无法触达的内部工具 | 在基础配置完善前就去构建 MCP 连接 |
| 子智能体* | 执行特定任务的独立 Claude 实例 | 被调用时 | 将探索与编辑分离、并行工作 | 在同一个会话中同时运行探索和编辑 |

*LSP 通过 plugin 层访问。子智能体是一种委派能力，而非配置化的扩展点。

#### 成功部署中的三个配置模式

如何为大型代码库配置 Claude Code，在很大程度上取决于代码库的结构。尽管如此，以下三个模式在我们观察到的部署中一致出现。

##### 让代码库在规模化场景下可导航

Claude 在大型代码库中的帮助能力，取决于它找到正确上下文的能力。每次会话加载过多上下文会降低性能，而上下文过少则让 Claude 盲目导航。最有效的部署在前期就投入让代码库对 Claude 可读。以下几个模式一致出现：

**保持 CLAUDE.md 文件精简且分层。** Claude 在遍历代码库时叠加加载它们：根文件提供全局信息，子目录文件提供本地约定。根文件应该只包含指引和关键注意事项；其他内容会逐渐变成噪音。

**在子目录中初始化，而不是在仓库根目录。** 当 Claude 的作用范围限定在与任务实际相关的代码库部分时，效果最好。在单体仓库中，这可能感觉有悖直觉，因为工具通常假定从根目录访问，但 Claude 会自动沿目录树向上查找并加载路径上的每个 CLAUDE.md 文件，因此根级上下文永远不会丢失。

**按子目录限定测试和 lint 命令。** 当 Claude 只修改了一个服务却运行全量测试套件时，会导致超时并浪费上下文在无关输出上。子目录级别的 CLAUDE.md 文件应指定适用于该部分代码库的命令。这对面向服务的代码库（每个目录有自己的测试和构建命令）效果很好。在具有深层跨目录依赖的编译型语言单体仓库中，按子目录限定更难实现，可能需要项目特定的构建配置。

**使用 .ignore 文件排除生成的文件、构建产物和第三方代码。** 在 `.claude/settings.json` 中提交 `permissions.deny` 规则意味着排除项是版本控制的，团队中每个开发者无需自行配置就能获得相同的降噪效果。在某些代码库中，生成的文件本身就是开发工作的主题。开发代码生成器的开发者可以在本地设置中覆盖项目级排除，而不影响团队其他成员。

**当目录结构本身不足以说明问题时，构建代码库地图。** 对于代码未按照传统目录结构组织的组织，在仓库根目录放一个轻量的 markdown 文件，列出每个顶层文件夹及其一行描述，就能给 Claude 一个目录表，让它在打开文件前先扫描。对于拥有数百个顶层文件夹的代码库，这最好采用分层方式：根文件只描述最高层结构，子目录 CLAUDE.md 文件提供下一层细节，在 Claude 遍历目录树时按需加载。对于较简单的场景，@ 提及 Claude 应参考的特定文件或目录也能起到同样的作用。

**运行 LSP 服务器，让 Claude 按符号而非字符串搜索。** 在大型代码库中 grep 一个常见函数名会返回数千个匹配，Claude 会消耗上下文打开文件来判断哪个是重要的。LSP 只返回指向同一符号的引用，因此过滤在 Claude 读取任何内容之前就已完成。设置这个功能需要安装对应语言的代码智能插件和相应的语言服务器二进制文件；Claude Code 文档涵盖了可用的插件和故障排除。

有一点需要注意：即使是分层 CLAUDE.md 方法也存在失效的边界场景，例如拥有数十万个文件夹和数百万个文件的代码库，或基于非 Git 版本控制的遗留系统。我们将在本系列的后续文章中讨论它们的挑战。

##### 随着模型智能演进主动维护 CLAUDE.md 文件

随着模型演进，为当前模型编写的指令可能对未来的模型产生反效果。曾经引导 Claude 处理它难以应对的模式的 CLAUDE.md 文件，在新模型发布时可能变得不再必要，甚至形成主动的限制。例如，一条告诉 Claude 将每次重构拆分为单文件修改的 CLAUDE.md 规则，可能曾帮助早期模型保持轨道，但会阻止新模型执行它完全能胜任的协调跨文件编辑。

为弥补特定模型局限性而构建的 skills 和 hooks——无论是模型推理方面的还是 Claude Code 工具本身的——一旦这些局限不再存在，就会变成额外开销。例如，一个拦截文件写入以强制执行 Perforce 代码库中 `p4 edit` 的 hook，在 Claude Code 添加原生 Perforce 模式后就变得多余了。

团队应预期每三到六个月进行一次有意义的配置审查，但在重大模型发布后感觉性能停滞时，也值得立即进行一次。

##### 为 Claude Code 的管理和推广分配所有权

仅有技术配置并不能推动采用。那些做得好的组织也在组织层面进行了投入。

推广最快的项目在广泛开放访问之前，都先进行了专门的基础设施投资。一个小团队，有时甚至只是一个人，提前搭建好了工具链，使得 Claude 在开发者首次接触时就已经适配了他们的工作流。在一家公司，几名工程师构建了一套 plugin 和 MCP，在第一天就可用。在另一家公司，一个专门管理 AI 编码工具的团队在推广开始前就已将基础设施就位。在这两种情况下，开发者的首次体验是高效而非令人沮丧的，采用从此扩散开来。

目前承担这项工作的团队通常隶属于开发者体验或开发者效率部门，这些部门通常负责新工程师入职和构建开发者工具。在多个组织中正在出现一个新兴角色：**智能体管理员**（Agent Manager）——一个专注于管理 Claude Code 生态系统的 PM/工程师混合职能。对于没有专门团队的组织，最小可行版本是一个 **DRI**（Directly Responsible Individual，直接负责人）：一个对 Claude Code 配置拥有所有权的人，有权对设置、权限策略、plugin 市场和 CLAUDE.md 约定做出决策，并有责任保持它们的时效性。

自下而上的采用能激发热情，但如果没有专人将有效做法集中起来，可能会导致碎片化。你需要一个人或一个团队来整合并推广正确的 Claude Code 约定（如标准化的 CLAUDE.md 层级结构或精选的 skills 和 plugins 集合）。没有这项工作，知识会停留在少数人手中，采用也会遇到瓶颈。

在大型组织中，尤其是受监管行业的组织，治理问题很早就会出现，例如：谁控制哪些 skills 和 plugins 可用？如何防止数千名工程师各自独立重建同样的东西？如何确保 AI 生成的代码经过与人工代码相同的审查流程？为了尽早解决这些问题，我们建议从一组已定义的已批准 skills、必需的代码审查流程和有限的初始访问权限开始，随着信心的建立再逐步扩展。

我们观察到最顺畅的部署出现在那些尽早建立跨职能工作组的组织中——将工程、信息安全和治理代表聚集在一起共同定义需求并制定推广路线图。

#### 将这些模式应用到你的组织

Claude Code 围绕传统软件工程环境设计，其中工程师是代码库的主要贡献者、仓库使用 Git、代码遵循标准目录结构。大多数大型代码库符合这一模式，但非传统设置——如包含大量二进制资产的游戏引擎、使用非常规版本控制的环境、或非工程师贡献代码库——需要额外的配置工作。我们的指南假设传统设置，所描述的模式已在我们的许多客户中得到验证。任何剩余的复杂性都需要针对你的代码库、工具链和组织的特定判断。这正是 Anthropic 的 Applied AI 团队直接与工程团队合作的地方——将这些模式转化为你的组织的特定需求。
