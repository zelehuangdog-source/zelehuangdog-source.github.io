> **摘要**：这是 Anthropic 三位成员（主持人、托管智能体产品负责人 Katelyn，以及 Angela）关于 Agent 未来的一场圆桌对谈。他们复盘了过去半年 Claude Platform 从"只提供推理与 token 的 API"演进为"帮你卸下基础设施与 harness 工程负担的富功能平台"的过程，并探讨了几个核心趋势：随着模型变得更聪明、更能自主推理和调用工具，过去为了对抗模型不确定性而堆砌的复杂 harness（智能体外壳/编排层）正在变得越来越薄，取而代之的是"多智能体竞争""对抗生成""求助更聪明的朋友"等组合式的元策略；Agent 身份将逐渐独立，通过"申请权限—创建服务账号—可审计"的模式运作；企业衡量 ROI 应从"个人提速"起步，再到团队、再到跨团队流程，而非一上来就想改造 120 个大流程；未来 Agent 会像无形的操作系统底座一样嵌入组织，主动发现并解决问题，而 Claude Platform 正通过 outcome（结果目标）+ 预算这样的抽象，让"每天随手起一个 Agent 干活"变得极其简单。

**主持人**：一听我们就是 API 极客——因为我们主张 Agent 之间应该通过 API 互相对话。

过去六个月简直是疯狂的六个月。因为如果回头看半年前，那时候 Claude Platform 基本上就是一个 API：它让你能访问推理能力和 token，从模型里拿到结果。当然，我们那时也已经开始围绕模型构建一些有意思的工具，能帮你获得更多智能、降低成本、或者跑得更快。但最近我们开始在平台里推出一批真正丰富的功能，帮你从模型中榨取出更多价值——帮你把基础设施的难题从肩上卸下，把 harness（智能体外壳/编排层）的工程难题也卸下，好让你的团队能以低得多的成本真正拿到那份智能。

Angela，你从客户那里看到过哪些最有意思的反馈模式？

**Angela**：最让我兴奋的是围绕 managed agents（托管智能体）的反馈，这块特别棒——我知道你（Katelyn）本身就是 managed agents 的产品负责人。反馈真的很好，尤其是围绕 memory（记忆）、outcomes（结果目标）和 dreaming 这些概念。不过我个人最喜欢的其实是个有点"老派"的反馈：我听到一位开发者说，他就是特别喜欢这些抽象层级（abstraction levels）的设计。这种反馈总能让我心里暖一下。

**主持人**：即便这些工作流一直在演进，"Agent 身份（agent identity）"这个概念依然存在。那我们该怎么看待"工作流"与"Agent 身份"结合这件事？

**Katelyn**：我觉得 Agent 身份将来很可能需要做成一个几乎独立的东西——几乎是说，Agent 需要拥有它自己的身份。今天这还处在很早期的阶段，大家仍在探索有趣的用例，而且你需要给 Agent 相当程度的信任。但我认为，Agent 身份会越来越接近这样一种形态：Agent 接收到一个你想要的 outcome（结果目标），然后它很可能会回来问你——"嘿，为了完成你交给我的这个目标，我需要访问 A、B、C、D。" 而你可能会说"A、B、C 没问题，但我不想让你碰 D"，然后 Agent 就去尝试看能不能在这个前提下完成任务。当它真的去做时，它几乎能为自己创建一个服务账号（service account）。在那样的世界里，你就可以对它进行审计（audit），确保它确实在做你想让它做的事。我觉得这大概更接近我们将来会看到的、身份层逐渐演化出来的运作模式。

关于 Agent 之间如何对话，有意思的一点是：你可以构建一个 Agent，然后暴露一个 API，或者暴露某种机制，让另一个 Agent 能用和人跟它交互几乎一样的方式来跟它对话。我们已经看到有人从这个角度做出了非常有意思的东西——比如有人基于平台里的 Claude 托管智能体来构建，然后再套上一个精巧、很薄的 MCP server 暴露出去，这样另一个 Agent 就能确切地知道该怎么调进来、跟那个 Agent 对话。我觉得这极其有用，大家已经能借此做出很多富有创造力的东西。

**主持人**：那为什么这类工作流现在才变得"名正言顺"了？模型层或基础设施层到底发生了什么变化，才让这一切成为可能？

**Katelyn**：模型显然是变得更好了，我觉得这是很大的一部分原因。因为在过去，你可能不得不围绕模型搭建一大堆脚手架（scaffolding），还有各种标准操作规程（SOP）之类的东西，来确保"先发生这件事、再发生那件事"。模型的不确定性（nondeterminism）过去比今天要棘手得多。而今天的模型真的很棒，能在一些合理的护栏（guardrails）范围内自己想清楚"我需要采取哪些步骤、我需要做哪些事"。

它们还能跑得更久了。我们现在有了合适的基础设施，能让一个 Agent 在工作区里"常驻（ambient）"，被某件事触发之后，就跑去执行某个工作流、持续一段时间，然后在真正准备好的时候再回来。所以我觉得，这一部分是模型的演进，另一部分是基础设施的演进——也就是大家能够真正把 Agent 搭起来、围绕它做构建的方式的演进。

**主持人**：Angela，我很想听听你的想法：Katelyn 说的这种"不确定性"，是如何真正推动 harness 层演化的？

**Angela**：是的。在过去——其实感觉也就几个月前——大家会真的去搭建那种非常复杂的"业务流程盒子"，把一堆东西拼在一起：先得走完步骤 A，而且只有当所有这些条件都满足时，步骤 A 才能走到 B……这是一张非常复杂的关系网。结果它变得非常脆弱。就 Agent 真正能否展现出你期望它拥有的那种智能而言，你本来是想自动化某件事、或者让它更有用一点，但我们其实一直在试图把模型"框死"。

正如 Katelyn 提到的，随着模型越来越聪明、能力越来越强、在工具调用上越来越 agentic、在自身推理上越来越有深度，你实际上能走到这样一步：开始删掉 harness 里那些限制性的部分。所以我看到 harness 正随着时间变得越来越薄。

我看到的另一件事是：随着 harness 变薄，你几乎会得到一种"元 harness（meta harness）"。我不知道该管这些东西叫什么——也许未来它们会像"马鞍（saddle）"之类的东西。但我确实觉得它们倾向于把多种策略组合起来。举个例子，我们看到有人做出非常创新的东西：多个 Agent（这本身就内建在 harness 里）真的会互相竞争，一起去尝试解决一个问题。还有一种情况是你起两个 Agent，其中一个产生想法，另一个则对它进行对抗（adversarial）。在此之上你还能搭建出非常多其他策略。我们最近做了个"顾问策略（advisor strategy）"作为例子：如果模型自己想不明白该怎么办，它就直接伸手"打电话求助一个朋友"，而那个朋友但愿更聪明，能帮它想清楚。所以我觉得，harness 的创新会越来越往这类方向走。我们会看到很多令人惊叹的方式，Agent 通过这种"扩张式（expansive）"的架构，去解决越来越复杂的问题。

**主持人**：对。我觉得这真的触及了我们思考 harness 演化的核心——归根结底，你手里有这么多不同的组合策略，随着时间推移，我们会演化到把这些策略做成混合体（hybrid）。比如你可以先用那种"扩张式、广撒网"的方式起步，一旦确定了正确的框架，再在那个单一框架上做迭代。

你刚提到复杂问题。跟我讲一个最近让你印象深刻的、特别复杂的问题吧。

**Angela**：有一个特别棒的黑客松（hackathon）获奖项目，非常鼓舞人心。我记得它叫 Urrea（可能读音不准）。他们面对的问题是：在一堆不同的制造工厂里，需要有一个真正懂机械的专家。你得去听、去监控某些机器是在正常运转还是出了故障，还得去读机器里那个特定部件的手册。传统上，一家工厂里往往只有一个人——他在这家厂里干了大概 10 年、15 年、20 年，才摸透了这一切——然后他很合理地退休了，于是你就再也没有那份专业知识了。

这个项目的人竟然能把所有这些拼图拼起来，说：好，如果我把标准操作规程（SOP）上传进去、如果我把监控做进去、我从工厂各个不同部件那里采集信号，那我就真的能让 Agent 去尝试模仿那个人的判断。看到他们真的能接管其中相当大一部分工作，非常酷——他们本质上是把"那个人退休"这件事做成了冗余（redundancy）备份，并且真的能回到那套 agentic 系统里说："我可以依赖它来沉淀那些真正重要的、必需的工厂知识。"

**主持人**：那你呢，Katelyn？你最近看到过什么有意思的、被解决了的问题？

**Katelyn**：是的。工程团队里——其实不只是工程团队，就是那些想把活干完的开发团队——正在发生的一件很酷的事是：大家搞出来的 Agent，已经比"我能写点代码"强大得多了。我们有像 Claude Code 这样出色的产品，围绕"你到底怎么写代码"有一大批优秀产品。但我现在看到人们走得更远，他们会说：好，如果我要从一个项目的最开头做起，为了把这活干成，到底需要发生哪些事？我该怎么考虑运行我的开发环境去真正测试我写的代码？我该怎么在一开始就把 PR、需求文档写出来，然后到后面再去验证所有那些 QA 测试之类必须发生的环节？

现在外面已经有一些例子，一些更大的公司真的搭起了完整的 agentic 系统和平台，帮他们做相当定制化的端到端开发。我觉得一个很好的例子是 Shopify 最近谈到他们做的这件事——我记得他们把它叫做 River。类似这样的例子还有几个。我觉得这是被"Agent 能力本身的演进"所促成的演化之一。

**主持人**：所以很明显，一些组织在它们能解决的问题上看到了天花板被大幅抬高。但并非所有组织都感受到了这一点。你觉得最大的障碍是什么？

**Katelyn**：真正的边界，就是那些会挡在人们面前的东西。安全与合规的护栏（security and compliance guardrails）——为了让人放心地让 Agent 去干它们能干的活，这些护栏必须先到位。还有 evals（评估集），我觉得这也是很大的一个，只有这样才能真正把这项技术的价值发挥到最大。

**Angela**：安全与合规在这里绝对是大问题。因为很多团队至今还运行在 20 年前那套安全假设之上，而现在 Agent 正在从根本上改变一切——随之而来的就是安全问题。我觉得我们对于"什么才算一个带有强护栏的安全 Agent"已经有了相当基础的认识，但要把这个理念往上推、去修订那份检查清单（checklist），一直是段不小的旅程。

**主持人**：对，是的。那也很好奇：你怎么看 Agent 的 ROI（投资回报），以及企业该如何管理它？

**Angela**：这对现在一大批不同的公司来说都是个非常紧迫的问题，因为它们看着一切都在加速，也想让自己加速起来。我觉得思考这个有好几种方式，但我倾向于鼓励一个稍微简化一点的心智模型。人们常常想一步跳到："我该怎么把我那些庞大的老式流程都 agent 化？"——也许他们有 120 个这样的流程，想照着清单一个个来；或者他们会说"太好了，这是我的时刻，如果消费者偏好正在变化，那就从根本上重塑我们整个产品与服务。"这些想法都很好，但要把它们全走一遍显然非常难，那里面的东西五花八门、范围极广。

我确实认为，从 ROI 的角度看，其实更容易的是几乎从"个人"起步，聚焦于那个人到底变快了多少。这听起来简单得几乎有点"不够高级"，但我真心觉得，如果你从这里起步、能把那一个人加速起来，你就能从个人推进到团队。到了团队层面，你就开始思考你在那里产生的速度。然后——大概也只有到那时——我才会开始鼓励说：好，如果我能让这个团队更快，那我现在有没有能力把这个团队拿来、去打通一个横跨全公司的流程？

而现实是，一个流程通常需要许多不同的团队、许多不同的个人——他们并不共享同一套 SOP，也许也不共享完全一样的专业知识。这也正是为什么我们把他们凑在一起时，往往是靠"胶带"把一堆东西勉强粘在一起。但如果你走完这样一个阶段——先关注个人层面的速度，再到团队及其生产力，最后才是你如何把这些工作流串起来——我觉得作为一家公司，你几乎就能点亮你最终在意的每一根进度条，最终一路走到那份"我真希望能 agent 化的 120 个工作流"清单。

如果从这个视角来看，你的大部分 ROI 计算首先、也最重要的，应该落在"速度"和"生产力"上。把速度作为首要观察指标，往往更具前瞻性、也更容易成功。当它开始在公司内部"开花"之后，再转向"好吧，也许有些财务指标是我想推动的，也许有些用户指标能驱动我在意的整体产出与生产力"就更合理了。我觉得如果领导者和公司能遵循这样一个循序渐进、分阶段的过程，他们其实能驱动出更多的 ROI。

**主持人**：Katelyn，你一直在说"工程团队"，我想就这一点深挖一下——如今到底什么才算一个工程团队？

**Katelyn**：对我们来说，工程团队仍然是一群人，而且这群人其实和 6 个月前、12 个月前的工程团队看起来没太大不同。你依然需要这么一群人去理解他们正在构建的系统、去理解怎么运维它、怎么在出问题时值班（on call）——所有这类事情。但其中每一个人，都被 Agent 疯狂地"涡轮增压"了，Agent 能帮他们把活干完。

我们看到的转变是：过去的工程团队也许是一位技术负责人对"系统该怎么设计"有主见，然后一大群工程师去领取工单、把活干完；而现在几乎是整个团队的人都对"我们该如何端到端地构建一个产品或系统、技术设计该长什么样"有强烈的主见。然后他们某种程度上是在"编排他们的 Claude"（姑且这么叫）去把活干完。所以对我们来说，工程团队的样子其实挺相似的，但他们能完成的工作量比过去多得多。

**主持人**：我很好奇，你怎么看组织过度依赖 Agent 可能带来的失效模式（failure modes）？

**Angela**：我确实觉得它会制造出一种"超级独立（hyper independence）"的感觉，而这种感觉也许有点虚。你会觉得——当然啦，现在人人都是 builder，我可以去构建，是的，我能一口气起十个原型。放在以前，你会想"这几个选项里哪个最好？"然后花点心思去想；而现在你有能力说"反正很便宜，那我干嘛不干脆十个全上线，哪个胜出就选哪个。"所以我确实觉得它给每一个人都制造了这种超级独立。

但很多时候，那种更系统化、更整体（holistic）的东西所汇聚出的质量，反而会更难协调。所以我觉得失效模式就在这里：如果你给了每个人超级独立，却没有把他们朝一个明确的方向组织起来，你就可能看到那种"蔓生（sprawl）"的局面。这有利有弊，但我觉得这类情况确实会带来明确的失效模式。

**主持人**：那你觉得"冰球"要滑向哪里（指趋势走向）？Agentic 开发的未来是什么样？

**Angela**：我觉得它会深度嵌入到组织内部，深到你可能都不会再以那种"如此显性地被实例化"的方式去使用工具。我的意思是：今天我们都在伸手去够这个 agentic 工具、那个 agentic 工具，这个擅长这、那个擅长那。而我觉得未来会更接近这样——也许存在某种共同的基座（common substrate），我们都在上面协作，界面很熟悉，等等；但你其实就是能随手"标记（tag）"一个 Agent、按需把它起起来、关下去，它就自己在后台无形地干了一大堆活。

它甚至可能是主动的（proactive）。也许是它来找你说："嘿，我们注意到这个东西挂了，所以我深入排查了细节、想明白了、把它修好了，这是 PR，你也许想 review 一下。"而你甚至可能早就告诉过它："以后这么小的事，别来烦我，直接上线（ship）就行。"我觉得未来会有点像这样——它几乎像一个你与之交互的、无形的底层基座。

在那样的世界里，我觉得每个人最终都会走到这样一个位置：他们几乎能构建"面向团队的 Agent"。但不是说它像另一个队友那样，而更像是——比如你和我共有的某个工作流有它自己的团队取向，那就有一个对应的 Agent，它能真正映射到我们俩的偏好；我们三个人有一个基于团队的 Agent，它理解一套略微不同的偏好，并开始去填补那些必要的空白。当然，我觉得我们仍会保有现在这些共同的界面和东西，但我们也许会更多地把它看成一种操作系统（operating system）之类的东西，而不是我们主动去伸手够的一个个具体工具。

**主持人**：那你觉得 Claude Platform 会如何帮我们抵达那个愿景？

**Katelyn**：是的。我们最近一直在努力推进边界的一个比较大的东西，是像 outcome（结果目标）这样的概念——这是个大事。我们在 Claude 托管智能体里发布了"outcome"这个想法：你告诉 Claude"好的样子长这样"，给它一份评分标准（rubric），并设定它在停下来之前，最多可以迭代多少次去尝试成功达成那个 outcome。我觉得随着我们把这个概念继续演化下去，我们大概会越来越接近这样一个世界：你和 Claude 对话，说"我想要这个 outcome，这是预算（budget），开干（Go）。"你其实不太需要再想更多了。

我觉得我们想通过平台推出的核心想法，就是把这件事做到极其简单。想象一个世界，你每天都在起一个 Agent，因为你会想"今天我得把一些访谈笔记总结一下、拼出一份反馈资料包"之类的。你就可以说"好，亲爱的 Agent，我想要的笔记长这样、看起来是这样，你可以花这么多预算，开干。"然后你就能拿回你想要的东西。让你不必更费力、不必更烧脑就能造出那样的产物——这就是我们正试图填补的空白，就是把它做到超级简单。

**主持人**：聊 Agent 的未来太开心了。非常感谢你们，各位！
