> **摘要**：本文由 Claude Code 团队撰写，系统梳理了「循环」（Loop）这一概念——智能体反复执行工作直到满足停止条件的模式。文章将循环分为四类：由用户手动驱动的 Turn-based 循环、以可验证目标为停止条件的 Goal-based 循环（`/goal`）、按时间间隔触发的 Time-based 循环（`/loop`、`/schedule`）、以及无需人工介入的 Proactive 循环（结合 auto mode 与动态工作流）。文章还给出了保持代码质量与控制 token 消耗的实践建议：让代码库本身保持整洁、用 skills 固化验证标准、引入第二个 agent 做代码评审、先小范围试跑再大规模铺开等。核心观点是：不是所有任务都需要复杂循环，应从最简单的方案开始，按需选用合适的循环原语。

近来关于用"设计循环"而非直接给编码智能体下达指令的讨论很多。如果你花点时间在 X 上尝试搞清楚"循环"到底是什么，会发现有很多种不同的答案。

在 Claude Code 团队内部，我们把**循环定义为：智能体重复执行工作周期，直到满足某个停止条件**。我们根据以下几个维度对循环进行分类：

- 如何被触发
- 如何停止
- 使用了 Claude Code 的哪种原语（primitive）
- 最适合哪种类型的任务

本文将介绍主要的循环类型、各自的适用场景，以及如何在控制 token 消耗的同时保持代码质量。并不是所有任务都需要复杂的循环，建议从最简单的方案开始，再按需选用这些模式。

#### Turn-based 循环（按轮次驱动）

- **触发方式**：用户下达指令（prompt）。
- **停止条件**：Claude 判断任务已完成，或需要更多上下文。
- **最适合**：不属于常规流程或排期的短任务。
- **用量管理方式**：编写具体明确的 prompt，并借助 skills 改进验证环节以减少轮次。

你发送的每一条 prompt 都会启动一个由你手动引导每一轮的循环。Claude 收集上下文、执行操作、检查自己的工作、按需重复，最后给出回复。我们把这个过程称为"agentic loop"（智能体循环）。

举个例子，让 Claude 创建一个点赞按钮：它会读取你的代码、进行修改、运行测试，然后交回它认为可行的结果。接下来你需要手动检查这份工作，再写下一条 prompt。

你可以通过把自己手动验证的步骤沉淀为一份 `SKILL.md`，来改进这个验证环节，让 Claude 能够端到端地检查更多自己的工作。这份文档应当包含能让 Claude "看到"、"测量"或"交互"结果的工具或连接器。检查项越量化，Claude 就越容易自我验证。

例如，你可以在 `SKILL.md` 文件中这样写：

```markdown
--- 
name: verify-frontend-change 
description: Verify any UI change end-to-end before declaring it done. 
--- 

# Verifying frontend changes 
Never report a UI change as complete based on a successful edit alone. Verify it the way a human reviewer would: 

1. Start the dev server and open the edited page in the browser. 

2. Interact with the change directly. For a new control (button, input, toggle): click it, confirm the expected state change, and screenshot before/after. 

3. Check the browser console: zero new errors or warnings. 

4. Use the Chrome Devtools MCP, run a performance trace and audit Core Web Vitals.

If any step fails, fix the issue and rerun from step 1 — do not hand back partially verified work.
```

#### Goal-based 循环（`/goal`，按目标驱动）

- **触发方式**：实时的手动 prompt。
- **停止条件**：目标达成，或达到最大轮次上限。
- **最适合**：拥有可验证退出条件的任务。
- **用量管理方式**：设定明确的完成标准和显式的轮次上限，例如"尝试 5 次后停止"。

有时候，单轮对话是不够的，尤其是对于更复杂的任务。当智能体可以持续迭代时，它们的表现会更好。你可以通过 `/goal` 定义"完成"意味着什么，来延长 Claude 持续迭代的时长。

当你定义了成功标准后，Claude 就不需要自己判断"是否已经足够好"从而提前结束循环。每次 Claude 试图停止时，一个评估模型（evaluator model）会检查你设定的条件，并把任务打回去继续执行，直到目标达成，或达到你设定的轮次上限。

这也是为什么确定性的标准（比如通过测试的数量，或达到某个分数阈值）如此有效的原因。

例如：

```bash
/goal get the homepage Lighthouse score to 90 or above, stop after 5 tries.
```

#### Time-based 循环（`/loop` 与 `/schedule`，按时间驱动）

- **触发方式**：指定的时间间隔。
- **停止条件**：你手动取消，或工作已经完成（PR 被合并、队列已清空）。
- **最适合**：周期性重复的工作，或与外部环境/系统对接的场景。
- **用量管理方式**：设置更长的时间间隔，或改为基于事件而非时间来触发。

有些智能体工作是周期性重复的：任务本身不变，只是输入在变化。例如，每天早上总结一遍 Slack 消息。还有一些工作依赖外部系统，与之对接的一种简单方式就是按固定间隔检查一次，并对变化做出反应。例如,一个可能会收到代码评审意见或 CI 失败反馈的 PR。

对于这类场景，你可以用 `/loop` 触发 Claude 的运行，它会按设定的时间间隔重复运行同一条 prompt。例如：

```bash
/loop 5m check my PR, address review comments, and fix failing CI
```

`/loop` 运行在你的本机上，所以一旦你把它关掉，它就会停止。你也可以通过 `/schedule` 创建一个例行任务（routine），把这个循环迁移到云端运行。

#### Proactive 循环（主动式循环）

- **触发方式**：某个事件或排期，全程无需人工实时参与。
- **停止条件**：每个具体任务在其目标达成时退出；例行任务本身会一直运行，直到你将其关闭。
- **最适合**：定义明确、持续出现的重复性工作流，例如 bug 报告处理、issue 分诊、迁移、依赖升级等。
- **用量管理方式**：将常规性工作路由给更小、更快的模型，把最强的模型留给需要判断力的场景。

上述这些原语，再结合 Claude Code 的其他能力，比如 **auto mode**（自动模式）和**动态工作流**（dynamic workflows，研究预览版），可以组合成一个用于长时间运行工作的循环。

例如，要处理接收到的反馈，你可以这样组合使用：

1. 用 **`/schedule`**（研究预览版）运行一个例行任务，用于检查新出现的报告
2. 用 **`/goal`** 定义"完成"是什么样子，再用 **skills** 记录如何验证
3. 用**动态工作流**编排多个智能体，对每份报告进行分诊、修复并评审
4. 用 **auto mode**，让整个例行任务无需停下来征求许可即可持续运行

把这些组合在一起，一条 prompt 大致会是这样：

```bash
/schedule every hour: check the project-feedback channel for bug reports. /goal: don't stop until every report found this run is triaged, actioned, and responded to. When fixing a bug, use a workflow to explore three solutions in parallel worktrees and have a judge adversarially review them.
```

#### 保持代码质量

一个循环最终产出的质量，取决于它所处的整套系统。在设计系统时，需要注意：

- **保持代码库本身的整洁**：Claude 会遵循代码库中已经存在的模式和约定。
- **给 Claude 一种能够验证自身工作的方式**：通过 [skills](https://code.claude.com/docs/en/skills) 把你和团队心目中"好的标准"固化下来。
- **让文档触手可及**：框架和库的文档中包含着最新的最佳实践。
- **用第二个智能体做代码评审**：一个带着全新上下文的评审者会更少偏见，也不会被主智能体的推理过程所影响。你可以使用内置的 `/code-review` skill，或针对 Github 使用 [Code Review](https://code.claude.com/docs/en/code-review)。

当某一次的结果没有达到标准时,不要只满足于修复这一个具体问题，而应该尝试把这次教训固化下来,以改进整个系统,让后续所有的迭代都受益。

#### 管理 token 用量

要控制 token 用量，循环需要有清晰的边界：

- **为任务选择合适的原语和模型**：小任务不需要多个智能体或复杂循环。有些任务可以用更便宜、更快的模型完成。
- **定义清晰的成功和停止标准**：明确说明"完成"是什么样子，这样 Claude 才能更快地(但也不会过早地)得出解决方案。
- **大规模运行前先小范围试跑**：动态工作流可以生成成百上千个智能体。先在一小部分工作上评估一下用量情况。
- **对确定性的工作使用脚本**：运行一段脚本比让模型逐步推理要便宜得多。例如，一个 PDF 相关的 skill 可以直接提供一份表单填写脚本，让 Claude 每次直接运行，而不必每次都重新推导出这段代码。
- **不要比实际需要的频率更频繁地运行例行任务**：让检查间隔和你所关注对象的实际变化频率相匹配。
- **审查用量**：`/usage` 命令会按 skills、subagents 和 MCP 细分展示近期用量；不带参数的 `/goal` 会显示目前为止的轮次数和 token 用量；`/workflows` 会展示每个智能体的 token 用量，你也可以随时停掉某个智能体。

#### 开始上手

总结一下：

| 循环类型 | 你交出的是 | 适用场景 | 使用工具 |
| --- | --- | --- | --- |
| Turn-based | 检查环节 | 你正在探索或做决策 | 自定义验证 skills |
| Goal-based | 停止条件 | 你清楚"完成"是什么样子 | /goal |
| Time-based | 触发时机 | 工作发生在项目之外、按排期进行 | /loop、/schedule |
| Proactive | 整个 prompt | 工作是重复性的且定义明确 | 以上全部，再加上动态工作流 |

要开始上手循环这套方法，不妨先看看你目前正在做的工作，挑出一个你自己是瓶颈的任务，问问自己可以交出哪一部分：你能写出验证检查项吗？目标是否足够清晰？工作是否会按固定排期出现？

一旦你有了想法，就实际运行这个循环，观察它的表现——比如在哪里卡住了，或者在哪里做得过头了——然后放心地去迭代它。
