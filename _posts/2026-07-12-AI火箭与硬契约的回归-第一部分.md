> **摘要**：AI 让软件"变便宜"的说法在大多数要紧的层面上都是错的——AI 真正压低的只是*实现*（把决策变成可运行代码）的成本，而判断、品味、集成、安全边界这些环节的价格纹丝未动。作者借苏联 N1 登月火箭"发动机工场"（造、点火、炸、修、再造）与阿波罗"发射前海量论证"两种建立信心的方式作类比，指出 AI 时代的正确姿势是：生成要慷慨，选择要严酷。但软件没有像物理那样免费的"神谕"来自动筛选对错，于是必须把系统设计成让生成的代码在进入时尽可能多地撞上编译器、类型系统、数据库约束、状态机、权限边界这些既有的"廉价判官"。由此得出一条反直觉却关键的结论：晚 90 年代那种"严苛契约"正在回归，但没有了当年的人力成本——**契约应当持久，实现应当可抛弃**，人的稀缺判断力应集中在意义与集成所在之处。

到处都能听到的那句"AI 让软件变便宜"，在大多数要紧的层面上都是错的。AI 真正压低成本的是*实现（implementation）*：把一个决策转化为可运行代码的这个动作。

围绕这个动作的一切，价格都保持着老样子；而且到目前为止，AI 模型也还没兑现"廉价到无需计量的智能"（它们把智能计量得相当到位，并据此收费）。仍然得有人来决定系统应该做什么、定义各部件如何拼合、划出安全边界、判断交回来的东西是否真的能用。今天的 agent 可以写出一份实现、重写它、产出四个备选方案、再以相对低廉的代价把它们全部丢弃。而判断力、品味和经验，仍然是它们一直以来的价格。

这种错配，正是 AI 辅助开发的核心经济事实。Agent 生成代码的速度，远远快过人类能够有意义地评估它的速度，而它们产出的大部分东西都看似合理却平庸。其中一些会有细微的错误。一些会解决眼前的局部问题，却悄悄地损害了它周围的系统。而在这股洪流里深埋着的，每隔一段时间，会出现一份比你自己能写出来的更好的实现。潜力是真实存在的，但前提是我们不再把每一件生成物都当作一件等待人类逐字审阅、逐一批准的成品。（我写这篇文章，主要是写给我自己的。这些话我自己听起来也很不好受。）

要看清另一种可能长什么样，我们该从一个完全出人意料的地方讲起：火箭发动机。

#### 购买信心的两种方式

我最喜欢的纪录片之一（每个工程师都该看）叫《Cosmodrome》。它讲的是为苏联 N1 登月计划所造发动机的故事，而在冷战历史的底下，是一种对比：一个工程组织可以用两种不同的方式来运作，并最终学会信任一台复杂的机器。

阿波罗用传统的、昂贵的方式购买它的信心。美国有钱、有深厚的工业底子、有成建制的专家大军、有专门建造的测试基础设施，还有一个政治使命：在十年结束前登月，抢在苏联人前面，而且不能在全国电视直播下把宇航员炸死。

于是 NASA 把它几乎全部的资源都倾注到一套庞大的飞行前体系里：建模、评审、文档、部件资格认证、静态点火、集成测试、任务演练。它专门建造设施来试车土星五号的发动机和各级箭体，飞行硬件在抵达肯尼迪航天中心之前就已经经过静态测试和认证。（[NASA History](https://www.nasa.gov/history/55-years-ago-first-saturn-v-stage-tested-in-mississippi-facility/ "First Saturn V Stage Tested in Mississippi Facility — NASA History")）阿波罗 4 号是完整三级土星五号的首次"全箭合练（all-up）"测试，这是一种激进的飞行测试策略，把 NASA 早先做法中原本会逐级递进飞行的多个系统合在一起。（[NASA](https://www.nasa.gov/mission/apollo-4/ "Apollo 4 — NASA")）这种激进建立在一个非同寻常的地面工作基础之上。发射依然是一次测试，只不过是一次由整个机构精心安排、并且十足指望它能通过的、非常昂贵的测试。

苏联的计划有杰出的工程师，此外几乎一无所有。他们没有资金、没有基础设施、没有协调、也没有对进度的掌控。于是他们依赖手上唯一有的那种资源，而在发动机这个层级上，那意味着与硬件的直接接触。造、点火、检查、修改、再点火。没人去"读"焊缝——他们直接给焊缝加压。少一点仿真，多一点点火：点起来，看它炸不炸，修好坏掉的地方，再来一次，宝贝儿。而这套流程是奏效的，至少在部件层级上是。Boris Chertok 记述该计划历史时提到，N1 的 NK-15 一级发动机在燃烧室压力和比冲上都显著高于土星五号的 F-1。（[Chertok, *Rockets and People* Vol. IV](https://www.nasa.gov/wp-content/uploads/2015/04/621513main_rocketspeoplevolume4-ebook.pdf "Boris Chertok, Rockets and People, Vol. IV: The Moon Race — NASA SP-2011-4110")）这些是精密的发动机，出自一群学会了把失败当作输入和向导的人之手。

N1 也恰恰暴露了这条路走到尽头的地方。它的一级——Block A——把三十台这样的发动机聚成一个复杂到令人咋舌的单一系统，而这个完整的箭级从未在地面上做过整级静态点火。整体的可靠性本应从各部件的可靠性推导出来，但单台发动机的点火无法揭示发动机之间、管路、结构、线路与飞行器动力学之间的相互作用。Chertok 后来形容每一次 N1 发射都像是没带扫雷器就走进了雷区。（[Chertok](https://www.nasa.gov/wp-content/uploads/2015/04/621513main_rocketspeoplevolume4-ebook.pdf "Boris Chertok, Rockets and People, Vol. IV: The Moon Race — NASA SP-2011-4110")）苏联工程师造出了极其出色的部件，却没有为这个*集成后的系统*造出一条能在飞行前廉价地失败的路径。四次 N1 发射全部以失败告终，计划就此终结。

这里的教训不是苏联的计划比阿波罗更好（它并没有），也不是说一方鲁莽而另一方谨慎（双方都在各自的约束里尽了全力）。有用的对比要窄得多。阿波罗把资源转化成了飞行前的信心。发动机工场把与硬件的反复接触转化成了知识。阿波罗有能力用一个专为"让失败变得不太可能"而设计的机构，把每一次发射团团围住。发动机工场则反其道而行，让失败变得频繁、廉价而富有信息量。

我在意的这个隐喻，并不是 N1 的发射计划本身（尽管它很有趣，而且把软件工程拿去和字面意义上的火箭科学作比较，会让我自我感觉良好一些）。我在意的是那个资源受限的发动机工场：大量尝试、破坏性的加压、直接的观察，以及对那些没能存活下来的设计毫不留情。

垃圾（slop）正在涌来。更好的模型会改善"信号与垃圾"的比例，但它们同时也会抬高被生产出来的代码总量。为一个"每份实现都单独交付、打磨精良、值得人类穷尽式审查"的世界殊死捍卫，就是把阿波罗的思维套用到 AI 经济学上。那等于是把一个发动机工场的产出，喂进一套专为一枚神圣火箭而设计的流程里。

不要把一门喷垃圾的加农炮硬拴在阿波罗的评审流程上，还指望人类跟得上。要偷师发动机工场那种"生成、点火、炸掉、丢弃、再来"的意愿。要从 N1 身上学到：部件的成功不会自动组合成一个能工作的系统。同时保留阿波罗对契约、集成，以及那些"失败绝不可接受"之处的严肃态度。重点不是在美国人和苏联人之间二选一。而是把昂贵的确定性放到意义与集成所在之处，把廉价的破坏性迭代放到其余一切地方。

这才是真正的那个反转：生成之所以可以慷慨，正因为选择必须严酷。

#### 物理是一个神谕。软件没有神谕。

传统的企业软件开发，运作方式非常像阿波罗模型，而且是有充分理由的。一个严肃的组织会试图在发射*之前*建立信心：设计文档、架构评审、有人逐一阅读每个 diff、威胁建模、QA、近似生产环境的预发布环境、受控发布、以及作为最后一道防线的可观测性与回滚。软件的失败会泄露客户数据、损坏数据库、把钱转错，所以整套机制的存在，就是为了在问题还廉价的时候抓住它们。

但请注意埋在这套流程里的那个假设：实现是昂贵的。当一个工程师花两周时间做出一处改动，让其他人来仔细审查这处改动就是合理的。实现是一件稀缺的产物，而分支和 pull request 的存在，就是为了保护它、打磨它、并最终为它加冕。

发动机工场则把实现看作某种远没有那么珍贵的东西（一个候选品）。工程师不必在发动机上试车台之前就预判到每一个缺陷。发动机被点火，压力被施加，结果就是证据。一个失败的设计不会被合理化、也不会被保留下来；它会被诊断、被修改，或者被报废。这并不比阿波罗少了纪律。这是纪律的重新安置——从飞行前分析和委员会评审，搬到了测试环境的质量、失败的仪表化程度、循环的速度，以及丢弃东西的意愿之中。

这种重新安置对火箭之所以奏效，是因为火箭活在一个有着外部裁判的宇宙里（物理，宝贝儿）。一个燃烧室要么撑得住压力，要么撑不住。一个涡轮泵要么继续旋转，要么把自己撕碎。热、振动和流体动力学根本不在乎那场设计评审说得多有说服力。宇宙就是那个神谕，而且它免费工作。

软件没有等价物，而这正是我们那个原本堪称完美的隐喻断裂的地方。一个程序可以既能编译又毫无用处。一个服务可以满足它的 API 契约，却实现了错误的业务规则。一个数据库可以保持完美的一致性，同时忠实地存储着对世界的一种错误解读。一个测试套件可以是绿的，只因为它编码了和被测代码同样的错误假设。软件中的正确性依赖于*意图（intent）*，而意图往往除了在建造系统的人脑子里以外无处存在。你不能生成一大堆代码、施加压力，然后指望现实来替你选出对的那份实现——因为在软件里，根本没有一个"现实"待命来做这份筛选工作。

一个诱人的应对（也是我在博客文章和 B2B SaaS 推销里最常见到的那种）是去*制造*那个缺失的神谕。强制要求穷尽式的测试、完美的仿真、形式化的规格说明、一个覆盖"系统应该和不应该做的一切"的完整可执行模型。但那是一个糟糕得可悲的前提，而且即便它*当真可能*（几乎总是不可能），为一个复杂系统构建一个完整神谕，通常比构建系统本身更难、更昂贵。如果你能事先完整地规定每一种有效行为、每一条安全属性、每一个业务决策，那你其实已经完成了大部分工程。一个资源受限的团队无法先造出阿波罗的软件，再造出第二个阿波罗来证明第一个是对的。

一个资源受限的团队*能*做的（这里的约束除了时间和金钱，还有合格的人类开发者），是去使用那些早已散落在四处的硬裁判。软件没有单一的物理，但它满是局部的类比物（至少你使劲眯着眼看的话）：编译器、类型检查器、数据库约束、事务、接口定义、状态机、权限边界、资源上限、沙箱。这些东西没有一个能告诉你你造的是不是对的产品，但每一个都能让一整类错误的实现以机械的方式、立刻地、且无需任何人阅读任何东西地失败。目标不该是一个完美的神谕。目标应该是把系统安排成：让生成的代码在进入的路上，尽可能多地撞上那些既有的、廉价的、硬的神谕。

这些机制并不都提供同一种信心。编译器、类型系统、schema、状态机或数据库约束是一个*判官*：它拒绝一整类它已知无效的实现。沙箱、能力边界或资源预算则是一堵*防爆墙*：它限制那些判官没能识别出来的一切所造成的破坏。判官让糟糕的作品更容易被杀死。防爆墙让幸存下来的错误廉价到足以让人从中学习。

#### 瓶颈转移到了阅读上

当你把 AI 丢进传统工作流时，实际会发生的是这样：一个测试失败了，一个 issue 被提出，一个 agent 产出一个补丁，然后一个人来审查这个补丁。如果 agent 产出补丁的速度比人能读它快十倍或一百倍，那么审查队列就成了整个系统的吞吐上限。瓶颈从写代码，转移到了读代码（且理想情况下，是理解代码）。

而阅读也许是最糟糕的落点。AI 的产出难以审查，恰恰是因为它*看似合理*。它看起来很干净，用着熟悉的模式，还经常能通过那些显而易见的测试。审查者不得不去重建 agent 的假设、搜寻被省略的边界情况、注意到那个被悄悄削弱的约束，并核实 agent 解决的是真正的问题，而不只是让症状消失。那是昂贵的认知劳动，而用更多看似合理的代码去淹没一个人，并不会带来成比例的生产力。它带来的是审查疲劳、冷漠（LGTM，发吧），以及最终一个批准了八百行看似合理代码、然后在生产环境里撞见那个 bug 的审查者。

你没法靠把 agent 节流到人类阅读速度来解决这个问题——那等于放弃了全部优势；你显然也不能干脆不读就放行代码（**你绝对绝对不该这么干，vibe coder 们。给老子读代码。**）。这并不意味着人类不再读代码了。它意味着"对每一个候选品都逐行穷尽式审查"不能再作为"软件是安全的"这一命题的默认证明。我们不会读每一行。但我们必须始终保有读任何一行的能力。

当一条授权边界发生移动、当证据自相矛盾、当性能数字讲不通、当实现触及了某条关键路径、或者当这套机制到达了它所能解释的极限时，一个有经验的工程师仍然必须潜进代码里，弄清楚到底发生了什么。但如果强迫每一个例行的候选品都走同一套人工审视，那就把一支 agent 舰队变成了一个非常昂贵的代码生成队列。剩下唯一的选项，是把系统安排成：让大多数糟糕的实现在任何人看到它之前就死掉——而这恰恰正是发动机工场所做的。生成之所以可以慷慨，正因为选择是严酷的。

不过，严酷的选择要求软件是*可裁判的（judgeable）*，而在这里，代码库自身的设计开始变得重要。一个松散、动态成形的系统，给了 agent 巨大的自由去"差不多正确"：它可以编造一个字段名、忽略一个非法状态、放宽一个输入、返回一个意料之外的结构、跳过一次权限检查，或者持久化一条结构上看似合理、语义上却错误的记录——而失败可能要等到三个服务和好几次用户操作之后才浮现。一个被严格规定的系统，则把这些失败往"创建的那一刻"拽回去。类型检查器拒绝那个非法组合，RPC 编译器拒绝那个不兼容的接口，数据库拒绝那一行不可能的数据，状态机拒绝那次非法的状态迁移，能力系统拒绝那次未授权的调用，monorepo 拒绝糟糕的依赖和糟糕的版本。实现被迫尽早地、向一台机器坦白它的误解，为它的罪过赎罪——而不是把误解藏起来，直到某个人或某个客户发现它。

这些都不能让代码变正确。它们所做的，是让更多种类的不正确变得*机械可见*，而这才是那个要紧的转变。AI 原生的代码库，其设计目标不应仅仅是帮机器写代码，而应该是帮机器证明代码是错的。

#### 契约优先，实现可抛弃

在大规模软件工程的黎明时期，我们的行事方式，仿佛深知不能信任自己的员工。那时有严格的 schema、检查、契约和官僚制度（以及多到爆的 XML）。但无产阶级最终起义了，在过去二十年（现在也许三十年了？）里，主流软件开发越来越朝着"人类工效学"去优化。动态语言削减了仪式感。无 schema 的数据库让早期迭代变得毫无痛感。非正式的 JSON API 免去了团队维护接口定义的摩擦。那些本可以活在 schema、生成客户端、校验器或显式状态模型里的规则，纷纷迁移进了应用代码——因为什么都是人在写，而样板代码在吞噬人的工时。一个能让小团队跑得快的技术栈，比一个把每个假设都预先编码的技术栈更有价值。

AI 把这个权衡反转了过来，因为 AI 的成本结构与人类的恰好相反。一个 agent 不会写腻了 struct。它不会怨恨 schema 迁移、穷举式的枚举匹配、生成的客户端、校验层，或重复的接口代码。AI 在"仪式"上是廉价的。AI 昂贵的地方在于*歧义（ambiguity）*。一个规定不足的请求，给了 agent 空间去做出那些局部合理、全局错误的决定。一个规定不足的接口，让两个 agent 各自独立地发明出互不兼容的解读。一个无 schema 的数据模型，把它们的分歧推迟到了运行时——那正是最昂贵的发现时机。

这指向一个真正古怪的结论：晚 90 年代那种"抠门苛刻的契约"回归了，但没有了晚 90 年代那种人力成本。不是到处都是 XML，不是配置泛滥，不是为官僚而官僚，而是对实现者的一种健康的不信任，在一切能让它"咬人"的地方都被显式地表达出来。

那些类型系统能在程序运行前就消除大类无效程序的语言：Rust 的所有权模型让编译器无需垃圾回收就能强制内存安全，并把许多并发错误变成编译期失败。（[Rust Documentation](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html "Understanding Ownership — The Rust Programming Language")）用显式的服务定义取代临时拼凑的网络请求：gRPC 用 Protocol Buffers 作为接口定义语言，并据此生成带类型的客户端和服务端。（[gRPC](https://grpc.io/docs/what-is-grpc/introduction/ "Introduction to gRPC")）把关系型 schema 当作系统可执行定义的一部分：`NOT NULL`、`CHECK`、`UNIQUE` 和外键约束，让数据库能拒绝无效状态，而不是信任每一个生成出来的调用方都记得每一条规则。（[PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html "Constraints — PostgreSQL Documentation")）把工作流建模成显式的状态机，而不是一堆松散相关的布尔值的星座。以及，给生成的代码授予狭窄的能力，而不是对数据库、文件系统和管理 API 的环境性访问权（ambient access）。最小权限原则的存在，恰恰是为了限定有 bug 或被攻陷的代码所能造成的破坏——而 agent 写的代码，理应被假定为偶尔两者兼有。（[OWASP Foundation](https://owasp.org/www-community/controls/Least_Privilege_Principle "Least Privilege Principle — OWASP")）

这一切底下的组织原则是：**契约应当持久，实现应当可抛弃。** 持久的产物，是那些定义了系统*意味着什么*的东西。类型、schema、服务定义、合法的状态迁移、不变量、权限模型、事务边界。这些边界之内的一切，都可以被生成、被拒绝、被重写、被替换，无需任何仪式。"可抛弃"并不是"无关紧要"的另一种说法。它是系统必须*挣得*的一种属性。必须有足够多的意图，存活在实现之上的契约、测试、示例、策略和证据里，以至于替换代码并不等于抹掉设计。如果删掉实现就删掉了别处无人保存的知识，那么这份实现还不算可抛弃。

这种划分也告诉了你，人类审查真正该待的地方。当一个 agent 改动一条授权边界、削弱一个类型、修改一个 schema、增加一次合法的状态迁移，或放宽一个不变量时，人应该极度上心——因为这些改动扩大了系统所允许的行为空间。而对于一个待在已被接受的契约之内、并被机械地强制去满足它的实现，人不应该必须去读它的每一行。契约，是人类判断力挣得其价值的地方。实现，则是候选材料。

把话说清楚，讲讲边界所在：没有任何架构能让糟糕的软件成为不可能。契约可以是不完整的。类型可以编码了错误的模型。一个数据库约束可以忠实地强制执行一条错误的业务规则。目标要窄得多，而且是真正可达成的：让大类糟糕代码*无法被表达*、无法被持久化、无法跨越一条边界，或者在它试图这么做时立刻可见。做到这一点，经济学就变了。Agent 可以去探索，而无需人为每一次尝试加冕。生成的实现会撞在系统的结构上失败，而不是在系统内部无声地累积。稀缺的人类判断力，会集中到意义被创造出来的地方，而不是代码仅仅被生产出来的地方。

旧的技术栈为"人类著述的成本"而优化。新的技术栈应该为"机器生成的歧义的成本"而优化。我们花了二十年剥除仪式，好让人类跑得更快；而如今实现变得廉价、审查变得昂贵，仪式已经成了基础设施。强类型、硬 schema、显式契约、关系型约束、状态机和能力边界，不再是官僚主义的拖累。它们是那个让你能点火一万台发动机、却只在撑得住的那几台上花时间的压力容器。

第二部分要讲的，是"点火一万台发动机"这件事的那个小小的实际问题：它们对你的笔记本电脑有 shell 访问权限。
