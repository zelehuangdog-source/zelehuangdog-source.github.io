#### 核心问题：LLM 天生无状态

LLM 在设计上就是无状态（stateless）的。每一次 API 调用都是从零开始。你和 ChatGPT 聊天时感受到的"记忆"，其实是一种错觉——它是把整段对话历史，在每一次请求里再发一遍造成的。

这套小把戏在闲聊里管用。但一旦你想做真正的 Agent，它就立刻崩盘。

---

#### 7 种失败模式

跳过记忆设计，就立刻会冒出来的 7 种失败模式：

1. **上下文失忆（context amnesia）**：Agent 反复来问你已经给过它的信息
2. **零个性化**：每一次交互都像在跟一个陌生人说话
3. **多步任务失败**：中间状态在任务做到一半时悄无声息地丢掉
4. **重复犯错**：没有情景回忆（episodic recall），同样的错就会被一犯再犯
5. **知识无法积累**：每次会话都从零开始
6. **信息缺口引发的幻觉（hallucination）**：上下文一旦溢出，模型就开始编
7. **身份坍塌（identity collapse）**：没有连续性，就没有信任

---

#### 为什么堆上下文长度解决不了问题

最直觉的回应是"往里塞更多上下文"。这也是为什么 128K、200K 的 token 窗口让人觉得它们似乎能解决一切。

**它们解决不了。**

- 当关键信息位于长上下文的中段时，准确率会下降超过 30%——这就是已被反复验证的**"中间迷失"效应（lost in the middle）**
- 上下文是一份共享的预算：系统提示、检索文档、会话历史、模型输出，全部要在同一份 token 预算里彼此抢占
- 哪怕窗口到了 100K token，缺乏持久化（persistence）、缺乏优先级（prioritization）、缺乏显著性（salience），光靠堆上下文长度依然不够

> 记忆的关键，不是把更多文字塞进 prompt，而是把 Agent 应该记住的东西结构化，让它在需要时能找到真正重要的那一部分。

#### 认知科学框架

Lilian Weng（OpenAI 研究员）2023 年的表述，如今已成为通用共识：

**Agent = LLM + Memory + Planning + Tool Use**

她的分类法借鉴了认知科学——人类记忆被划分为三套系统：

| 记忆类型 | 说明 | 对应 Agent 组件 |
|---------|------|----------------|
| 感觉记忆（sensory memory） | 捕捉原始感知输入，只保留不到一秒 | 输入流 |
| 工作记忆（working memory） | 主动思考发生的地方，约 7±2 个项目 | 上下文窗口 |
| 长期记忆（long-term memory） | 可持久存储，无容量上限，瓶颈在检索 | 外部存储 |

长期记忆又可细分：

- **情景记忆（episodic）**：具体的过往事件（"周二 PostgreSQL 集群挂了"）
- **语义记忆（semantic）**：事实和概念（"PostgreSQL 是关系型数据库"）
- **程序性记忆（procedural）**：技能与工作流（"用户申请退款时，先查购买日期"）

情景记忆与语义记忆之间的桥梁，是**记忆固化（memory consolidation）**：反复出现的具体事件被提炼成通用知识。没有固化，Agent 只能把单个事件回放，而不是从中学到东西。

#### 记忆层演进：四个 Layer

##### 最小 Agent，以及它最先崩在哪里

把各类框架的外壳剥掉，一个 Agent 不过是一个循环：**感知—思考—行动**。

```python
class Agent:
    """Minimal AI agent: perceive, think, act"""
    def __init__(self):
        self.client = anthropic.Anthropic()
        self.model = "claude-sonnet-4-20250514"

    def run(self, user_input: str) -> str:
        response = self.client.messages.create(
            model=self.model,
            max_tokens=1024,
            messages=[{"role": "user", "content": user_input}],
        )
        return response.content[0].text
```

告诉它"我有 4 个苹果"，再问它"我吃了一个，还剩几个？"——它根本不知道你在说哪批苹果。每一次调用都是孤立存在的。

##### Layer 1：Python list

```python
class Agent:
    def __init__(self):
        self.client = anthropic.Anthropic()
        self.messages = []  # The entire "memory" is a list

    def chat(self, user_input: str) -> str:
        self.messages.append({"role": "user", "content": user_input})
        response = self.client.messages.create(
            model="claude-sonnet-4-20250514",
            max_tokens=1024,
            messages=self.messages,  # Full history sent every time
        )
        reply = response.content[0].text
        self.messages.append({"role": "assistant", "content": reply})
        return reply
```

**优点**：多轮对话能跑了。

**问题**：
- list 会无限增长，约第 200 轮会撞上上下文容量上限，最早的消息悄悄丢掉
- 没有任何优先级，只有严格的时间顺序
- 一切活在内存里，进程结束就全忘了

##### Layer 2：用 Markdown 文件做持久化

```python
class MarkdownMemoryAgent:
    def __init__(self):
        self.client = anthropic.Anthropic()
        self.history_file = Path("memory/conversation_history.md")
        self.facts_file = Path("memory/known_facts.md")

    def save_to_disk(self, role: str, content: str) -> None:
        with open(self.history_file, "a") as f:
            f.write(f"### {role} at {datetime.now().isoformat()}\n{content}\n\n")

    def load_history(self) -> str:
        if self.history_file.exists():
            return self.history_file.read_text()
        return ""

    def chat(self, user_input: str) -> str:
        self.save_to_disk("user", user_input)
        history = self.load_history()
        response = self.client.messages.create(
            model="claude-sonnet-4-20250514",
            max_tokens=1024,
            system=f"Previous conversation:\n{history}",
            messages=[{"role": "user", "content": user_input}],
        )
        reply = response.content[0].text
        self.save_to_disk("assistant", reply)
        return reply
```

**优点**：解决了持久化，人类可读，对 Git 友好。Claude Code 用的就是这个模式（CLAUDE.md、MEMORY.md）。

**问题**：规模一旦上来（2000 条事实、200 段会话），50 万 token 的 markdown 装不进 128K 的上下文窗口，而关键词搜索解决不了同义词和改写问题：

```bash
# 用户问："云迁移的进展如何？"
grep("cloud migration", facts_file)
# 返回：[]
# 磁盘上的事实写的是"将生产数据库迁移到新的 AWS 区域"
# "cloud migration" 这几个词根本不存在
```

> 没有智能检索的存储，就是一座没有目录的图书馆。

##### Layer 3：向量搜索，以及它撞上的那堵墙

外挂嵌入（embeddings），把 markdown 切块，按余弦相似度检索。同义词问题化解了。

**但新问题来了**——多跳推理失效：

假设向量库里有这三条事实：
- "Alice 是 Atlas 项目的技术主管"
- "Atlas 项目使用 PostgreSQL 作为主数据存储"
- "PostgreSQL 集群周二宕机"

用户问："**周二的故障是否影响了 Alice 的项目？**"

向量搜索会把第一条和第三条排得很高（因为出现了 Alice 和"周二"），但真正起桥梁作用的第二条——"Atlas 项目使用 PostgreSQL"——既没提 Alice 也没提周二，**恰恰是浮不上来的那一条**。

> 每一条事实都是嵌入空间里一个孤立的点。把它们串起来的关联线索，向量看不见。

#### 能力对比

| 能力 | Python list | Markdown | 向量搜索 | 你真正需要的 |
|------|------------|----------|---------|------------|
| 持久化 | ❌ | ✅ | ✅ | ✅ |
| 抗上下文溢出 | ❌ | ✅ | ✅ | ✅ |
| 语义检索 | ❌ | ❌ | ✅ | ✅ |
| 多跳推理 | ❌ | ❌ | ❌ | 图遍历 |
| 实体去重 | ❌ | ❌ | ❌ | 哈希 + 实体消解 |
| 关系追踪 | ❌ | ❌ | ❌ | 图的边 |
| 自我提升的召回 | ❌ | ❌ | ❌ | 按使用情况加权的检索 |

你需要在同一层记忆里同时拥有：**持久化、语义理解、关系推理**。

#### 解决方案：Cognee

Cognee 是一个面向 Agent 记忆的开源知识引擎，把向量搜索、知识图谱和关系型溯源合并成一个系统。

##### 4 个 API 调用

```python
import cognee

await cognee.add("Your document here")   # 装入任何内容
await cognee.cognify()                    # 构建知识图谱 + 嵌入
await cognee.memify()                     # 自我提升记忆
await cognee.search("Your query")         # 带推理的检索
```

##### 三套存储，各司其职

| 存储类型 | 捕获什么 |
|---------|---------|
| 关系存储 | 溯源：数据来自哪里、何时装入、谁有权限 |
| 向量存储 | 语义：内容是什么意思、与哪些内容相似 |
| 图存储 | 关系：实体之间如何连接、什么导致什么 |

默认栈：**SQLite + LanceDB + Kuzu**，全部内嵌、基于文件，无需 Docker。
生产环境可替换为：Postgres + Qdrant/Pinecone + Neo4j/FalkorDB，API 不变。

##### cognify 内部流水线

1. 按类型与领域对文档分类
2. 多租户访问控制下的权限校验
3. 尊重段落结构的切块抽取（不是固定大小的硬切）
4. 通过 LLM 抽取实体与关系，并基于内容哈希**自动去重**
5. 为高效检索生成摘要
6. **双重索引**：同时写入向量存储（嵌入）和图存储（边）

> 每一个图节点都对应一个嵌入。从向量入口进入（找到语义相似的内容），从图出口离开（沿着关系跳到相邻实体）——这就是它能在不牺牲语义检索的前提下把多跳查询跑通的原因。

##### memify：会学习的记忆

- 强化那些导向了高质量检索结果的有用路径
- 修剪长期未被访问的过期节点
- 基于真实使用情况自动调整边权重
- 通过识别隐含关系，补充派生事实

##### 完整 Agent 示例

```python
import cognee
from cognee import SearchType

class CogneeMemoryAgent:
    """Agent with graph-vector hybrid persistent memory."""

    def __init__(self, session_id: str = "default"):
        self.llm_client = OpenAI()
        self.session_id = session_id

    async def ingest(self, text: str, dataset: str = "main"):
        await cognee.add(text, dataset)
        await cognee.cognify([dataset])

    async def recall(self, query: str) -> str:
        results = await cognee.search(
            query_text=query,
            query_type=SearchType.GRAPH_COMPLETION,
            session_id=self.session_id,
        )
        return results[0] if results else ""

    async def chat(self, user_input: str) -> str:
        context = await self.recall(user_input)
        messages = [
            {"role": "system", "content": "You are helpful. Use memory context."},
            {"role": "system", "content": f"Memory context:\n{context}"},
            {"role": "user", "content": user_input},
        ]
        response = self.llm_client.chat.completions.create(
            model="gpt-4o-mini", messages=messages
        )
        reply = response.choices[0].message.content
        await cognee.add(
            f"User: {user_input}\nAssistant: {reply}",
            "conversations"
        )
        await cognee.cognify(["conversations"])
        return reply
```

#### 落地路径

先问自己："我的 Agent 需要记住什么？它要回答什么样的问题？"

- 查询只需要**相似度搜索**（"找跟这次类似的会话"）→ 仅向量的记忆就够用
- 查询需要**跨越实体边界**（"周二的故障是否影响了 Alice 的项目？"）→ 必须用到图遍历

---

#### 核心结论

> 智能需要的是结构，而不仅仅是存储。三种存储范式（关系、向量、图）不是相互竞争的选项，而是同一套记忆系统里互补的几层。把它们当作互补层来对待——这才是把无状态的 LLM 套壳，真正变成会学习的系统的关键所在。
