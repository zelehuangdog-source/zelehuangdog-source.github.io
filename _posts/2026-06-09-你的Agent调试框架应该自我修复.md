> **摘要**：当 AI Agent 在生产环境出问题时，现有的可观测性平台只能告诉你「发生了什么」，却几乎不告诉你「为什么坏」「怎么修」「下次怎么避免」。真正的瓶颈不是 trace 本身，而是 trace 落到屏幕之后的所有手工劳动——读 span、形成假设、手写补丁、祈祷不要打破其它东西。文章以 Opik（开源 AI 可观测性与评测平台）为例，提出一个四层闭环架构：Tracing（自动追踪）→ Ollie（内置 Coding Agent 自动定位 + 提交 diff）→ Test Suites（用自然语言断言把每次失败固化为回归测试）→ Agent Sandbox（端到端沙盒验证），把传统观测工具留给人工的那段循环交还给系统自己跑。每一次失败都让 harness 变得更难被打破。

#### 你的 Agent 调试框架应该自我修复

当一个 AI Agent 在生产环境失败时，你的可观测性工具能告诉你它做了什么，但几乎不告诉你怎么修。

你能拿到一份干净的运行 trace：每一次模型调用、每一个被触发的工具、每一步耗时多久、消耗了多少 token。

你拿不到的是：它为什么坏、改什么能修好、以及下周同样的问题会不会再出现一遍的任何承诺。

于是你只能 span 接 span 地翻 trace、对失败原因形成一个假设、手写一个补丁，然后祈祷它不会把原本能跑的东西搞坏。

接着新模型一发布，又带来一批新的失败模式，你再把整套手工流程从头跑一遍。

真正的瓶颈不是你的可观测性。是 trace 出现在你屏幕之后，所有不得不发生的事情。

虚线左边的所有事都自动化运行，虚线右边的所有事都得占用你的时间——而生产调试恰恰就活在右边。

Cursor 最近分享了他们在 Agent 周围的 harness（包裹在原始模型外面的一层 prompt、工具与校验）上投入了多少工程量。同样的模型，更好的 harness 能带来好得多的结果，而这件事永远做不完。

每个可观测性平台把你扔在这里。它回答了「发生了什么」，然后把「为什么发生」「要改什么」「怎么不再坏」一并丢回给你。

这就是今天大多数团队卡住的那个循环。下面解释为什么这个循环一直在重新打开，以及最终需要什么才能闭合它。

#### 为什么现有可观测性在规模化之后会崩

大部分 Agent 可观测性平台，给你一份 trace 就停了。

你拿到一棵 span 树、一组延迟数字、token 成本、一块 dashboard。你拿不到的是：它为什么失败、要修什么、以及它不会再坏的任何保证。

- 「发生了什么」 → 平台帮你处理
- 「为什么发生」 → 手工
- 「这是修复方案」 → 手工
- 「不会再坏」 → 手工

这在 2023 年是个合理的产品。对今天把 Agent 跑在生产环境的团队来说，这是错的抽象层级。

问题会自我累积。每一次模型升级都引入新的失败模式，每一个新工具都带来新的边角情况。harness 复杂度的上升速度，比任何团队靠人手追踪并修复的速度都更快。

下面是真正能搞定这件事的技术栈。

大部分平台止步于 dashboard，把剩下的留给你。右边那一段，是 Opik 自己跑的循环。

#### Opik：面向 Agentic 时代的 AI 可观测性与评测

Opik 是一个开源的、用于 AI Agent 与 LLM 应用的日志、调试与优化平台。Opik 的核心前提是：这个循环应该被自动化，而不是堆人。

##### 四层架构

Opik 的架构是一个连贯的工作流：

Trace → Ollie 诊断 → Ollie 提交修复 → 修复被应用并验证 → Test Suite 把这次失败固化为一条回归用例 → 回到 Trace

四层不是四个独立的功能。它们彼此喂养，组成一个能自己闭合的循环。

下面看每一层。

##### Layer 1：Tracing

每一次 LLM 调用、工具调用、检索步骤都会被一个装饰器自动埋点。

```python
import opik

@opik.track
def my_agent(query: str):
    # 你的 agent 逻辑
    ...
```

开箱即支持 LangGraph、CrewAI 等 50+ 框架。每一条 trace 都会记录当时生效的 Agent 配置，确保未来要重跑这条失败输入时具备完整可复现性。

四层不是四个独立的功能。它们彼此喂养，组成一个能自己闭合的循环。

##### Layer 2：Ollie

每个其它的可观测性平台都止步于「这是你的 trace」。Opik 走得更远——从 trace 一直走到被修好的代码，背后由 Ollie 驱动。

Ollie 是内嵌在 Opik 里的一个 Coding Agent。一个 Agent，全量上下文。

Ollie 在侧边栏一步步推进修复，只在你逐步确认后才读写文件。

在没有任何代码访问权限的情况下，Ollie 就能读 span 树、识别失败模式、解释跨多次 LLM 调用的因果链。问它「为什么最终回答忽略了被检索到的上下文？」它会沿着 span 树走完一遍，把根因浮上来。

在你的项目根目录跑 `opik connect`，Ollie 升级为完整的「修代码」模式：

- 读取你的源文件
- 定位到具体哪几行该负责
- 提交 diff；任何改动都需要你显式批准

一旦你批准，Ollie 会用原始失败 trace 的同一份输入重新运行你的 Agent，把新的 trace 流式推过来做并排对比，并把原始失败固化成测试套件中的一条回归用例。

错的 trace → 根因 → diff → 批准 → 重跑 → 回归用例锁定

从一条坏的 trace 一路走到锁定回归测试的完整路径，你的批准是其中唯一的一步人工动作。

##### Layer 3：Test Suites

大多数评测工作流：构造一份打过标的数据集、定义一个数值指标、对比浮点数。这套模型对研究者管用，对工程师怎么思考质量不匹配。

Opik 用纯英文的断言替换了它。

```python
suite = opik.TestSuite("crm-agent-v2")
suite.add_assertion("回答必须包含具体的交易细节，而不是只给一个数量")
suite.add_assertion("回答绝不能泄露未授权的信息")
suite.run_tests()
```

Opik 在底层把它们转成 LLM-as-a-judge 检查。每条测试用例干净的 pass/fail。

一个由真实失败构成的回归套件，每一条断言都用一句自然语言写成。

真正改变工作流的部分是：你调过的每一条失败 trace，都会自动变成一条新的测试用例。这个套件是从生产真实失败中长出来的，而不是某人提前编出来的合成场景。

每跑一轮，harness 就更难被打破。

但即使有一份在生长的测试套件，你仍然需要一个安全的地方在发布之前测试改动。这就是 Layer 4 的用途。

##### Layer 4：Agent Sandbox

大部分 playground 都是 prompt playground。你改一段 system prompt，重跑一次 LLM 调用。它回答的是错的问题。

生产环境的问题是：当我改这一处时，整个 Agent 图会发生什么。

Opik 的 Agent Sandbox 在 UI 内端到端运行被完整埋点的 Agent。改一段 prompt、换一个模型、加一个工具，看整个系统在完整 span 树上如何反应。每一次 sandbox 运行都会产出一份完整的 Opik trace。

非开发的 stakeholder——PM、领域专家、QA——都可以在不碰 git 的前提下安全地测试配置。

#### 飞轮跑起来

四层不是独立功能，是一个循环。

用 `@opik.track` 埋点。声明一份 `opik.Config`。生产环境出错。Ollie 读 trace、读你的源码、提交修复。你批准。Ollie 在 Sandbox 里用原始失败输入重新跑 Agent。修复通过。把它存为一份新的 Blueprint。环境指针推到 staging。原始失败被锁成回归测试。

把同一个循环端到端画一遍，从给 Agent 埋点开始，到下一次失败从顶部进入循环。

下一次失败从同一个循环的入口进来。

每跑一轮，harness 就更难被打破。

#### 闭合循环

「止步于 trace」的可观测性，在 Agent 还简单的时候是合理的。一旦它们进了生产，真正的工作全发生在 trace 之后——而那一段，Opik 替你跑，而不是把它丢回你盘子里。

整套技术栈都是开源的：Tracing、Ollie、Test Suites、Agent Sandbox、一个 6 算法的 Agent Optimizer，以及 50+ 框架集成。项目在 GitHub 已经超过 19.3K star。

三条命令自托管：

```bash
git clone https://github.com/comet-ml/opik
cd opik
./opik.sh
```

Cursor 描述的那段手工循环，正是 Opik 自己闭合的那段——从一条坏的 trace，一直走到一条被锁定的回归测试。
