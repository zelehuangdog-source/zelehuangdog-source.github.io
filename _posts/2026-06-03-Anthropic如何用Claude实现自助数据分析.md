#### Anthropic 如何用 Claude 实现自助式数据分析

**分类**：Enterprise AI · **产品**：Claude Code · **发布日期**：2026 年 6 月 3 日 · **阅读时长**：5 分钟

正如许多数据科学和数据工程团队所体会到的那样，让业务自助分析真正落地，向来是一项苦差事。

为了让数据模型对技术能力较弱的同事更友好，团队往往会构造大宽表和反范式表，但随着业务规模扩大，这些表很快就会衍生出口径不一致的重叠视图（而且对那些根本不想学 SQL 的员工依然帮不上忙）。另一种思路是为用户搭建更受约束的分析环境，但这种做法往往覆盖不到业务问题的长尾，而且会随着团队各自为政，导致指标和看板泛滥。

LLM 的兴起为自助分析提供了一条规避这些挑战的新路径。然而，把 Claude 直接对接到数据仓库、让代理自由执行查询，会带来一种虚假的精准感。

最初摆脱 ad-hoc 取数请求的快感很快会变成隐忧——团队意识到这种架构把业务方与原本指引他们使用经过精心治理的数据集的底层基础设施、文档和专业知识隔离开了。

在 Anthropic，95% 的业务分析查询通过 Claude 自动化完成，整体准确率约 95%。把这类机械重复的工作交给 Claude，我们的数据科学团队就能聚焦于因果建模、预测和机器学习等更具战略意义的工作。

我们与数十位 Anthropic 内部 Claude Code 的重度用户进行了交流，也见过分析代理的各种设计模式。在这篇文章里，我们将分享面向其他数据团队的最佳实践，包括：

- 为什么分析准确性是一个上下文与验证问题，而不是代码生成问题；
- 导致绝大多数错误的三种失败模式；
- 我们为应对这些错误所搭建的 agentic 分析栈；
- 我们如何衡量效果；以及
- 我们用来构建大多数 Skill 的基础模板（见附录）。

#### 数据不是软件

LLM 的生成能力是一把双刃剑：那些能为复杂问题创造性给出方案的机制，同样会让模型产出幻觉性的错误结果。要充分理解分析代理面临的挑战，把它和编码代理做一番对比会很有帮助。

编码本身是一个开放式的解空间，奖励模型的创造力；同时文档与测试为防幻觉提供了天然护栏。相比之下，分析场景往往只有**一个**正确答案，需要使用**一个**正确数据源，并且无法以确定性方式证明结果的正确性。

对于自助式 agentic 业务分析，复杂性主要来自数据本身的歧义。核心问题归结为：能否把用户的问题映射到数据模型中具体且最新的实体，并且知道与之打交道的正确方式。如果能做到这一点，后续的执行和 SQL 编写就变得轻而易举。

我们识别出这一问题的三个属性，它们是绝大多数错误回答的根源：

- **概念 ↔ 实体歧义**：在一个数据模型中可能存在数百个可选项（在数百万字段中），代理无法选出最能回答用户问题的字段。例如衡量"活跃用户数"：怎样的行为算"活跃"？是否包含欺诈用户？回看窗口取多长？
- **数据陈旧**：数据源、业务定义和 schema 不断变化；资产和代理的知识会逐步过期，开始返回微妙错误的答案。
- **检索失败**：正确的信息可能确实存在于数据模型中并且做了恰当注释，但搜索空间过于庞大，代理就是找不到。

#### 我们的 agentic 分析栈

在 Anthropic，我们主要通过 agentic 数据栈来抑制这三类错误。每一层都主要为应对其中一个或多个问题而存在：

- **实体歧义**：**数据基础**与**真相之源**把可信实体的空间收敛到唯一的受治理答案。
- **陈旧**：维护与验证流程让一切随业务变化保持鲜活而不腐烂。
- **检索失败**：**Skills** 确保代理可靠地找到并正确使用那个答案。

下面我们逐层展开。

##### 数据基础（Data foundations）

确保分析代理准确性的最重要因素，是强大的数据基础——包括数据仓库中的数据模型、变换、测试、表，以及描述它们的元数据。维度建模、左移测试、关键管道的新鲜度与完整性检查这些标准的数据工程与数据质量实践依然适用（这里不再赘述）。

> 维度建模等标准数据工程实践，重要性丝毫未减。

变化的是：你的数据模型的最终用户不再是数据专家（如数据科学家），而是代表用户行事的**代理**——而这些用户的数据素养和对底层基础设施的理解程度参差不齐。这种转变带来一个挑战：结果不能依赖用户去验证底层正确性，因为用户根本不知道。

数据基础层主要针对歧义问题：例如"营收"如果能解析为唯一的受治理数据集，而不是四十个似是而非的候选，那么这个问题在代理开始搜索之前就基本消失了。它也是抗陈旧的第一道防线——因为定义规范模型的同一个仓库，是强制保持其新鲜度的天然位置。

我们看到以下做法尤其有效：

- **构建规范数据集（canonical datasets）**：迄今为止最常见的失败是代理无法把一个概念（如"产品 X 的营收"）映射到唯一正确的表、列和指标定义，原因通常是存在多个实现细节略有差异的可信候选。解法是**减少**逻辑模型并加强治理：精选少量规范的、单一来源的、归属明确、可直接消费且易于发现的数据集，并积极弃用那些近重复的副本。物理 rollup 与缓存对成本与性能仍然重要，但应该机械地从规范模型派生，而不是与之平行存在。目标是：当代理搜索某个概念时，它找到的是**唯一**的受治理答案。
- **强制执行你的标准**：基础只有当规范模型与指标定义同时被三方面强制时才会牢固——**工具**（代理结构性地优先路由到它们，下文详述）、**CI**（绕过它们的变更评审失败）、**机制**（下游团队必须在受治理层之上构建，否则要给出理由）。无强制的治理很快会衰退回"多候选"问题。
- **共址化制品（colocate artifacts）**：我们应对数据模型与业务逻辑频繁变化的主要防线是**共址**。几乎所有数据代码（建模、语义层、参考文档、规范看板定义）都放在同一个仓库里，CI 检查保护跨层完整性。如果建模变更会破坏下游看板或使某条已记录的指标失效，CI 会触发告警，并且修复在同一个 PR 中提交（我们将在 Skills 章节回到具体机制）。
- **把元数据当成一等产品**：编码代理表现出色，部分原因在于代码库本身就是可读的——README、类型签名、docstring 等等。你的数据仓库可以同样可读，但前提是列与表的描述、规范指标定义、粒度文档、值域、血缘、归属与模型分级，都要以与变换本身同等的严谨度进行维护。这并非什么新见解，但好的治理为代理选择正确数据集提供了关键上下文。

##### 真相之源（Sources of truth）

如果数据基础是数据仓库本身，那么真相之源是代理用来导航数据仓库的参考表面。这一层降低概念 ↔ 实体歧义，把业务方提到的"周活跃用户"转化为数据模型中具体的、受治理的实体。大致按可信度从高到低排列：

- **语义层（Semantic layer）**：编译后的指标与维度定义。如果一个问题能干净地映射到已定义指标，代理就调用一个函数得到一个数字——这是公司其他每个表面都会得到的同一个数字。我们的代理被结构性要求（通过 Skill 指令）优先调用语义层（见附录）。我们尝试过但失败的一个想法：让 LLM 从原始表与查询日志自动生成指标定义来引导语义层。它产出的定义看起来合理，但恰恰编码了我们要消除的那些歧义；在评估上比一个更小、由人类策划的语义层还差。因此我们的建议是：用 Claude 生成文档，但**让人类拥有定义**。
- **血缘与变换图（Lineage and the transformation graph）**：当语义层覆盖不到某个问题时，血缘和（基于引用次数的）表排名让代理可以推理：哪些上游模型供给了这个概念、哪些已被弃用、哪些共享相同粒度。这把"我不知道这个指标"转化为"我知道该从哪个受治理模型聚合"。它也是我们在线验证中所暴露的新鲜度与出处信号的骨干（见下文）。
- **查询语料（Query corpus）**：来自看板、Notebook 和先前分析的历史 SQL。直觉上这应该是高价值的——它记录了所有曾经被正确回答过的问题。但实践中我们发现：让代理对数千条历史查询拥有原始检索访问权，对准确率的提升不到 1 个百分点（下文会展开这个消融实验）。无结构检索无法把新问题映射到正确的先例。**真正有效的做法**是把这个语料蒸馏为按领域组织的结构化参考文档，以及在 Skills 中描述的可复用分析模式。把查询历史当作**策划的原料**，而不是代理直接读取的真相之源。
- **业务上下文（Business context）**：这是大多数团队跳过、也是我们低估时间最久的一层。一个不理解你业务的代理，会回答用户**所问**，而不是用户**所想**。它不会知道"Q2 发布"指的是某个具体产品，也不会知道两个团队对同一个术语有不同定义，更不会意识到这个问题是因为周四要开董事会才被提出。我们引入了一个公司知识图谱，包含已索引的文档、路线图、决策记录和组织架构，让代理能解析弱引用并提出更恰当的澄清问题。

这四层共同的失败模式，与数据基础层是同一个：糟糕或陈旧的文档。Claude 在弥合这一缺口上极其有用（起草列描述、根据查询模式提出指标文档、在 CI 中标记未文档化的模型），但**策划与归属由人类管理**。

接下来两节将讨论：如何让这种归属足够廉价，从而真正发生。

##### Skills

如果真相之源是代理的**陈述性知识**（一个指标的含义），那么 Skill 就是它的**过程性知识**：以什么顺序查阅哪些来源、如何在歧义数据中导航、一个完成的分析长什么样。

在 Claude Code 中，一个 Skill 是一个 markdown 文件夹，代理按需阅读。在 Anthropic，我们开发的 Skill 价值巨大。**没有 Skill 时，Claude 在我们评估集上的分析准确率不超过 21%；加上 Skill 后，整体稳定保持在 95% 以上，某些领域常达到 99% 左右**。我们用于构建大部分 Skill 的骨架见附录。

一些最佳实践：

- **构建配对 Skill**：一个**知识 Skill**作为顶层薄路由器，按需加载领域细节。它在说："先试语义层；如果没覆盖，这里有约 30 个针对该领域的参考文件，描述相关的表、列、连接和坑位。" 这个路由器实际上是我们对**检索失败**问题的回答：与其让代理在百万字段的仓库中搜索，不如在写出查询之前就把空间收敛到几十个精心策划的文件。**Unbook Skill** 编码了一位资深分析师会遵循的流程：澄清问题 → 找到来源（通过知识 Skill）→ 执行查询 → 把结果交给对抗性评审子代理循环检查。它还内置了一打可复用的分析模式（留存曲线、比率分解、漏斗分析），常见请求不必每次重新发明。
- **构建合格的参考文档**：这些文档**为 LLM 检索而写**。我们的参考文档描述表（粒度、范围、排除项）、坑位的机理（如"排除已知免费邮箱域名，但保留 anthropic.com 这类自定义域名"）、显式的路由触发条件（如"IF 问题与实验提升有关… DO NOT 用于原始事件计数"），但避免那些会很快过期的指令式食谱。下面是我们用来构建参考文档的骨架：

```markdown
# [Domain] Tables

## Quick Reference
### Business Context — [这个领域用大白话说是什么意思]
### Entity Grain — [一行代表什么]
### Standard Hygiene Filter — [本领域每条查询都要套用的过滤条件]

## Dimensions
- [关键维度如何编码，以及同一概念在不同表中如何被命名得不一样]

## Key Tables
### [table_name]
- **Grain**: [...] · **Scope/exclusions**: [...]
- **Usage**: [何时使用、何时不要用、连接键、必需过滤条件]
[... 每个受治理表一节简短说明 ...]

## Gotchas
- [一位资深分析师会警告你的"错误答案模式"]

## Best Practices / Common Query Patterns
- [默认选项、标准切片、那些"具体写法本身就是难点"的模式]

## Cross-References
- [负责相邻问题的邻近领域文档]
```

- **把 Skill 维护当成头等大事**：Skill 文档描述的是每天在变的数据模型，因此没有主动维护，几周内就会失准。**我们曾眼看着离线准确率从上线时的约 95% 在一个月内漂移到约 65%，之后才把这件事当作工程问题对待**。这意味着把 Skill markdown 文件与变换模型放在同一个仓库——**修改模型的 PR 必须同时修改描述它的文档**。一个 Code Review 钩子会标记任何不触及 Skill 文件的报表模型变更。如今我们大约 90% 的数据模型 PR 在同一份 diff 中包含 Skill 改动。我们也会定期裁剪那些随着模型进步、原失败模式不再成立的 Skill 脚手架。
- **跨表面提供一致且无缝的体验**：同一个 Skill 必须在 Slack、IDE、看板工具和独立代理会话中给出同一个答案。我们通过两点保证这一点：单一规范来源（数据仓库），以及 Skill 改动自动同步。合并时，Skill 同步到插件市场（供 IDE 用户使用）、同步到云存储 blob（供托管应用读取单一文件），并通过 MCP 直接作为资源提供。我们从一开始就为可移植性设计——避免硬编码仓库路径以及与具体表面绑定的命名空间。

##### 验证（Validation）

最后，验证是用来**发现**三种失败模式中哪一种仍在漏出的。

###### 离线评估（Offline evaluations）

我们看到一个常见模式：数据团队搭建了精巧的分析环境，但完全没有衡量分析代理准确性的流程。

弥补这一缺口的一种方式是**离线评估**——简单的问答对。可以把它类比为 ML 模型的离线测试：它不会告诉你在线代理的真实表现，但能让你心里有数，知道是否存在严重缺口。

我们在 Anthropic 部署了两类离线评估：**基于看板的评估**由 Claude 自动生成（再由人工校验），覆盖最常见的业务方问题；**长尾评估**则是把业务上下文（路线图、表文档）喂给 Claude，让它在该领域剩余空间生成合理的问题。我们也持续从业务方在线程中纠正代理的每一次反馈中收割候选评估。

其他最佳实践：

- **锚定 ground truth，防止漂移**：针对实时数据写的评估，底层数字一变就会失准。把每条评估**锚定到一个快照日期**、**写在稳定的事实表上**，或者**让评分器评判代理的查询而非数字**。把整个评估集挂到 CI 上，一旦 PR 触及依赖项，就重新运行受影响的评估。
- **像存遥测一样存结果，而不是像存测试日志**：每次运行都落到一张数据仓库表里，含 Skill 版本、git SHA、模型 ID、每条断言的通过/失败、token 数与墙钟时间。"这次改动是否有帮助？" 就变成一次查询，并且你拥有时间序列，可以捕捉单次 CI 难以发现的缓慢回归。
- **按领域门控发布**：在该领域所属的评估子集越过某个阈值（我们最初使用约 90%）之前，领域负责人不得向其业务方宣布代理可用。这迫使在用户看到失败前，先把参考文档修好。
- **把评估数量调到合适**：你应该有多少评估，取决于业务领域复杂度和底层数据模型复杂度。校准方法是跟踪离线准确率对在线准确率的预测程度——我们发现每个主题（如"增长"）超过几十条之后边际收益递减，且这个上限会随着每代新模型下降。
- **离线评估准确率应当接近 100%**；如果你有语义层，每个正确答案也应当击中语义层。再次提醒，这个准确率水平**并不**告诉你系统不会产生错误答案，只是告诉你在评估覆盖到位的前提下没有明显缺口。

###### 消融技术（Ablation techniques）

关于 Skill 的每一个结构性决策（暴露哪些来源、子代理是否值得它带来的延迟、是否合并两个 Skill），都是在**保持离线评估集不变**的前提下做出的。

我们每次只改变一个组件，比较通过率。每次运行只需一小时，却能替代大量争论。**方法论比任何单一结果都更重要**：

- **为零结果做设计**。我们最有用的一次消融是负面的。我们给了代理对全部看板、变换以及分析师 Notebook SQL（数千个文件）的直接 grep 访问权。我们在 transcript 中验证它确实在每次回答前都阅读了。**两个方向的准确率变化都不到 1 个百分点**。我们随后检查了显然的混杂因素：在它答错的问题中，答案是否真的存在于语料中？大约 80% 的情况是的。"答案存在"是否能预测"现在能答对"？不能，翻转率是平的。**信息在那里，代理看到了，可它依然没有用上**。这一个实验告诉我们：瓶颈不是对历史工作的访问权，而是结构（即把问题映射到正确实体）。这一洞察重定向了好几个月的路线图。
- **以 PR 粒度做消融**。每一次有意义的 Skill 编辑都在相关评估子集上跑一次"前后对比"，把 delta 写进 PR 描述里。这让"我改进了文档"保持诚实，并且能捕捉那种出乎意料常见的情形——一项善意的添加反而让事情变糟。
- **保留一份"什么没用"的简短清单**。我们的两条："超过某个点继续叠加文档精炼"（我们撞上了三轮连续的负向迭代——文档变得更长，并未变好）；以及"为降延迟把对抗性评审者换成更便宜的模型"（损失了大部分准确率收益，速度也并未真正提升）。负面结果的记录成本极低，却能阻止下一个人重复同样的实验。

###### 在线验证（Online validation）

最后一步是确保在线系统的真实表现尽可能准确。我们采取的部分措施包括：

- **对抗性评审**：我们发现，使用一个 Claude Skill 对潜在最终答案的所有底层假设激进发难，可以让评估集准确率提高 6%，代价是 token 消耗增加 32%、延迟增加 72%。
- **出处页脚（Provenance footer）**：每个回复都带一个页脚，包含：来自哪个来源层级（语义层 › 策划参考 › 原始表）、底层数据有多新、谁拥有该模型。它**不会**让答案更正确，但**会**帮助消费者判断该有多信这个回答。"原始表，新鲜度未知"这种页脚就是一个"在向上转发前先核实"的信号——这是我们针对沉默失败为数不多的缓解手段之一。
- **数据质量检查**：你的代理可能用对了字段、用法也对，但**数据本身**是错的。增加基本的数据质量检查（确保所引字段是最新的、完整的、无异常）通常是好的卫生习惯。
- **被动监控**：我们持续跟踪两个生产信号：通过语义层解决的代理查询占比，以及含有纠正性语言（"那是错的表"、"你漏了反欺诈过滤"）的回复占比。两者都进入一个看板，每周与离线通过率一同评审。
- **主动收割纠正信号**：这是闭环的关键一环。一个定时代理每隔几小时扫描业务方频道里类似的纠正语言，起草一行对相关参考文档的修复，并以领域负责人为标签开一个 PR。**修复路径被刻意设计得无聊**——编辑一个 markdown 文件、合并、自动同步到所有地方——领域负责人不必为此花太多时间。同样的纠正会被反喂回离线评估集。

这些都没法完全捕捉的是**沉默的失败模式**：答案是错的，但看起来合理，并且被无异议地使用了。我们的缓解措施是：出处页脚、对所有面向高层的内容要求人工显式签字、以及为每个领域的核心 KPI 设置一项每日对照"祝福过的看板"做一致性核查的常驻评估——尽管我们目前并没有真正稳健的解决方案。

#### 从零开始

如果你从零起步，**少量规范数据集 + 几十条离线评估 + 一个轻薄的知识 Skill**就能拿下大部分收益；本文其余内容都是我们在这些之上才陆续添加的。

我们也分享了不少最佳实践，但它们并非对每个数据团队都适用。请就以下问题与你的组织对齐若干原则，它们会影响你的方法选择：

- **现在就要正确答案 vs 未来再要？** AI 模型进步飞速。我们经常看到公司为应对当前模型短板搭建了大量基础设施，而这些短板在模型变强后就成了无意义的开销。**知道模型在哪里短，并等待模型迭代填补缺口**，开销显著更小，但未必符合你公司的风险偏好。
- **你预期业务复杂度如何随时间变化？** 如果你产生的数据不多、输出消费方很少、数据模型大概率保持简单，本文讨论的某些流程会显得过度。
- **输出的目标受众有多技术？** 换句话说，如果你为能识别错误答案的数据科学家搭建分析系统，你或许可以容忍更多错误；而如果受众对底层数据模型完全陌生，标准则截然不同。
- **你愿意为提高准确率花多少钱？** 我们发现像对抗性验证这类流程能显著提高准确率，但成本和延迟也更高。
- **你对访问控制与内部数据隐私的容忍度如何？** 代理上下文越多通常表现越好；然而广泛的数据访问与多数公司的治理立场背道而驰。这决定了你是构建**一个**代理，还是**多个**有限范围的代理。

无论选哪条路线，我们最大的收益都来自针对三种失败模式的应对：把歧义收敛为唯一的受治理答案、让答案易于发现、当任一条件失效时及时告警。
