#### 核心要点速览

1. **预缩放截图**是对点击精度影响最大的单一优化措施
2. 对于 4.6 系列模型，**"中等"思考力度**提供最佳精度/成本比；Opus 4.7 推荐**"高"力度**

#### 一、入门：分辨率与缩放

点击精度是任何计算机操作集成的基础。如果点击没有落在应有的位置，下游的一切都无法正常工作。**影响最大的单一优化也是最简单的：在发送截图到 API 之前预先缩小尺寸。**

##### 1.1 确保正确缩放

当你向 Claude 的计算机操作 API 发送截图时，模型会在你指定的 `display_width_px` / `display_height_px` 坐标空间中返回点击坐标。但有一个重要约束：API 对图像大小有内部处理限制。超出限制的图像会被静默缩小，导致模型基于降级版本的图像进行点击，而你的工具链期望的坐标却对齐到原始分辨率。

**API 内部限制：**

| 模型系列 | 最大长边 | 最大总像素 |
|---------|---------|-----------|
| Claude 4.6 系列 | 1568 px | 1.15 MP (115 万像素) |
| Opus 4.7 | 2576 px | 3.75 MP (375 万像素) |

当坐标空间与模型感知的图像不匹配时，模型预测的点击会落在与实际看到的图像不同的显示比例上。**这是高分辨率下点击不准确的首要原因。**

##### 1.2 推荐分辨率

- **4.6 系列起始推荐**：`1280×720`，使用约 80% 的像素预算，安全地在两个限制之内
- **Opus 4.7 起始推荐**：`1080p`，相比 720p 带来有意义的质量提升

对于想要最大化视觉信息的开发者，推荐"最大 API 适配"方法——根据源图像的原生宽高比计算最优分辨率：

```python
import math

# 4.6 系列为 1568，Opus 4.7 为 2576
MAX_LONG_EDGE = 1568
# 4.6 系列为 1.15MP，Opus 4.7 为 3.75MP
MAX_PIXELS = 1_150_000

def compute_max_api_fit(native_w, native_h):
    """计算符合 API 限制的最大分辨率，同时保持宽高比。"""
    aspect = native_w / native_h
    h_from_pixels = math.sqrt(MAX_PIXELS / aspect)
    w_from_pixels = h_from_pixels * aspect

    if native_w >= native_h:
        w = min(w_from_pixels, MAX_LONG_EDGE)
        h = w / aspect
    else:
        h = min(h_from_pixels, MAX_LONG_EDGE)
        w = h * aspect

    w = min(w, native_w)
    h = min(h, native_h)
    return int(w), int(h)
```

**应避免的分辨率：**
- **原始分辨率（未缩放）**：最常见的点击不准原因
- **极低分辨率（低于 960×540）**：丢失太多细节
- **MacOS 注意**：截图常以 2x 设备像素比捕获
- **4.6 系列避免 1920×1080 及以上**：超出像素限制会被静默缩小

##### 1.3 坐标缩放

调整截图大小后，模型返回的点击坐标在显示分辨率中。执行点击前必须缩放回实际屏幕分辨率：

```python
scale_x = screen_w / display_w
scale_y = screen_h / display_h
screen_x = int(api_returned_x * scale_x)
screen_y = int(api_returned_y * scale_y)
```

##### 1.4 内容排序

构造消息内容数组时，**将文本指令放在图像之前**。这让模型在处理截图时知道要寻找什么，从而提高点击精度。

```python
# 推荐——文本指令在前，截图在后
content = [
    {"type": "text", "text": "点击提交按钮"},
    {"type": "image", "source": {...}},
]
```

##### 1.5 诊断点击问题

| 症状 | 可能原因 | 解决方案 |
|------|---------|---------|
| 点击持续向一个方向偏移 | display 尺寸与实际发送图像不匹配；截图超出 API 限制被静默缩小 | 确保 display 尺寸与调整后的截图完全匹配；预缩小到 1280×720 |
| 点击大致在正确区域但偏离目标 | 目标太小；高分辨率源图像缩小后丢失细节 | 启用 `enable_zoom: True`；保持源宽高比 |
| 模型点击了完全错误的元素 | 指令模糊；附近有视觉相似元素 | 使用更具体的提示（含位置上下文）；拆分为更小步骤 |
| 整体精度差 | 截图超出 API 限制 | 预缩小所有截图以适配限制 |

##### 1.6 模型选择

- **Sonnet 4.6**：机械精度更高（更好的空间准确性），对重度缩小更鲁棒，**推荐作为默认起点**
- **Opus 4.7**：点击精度与 Sonnet 4.6 大致持平，更高分辨率预算减少缩小需求，推理能力更强
- **Haiku 4.5**：延迟优先时的优选
- **高级工作流**：编排器+子智能体模式——推理模型处理规划，Sonnet/Haiku 执行机械点击

##### 1.7 处理小目标

针对小目标（复选框、系统托盘图标、下拉箭头、小开关等）：

1. **使用缩放功能**：设置 `enable_zoom: True`
2. **使目标更大**：降低系统 DPI、浏览器缩放、调整 UI 缩放设置
3. **使用键盘替代**：Tab 导航或快捷键可能比点击更可靠
4. **考虑源图像分辨率**：4K 截图压缩到 720p 会严重丢失细节

##### 1.8 经测试无效的方法

- 将图像拆分为更小的块/区域
- 在截图上叠加坐标网格
- 不同的缩放算法选择（PIL LANCZOS、sips 等结果相同）

#### 二、调优思考力度

Claude 最新模型支持**自适应思考**，让 Claude 根据请求复杂度动态决定推理深度。通过 `effort` 参数控制：`low`、`medium`、`high`、`xhigh`（仅 Opus 4.7）和 `max`。

##### 2.1 Opus 4.7

Opus 4.7 在所有思考力度级别上都优于 4.6 系列。在 OSWorld Verified 基准测试中，Opus 4.7 低力度的得分与 Sonnet 4.6 最大力度相当，而 Token 用量仅为后者的约 1/10。

| 场景 | 推荐力度 | 原因 |
|------|---------|------|
| 大多数用例的默认值 | **high** | 足够的推理来规划复杂多步交互，不会显著增加 Token 用量 |
| 高吞吐/成本敏感 | **low** | 更低 Token 用量，质量介于 Opus 4.6 的 high 和 max 之间 |
| 简单、明确的工作流 | 建议用 Sonnet 4.6 | 低延迟优先 |
| 复杂的一次性任务 | **max** | 需要首次就做对时使用 |

##### 2.2 Claude 4.6 系列

两个关键发现：

1. **中等力度是最佳点**：以 high 大约一半的输出 Token 成本达到接近最高的成功率。有重试时，medium 和 high 收敛到相同成功率。
2. **少量思考效果显著**：low 力度实际上比完全禁用思考使用更少的总输出 Token（模型犯更少错误，需要更少重试循环）。

| 场景 | 推荐力度 | 原因 |
|------|---------|------|
| 大多数用例的默认值 | **medium** | 最佳精度/成本比 |
| 高吞吐/成本敏感 | **low** | 比不思考更准确，Token 用量更低 |
| 简单明确的工作流 | 禁用思考 | 低延迟优先 |
| 复杂一次性任务 | **high** | 首次做对时使用 |

**不推荐 max 力度用于计算机操作**——测试中相比 high 无精度提升，但 Token 成本更高。UI 任务主要是感知性而非深度逻辑性的。

配置示例：

```python
response = client.beta.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=16000,
    betas=["computer-use-2025-11-24"],
    thinking={"type": "adaptive"},
    output_config={"effort": "medium"},
    messages=[...],
    tools=[{
        "type": "computer_20251124",
        "name": "computer",
        "display_width_px": 1280,
        "display_height_px": 720,
    }],
)
```

##### 2.3 更多思考并非总有帮助的原因

UI 自动化与编码/数学问题根本不同。大多数操作是**感知性和机械性的**。思考最有帮助的场景：
- 在开始前规划多步序列
- 从意外 UI 状态中恢复
- 在屏幕内容和任务指令之间交叉引用信息
- 在专业软件上完成有挑战性的项目

#### 三、提示注入防御

计算机操作智能体在设计上会与不受信任的内容交互。每个截图、网页或应用 UI 都可能包含对抗性指令。

##### 3.1 Anthropic 的防御策略

1. **训练时鲁棒性**：通过强化学习，在训练中将提示注入抵抗力直接构建到模型能力中
2. **实时分类器**：扫描进入上下文窗口的内容，标记潜在的提示注入
3. **持续红队测试**：安全研究人员持续探测防御，参与外部对抗性评估

##### 3.2 使用内置分类器

使用官方 `computer_20251124` 工具类型时，提示注入分类器**自动运行**，几乎不增加延迟和成本。无需额外配置。

##### 3.3 最佳实践（无论是否使用分类器）

1. **高风险操作引入人工确认**：提交表单、购买、发送消息前暂停并请求用户确认
2. **限定智能体权限**：工作流不需要的能力就不要授予
3. **监控和记录操作**：记录完整操作序列和每步截图
4. **将所有网页内容视为不可信**：在系统提示中明确区分用户指令和任务执行中遇到的内容

#### 四、上下文管理

截图积累很快。每个操作生成一张新图像，每张消耗约 1000-1800 Token。200k 上下文窗口在不到 100 张截图内就能填满。

##### 4.1 放置缓存断点

API 支持 4 个缓存断点。推荐：
- **1 个**放在系统提示或尾部工具定义上（稳定前缀）
- **最多 3 个**放在最近的工具结果上（每轮推进并清除前一轮的断点）

##### 4.2 方法一：滚动缓冲区（缓存感知）

保留最近 N 张截图，丢弃其余。关键是**批量修剪**而非逐张丢弃，以保持前缀字节级一致：

- 保留最近 `keep_n` 张截图（建议 3 张）
- 截图总数超过 `keep_n + interval` 时，一次性替换最老的 `interval` 张（建议 25 张）
- 修剪事件之间，消息数组字节级一致，缓存断点持续命中

##### 4.3 方法二：基于 LLM 的压缩

不是静默丢弃旧图像，而是**在丢弃前总结完整对话**。总结保留：发生了什么、用户要求什么、已完成什么、从哪里恢复。

压缩提示应包含以下关键部分：
1. **用户指令**：完整的初始任务定义（尽可能逐字）
2. **任务模板**：如果是可重复工作流，记录模式
3. **约束和规则**：所有用户指定的规则和限制
4. **已执行的操作**：访问的页面和交互的元素
5. **错误和修复**：出了什么问题、如何解决
6. **进度跟踪**：已完成 vs 剩余项目
7. **当前状态**：当前应用、URL、页面状态
8. **下一步**：接下来应该做什么

##### 4.4 服务端压缩（Beta）

通过 `context_management` 参数让 API 自动处理压缩：

```python
response = client.beta.messages.create(
    model="claude-opus-4-7",
    max_tokens=16000,
    betas=["compact-2026-01-12", "computer-use-2025-11-24"],
    context_management={
        "edits": [{
            "type": "compact_20260112",
            "trigger": {"type": "input_tokens", "value": 150_000},
            "instructions": COMPACT_PROMPT,
        }]
    },
    messages=[...],
    tools=[...],
)
```

##### 4.5 综合推荐

长时间运行的计算机操作智能体的良好默认配置：
1. 1 个缓存断点在稳定前缀，3 个在尾部工具结果
2. 缓存感知滚动缓冲区：`keep_n=3`，`interval=25`
3. 服务端压缩在约 150k 输入 Token 时触发，配合客户端截断

#### 五、实验性设置

##### 5.1 批量工具

`computer_batch` 和 `browser_batch` 接受子操作列表，在单个工具调用中执行。N 个操作变成单次往返。

**适用场景**：子操作自包含、不依赖彼此视觉结果（填写多个表单字段、链接键盘快捷键等）
**不适用**：探索性导航、错误恢复序列

##### 5.2 顾问工具（Beta）

将执行器模型与更高智能的顾问模型配对。执行器运行循环，遇到需要更深推理的情况时咨询顾问。这在服务端单个请求内完成。

```python
response = client.beta.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=16000,
    betas=["advisor-tool-2026-03-01", "computer-use-2025-11-24"],
    tools=[
        {
            "type": "advisor_20260301",
            "name": "advisor",
            "model": "claude-opus-4-7",
        },
        {
            "type": "computer_20251124",
            "name": "computer",
            "display_width_px": 1280,
            "display_height_px": 720,
        },
    ],
    messages=[...],
)
```

##### 5.3 定期提醒

长会话中，执行器模型可能忘记可用工具。两种提醒模式：
- **批量提醒**：观察到模型链接单操作调用时，附加短提示
- **顾问提醒**：超过约 20 轮未调用顾问时，附加简短提醒

#### 六、教学模式：展示而非描述

与其反复迭代文本提示，不如**直接展示正确行为**。录制自己执行任务的过程（截图、操作、可选语音旁白），然后在 Claude 执行相同工作流时作为上下文回放。

##### 6.1 核心概念

用户演示任务，系统记录操作。回放时 Claude 接收完整演示作为上下文，遵循相同步骤序列，同时适应当前 UI 的差异。

**回放不是严格重放**——Claude 将演示作为指南，同时推理实时环境。如果按钮移动了或菜单重组了，Claude 能找到当前 UI 中的等效元素。

##### 6.2 数据模型

基本单元是"工作流步骤"——录制期间捕获的单个操作，包含：操作类型、描述、时间戳、选择器、坐标、URL、截图、视口尺寸、语音转录、输入值。

##### 6.3 回放模式

- **严格模式**：完全按步骤执行；UI 变化太大时停止报告。适合合规敏感工作流
- **自适应模式**（推荐默认）：以演示为指南但适应 UI 变化
- **目标导向模式**：关注最终结果；将录制步骤作为提示而非指令

#### 七、总结

这些实践反映了当前对可靠计算机操作集成的最佳理解，适用于 Claude 4.6 系列和 Opus 4.7。随着集成的成熟，最重要的模式将取决于具体环境、目标应用和可靠性要求。

**最重要的三个优化：**
1. 预缩放截图以适配 API 限制
2. 选择合适的思考力度（4.6 用 medium，Opus 4.7 用 high）
3. 实施有效的上下文管理策略
