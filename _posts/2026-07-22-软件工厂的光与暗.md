> **摘要**：本文用"软件工厂"这一半个世纪前的旧梦，重新审视 AI 智能体大规模驱动软件生产的今天。作者区分了两种工厂：让人类留在循环中的"明工厂"（用判断力和专注换速度与风险），以及让智能体自主完成范围界定、构建、上线而无人真正阅读代码的"暗工厂"。核心论点是——真正的瓶颈从来不是生成，而是**验证**；一个循环能获得多少自主权，取决于你能多廉价、多可靠地验证它（这被称为"背压"）。忽视人类理解会积累"理解债务"，暗工厂不会偿还它，只会在测试全绿的假象下一路欠债，直到系统在某个安静的深夜崩溃。作者主张把人类判断前置到产品、设计、架构环节，并给出了判断"哪个循环该关灯、哪个该开灯"的具体标准。

**软件工厂就是把循环（loop）规模化。你可以让人类留在循环里（明工厂）：用判断力和专注度去换取速度，同时承担出错的风险。你也可以无视人类（暗工厂），让智能体自己界定范围、构建、上线代码，而没有任何人真正去读那些细节。但如果人们停止阅读，他们就会停止理解你的软件。你现在最难的工作，是搞清楚该搭建哪些检查点、该把多少自主权下放出去。**

"软件工厂"这个概念可以追溯到 [Bob Bemer](https://en.wikipedia.org/wiki/R._W._Bemer) 在 1968 年发表的论文《程序生产的经济学》（The economics of program production）。半个世纪以来，许多人梦想着这样一个世界：软件是一个可重复、可度量的生产过程（类似工厂里冲压汽车零件），而不再是个人孤立的手艺活。历史上，这个梦大体上（虽非绝对）都以失败告终，部分原因在于"冲压想法"本身就极其困难。

但在过去两年里，情况发生了足够剧烈的变化，以至于现在重新审视这个旧梦变得有意义了。而且由于一些微妙之处很容易被一笔带过，我们有必要精确地厘清：到底什么才是真正新颖、不同的东西，以及什么只是披着新机遇外衣、反复出现的老陷阱。

HumanLayer 联合创始人 Dex Horthy 最近在 AI Engineer World's Fair 上做了一场精彩的演讲，题为 **[《只有 Harness 工程还不够：软件工厂为何失败》](https://youtu.be/htM02KMNZnk?t=27219)**（Harness Engineering is not Enough: Why Software Factories Fail），值得就这个话题一看。

#### 循环是原子，工厂是规模化的循环

结构就是一切，而这一切都始于微小的单元。整个技术栈其实就是三个概念层层叠加：循环（loop）、Harness、以及工厂（factory）。

**循环（loop）是一个智能体反复做单一工作：收集上下文、采取行动、检查结果，然后再来一遍，直到满足某个条件为止。它是智能体工作的最小单元，其上的一切都不过是循环叠着循环。**

[循环工程（loop engineering）](https://addyosmani.com/blog/loop-engineering/)的要点在于：你不再逐轮地给智能体写提示词，而是去设计那个替你给它写提示词的小系统。

**Harness（挽具/框架）是循环周围的四壁：它运行的沙箱、它能触及的工具、在多次运行之间存活下来的记忆，以及决定"什么算完成"的那些关卡（gates）。循环是行为，Harness 是这个行为运行于其中的环境。**

给一个裸模型不配任何 Harness，它会乐呵呵地永远转下去。Harness 就是它周围让它变得有用且能安全运行的一切。

**软件工厂是许多被 Harness 约束的循环同时运行，由一个工作队列喂给它们，经过一道评审关卡（review gate）流入生产环境，而人类从上层掌控着这整件事。它不是一个更大的智能体；它是一张由循环构成的组织架构图。**

最终的范式转变，是从"写代码"转向"构建并运营那座写代码的[工厂](https://addyosmani.com/blog/factory-model/)"。工作的单元上升了一个层级——变成了循环、Harness，以及它们之间的流动，而不再是单个的代码 diff。

循环 → Harness → 工厂。工厂不是一个更聪明的智能体；它是许多被 Harness 约束的循环，共同喂给一道评审关卡，由一个人类掌控着外层循环。

#### 画出来的工厂

Dex 花最多时间讲解的那张核心幻灯片非常精彩，因为它是一张有澄清作用的接线图，把一个原本显而易见的循环可视化了出来。这是我的理解：

工厂是一个闭环：意图（intent）和生产信号喂给队列，Harness 进行构建，自动化检查和评审关卡对其把关，部署把它上线，监控又把生产环境变回信号。

意图从工程领导层的愿景、以及直接从工程师那里，流入一个待办事项队列。由事故和用户请求驱动的信号，也推动着同一个队列。Harness 不过是那个从队列中挑出一项、并为其构建变更的东西。在 Harness 之外，我们能看到让变更足够安全、可以放进生产环境所需的全部自动化检查。这些自动化检查瞬间完成、毫不费力，无需工程师任何有意识的参与——这得益于 CI、测试、静态分析和各种扫描。这里唯一的决策点就是评审关卡。批准之后，变更被部署并在生产环境中受到监控，监控数据又反哺回那些最初驱动循环运转起来的信号。

总的来说，这张图里的每一个方框几乎都是零成本的：生成、测试、扫描。它们全都能以微不足道的成本大规模运行。只有一个方框昂贵得顽固地抗拒规模化，那就是评审关卡。那个闪亮的琥珀色方框就是"判断力"（judgment），也正是"我们能否让开发变得更快、更频繁"这一争论的症结所在。

#### 为什么我们称它为"暗"

**暗工厂（dark factory）在物理意义上关着灯运行，因为车间里只有机器，而机器不需要光就能看见。暗软件工厂是同一套逻辑：代码上线了，却没有任何人类读过它，只由其他机器验证过。**

这个意象借自制造业。它的起源是物理的而非数字的，植根于那些关掉灯、由机器人完成工作的工厂。[日本的 FANUC 自 2001 年起就在运营这种熄灯工厂](https://en.wikipedia.org/wiki/Lights_out_\(manufacturing\))；小米在 2024 年也开设了一座高度自动化的暗工厂。它们的共同点是：产品被组装、被出货，却没有一个人类读过其中任何一部分。当"阅读"这个动作从流程中被移除时，"暗"就出现了。

我借用这个概念不是为了它的氛围感，也不是作为一种侮辱。尽管它有着令人毛骨悚然的话题性，这里的"暗"是一个朴素的物理主张：还是原来那个车间，只是没了光。在软件里，车间就是 diff。写这个 diff 的人、评审它的人、上线它的人——这些人都消失了，剩下的是一个只由构建它的机器验证过的 diff。

这件事出人意料地容易做到，至少一开始是这样。之所以容易，是因为那个缺失的评审步骤挡了所有事情的路。它的缺席让你对团队"纵向吞吐量"的感知，突然而剧烈地变高了。感觉就像你突破了音障。然而，尽管它表面上如此轻松，要在那些暗工作流中存活下来——连同它们所有那些被埋藏的成本——远比看上去更难。

#### 只有 Harness 工程还不够

编排、沙箱化原型、以及模型与世界和彼此交互时的工具调用，这套 Harness 会变得越来越强大、越来越有效。然而，在长线博弈中、在不断叠加的增量变更中，试图跟上代码库质量这件事，存在一种模型内在的失败倾向；而且我认为有充分理由相信，模型单打独斗最终会输掉这场对抗[理解债务（comprehension debt）](https://addyosmani.com/blog/comprehension-debt/)的战争。

**理解债务是"存在多少代码"与"还有任何人类理解多少代码"之间不断扩大的差距。暗工厂不会偿还这笔债；它会以最快的速度把债背上，而且一路上测试全都是绿的。**

这是一个重要的区分，因为模型在某些任务上确实表现出色。但对于任何不是"对代码库一小部分的即时改动"的事情——尤其是在复杂的棕地（brownfield）系统里——纯模型的自动化编码会撞上一道无法逾越的障碍。周末玩具和业余项目有个共同点：几个月的开发周期通常足以把事情弄到能用、或至少接近能用。但一个已经开发了十年甚至更久的企业级系统是另一头猛兽；它必须在专业环境中、以专业的节奏被维护。项目进行到三到六个月时，你就已经淹没在没人读过的代码里了。那种环境，尤其是生产代码所强加的约束，会让即便是强大的智能体也表现糟糕——这一切都与那些做周末玩具的开发者所享受的 vibe coding 形成鲜明对比。

Dex 从经验中报告说，这是一次重大的失败，严重到需要费力的人工调试才能定位病根。这来自于他运营一座全自动代码工厂约四个月的经历，期间没有任何人类看过所写的代码。这段经历的底层，是两个相互冲突的指标之间的权衡。一个是最大化 token 利用率——这个数字我们目前当作进展来对待。另一个则是被它悄悄最小化的东西：在任一时刻，还有任何人类参与者理解这个系统的多少。

暗工厂真正大放异彩之处，在于它能在测试保持全绿的同时烧穿原本纯净的代码。最终的清算到来时，不会是一个戏剧性的"一切瞬间崩盘"的时刻。它会是安静的，而且姗姗来迟。

暗与亮是同一条流水线，只是灯装在了不同的地方。亮着灯的版本不只是在末尾重新加上评审——它还把人类判断力上移到了设计和架构环节。

#### 瓶颈从来不是生成

软件工厂里的根本约束，不是我们能产出多少代码，而是我们能多快地验证它。

**背压（back pressure）这条规则是说：你只能把"你能廉价且可靠地验证"的那么多自主权交给一个循环，一寸都不能多。验证，而非生成，才是工厂真正的约束。**

因为无上限的生成能力，与"人类注意力"这个有限、不可规模化的资源之间存在着永恒的张力，核心问题就是廉价生成与有界评审之间的差距。看看这个漏斗：只要代表验证的那个瓶颈不变宽，它就一定会堵。正如 Dex 所指出的，光有数量本身不是问题：我们真正受苦于的是过剩的烂 PR。当你有着高数量却没有可信赖的关卡时，被制造出来的缺陷就无可避免。这仍然只是背压：自主权无法扩张到超出"能被廉价且可靠地验证"的范围。

第二层问题是：为什么改进模型不应该自动弥合"它能生成的"与"能被验证的"之间的差距。在架构良好的系统上训练，可以说是比通过简单测试更难的命题：请记住，衡量架构卓越性的成本函数不是以秒、甚至不是以分钟来计量，而是以月和年。整洁的梯度实际上不可能被计算出来，所以一个指望对复杂设计决策做出清晰、即时评价的系统，是不会在好的样本上被训练出来的。

生成是一张宽大的嘴；验证是狭窄的瓶颈。加快那张嘴，只会让瓶颈处的堆积更深。

#### 把灯重新打开

**亮工厂（lit factory）是同一条流水线，只是在"判断力所在之处"把灯留着。智能体仍然完成大部分构建工作，但在上线之前会有一个人类去读一读产出的东西，而且凡是"做错代价高昂"的地方，灯都一直亮着。**

亮着灯的版本不是把评审硬塞到末尾，而是把人类判断的落点上移——移到产品、设计和架构环节，赶在智能体开始一个循环之前。

那预先花掉的一小时有个绝妙之处：它带来更少的实现工时。它把一场漫长而令人沮丧的代码评审，变成对一份两百行计划的快速一读。你得以在一个决策被构建出来之前就评审它，这样往后你就不必在两千行生成的代码里一路追查、只为搞清楚当初那个决策到底是什么。有些决策昂贵且影响深远，你会希望有个人早早介入其中，赶在成本滚雪球之前。当然，即便你在前期花了时间，仍然有些时候你要去看 diff。

你可能在想，这一切听起来都不怎么光鲜。你说得对。这张安全网是由一些再普通不过的架构实践织成的——那些我们一直都知道、却大多忽视了的实践：好的类型和方法签名，让错误被编译器抓住而不是在生产环境里暴露；测试接缝（test seams），让我们能钉住行为、让变更可观测；把代码布局好，让下一个读者——无论是人还是模型——都知道去哪找他关心的东西；保持调用栈短且易读；保持组件边界定义良好，这样一次改动不会有巨大的爆炸半径；以及依赖注入，让我们能把一个部件换成另一个。这些都不是新东西。我们一直嘴上说在乎好的架构。但现在既然我们在用自动化编码智能体，那套架构终于开始干起第二份活：充当一张廉价且难以糊弄的安全网，去防范智能体注定会犯的错。

那张安全网必须活在模型之外，因为模型不会提供它。那些感觉最能干的编码智能体——Claude Code 和 Codex 都在其列——是针对它们自己的 Harness 和工具做强化训练的：对这行的所有工具和惯用法都无比娴熟，却不擅长长期可维护性这类东西。我们一直挂在嘴边的那种深思熟虑的架构，正是抓住这笔债务的工具，而我们对它的投资，就是我们在买回自己的自主权。把它和安全的基础设施结合起来，就有一些紧凑、低风险的循环可以无人值守地运行。Horthy 在最近一篇文章里描述过一个：一个每晚运行的 GitHub Actions 定时任务，只修复恰好一个反模式——一处 lint 违规、或一个不必要的可选属性——提交，然后开一个小小的 pull request，全都自己完成，于是团队醒来时会看到一个稍微好一点的代码库，和一个短到能读完的 diff。但对于风险足够高的循环，你不会想冒险醒来发现认证系统、计费引擎、或公开 API 契约坏掉了。在那些地方把灯留着，并且相信一个有判断力、对系统有真实工作认识的人会抓住那个错误。

#### 什么样的循环配得上"暗"

无论你叫它背压、验证、还是灯的开关，这条规则都适用。

一个循环只有在"检查廉价、高频运行、且依赖某种不易被糊弄的东西"时，才能为自己挣得全自动化的地位。绿或红的裁决器（oracle）、类型关卡、属性测试、以及一个配有真实评分标准（rubric）的评审智能体，全都符合。你还需要这个裁决器立即给出答案，且不随时间漂移。当"完成"不仅能被你、还能被一台机器证明时，你就抵达了自动化。

短循环比长循环更容易验证。[Dex 的经验法则](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-10-small-focused-agents.md)：一个智能体能撑住三到十步，超过二十步就开始跟丢线索。原因是上下文累积——智能体拖着的东西越多，它就越可能走偏。当一个循环很短时，验证它就很廉价。庞杂的循环把错误藏在角落里，这是"它们从未挣得熄灯资格"的另一种说法。

把灯开着则是相反的情形。如果一个错误答案代价高昂、且只有人能抓住它，那这个循环就需要被评审。测试抓不住的微妙生产 bug、巨大的爆炸半径、以及一个将塑造未来一年甚至更久工作的决策，全都符合。在这些情况下，[你的注意力就是真正的产品](https://addyosmani.com/blog/human-is-the-expensive-part/)——那个昂贵而不可或缺的产品。

危险在于忘了逐个去拨那些开关，而是把它们全都设成同一种模式。全关灯，四个月后你就困在推倒重来里。全开灯，没人能及时完成评审，你就困在一个巨大的瓶颈里。那份艰难而需要技巧的工作，是决定每个开关该放在哪。

#### 循环、图，还是状态机？

当你把一个任务交给智能体时，你多半会围绕它构建一张图（graph）——无论你把这张图叫做有限状态机，还是一组有条件连接的服务调用。这是一种视角：软件不再只是遵循某些抽象规则，而是遵循一个结构化的工作流：每个节点都是一个显式的步骤，节点之间的每条边都是一个显式的条件。

这听起来结构感很强，但其中大部分在任何软件里都早已存在，因为任何代码都能被表达为一张控制流图。所以唯一真正新颖的地方在于：一个坚持自主性的智能体，其实只是在一张特定的图上四处游走，而它的自由被约束在某个节点的内部。而这里有个人们会忘记的部分，[Dex 一年前就写下过](https://github.com/humanlayer/12-factor-agents)：软件本来就注定会有那种结构。我们过去把程序画成流程图是有原因的。真正新颖的动作，是试图把那张图扔掉，转而依赖一个循环，让模型一次一个工具调用地挑选路径，直到它宣布自己完成。那感觉像是一种解放，直到它撞上一个十年老代码库——而如今大家正在重新发现的那种纪律，即掌控你自己的控制流，其实不过是把那张图重新绕着循环走一遍。所以，"我们是否应该从循环退回到图"这个问题，几乎就是在承认：我们一直都需要那张流程图。

来看看它在实践中是什么样。拿一个要修的 bug 来说。作为一个纯循环，你坐下来思考：搞清楚哪里错了、改点代码、跑测试、看结果，如果这一轮没把整个运行搞挂，就绕回去重新开始。整段旅程都是边走边定的——追哪个问题、到底改哪段代码、跑哪些测试、按什么顺序跑、要不要跑测试、以及要再试一次还是宣布胜利。而作为一张图，你做的第一件事是画出应该发生什么：复现 bug 或去索取更多信息、找到原因、尝试修复、跑测试，让失败的运行路由回修复环节、而通过的运行则前往评审，只有一个批准才能抵达"完成"。智能体在每个方框内部依然聪明；它只是不能偏离你所批准的那些路径。Santi 用一张图把这个区别画得一目了然。

那张图真正的吸引力，当然在于它就是被画成图的背压。你放弃智能体的一部分自由，换回强制性的检查和清晰可读的失败点，于是当一次运行挂掉时，你可以指着那个杀死它的节点。这背后是和 Dex 那句直白的话同样的直觉——大多数所谓的智能体其实一点也不"智能体化"，"大部分是确定性代码，只在恰当的几个点上撒进一些 LLM 步骤"。而这也不只是当下人们恰好这么构建东西的产物：你能在 LangGraph 和 LlamaIndex Workflows 里看到同样的模式，在 Jerry Liu 那种"图套智能体的混合工作流、外层循环在运行时生长出图的部分"里看到，也在 David Khourshid 的提醒里看到——他说这其实不过是状态机和 actor 模型换上了新衣裳。

有一点需要澄清，因为这个词被严重滥用了：当我一直把这个叫做"图"时，我指的不是知识图谱（knowledge graph）。我指的是一张预定义的有向图，描述工作应该如何流动、连同所有的条件边，给循环一个你真正能信任的形状。

#### 人类究竟去了哪里

请注意，人从未离开工厂。他们只是挪了位置。

我认为工程师需要越来越多地掌控[外层循环（outer loop）](https://addyosmani.com/blog/own-the-outer-loop/)。智能体可以调查一个 bug、写出诊断、实现修复、跑测试、写出报告。那是内层循环的执行，而且它们能做得和任何人一样高效。但那从来就不是这份工作的本质。你所拥有的那些部分，我会称之为外层循环：决定这是不是解决问题的正确方式、验证诊断和实现是否站得住脚、批准变更、并承担判断错误的后果。两个循环之间的边界是证据——diff、测试、日志，以及把它们串起来的一段简短说明。类型、接缝和评分标准让你有可能监督这一切，而不必为每一次变更做大量的活。

我觉得这样说很有用：你不再是在流水线上写变更了；你在生产线的末端，设计它、并守着那道关卡。你有很多事情可以做，去让模型更好、让 Harness 更有能力，但我观察到，识别那些长期来看代价高昂的问题，通常并不是你能自动化掉的东西。仍然是这份工作核心的那件事，是把人类判断力发挥得比任何纸张和算力的洪流都更好。

机器人在黑暗中作业没问题，但人类需要看见他们在做什么。如果工厂车间里一切都是黑的，你什么也看不见，甚至连电灯开关都找不到——那才是危险所在。
