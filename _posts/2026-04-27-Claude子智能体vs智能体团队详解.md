大多数人一遇到复杂任务就想到多智能体系统。

这几乎总是错误的直觉。

正确的问题不是"我该用多个智能体吗？"而是"这个任务实际上需要什么样的协调？"

答案决定了架构的一切。

Claude 提供两种截然不同的多智能体范式：**子智能体**和**智能体团队**。表面上看起来相似，但在架构上，它们解决的是完全不同的问题。

---

#### 子智能体：通过隔离实现并行

子智能体是一个专门的 Claude 实例，运行在自己独立的上下文窗口中。

心智模型是这样的：想象你是一位研究主管。你不会亲自阅读每一份原始资料，而是把聚焦的问题委派给研究员，他们带着提炼好的发现回来，你再将一切综合成连贯的输出。

这正是子智能体的工作方式。

每个子智能体拥有：
- 定义其专长的独立系统提示
- 可访问的特定工具集
- 干净、隔离的上下文窗口
- 一项具体任务

完成后，只有最终结果返回给父智能体——不包含完整的推理链，不包含中间步骤，只有压缩后的输出。

子智能体的意义不仅仅是并行，更是**压缩**。你把大量的探索浓缩成干净的信号，而不会用噪音污染父智能体的上下文。

**一个硬性约束**：子智能体不能派生其他子智能体，也不能互相通信。所有结果都流回父智能体，父智能体是唯一的协调者。

这个约束是特性，不是限制——它让系统保持可预测性，你始终清楚信息的流向和决策的位置。

以下是定义和调用子智能体的最简 SDK 示例：

```python
from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition

async def main():
    async for message in query(
        prompt="Review the authentication module for security vulnerabilities",
        options=ClaudeAgentOptions(
            allowed_tools=["Read", "Grep", "Glob", "Agent"],
            agents={
                "security-reviewer": AgentDefinition(
                    description="Security specialist. Use for vulnerability checks and security audits.",
                    prompt="You are a security specialist with expertise in identifying vulnerabilities.",
                    tools=["Read", "Grep", "Glob"],
                    model="sonnet",
                ),
                "performance-optimizer": AgentDefinition(
                    description="Performance specialist. Use for latency issues and optimization reviews.",
                    prompt="You are a performance engineer with expertise in identifying bottlenecks.",
                    tools=["Read", "Grep", "Glob"],
                    model="sonnet",
                ),
            },
        ),
    ):
        print(message)
```

`description` 字段告诉父智能体该调用哪个子智能体。这里提示词提到了"安全漏洞"，所以父智能体路由到 `security-reviewer` 而非 `performance-optimizer`。如果提示词问的是延迟或瓶颈，则会选择另一个智能体。**description 是路由信号，要写得具体。**

#### 智能体团队：通过通信实现协调

智能体团队是一种完全不同的模型。

子智能体是完成任务后消失的短期工作者；智能体团队则是持久运行的实例，彼此直接通信，通过共享状态协调工作。

就像雇佣承包商完成独立任务，与组建一个在同一个房间里协作的团队之间的区别。

智能体团队有三个组成部分：
- **团队负责人**：协调工作、分配任务、综合结果
- **团队成员**：独立的智能体实例，各有自己的上下文窗口，并行工作
- **共享任务列表**：追踪待办、进行中和已完成的任务，以及任务间的依赖关系

典型的生命周期如下：

```plaintext
Claude（团队负责人）:
└── spawnTeam("auth-feature")
    阶段 1 - 规划:
    └── spawn("architect", prompt="设计 OAuth 流程", plan_mode_required=true)
    阶段 2 - 实施（并行）:
    └── spawn("backend-dev", prompt="实现 OAuth 控制器")
    └── spawn("frontend-dev", prompt="构建登录 UI 组件")
    └── spawn("test-writer", prompt="编写集成测试", blockedBy=["backend-dev"])
```

注意测试编写者上的 `blockedBy` 字段——这是共享任务列表在发挥真正的协调作用：测试编写者在后端智能体完成之前不会启动，无需负责人手动管理这个排序。

与子智能体的最大区别是**直接的点对点通信**。团队成员可以互相发消息、分享发现、提出阻塞问题，无需把一切都路由给负责人。

你也可以直接与单个团队成员交互，不必凡事都通过负责人。

#### 核心区别：即发即忘 vs. 持续协调

如何在两者之间做选择：

**子智能体是即发即忘的**：
- 给它们一个任务，完成后报告
- 智能体之间没有对话
- 没有共享内存，没有持续状态
- 每个子智能体在单次会话中生死

**智能体团队是协作性的**：
- 智能体持久存在，随时间积累上下文
- 任务中途的发现立即浮现给团队成员
- 前端智能体可以告诉后端智能体"API 响应结构需要改变"，后端立即调整，无需等待负责人居中协调

**最清晰的选择标准**：
- 工作是**完全并行**的（独立的研究流、代码库探索、只需摘要的查询）→ 用子智能体
- 工作需要**持续协商**（智能体需要在推进前协调输出，或一个线程的发现改变另一个线程的方向）→ 用智能体团队

#### 从第一原则设计智能体系统

大多数多智能体设计失败，是因为人们**按角色而非按上下文**拆分工作。

直觉上的做法是按角色拆分：规划者、实施者、测试者。看起来很有条理，但实际上制造了一个信息在每次交接时都会降级的"传话游戏"：

- 实施者没有规划者知道的信息
- 测试者没有实施者做出的决定
- 每个边界都会降低质量

**正确的心智模型是以上下文为中心的分解**。

问自己：这个子任务实际上需要什么上下文？如果两个子任务需要深度重叠的信息，它们可能属于同一个智能体。如果它们能以真正隔离的信息和干净的接口运行，那才是拆分的地方。

实际例子：实现某个功能的智能体也应该编写该功能的测试——它已经有了上下文。把这两件事拆给不同智能体会制造交接问题，成本高于并行带来的收益。

**只在上下文能真正隔离时才拆分。**

#### 五种值得了解的编排模式

无论使用哪种范式，这五种模式覆盖了大多数真实需求：

1. **提示链（Prompt Chaining）**：每次调用处理上一次的输出，顺序执行。适用于步骤有依赖、顺序重要的场景。

2. **路由（Routing）**：分类器决定哪个专门处理器接收任务。简单问题路由到更便宜、更快的模型；复杂问题路由到更强大的模型。这是控制成本不失控的方法。

3. **并行化（Parallelization）**：独立子任务同时运行。要么同一任务多次运行以获得多样化输出（投票），要么不同子任务同时运行（分段）。

4. **编排者-工作者（Orchestrator-Worker）**：中央智能体分解任务、委派给工作者、综合结果。这是子智能体和智能体团队的主导架构，也是大多数生产系统实际使用的模式。

5. **评估者-优化者（Evaluator-Optimizer）**：一个智能体生成，另一个评估并在循环中提供反馈。适用于质量比速度更重要、单次结果不够可靠的场景。

#### 什么时候完全不该用多智能体系统

这是大多数文章跳过的部分。

有些团队花了几个月构建精密的多智能体流水线，最后发现对单个智能体进行更好的提示词工程就能达到同等效果。

**先从简单开始，只在能清晰衡量到必要性时才增加复杂度。**

多智能体系统在三种情况下值得其成本：

- **上下文保护**：子任务生成的信息与主任务无关，放在子智能体中防止上下文膨胀
- **真正的并行化**：独立的研究或搜索任务，能从同时覆盖中受益
- **专业化**：任务需要相互冲突的系统提示，或一个智能体同时管理太多工具导致性能下降

以下情况则是错误选择：

- 智能体需要不断相互分享上下文
- 智能体间的依赖制造的开销超过执行价值
- 任务足够简单，一个提示词工程好的智能体就能处理

**对编码的特别警告**：并行编写代码的智能体会做出不兼容的假设。合并它们的工作时，这些隐式决定会以难以调试的方式冲突。用于编码的子智能体应该负责回答问题和探索，而不是与主智能体同时写代码。

#### 多智能体系统真正失败的原因

三种失败模式反复出现：

**1. 模糊的任务描述导致智能体重复彼此的工作。**

每个智能体都需要：明确的目标、预期的输出格式、使用哪些工具或来源的指引、以及明确的边界（不应覆盖什么）。没有这些，两个智能体会研究同样的内容，而且谁都不会注意到。

**2. 验证智能体在没有真正验证的情况下宣布成功。**

必须给出明确、具体的指令：运行完整的测试套件、覆盖这些具体用例、在每个用例通过之前不得标记为完成。模糊的批准标准会产生假阳性。

**3. Token 成本的增长比预期快得多。**

解决方案是智能地对模型分层：
- 在真正重要的地方使用最强大的模型
- 把常规工作路由到更快、更便宜的模型
- 建立预算控制，防止成本失控

---

#### 真正重要的一个设计原则

**围绕上下文边界设计，而非角色或组织架构。**

从单个智能体开始，推进到它崩溃的地方。那个失败点精确告诉你下一步该加什么。

**只在解决真实的、可衡量的问题时才增加复杂度。**
