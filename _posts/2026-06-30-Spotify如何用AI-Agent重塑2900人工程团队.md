> **摘要**：Spotify 工程副总裁 Niklas 分享了公司如何从 5-6 年前的"舰队管理"自动化迁移，演进到基于 Claude Agent SDK 构建的内部工具 Honk，实现 73% PR 由 AI 编写、PR 频率提升 75% 以上的成果。核心经验包括：验证环节是闭环 Agent 开发中最重要的投资、代码库标准化程度越高 Agent 工作效果越好、速度与质量并非二元对立——自动化质量实践才是加速的前提。此外，Spotify 还构建了内部原型应用商店，让包括联合 CEO 在内的非工程人员也能在数小时内用自然语言实现产品原型。

#### 从 IDE 到 Agent：工作方式的巨变

**主持人**：我记得去年大概九月跟你聊的时候，你说过一句话："我觉得到年底就没人会再用 IDE 了。" 当时我心里想，这也太疯狂了，不可能的。也许两年的时间窗口我能接受，但两个月太极端了。结果两个月后，我发现自己真的不再用 IDE 了。我工作的方式彻底变了——这是我做这行 30 年来从未经历过的变化。

**Niklas**：有趣的是，在公司内部我们的感受跟外界完全一样。

**主持人**：真的吗？

**Niklas**：只不过我们提前了几周。就这么点差距。但体感完全一样。

#### 编程之路的起点

**主持人**：好，我想先聊聊你是怎么入行的？

**Niklas**：我的正式学术背景其实是生物学。我是分子生物学出身，读博的时候，我们开始接触当时所谓的"大数据"——来自基因组测序的海量数据。我觉得自己需要提升编程能力，于是转了行。原本只打算做一年学术休假（sabbatical），结果一转眼就在这个行业待了快 30 年。

#### 个人的"感受 AGI"时刻

**主持人**：快进到今天，Agent 和 LLM 带来的变化中，我觉得你个人的使用方式和 Spotify 的实践都处于行业前沿。你个人第一次"感受到 AGI"是什么时候？

**Niklas**：我经历过好几个这样的时刻，取决于当时在解决什么问题。我们在 LLM 刚出现时就开始尝试用它们自动化代码变更，刚开始真的很挣扎。但随着我们逐渐摸索出如何利用 LLM 和 Judge（评判器）等手段，开始看到一些令人振奋的结果。

**主持人**：这是几年前的事了？

**Niklas**：对，比 Claude 还早，大概是 GPT 早期阶段。当时的效果还达不到"能解决所有问题"的程度，但让我们看到了未来的方向。

不过就我个人编程体验而言，真正的突破时刻大概是 Opus 4 或 5，去年 11-12 月的事。它从一个"智能自动补全"工具，变成了我可以把真实问题抛给它、而且不需要花太多精力做 prompt 工程的东西。对我来说最大的变化是——我不再需要手动编辑代码了。在那之前，我的工作流是：让模型写大概 70%-80% 的代码，然后我总得进 IDE 做最后一步的修改。

**主持人**：然后你就不需要了。

**Niklas**：对，这太疯狂了。

**主持人**：我觉得这就是为什么感觉像是一个巨大飞跃的原因。

#### 当前的工作流

**主持人**：那你现在的工作流是什么样的？你怎么用 Claude Code？Spotify 怎么用？

**Niklas**：我的用法比较朴素。我在终端里开多个 tmux 会话来运行它，通常有一堆 Agent 在后台跑。

**主持人**：你开多少个终端 tab？

**Niklas**：一般 5 到 10 个。另外我还会用一些 pane，因为我喜欢有一个终端能看 diff 之类的。所以我的设置是一组 Claude 会话加上对应的终端，分布在多个 worktree 中。

我们的代码组织方式是：有几个非常大的 monorepo（我们正逐步迁移过去），但仍然有数千个小的 polyrepo。我大部分工作都在 monorepo 里，所以那里通常有几个 Claude 会话和终端在同时运转。如果我需要跳进某个 polyrepo，就临时开一个 Claude 会话。

**主持人**：你觉得 monorepo 和 polyrepo 哪个更适合 Claude？

**Niklas**：说实话，我一开始对 monorepo + Agent 的组合有点担心，因为之前用过的一些工具在索引方面遇到过问题，而且这些仓库相当大——我们后端的 monorepo 超过 2000 万行代码。但事实证明 Claude 在这些大仓库里的表现非常好。我们发现的一个亮点是：Claude 非常擅长查看仓库中其他代码，从中获取"灵感"来解决你当前的问题。

#### Honk 的诞生：从舰队管理到 AI Agent

**主持人**：我想聊聊你们构建的基础设施。你们在 Spotify 构建了 Honk，从最早期的模型实验到基于 Agent SDK 构建 Honk 和后台 Agent，你们总是比其他人更早看到未来。是什么样的文化或团队促成了这一点？讲讲这个故事。

**Niklas**：大约五六年前，我们发现代码库的增长速度远超工程师人数——快了七倍。这意味着随着时间推移，我们需要维护越来越多的代码。而 Spotify 是一家永远有无穷创意想交付给用户的公司，被维护工作拖住不是个好状态。

所以我们开始尽可能地自动化维护工作。很多都是枯燥的事情——迁移到最新 Java 版本、更新依赖库、把代码从一个 API 迁到另一个 API。我们构建了一套叫做"舰队管理"（Fleet Management）的基础设施。以前做迁移的方式是：把迁移文档发给所有团队，让他们手动操作各自的组件。我们换了个思路——能不能找到方法，直接对分布在数千个仓库中的整个代码库进行变更（mutation）？

**主持人**：因为每个团队其实都在做同样的事。

**Niklas**：对。数百个团队在数千个组件上手动执行相同的操作。每次迁移要花好几个月才能完成。一年我们最多能做 10 次迁移，勉强跟上框架版本的更新。

所以我们开始自动化这件事，构建了整套基础设施。我们已经合并了数百万个这类 PR。但它们都依赖于确定性脚本——通过脚本来执行代码或配置变更。我们很早就发现：代码有巨大的 API 表面积，想对代码做改动很快就会变得极其复杂。

**主持人**：就是传统的 AST 静态分析转换？

**Niklas**：没错。比如一个 API 调用，你把它赋值给一个变量，现在你就需要做变量追踪和状态追踪。

**主持人**：这很混乱。

**Niklas**：对。所以每个迁移脚本最终都膨胀成数千行代码，要处理各种边界情况。

这启发了我们——当早期 LLM 出现时，我们想：能不能把它们应用到这个问题上？刚开始完全不行，部分原因是模型不够好，部分原因是我们太天真——基本就是把代码丢给模型，试图让它一次性生成正确的变更。

随着时间推移，模型变好了，我们的思路也进化了。我们开始用 LLM-as-Judge 来验证输出是否符合预期，开始分解问题、用各种方式解构它。经过无数次迭代和内部 Hackathon，我们开始整合这些成果，最终形成了现在叫做 Honk 的东西。

它最初跟现在很不一样——不是基于 Claude，更多是一些自研的东西拼凑在一起。但这是第一次让我们看到"隧道尽头的光"——这个问题确实可以解决。

后来我们在 Honk 上做了非常多次迭代。今天我们发布了 V2，但实际上可能是 V8 什么的，只是我们没记录版本号。它从最初的"自动化代码变更、调度并编排到所有仓库"，很快就被工程师发现可以用来做其他事情——比如在 Slack 上提一个需求让它帮我完成任务之类的。所以今天的 Honk 已经成为我们一个更加无处不在的工具。

#### Honk 的架构

**主持人**：给我讲讲 Honk 的架构。有一个编码 Agent，是基于 Claude Agent SDK 构建的，然后还有一个验证步骤？

**Niklas**：我们以前在 Honk 里有一个 Judge，但现在已经去掉了。因为到了 Opus 4 或 5，Agent 和模型本身已经足够好，不再需要 Judge 了。Judge 在早期版本中非常重要——它让 PR 成功率从大约 20-30% 提升到了 80%。变化很大。但后来模型追上来了，Agent 框架也追上来了，所以我们去掉了 Judge。

架构上其实很简单：Agent SDK 运行在一个 Kubernetes Pod 里，可以访问一组工具。V2 之前，这些工具是预定义的白名单——我们信任并授权给 Agent 的那些。V2 之后，用户可以自行添加工具，Agent 可以使用我们任何内部工具。其中最重要的工具之一是运行验证——基本上就是跑 CI 构建，支持 Linux 和 macOS。macOS 对我们特别重要，因为 iOS 开发需要 macOS 构建。

**主持人**：只是构建还是更深入的测试？比如打开 iOS 模拟器让模型启动应用？

**Niklas**：可以做那种级别的测试。我们确实有把模拟器和 Claude 集成在一起的案例——比如直接从 Figma 设计稿到 UI 实现的自动化，我们一直在用它把 iOS 应用移植到电视应用。

#### 验证是闭环开发中最重要的投资

**主持人**：我觉得验证这件事，在闭环 Agent 开发中——Agent 接到任务后需要拆解、规划并执行大量工作而无需人类参与——验证就是最最重要的事。我看到的常见错误是：公司在验证环节投入不足。

**Niklas**：我觉得这非常正确，对我们也是如此。我们在工程实践上做的一个重大改变就是加强测试自动化。

我们把代码库划分为数千个组件，每个组件都有明确的所有权——归属于某个特定团队，由他们设计、实现和运维。在舰队管理投资之前，每次变更合并到代码库时那个团队都在环路中。这意味着在某些情况下，我们在测试自动化上可以有些松懈，因为团队总是可以在需要时检查每个 PR。

但当我们开始自动化 PR 后，我们需要改变对团队的期望：你可能不再在这些变更的环路中了。大部分变更会自动合并，你甚至可能看不到那个 PR。所以我们必须构建更好的测试自动化，确保所有软件都能经受住这种自动化变更。

放到今天来看，这对我们非常有帮助——我们可以把 Agent 扔向那些代码，使用同样的验证机制。

#### 速度与质量不是二选一

**主持人**：工程领域有一个人们经常讨论的权衡——可靠性/质量 vs 速度。对我来说这像是一个伪命题，因为如果你想更快，你需要做的是自动化你的质量实践——把它编码到系统中，而不是留在某个人脑子里。把它放在 Skill 里、CLAUDE.md 里、或者某组 MCP 中——让 Claude 能做的事。这才是真正让你加速的东西。工程生产力始终是关于基础设施投资，不是加班加点，而是让基础设施越来越好。

**Niklas**：我们看到的是：质量指标保持不变的同时，速度显著提升。但这不是免费的——我们必须做测试自动化的投资。我觉得我们还需要继续投资可靠性实践。

**主持人**：你想走得越快，就越需要在可靠性上投入更多。

**Niklas**：完全正确。我们每天大约做 4500 次生产部署，有大量出错的机会。所以需要有好的实践来确保每次发布到生产环境的代码都达到我们要求的质量。

#### 从想法到上线：一小时内完成

**主持人**：做这么多部署的目的是什么？

**Niklas**：这是我们从 Spotify 创立之初就一直在优化的事。我们希望开发者有一个想法后，能尽快将其发布到生产环境。以前这需要几周甚至几个月，现在大约一小时。

我们有很多想法需要验证和探索。在某些情况下反馈来自内部用户，某些情况下来自外部用户。无论哪种，迭代越快，我们发现产品做得越好，也能更快交付。不是每个想法都能在一小时内上线，很多需要大量探索。但快速验证的能力对我们来说至关重要。Agent 当然也是这个循环的一部分。

#### 衡量 ROI

**主持人**：Spotify 工程组织很大，大概有几千名工程师？

**Niklas**：大约 2900 名工程师。

**主持人**：你们怎么思考 ROI？

**Niklas**：衡量 ROI 方面，信号一直很清晰。我们看到 PR 频率提升了 75% 以上，可以直接归因于 AI 工具。目前大约 73% 的 PR 直接归因于 AI 编写。这些指标表现很好。但我们当然想把它连接到用户价值和营收上。

**主持人**：怎么衡量这个？是 AB 测试还是什么？

**Niklas**：我们想做的是把工程师的交付物——PR、部署——连接到我们称之为"工作项"的东西，也就是计划中的工作。然后这些工作项连接到 AB 测试和发布，我们就能回溯说："这个 PR 贡献了这个 DoD（完成定义），而这个 DoD 贡献了这些用户价值。" 这是目标，我们正在构建这些连接。

**主持人**：以前做开发者效能，一个大的胜利可能就是几个百分点的提升。

**Niklas**：没错。而且你还不一定能衡量得出来。现在的提升是如此明显，所有人都能感受到。但作为工程师，我们仍然想量化它。

ROI 的讨论一开始很简单，因为提升太大了。但随着成熟度提高、成本在降低，对 ROI 估算精度的期望也在提高。所以我们在改进衡量方法。一部分是生产力提升，另一部分是获得这些提升需要多少成本。

**主持人**：现在人们看到几十个甚至上百个百分点的提升，就会想搞清楚：花了多少 token？用了多少小时？产出了什么？

**Niklas**：完全正确。

#### 给技术领导者的建议

**主持人**：你会给其他 CTO 和工程 VP 什么建议？

**Niklas**：我们发现，那些对基础能力的投资——测试自动化、验证——回报巨大。另一个方面是标准化。我们一直在推动代码库的一致性、工具和框架的统一。这最初是为了简化人类的工作、提高人类的生产力，但我们发现它同样能很好地过渡到 Agent。

前面提到 Claude 擅长从 monorepo 中其他代码获取灵感——如果代码有 10 种不同的写法，Claude 会更困惑。我们发现一致性越高，Agent 的效果就越好。

如果让我给一个建议：不要忽视这些基础投资。你需要保持跟以前一样健全的工程实践——它们在新世界中同样适用。可能形式不同，代码库里多了一个新角色（Agent），但基本面似乎同样重要。至少在我们的环境中是这样。

#### 给工程师的建议

**主持人**：对一直在做工程工作的人，你有什么建议？Spotify 有工程师在地铁上就能提交 PR 的故事，这很酷。显然工程在变化，你对正在适应这一切的人有什么建议？

**Niklas**：让我从个人角度来说。我是一个真正享受编程中问题解决部分的人。听起来很书呆子，但我闲暇时间会做竞赛编程，就是好玩的脑力锻炼。

在内心深处，我一直有点担心——正如我们前面聊到的——这些变化彻底改变了我们的工作方式。从个人角度我很担忧：我会不会怀念那种硬核的智力挑战？

现在我发现自己有五个 Agent 在后台工作，我跟它们交互的方式跟一两年前完全不同。结果是：我之前的担心是多余的。我真正喜欢的是解决问题，而解决问题的具体方式对我来说并不是最关键的。

这因人而异，每个人都要以自己的方式完成这个转变。但我建议关注你现在能解决的问题类型。我发现自己不仅更有产出、能创造更多价值，还能解决以前根本无法解决的问题。我可以跳进以前需要花几天几周才能上手的代码库，并立即开始做贡献。

对我来说这很棒。对不同的人会不一样，但我建议试试看，找到适合自己的使用方式。

#### 原型开发的民主化

**主持人**：对我来说，我看到的最大变化是：实现时间大幅减少——因为 Claude 在后台完成——取而代之的是思考下一步、跟客户交流，以及大量原型开发。你呢？

**Niklas**：我的体验类似。我们正在大力投资原型开发。这面向工程师，但也面向非工程人员。Claude 和类似工具解锁的一个能力是：任何人都可以把自己的想法用自然语言表达，然后让 Claude 去实现它。

当人们开始发现这一点——包括非工程师——他们开始尝试在我们真实的应用中做这件事。这些是相当复杂的代码，但他们开始看到曙光。所以几个月前，我们搭建了基础设施让这件事变得简单。

今天我们有一种非常简便的方式来构建移动应用和后端的端到端原型，我们还有一个内部原型应用商店，你可以分享原型、试用别人的原型。

这对那些——包括不太熟悉如何在移动应用中构建东西的工程师——来说是一个巨大的解锁。以前你要说服一群工程师帮你实现一个想法，现在你自己进去，一两个小时就有一个可运行的原型，可以分享给人看——真实用户、真实数据。这在一年前是不可想象的，现在我们每天都在做。

**主持人**：你看到产出者的构成变化了吗？是工程师在做还是设计师和产品经理？

**Niklas**：所有人都在做。我们的一位联合 CEO 也在那个应用商店里有原型。很多高管都做了不错的原型——都是他们脑子里一直有的想法，虽然有专门的工程团队能实现，但那些团队在忙别的事。现在他们能更快地尝试，亲手感受这个东西会是什么样子。让你能在一天内验证一个想法，而不是几周或几个月。

**主持人**：Niklas，非常感谢。
