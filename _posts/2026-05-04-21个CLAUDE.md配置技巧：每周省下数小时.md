大多数使用 Claude 的人从未听说过它。听说过的人也不知道该往里面写什么。

这个认知差距每周都在浪费人们数小时的时间。

每次你打开一个新的 Claude 会话，它都从零记忆开始。它不知道你的名字、你的工作、你的偏好，或者你喜欢怎样完成事情。你要么花前几分钟重新解释一切，要么不解释——然后 Claude 给你的东西完全不符合你的实际工作方式。CLAUDE.md 永久解决了这个问题。

#### 为什么这对所有人都重要——不仅仅是开发者

大多数人认为 CLAUDE.md 是开发者工具。不是的。它是一个指令文件，Claude 在每次会话开始时自动读取——对任何经常使用 Claude 的人都有效。

- **写作者**用它锁定自己的声音和语调，让 Claude 永远不会听起来像别人。
- **营销人员**用它定义目标受众，让 Claude 不再写泛泛的文案。
- **研究人员**用它设定信息结构化的方式。
- **企业主**用它给 Claude 公司的完整上下文，让每个输出都符合实际情况。

没有 CLAUDE.md，你每次会话都从零开始。你重复自己。你纠正同样的错误。你第一百次解释你的偏好。

CLAUDE.md 是你在用 Claude 做任何正经工作之前应该设置的第一件事，无论你用它做什么。

#### 如何创建文件——只需2分钟

1. 打开你的项目文件夹，创建一个新文件。命名为 "CLAUDE.md"——大写字母，没有空格。它只是一个 `.md` 扩展名的纯文本文件。
2. 用任何文本编辑器打开——记事本、TextEdit、VS Code 等等。你将直接把指令粘贴到这个文件中。
3. 从本文复制与你相关的指令并粘贴进去。你不需要全部21条，先从解决最大痛点的3-4条开始。
4. 保存文件。Claude Code 在你每次打开该文件夹的会话时自动读取。无需设置，无需额外步骤——从第一条消息就生效。

#### 第一部分：Claude 如何与你对话

##### 1. 去掉废话

Claude 的默认行为是每次回复都以"好问题！"、"当然！"、"当然可以！"、"绝对没问题！"开头——这些短语毫无意义，浪费你的时间。当你每天使用 Claude 数小时，这种摩擦会不断累积。

一条指令就能永久消除它。每个回复直接从答案开始。没有预热，没有表演式的热情——只有你要的信息。

```
永远不要用"好问题！"、"当然！"、"当然可以！"、"绝对没问题！"、"好的！"或类似的废话开头。

每个回复直接以实际答案开始。
不要有前言，不要确认问题。
只给信息。
```

##### 2. 行动前总是先展示选项

Claude 默认会选一种方法就直接动手。你让它重写一段话，它改变了整篇文章的语调。你让它重组文档结构，它按照不符合你思维方式的方式重新组织。现在你在纠正一个你没有要求改变的东西。

这条指令完全改变了这种动态。在任何重要任务之前，Claude 会展示2-3种可能的方法。你选择合适的方向，后续输出就是你真正想要的。

```
在执行任何重要任务之前，先展示2-3种可能的方法供我选择。
等我选择后再继续。
不要自行决定最佳方法并直接执行。
```

##### 3. 不知道的时候坦诚说

Claude 会在承认不确定之前给你一个自信、详细、完全错误的答案。它用听起来合理的信息——日期、统计数据、引用、事实——来填补空白，感觉是真的但实际不是。你使用了那些信息，问题在最关键的时候暴露出来。

这条指令改变了这个行为。Claude 在回答之前先标记不确定性，而不是把它藏在自信的回复里。

```
如果你对任何事实、统计、日期、引用或信息不确定，请在包含它之前明确说明。

"我不确定这一点"永远比把猜测当事实呈现更好。

永远不要用听起来合理的信息填补知识空白。
有疑问时，直接说。
```

##### 4. 长度匹配实际需要

问 Claude 一个简单问题，它写四段话。让它写复杂的东西，它给你一个看起来完整但实际不是的骨架。两者都没用。回复长度应该匹配任务实际需要——简单的答案就短，需要深度的工作就详细。

```
回复长度匹配任务复杂度。

简单问题给直接、简短的答案。
复杂任务给完整、详细的回复。

永远不要压缩或概括需要真正深度的工作。
永远不要用重述问题或重复刚说过内容的结尾句来填充回复。
```

#### 第二部分：Claude 的行为约束

##### 5. 大改之前先问

你让 Claude 修一段话，它重写了整个文档。你让它缩短内容，它删除了你需要的段落。你让它调整语调，它连结构也改了。每次你都会失去不想失去的东西，不得不从记忆或早期版本中重建。

这条指令把每个重大改动变成一个检查点。Claude 停下来，告诉你它将要做什么，然后等你同意后才动手。

```
在做任何会显著改变我已创建内容的改动（重写段落、删除部分、重组结构、改变语调）之前，完全停下来。

描述你将要改变什么以及为什么。
等待我的确认后再继续。

"我觉得这样会更好"不是修改的许可。
```

##### 6. 只关注被要求做的事

让 Claude 修一个东西，它会顺手"改进"其他五个——调整你的措辞、重组结构、改写你满意的句子。有时这些改动是改进。通常不是。而现在你得检查所有东西来找出实际改了什么。

```
只改我明确要求改的。

不要重写、改措辞、重组、或"改进"我没提到的任何东西——即使你认为会更好。

如果你注意到其他地方可以改进，在回复末尾提一下。
除非我明确要求，否则不要碰它。
```

##### 7. 总是告诉我改了什么

Claude 完成任务后，你得扫描输出试图搞清楚什么跟之前不同了。哪些部分改了？有删除的吗？有没有加你没要求的东西？没有摘要的话，你每次都在手动做 diff。

```
完成任何编辑或写作任务后，总是以简短摘要结尾：
- 改了什么：[描述]
- 没动什么：[如果相关]
- 需要我注意什么：[任何需要决定或审查的事]

保持简短。这是状态更新，不是重述你刚做的一切。
```

##### 8. 未经允许不代我执行任何操作

随着 AI 工具与你的邮件、日历、社交账号、文档的连接越来越多，Claude 执行你未完全意图的操作的风险也越来越大。发消息、发内容、分享文档、安排日程——这些操作有真实后果且发生得很快。

```
未经我在当前消息中明确确认，永远不要代我发送、发布、分享或安排任何事情。

包括：
- 邮件
- 社交帖子
- 日历邀请
- 文档分享
- 任何影响本对话之外事物的操作

"你之前提到想做这个"不算确认。
我必须在当前消息中说是。
```

#### 第三部分：你的上下文

##### 9. 告诉 Claude 你是谁、你知道什么

Claude 不知道你是专家还是初学者，是创始人还是自由职业者，是想要技术深度还是通俗语言。没有这个上下文，它只能猜——猜错的概率和猜对一样高。

关于你自己的一段话就能校准 Claude 给你的每个回复。

```
关于我：
- 姓名：[你的名字]
- 角色：[你做什么——写作者、创始人、营销人员、研究员等]
- 背景：[相关经验或知识水平]
- 擅长：[你熟悉的领域——这里跳过基础知识]
- 正在学习：[需要更多上下文和解释的领域]

根据这个背景调整每个回复的深度。不要过度解释我已经知道的。不要跳过我需要的上下文。
```

##### 10. 给 Claude 你当前工作的上下文

每次会话，Claude 都不知道你在做什么、为谁做、什么重要。它给你通用输出是因为别无选择。

一段简短的上下文描述改变一切。建议不再通用，而是符合你的实际情况。

```
我正在做的：
- 项目：[一句话描述这是什么]
- 目标：[成功是什么样子]
- 受众：[这是给谁的，他们关心什么]
- 语调：[输出应该什么感觉——随意、专业、直接、对话式等]
- 避免什么：[不合适的东西——术语、某些话题、特定风格]

将这个上下文应用到每个任务。当某些东西不符合这个画面时，继续之前先标记。
```

##### 11. 锁定你的声音和风格

Claude 有默认写作风格。还行。但不是你的。它用特定短语，以特定方式组织句子，有一种不匹配你实际沟通方式的语调。

在 CLAUDE.md 中定义一次你的声音，Claude 从第一稿就用你的风格写作。更少编辑，更多真正像你的输出。

```
我的写作风格——始终匹配：
- 声音：[例如：直接、对话式、自信、无废话]
- 句子长度：[例如：短而有力 / 长而详细 / 混合]
- 我用的词：[听起来像我的短语或词汇]
- 我从不用的词：[不符合我风格的词或短语]
- 格式偏好：[例如：纯段落 / 要点列表 / 标题 / 无标题]

代我写任何东西时，精确匹配这个风格。不要默认使用你自己的模式。
```

#### 第四部分：记忆与连续性

##### 12. 让 Claude 维护记忆文件

Claude 在会话之间忘记一切。每次对话都从头开始。但 Claude 可以写文件，文件是持久的。这条指令让 Claude 维护一个 MEMORY.md 文件，记录你们一起做的每个重要决定：决定了什么、为什么、考虑并拒绝了什么替代方案。

每次会话开始时，Claude 读取这个文件。突然它知道你两个月前为什么做了那些选择。它不再重新建议你已经试过的东西。它在你的决定基础上构建，而不是与之矛盾。

```
维护一个名为 MEMORY.md 的文件。在任何重要决定之后——关于方向、格式、内容、方法或策略——添加一条记录：

## [日期]，[决定]
**决定了什么：** [做出的选择]
**为什么：** [推理过程]
**被拒绝的：** [考虑过的替代方案及其被否决的原因]

每次会话开始时先读取 MEMORY.md。没有先标记就不要与已记录的决定矛盾。
```

##### 13. 会话结束摘要——永不丢失进度

你关闭会话。两天后回来。你花15分钟读旧消息试图记住你在哪里、完成了什么、正在做什么。这完全是可避免的浪费。

这条指令让 Claude 在你结束前把会话摘要写入 MEMORY.md。下次会话直接带着完整上下文打开。你从上次停下的地方精确继续。

```
当我说"会话结束"、"收工了"或"我们到此为止"时，写一个会话摘要到 MEMORY.md：

## 会话摘要，[日期]
**做了什么：** [我们关注的内容]
**已完成：** [什么完成了]
**进行中：** [开始但未完成的]
**做出的决定：** [本次会话的关键选择]
**下次会话：** [首先要做什么，以及需要带入的重要上下文]
```

##### 14. 记录失败的方法——停止重复解决同一个问题

你为一段内容尝试了一种提示方法。花了四次才得到可用的结果。三周后你回来做类似任务，Claude 又从同样糟糕的建议开始。同样的试错，同样的浪费时间。

错误日志打破这个循环。每个失败的方法都被记录下来——你试了什么、为什么没用、最终什么有效。下次 Claude 先检查日志，直接跳到已知有效的方法。

```
维护一个名为 ERRORS.md 的文件。当某个方法需要超过2次尝试才成功时，记录：

## [任务类型或描述]
**没用的：** [失败的方法及原因]
**有用的：** [最终成功的方法]
**下次注意：** [类似任务值得记住的]

在为类似已记录任务建议方法之前，先检查 ERRORS.md。如果任务匹配已记录的失败，说出来并直接跳到有效的方法。
```

##### 15. 给 Claude 一个永不改变的事实列表

每个项目都有永久事实：来自过去决定的约束、因重要原因存在的规则、关于你工作始终为真的事情。没有这条指令，Claude 不知道这些事实存在，会随意建议与之矛盾的东西。

```
这些事实永远为真。在每次会话和每个任务中无例外地应用它们：

- [永久事实 #1，例如"我的受众没有技术背景"]
- [永久事实 #2，例如"所有内容必须适合专业场景"]
- [永久事实 #3，例如"我们从不做没有来源的声明"]
- [永久事实 #4，例如"品牌声音始终温暖，从不企业化"]

如果任何任务与这些之一冲突，继续之前先标记。不要在未告知我的情况下绕过约束。
```

#### 第五部分：开发者专用

以下指令专门针对使用 Claude Code 编写、审查或管理代码的人。如果不是你，上面的内容就够了。如果是，这六条规则就是 Claude 作为有用编码助手和在你代码库里乱来之间的区别。

##### 16. 保持在范围内——不要碰没被要求的东西

让 Claude 修一个 bug，它会重构三个文件、重命名你的变量、重组 import、"改进"你用了几个月的代码——全都没有问过你。有些改动会搞坏东西。有些引入微妙的差异，需要花几天才能追踪到。

这是使用 Claude Code 最重要的规则之一。范围控制是精确工具和代码库里的散弹枪之间的区别。

```
只修改与当前任务直接且明确相关的文件、函数和代码行。

不要重构、重命名、重组、重新格式化或"改进"我没有明确要求改变的任何东西。

如果你注意到其他地方值得修复的，在备注中提及。
永远不要碰它。
```

##### 17. 任何破坏性操作前先确认

Claude Code 在你的终端中运行，有权访问你的文件系统。它会毫不犹豫地删除文件、覆盖函数、删除数据库表——因为你告诉它这样做了，即使你没有完全意识到你在告诉它什么。一个误解的指令，数小时的工作就没了，无法撤销。

```
在删除任何文件、覆盖现有代码、删除数据库记录、移除依赖，或做任何不能轻松撤销的改变之前，完全停下来。列出将被影响的确切内容。请求明确确认。只有在我在当前消息中说是后才继续。
```

##### 18. 硬停——未经明确许可永远不发生的操作

部署到生产环境。在活数据库上运行迁移。向外部服务发送 API 调用。这些不是"小心"的情况——它们是完全停止，需要你有意识地在场并刻意说是。

```
以下操作在执行前需要会话内明确确认，无例外：
- 部署或推送到任何环境（staging、production 等）
- 在任何数据库上运行迁移或 schema 变更
- 发送任何邮件、消息或外部 API 调用
- 执行任何具有不可逆外部副作用的命令

"你之前提到过这个"不算确认。我必须在当前消息中说是。
```

##### 19. 锁定你的技术栈

没有定义的技术栈，Claude 会建议它认为最流行的框架、它最常见的库、它默认的包管理器。有时还行。通常不是你用的、不是你团队会的、也不兼容你已经构建的。

```
技术栈——始终使用这些，除非我要求否则不要建议替代方案：
- 语言：[列表]
- 框架：[列表]
- 包管理器：[npm / yarn / pip / cargo / 等]
- 数据库：[列表]
- 测试：[你的测试框架]
- Lint / 格式化：[你的工具]

如果栈中的某些东西看起来不合适，标记出来——但还是用它，除非我另外说明。
```

##### 20. 总是准确展示改了什么

Claude 完成任务，你得扫描输出试图搞清楚什么不同了。哪些文件改了？有没有碰别的？有没有留下未完成的？没有文件级摘要，你每次让 Claude 做事都在手动 diff。

```
完成任何编码任务后，总是以此结尾：
- 改动的文件：[列出每个碰过的文件]
- 修改了什么：[每个文件一行]
- 刻意没碰的文件：[如果相关]
- 后续需要：[任何需要我注意或决定的]

保持简短。这是状态更新，不是重述。
```

##### 21. 让 Andrej Karpathy 的 CLAUDE.md 登顶的4条规则

Andrej Karpathy，前特斯拉 AI 总监、OpenAI 创始成员，识别出了4个让 Claude Code 在编码任务中失败的具体行为。一位开发者将它们提炼为单个 CLAUDE.md 文件中的4条指令。那个文件登上了 GitHub Trending 第一名，将编码准确率从 65% 提升到 94%。

```
1. 问，不要假设。如果某些东西不清楚或定义不足，在写任何一行代码之前先问。永远不要对意图、架构或需求做无声的假设。

2. 最简方案优先。始终实现可能有效的最简单方案。不要添加没有明确要求的抽象、层次或灵活性。

3. 不要碰无关代码。如果一个文件或函数不是当前任务的直接部分，不要修改它——即使你认为可以改进。

4. 明确标记不确定性。如果你对一个方法、一个库的行为或一个技术细节没有信心，在继续之前说出来。没有确定性的自信比承认知识缺口造成更多损害。
```

#### 总结

CLAUDE.md 不仅仅是开发者工具。它是一个永久指令文件，任何认真使用 Claude 的人都应该在第一次正式会话之前设置好。

- **指令 1-4** 修复 Claude 的沟通方式
- **指令 5-8** 阻止它改变你未授权的东西
- **指令 9-11** 给它上下文以产出符合你实际工作的输出
