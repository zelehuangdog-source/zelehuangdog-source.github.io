> **摘要**：本文通过"上下文工程"（Context Engineering）的视角重新审视单文档 RAG 管道，揭示了每个 RAG 答案背后的四种类型化输入：固定系统提示、检索过滤后的行、文档级上下文 JSON、以及将前三者聚合的 PromptContext 容器。作者论证了将 RAG 管道中每个组件（解析、问题解析、检索、生成）视为"类型化上下文发射器"的设计理念，使得整个系统具备可审计性、成本可控性和可组合性。

当单文档 RAG 的四块砖搭建完成时，组装方式就已确定。解析产生关系表。问题解析产生类型化的 `ParsedQuestion`。检索产生过滤后的行子集，外加一份选择审计。生成产生一个带引用证据的 Pydantic 答案。整个流程汇聚于一次 LLM 调用，包含一个固定的系统提示和一段由上游片段组装的用户内容。

这条管道现在有了名字。2025 年 6 月，[Tobi Lütke 发推](https://x.com/tobi/status/1935533422589399127)说*"提示工程"*是错误的框架，并提出了*"上下文工程"*作为替代：*"为任务提供所有上下文以使 LLM 能够合理解决它的艺术。"* 一周后 [Andrej Karpathy 表示认同](https://x.com/karpathy/status/1937902205765607626)，称之为*"用恰到好处的信息填充上下文窗口以完成下一步的精妙艺术与科学。"* 几个月内，这个术语已登上 O'Reilly 图书封面，并被 LangChain 系统化为分类框架。

接下来将通过这个视角来解读单文档 RAG 管道。每块砖发射类型化片段；组装阶段将它们编织进 LLM 调用；系统提示保持固定以支持缓存。给这个实践命名不会改变架构。它改变的是当审计员询问系统如何工作时你如何称呼它，它也告诉读者这个架构正是 2025 年生产团队趋同的那一个。

#### 1. 这个名称，以及它涵盖什么

提示工程（Prompt Engineering）过去指两件相关的事。调整一个提示的措辞来诱导更好的行为，以及编写示例 shot 让模型知道好的输出长什么样。两者都是狭隘的。它们关注的是发送给一次调用的一段文本。

上下文工程涵盖的是一次调用中进入模型上下文窗口的所有内容：

- 系统提示（角色、规则、示例）。
- 检索到的文档或行。
- 会话历史（如果有的话）。
- 工具定义及其输出。
- 记忆、暂存区、智能体状态。
- 关于文档、语料库、项目的结构化元数据。
- 实际的用户输入。

在一个多次调用模型的长时运行智能体中，提示只是六到八个槽位中的一个。其余来自上游的某个地方：检索器、工具、记忆存储、配置文件查询。纪律从*"我应该在提示中写什么"*转向了*"我应该在上下文中组装什么，每个片段来自哪里，以及如何在跨调用时保持组装的稳定性。"*

那就是工程工作。它看起来像软件架构：类型化对象、组件间契约、审计跟踪、缓存。2025 年的这个术语早该出现了，因为这个实践在已运行的生产系统中早已存在。Lütke 和 Karpathy 只是为团队已经在做的事情命了名。

本系列从一开始就是这么做的，一砖一瓦。接下来的章节将逐一讲解每块砖对单文档 RAG 负载的贡献，然后讲解进入 LLM 调用的四种类型化片段以及生成每个片段的代码。语料库、会话和工具调用的场景在最后作为超出范围的工作提及，并指出系列中将在何处解决它们。

#### 2. 每块砖都发射类型化上下文

*四块砖发射类型化上下文通道，汇聚到顶部的组装带，在那里 PromptContext、固定系统提示和用户模板在 LLM 调用前组合。– 作者配图*

上面的架构图是本系列已交付内容的回顾。每块砖都是一个类型化上下文发射器。方框上的名称就是代码中实际 Pydantic 类和 DataFrame 的实际字段名。

**解析发射关系表和一个合成字典。** `line_df` 每行一条记录，带边界框。`page_df` 每页一条记录，包含类型和列数。`toc_df` 存放目录条目，包含起始页和深度。`image_df` 存放内嵌图片，包含感知哈希和元数据。`parsing_summary` 是文档级合成：`doc_type`、`n_pages`、`typical_fields`、`summary`，加上机制字段。检索砖消费逐行表。问题解析砖通过 `DocContext` 消费 `parsing_summary` 的语义子集。

**问题解析发射一个 `ParsedQuestion`。** 它的字段不是自由格式的。`keywords` 是用于检索的内容名词短语短列表。`intent` 是从固定枚举中选出的字面量标签，驱动生成阶段的形态分派。`structural_hints.pages_hint` 在用户说了*"在第 3 页"*时携带锚定页。`answer_shape` 携带预期输出形态（text、amount、date、list、table、address）用于生成阶段的 schema 查找。每个字段被不同的下游砖消费。它们都不作为原始字符串传递给 LLM。

**检索发射一个过滤后的 DataFrame 和一个审计字典。** `filtered_line_df` 是生成砖看到的 `line_df` 子集。`anchor_pages` 是被保留的页面 ID 及其原因。`retrieval_audit` 携带获胜的方法（keyword、TOC、LLM 仲裁器）、适用时的 LLM TOC 推理、以及选中的章节。过滤帧是 LLM 阅读的内容。审计是审计员阅读的内容。

**生成是消费者，不是发射器。** 它接收问题、过滤后的行、`PromptContext` 和答案 schema。它调用 LLM。它返回一个 Pydantic 类型化答案。生成方框上的虚线边框标志着这个角色。

右侧紫色的"PROMPT ASSEMBLY"区域是上下文工程作为代码发生的地方。本系列通过三个原语实现它：

- 一个 `PromptContext(BaseModel)` 聚合器，每个上游上下文源有一个字段：`doc_context`、未来的 `corpus_context`、未来的 `project_context`。
- 一个模块级固定的 `MODULE_SYSTEM_PROMPT`，供每个调用 LLM 的砖使用。
- 一个带命名占位符的 `MODULE_USER_TEMPLATE`，砖通过 `str.format(...)` 填充。

第 1 篇（最小四砖 RAG）将砖作为流程介绍。第 6A 篇（问题解析论文）使问题解析器类型化。第 8A 篇（类型化生成契约）使生成 schema 类型化。本文通过*"每块砖贡献什么上下文，它们如何在不互相污染的情况下到达 LLM 调用"*的视角来解读同样的四块砖。同样的代码，不同的视角。

#### 3. 单文档负载的四种类型化片段

单文档 RAG 的 LLM 调用中包含四个片段，每个由不同的代码生成，每个有不同的成本与缓存特征。本节按它们在 LLM 读取的用户内容中出现的顺序逐一讲解。

##### 3.1 固定系统提示

第一个片段是系统消息。角色描述、规则、示例。它不会跨调用变化。本系列将其写为模块级 Python 常量，然后作为带默认值的关键字参数暴露，这样调用者可以按领域覆盖而无需 fork：

```python
PARSE_QUESTION_SYSTEM_PROMPT = (
    "You extract content noun phrases from the user's question..."
)

def parse_question(question, *,
                   system_prompt: str = PARSE_QUESTION_SYSTEM_PROMPT,
                   user_template: str = PARSE_QUESTION_USER_TEMPLATE,
                   context: PromptContext | None = None):
    ...
```

两个运营层面的影响。提示是**可缓存的**，因为它在同一模型的跨调用中不变。缓存输入在公布费率的提供商处大约比新鲜输入便宜十倍。并且提示是**可审计的**，因为它存在于一个稳定的 Python 符号上，审计员可以 grep、版本化，并在版本间 diff。

##### 3.2 检索过滤后的行

第二个片段是 LLM 实际阅读的行。分派器消费 `ParsedQuestion.keywords` 和 `structural_hints`，选择一种方法（keyword、TOC、LLM 仲裁器），返回过滤帧加审计。用户内容得到的是过滤帧；审计保存在磁盘上供运维人员稍后检查：

```python
retrieved, filtered_line_df, audit = dispatch_page_retrieval(
    question, line_df, page_df,
    toc_df=toc_df, keywords=keywords,
    top_k=5, use_toc=True,
)
```

发送给 LLM 的用户内容是过滤帧，而非整个文档。一份 200 页的合同变成十页相关行。用户内容保持在几千个 token 以内。审计解释了为什么每页被选入，这样调用者可以在不重新运行调用的情况下质疑选择。

##### 3.3 文档上下文块，紧凑 JSON

第三个片段是文档级合成：文档类型、页数、典型字段、摘要。它以紧凑 JSON 对象的形式进入用户内容，让 LLM 可以根据文档性质来限定模糊措辞的范围。本系列将其实现为每个携带上下文的 Pydantic 类上的方法。`DocContext.as_prompt_json()` 构建仍然命名四个字段的最小 JSON；null 和空值被丢弃：

```python
class DocContext(BaseModel):
    doc_type: str | None = None
    n_pages: int | None = None
    typical_fields: list[str] = []
    summary: str | None = None

    def as_prompt_json(self) -> str:
        payload = {k: v for k, v in self.model_dump().items()
                   if v is not None and v != []}
        return json.dumps(payload, separators=(",", ":"))
```

在一份 `doc_type="resume"`、`n_pages=1`、四个典型字段的简历上测量，负载不到 200 字符。在一份每个字段都是 null 或空的未知文档上，负载是空对象 `{}`，该块从用户内容中被完全省略。当后续文章激活预留的 corpus-context 和 project-context 槽位时，同样的模式适用。

##### 3.4 包装上述三者的 PromptContext 聚合器

第四个片段是聚合器。每个调用 LLM 的砖接收一个可选的 `context: PromptContext` 关键字参数。聚合器今天在自己的类型化槽位中携带 doc-context，同时为后续文章将激活的 corpus-context 和 project-context 预留了槽位。辅助函数 `render_context_block(context)` 遍历非 null 字段，在用户内容的头部为每层发射一个带标签的 JSON 块：

```python
class PromptContext(BaseModel):
    doc_context:     DocContext | None = None
    # corpus_context:  CorpusContext  | None = None  # reserved
    # project_context: ProjectContext | None = None  # reserved
```

每个 LLM 砖接收一个可选的 `context: PromptContext` 关键字参数。辅助函数 `render_context_block(context)` 遍历每个非 null 字段，渲染其紧凑 JSON，并为每层发射一个带标签的块。添加一个新层意味着取消一个字段的注释，在辅助函数中添加两行代码，每个砖就免费获得了新层。签名在跨版本中保持稳定。

#### 4. 实践中的变化

给这个实践命名改变了三件运营层面的事情，即使代码不变。

**审计。** 当答案错误时，问题不再是*"提示说了什么。"* 问题变成了*"那次调用的上下文窗口中进入了什么。"* 本系列将每个砖的输出持久化到磁盘：`parsing/`、`questions/<hash>/parsed_question.json`、`retrieval/<hash>/retrieved_pages.parquet`、`retrieval/<hash>/retrieval_audit.json`。审计员从这些文件重建上下文负载。然后问题变得具体：doc\_context 是否错误、是否选错了页面、系统提示是否在版本间漂移、用户模板是否过时。每个问题都有不同的修复方案。

**成本。** 两个杠杆叠加。系统提示在同一模型的跨调用中是固定的，所以它支付缓存输入费率。用户内容通过 `as_prompt_json` 压缩并通过检索选择，所以可变部分很小。在 100 份文档各 10 个问题的语料库上，主导成本是可变部分乘以 1000 次调用。命名这个实践不改变数学，但它使每次调用的预算清晰可读：上下文负载中的每一行都有一个可以指向的生成器。

**跨后续工作的可组合性。** `PromptContext` 聚合器今天激活了一个字段，另外两个为系列后续添加的 corpus-context 和 project-context 层预留。当它们到来时，本文不需要重写。签名保持不变。`render_context_block` 的函数体增长一个分支。每个已经接收 `context: PromptContext | None` 的砖免费获得新的子上下文。这种纪律在延迟跨版本破坏方面获得回报。

#### 5. 超出范围，附指引

单文档场景到此为止。上下文工程在更大范围内涵盖三件本文未触及的事情：

- **语料库上下文。** 当答案需要跨多文档阅读时，LLM 需要感知*哪些文档在范围内以及它们有什么共同点*。这将存在于未来的 `CorpusContext` Pydantic 中，由每文档 `parsing_summary` 值的聚合器填充。槽位在 `PromptContext` 中已预留，使砖的签名不变。后续文章将讲解构建和消费者接线。
- **会话历史。** 多轮对话携带先前的问答对，LLM 在回答新问题前应考虑它们。这是一个状态问题（历史存在哪里、何时摘要化、何时裁剪）叠加在上下文问题之上。系列后续文章将其视为一等砖处理。
- **工具调用。** 智能体循环将工具定义、工具输出和中间状态带入上下文窗口。选择/压缩/隔离问题在那里变得更尖锐，因为上下文窗口在跨轮次中很快填满。系列后续文章将 agentic 上下文工程作为独立主题处理。

[LangChain 博客](https://blog.langchain.com/context-engineering-for-agents/) 命名的四种典型策略（*write*、*select*、*compress*、*isolate*）是针对智能体循环开发的。其中两种（write 和 select）干净地映射到单文档场景，分别对应系统提示和检索分派器。另外两种（compress 和 isolate）在精神上适用，但一旦语料库和会话进入画面就变得更加棘手，这也是本文不强行套用四路映射的原因。

#### 6. 结论

2025 年业界围绕*上下文工程*的对话，为单文档 RAG 已经逐砖实践的纪律赋予了一个名字。解析发射关系表和文档级合成。问题解析发射类型化的 `ParsedQuestion`，其每个字段各自驱动不同的下游砖。检索发射过滤行集加审计。生成通过固定系统提示、模板化用户内容和每上游层一个类型化槽位的 `PromptContext` 聚合器来消费组装的负载。

改变的是标签：审计员、招聘经理或阅读架构的供应商可以将其放入 2025 年的词汇表中，无需进一步翻译。砖块、schema 和成本对缓存的权衡不变。语料库、会话和工具调用场景作为后续工作出现，每个都有自己的类型化槽位预留在同一聚合器中。

分类框架对比。

- Lance Martin：智能体循环的四种策略（*write*、*select*、*compress*、*isolate*）。单文档 RAG 干净地映射前两种；另外两种在语料库和会话进入画面后变得更棘手。
