#### 开场与背景

大家好，欢迎来到这次工作坊，今天座无虚席，很高兴看到这么多人。我叫 Ara，是应用 AI 团队的架构师。今天我要分享的是我们在 Anthropic 内部如何使用 Claude Code，并带大家做一次动手实践。

今天的内容基于 Tar 大约一周半前在旧金山做的那个演讲——**"HTML 文件的不合理有效性"（The Unreasonable Effectiveness of HTML Files）**。他的核心观点是：我们正在从 Markdown 文件迁移到 HTML 文件来编写规格说明。

#### 为什么需要改变工作方式

现在大家应该都注意到了——Agent 正在变得越来越强大。为什么？因为底层模型在变得越来越强大。模型越强大，Agent 就能运行更长时间，你就能交给它们更复杂的任务。但这也意味着我们必须改变工作方式、改变习惯。

如果你让 Agent 运行更长时间，当它做错事时会烧掉大量 token，你希望在一开始就避免这种情况。**这就是把验证前置到 HTML 规格说明中的核心动机**——因为 HTML 是一种更丰富、对人类更友好的方式来审查 Agent 即将为你构建的内容。

#### 核心理念：苦涩的教训

这里有一个类比来自 Richard Sutton 的"苦涩的教训"（The Bitter Lesson）。Sutton 本质上是强化学习之父，他的核心观点是：你可以花大量时间用人类智慧去硬编码和约束系统，但最终灌入更多数据和更多计算所获得的能力，会超越你能想到的任何方案。

**类比到当下**：模型越来越强大，你应该接受一个事实——模型可能比你更擅长从你身上提取需求，而不是你自己去定义需求。需求潜藏在你内心——就像你跟用户打交道一样，用户看到东西时知道对不对，但往往说不清楚自己要什么。同样地，你看到结果时知道想要什么，但 Claude 比你更擅长把它从你脑子里挖出来。

#### 三个层次

今天我们关注三个层次：

##### 第一层：让 Claude 采访你（去除歧义）

**坏的提示词**：直接说"让它变好"或"不要犯错"——很多人就是这样用 Claude Code 的，这不是好的提示方式。

**好的提示词**：鼓励 Claude 从你身上提取具体细节。不要过度指定结果，而是指定你关心的领域。比如聚焦受众、用开放式问题引导 Claude 进行迭代式访谈。

关键技巧：在 prompt 中**显式引用 `ask user question` 工具**，这会触发 Claude 用交互式问答工具逐轮向你提问。根据你 prompt 的质量，你会得到更好的结果。

##### 第二层：HTML 规格说明（取代冗长的 Markdown）

我的一位同事曾说过："Markdown 文件是 AI 原生软件开发生命周期的通用语言。"这话挺诗意的，但这种格式正变得越来越受限——Markdown 文件太长了，读不完。

**HTML 文件的优势**：
- 信息密度更高
- 对人类更友好——你能直观看到最终效果
- 可以配合截图使用，也可以用 Playwright MCP 交互
- 比起从 Markdown 文件推断最终效果，HTML 让你能直接**看到**它

如果 Markdown 文件超过 200 行，你大概率不会读完，你的同事更不可能读。

**实践示例**：我让 Claude（Opus 4.7）为一个账单拆分 App 生成了四个不同的设计方向，输出为 HTML 文件——一个 Brutalist 风格、一个东京金融科技风格等等，完全不同的美学风格。我可以在这些方向之间点击切换，这比从 Markdown 推断外观好太多了。

##### 第三层：验证框架（Agent 原生验证）

这是最重要的部分。核心问题是：**如何将验证嵌入到制品本身，使其对 Agent 原生可测？**

#### 验证框架详解

我们用一个 React 写的 Todo 应用作为示例，展示了三种验证方式：

##### 1. 人类可读的验证仪表盘

组件将自身状态发布到 DOM——通过 `data-verify-*` 属性暴露 total、done、active 等状态。当你添加/完成 todo 项时，这些数据属性会实时更新。

**关键设计**：将状态以 DOM 数据契约的形式暴露，而不是让 Agent 去抓取内部 DOM 结构。这样验证可以独立于应用内部状态运行。

每个组件都有：
- **Schema**（数据模式）
- **Fixtures**（测试数据/已知状态）
- **Invariants**（不变量——必须始终成立的条件）
- **Probes**（探针——推离快乐路径的测试）

##### 2. Agent 驱动的验证

Claude 通过 Playwright MCP 连接浏览器，读取 DOM 中发布的状态数据，自动运行验证清单。它可以：
- 读取验证步骤的 manifest
- 逐个执行验证
- 发现并诊断失败原因

演示中我们故意硬编码了一个会失败的验证（3 + 4 ≠ 10），让 Claude 去发现并解释为什么失败。

##### 3. CI 无头运行

直接运行 `bun verify`，执行完整的测试矩阵——适用于 CI 环境。

##### 录制与存证

你可以录制验证过程的视频片段，存储到 S3 或分享给同事。**Claude Code 团队目前就是这样工作的**——所有前端变更都会录制验证视频作为证据，尤其是在当前高速发布的节奏下。

#### 实用建议

##### Claude Code 设置推荐

- **Auto mode**：必须开启——如果你还没用 auto mode，现在就开
- **Fast mode**：花费更多但迭代速度更快，非常适合快速迭代规格说明
- **Effort 参数**：推荐设为 `x-high`
- **模型选择**：用 **Opus 4.7**，因为它的视觉模型更强——这对 HTML 规格说明的工作流至关重要；不建议用 Sonnet

##### 截图反馈

如果你在做前端开发，经常给 Claude 截图是非常好的习惯。因为有时候很难用语言描述"这里有点偏"或"对齐不对"，而 Opus 4.7 更强的视觉能力可以直接从截图中理解问题。

##### HTML 规格说明的 token 效率

有人会问 HTML 规格说明是不是比 Markdown 更费 token？答案通常是**否**。原因是：虽然单次生成 HTML 可能花更多 token，但长期来看你的迭代次数会更少——因为一个好的、丰富的 HTML 规格说明大大减少了返工。

#### 总结

三个核心实践：

1. **让 Claude 采访你**——Agent 运行越久，规格说明就要越全面；让 Claude 从你身上提取需求比你自己定义更好
2. **用 HTML 替代 Markdown**——更高信息密度、更好的人机交互
3. **将验证嵌入制品**——三个验证表面：人类仪表盘、Agent 浏览器驱动、CI 无头运行

这些不是什么全新的原语——它们是你已经在用的东西的重新组合，只不过重新编排成了 Agent 优先（Agent-first）的形式。这就是 Claude Code 团队目前的工作方式，也是方向所在。
