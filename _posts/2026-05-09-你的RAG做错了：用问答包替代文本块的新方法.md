#### 摘要

本文指出传统 RAG 管道中"文本块（chunk）作为知识单元"这一从未被审视的假设，是大多数检索失败的根源。文本块没有语义边界、版本上下文和访问控制，导致检索到半张表、过时内容、或缺乏上下文的断言。作者提出用**问答包（Question-Answer Packet）**替代文本块作为嵌入单元——每个单元包含一个问题、一个经过验证的答案以及治理元数据。这种方法在实测中实现了语料库缩减 40 倍、每次查询 token 减少 3 倍、向量检索相关性提升 2.3 倍的效果，且无需更换检索算法、重排序器或嵌入模型。文章详细介绍了 Blockify 的七阶段处理管道，从文档摄入到语义去重再到人工验证的完整流程。

#### 你的 RAG 做错了

有一种新方法：

- 语料库缩减 40 倍
- 每次查询 token 减少 3 倍
- 向量搜索相关性提升 2.3 倍

而且它不碰你的检索算法、重排序器或嵌入模型。它修复的是上游一个几乎没人审视的东西。

#### 为什么文本块是个糟糕的知识单元

每个 RAG 管道都始于同一个假设：一段文本是正确的知识嵌入单元。

这个假设几乎从未被审视过。而它恰恰是人们试图在下游修复的大多数检索失败的根源。

一段文本是一个结构中性的容器。它对以下信息一无所知：

- 其中的思想从哪里开始、到哪里结束
- 它来自文档的哪个版本
- 谁有权查看它

由于文本块没有语义边界，分割器在 token 数耗尽的地方直接切断。

你最终检索到的是半张表格、没有论证的结论、或者被剥离了使其成立的上下文的断言。模型无法知道缺失了什么。

##### 版本问题同样严重

大多数企业语料库在 SharePoint、Confluence 和 Git 中有十几个几乎相同版本的同一文档。

Top-K 检索返回同一段落的五个副本，当前版本和已弃用版本混在一起。LLM 将它们混合成一个自信但错误的答案。

##### 访问控制的缺失

由于文本块不携带元数据，无法在数据本身中附加访问控制。角色过滤、版本状态、权限级别——所有这些最终都作为逻辑附加到编排器上，与它应该治理的内容脱节。

LangChain、LlamaIndex 和 Haystack 坐落在这一切之上。它们编排从向量存储中检索，无论你放了什么进去。

大多数技术栈在文档解析器和向量存储之间什么都没有。这个空白正是三个问题叠加的地方。

#### 更好的单元：问答包

文本块之所以失败，是因为它在结构上是不可知的。修复方法是使知识单元在结构上变得显式。

不是嵌入一段散文窗口，而是嵌入一个断言：一个问题、其经过验证的答案，以及作为类型化 schema 的治理字段。

**每个单元一个事实，仅此而已。**

你的查询本身就是问题。当你的索引存储的是问题的答案时，匹配变成了结构性的，而非仅仅是语义性的。

你不是希望正确的段落浮到顶部。你是在直接将问题匹配到其答案。

Blockify（来自 Iternal Technologies 的预处理层）将此实现为一种称为 **IdeaBlock** 的结构：一个问题、其经过验证的答案，以及类型化的治理字段（如权限级别、版本状态和来源），所有字段都在同一个对象上。

**关键洞察**：当你嵌入一个问答包而非文本窗口时，你的嵌入表示的是单个原子断言，而非恰好包含该断言的一段叙事。

这对向量几何有可衡量的影响。

在 Blockify 针对 17 个文档和 298 页的内部基准测试中，查询到最佳匹配块的平均余弦距离：IdeaBlock 为 0.1585，朴素文本块为 0.3624。

**检索距离降低了 2.29 倍。**

#### 反直觉的发现：更少的数据，更高的准确性

大多数人预期缩减语料库会损害检索。但语义蒸馏并非如此。

在 Blockify 的内部基准测试中，管道从源文档产生了 2,042 个原始 IdeaBlock。

经过 3-5 轮 80-85% 相似度的迭代去重：

- 2,042 个块折叠为 1,200 个规范 IdeaBlock
- 词数从 88,877 降至 44,537
- 蒸馏后的数据集在向量准确度上优于未蒸馏版本 13.55%

**原因**：冗余副本反而有害——同一段落的十五个近似副本在嵌入空间的同一区域创建了十五个竞争向量。检索将概率质量分散到所有副本上，拉低了规范版本的匹配分数。将它们折叠为一个规范块，信号就会增强。

你的向量索引不是你想填满的硬盘。它是一个检索表面，冗余会降低其性能。

#### 处理管道：从文档到 IdeaBlock

修复方案是一个在任何内容进入向量存储之前运行的预处理管道。

Blockify 的处理分为七个阶段。每个阶段都有明确的输入和输出，因此故障可定位且可复现。

##### 阶段 1：范围定义

在解析任何文档之前，定义索引层次结构：组织 > 业务单元 > 产品 > 角色。

这决定了哪些块被标记到哪个访问层级，并影响后续去重的运行方式。

##### 阶段 2：摄入

文档以 DOCX、PDF、PPT、PNG/JPG、Markdown 或 HTML 格式进入。

解析器交给 LLM 层，运行微调后的 LLaMA 3/QWEN 3.5/Gemma4（及其他自定义基础模型变体），将原始块转换为草稿 IdeaBlock：一个关键问题、一个两到三句话的经过验证的答案，以及类型化的治理字段。

输入大小限制在 1,000 到 4,000 字符之间，实际中位数为 2,000。

##### 阶段 3：分块与提取

上下文感知的分割意味着 LLM 将块转换为草稿 IdeaBlock，而非仅仅按 token 数切割。每个块的输出是一个问答对，而非一段散文窗口。

##### 阶段 4：语义去重

这是检索表面被清理的地方。

块按余弦相似度在 80-85% 阈值下进行 3-5 轮迭代聚类。近似副本通过第二个专门调优的 LLM 合并为单个规范块。管道针对 GPU 优化，但也可以通过 Intel Xeon 优化版本在额外 CPU 容量上运行。

结果是一个数据集，其中索引中的每个向量代表一个独立断言，而非十五个争夺同一检索槽位的近似副本之一。

##### 阶段 5：自动标记

每个块接收类型化元数据：权限级别（PUBLIC、INTERNAL、CONFIDENTIAL、SECRET）、版本状态（Current、Deprecated、Draft、Approved）、产品线、出口管控标志和数据隐私标签。由管道而非文档作者应用。

##### 阶段 6：人工验证

一个包含 2,000 到 3,000 个 IdeaBlock 的产品语料库分配给 5 到 10 个主题专家（SME），每人每季度花 1-2 小时处理自己负责的部分。验证的是带有来源引用的结构化断言，而非原始文档。

##### 阶段 7：导出

经过验证的块通过 API 推送到向量数据库或导出为 JSON-L。支持的向量存储：Azure AI Search、Pinecone、Milvus、Vertex Matching Engine。支持的嵌入模型：OpenAI、Bedrock、Mistral、Jina、开源模型。

管道位于文档解析器和向量存储之间，无论使用哪种组合。

#### 应用层的变化

你嵌入的单元决定了应用层能做什么。

##### 查询构造变得更简单

你的查询本身就是问题。当索引存储的是问题的答案时，匹配是结构性的而非概率性的。你不再需要调整相似度阈值来弥补查询形状和文档形状之间的语义不匹配。

##### 治理进入数据层

基于角色的访问、版本状态、权限级别是每个块上的类型化字段，而非附加到编排器上的逻辑。一个销售工程师和一个法务审查员查询同一个索引时获得不同的数据集，不是因为检索层过滤了它，而是因为块本身携带了访问边界。

##### 更新从单条记录传播

当规格说明发生变化时，你更新一个 IdeaBlock。查询该块的每个应用在下一次请求时获得修正后的答案。使用朴素分块时，同一事实存在于多个文档中数十个近似副本的段落里。更新它意味着找到所有副本，这在企业规模下不是一个可行的问题。

架构不改变你的查询方式。它改变的是你能多信任答案。

#### 根本原则

文本块是一种解析便利，后来成了检索假设。

它没有语义边界、版本上下文或访问状态。检索技术栈花了多年修补这种不匹配：重排序器、混合搜索、阈值调优、提示工程。

所有这些都在真正问题的下游。

修复方案不是更好的检索算法，而是更好的单元。

RAG 技术栈正在解析和向量化之间长出一个蒸馏层，就像 Web 技术栈在源服务器和浏览器之间长出了 CDN 层一样。

你可以用聚类、基于 LLM 的摘要和 schema 强制来自己构建它。或者使用为此专门构建的工具如 Blockify。

无论哪种方式，**文本块作为单元的假设就是 bug**，在数据层修复它比调优检索带来的回报更大。
