> **摘要**：Claude Code 提供了两个看似都能"让答案变得更好"的设置——模型（model）和努力程度（effort），但二者作用的机制完全不同。模型决定的是一套固定权重，权重里编码了 Claude 在训练时学到的全部知识，请求时只读不写；effort 则决定 Claude 在这套权重之上愿意为这次请求做多少工作，包括读多少文件、验证到什么程度、多步任务要推进多远才向你确认。文章给出一条简单的排查思路：当 Claude 给出错误答案时，先检查上下文是否给够，再问自己"它是没试够，还是不够懂"——不够懂是模型问题，该换更大的模型；没试够是 effort 问题，该调高努力程度。文中还用"专家—通才—专才"的比喻说明 Fable、Opus、Sonnet 在能力与耗时上的权衡，并指出 effort 只是决定 Claude 愿意在能力曲线上走多远，并不代表它一定会走到那么远。

Claude Code 给了你两个设置，二者看起来都能"让答案变得更好"：模型（model），以及努力程度（effort）。但它们究竟对输出做了什么？你又该如何判断该换一个模型，还是只需要调整努力程度？人们很容易想当然地认为，选择像 Fable 这样更大的模型会比 Sonnet 给出更聪明的输出，而更高的努力等级只是意味着 Claude 在回答前会想得更久。

第一个假设是对的。按照行业标准的基准测试，我们最大的模型确实**能力更强**。

但 effort 的含义远不止"思考时间"。effort 控制的是 **Claude 在你的请求上整体做了多少工作**。这不仅包括它思考了多久，还包括：

- 它读了多少个文件；
- 它验证到什么程度；
- 在多步任务中，它会推进多远才回来找你确认。

在更高的 effort 下，Claude 会在给你反馈之前多做这些动作（读文件、跑测试、反复核对）。而在更低的 effort 下，它更倾向于向你要更多上下文，而不是自己花 token 去摸索答案。

#### 模型选择的工作原理

要理解模型设置到底控制了什么，最好从最开始说起——从你按下回车的那一刻。

Claude Code 会把你的消息，连同系统提示词、工具定义、你的 CLAUDE.md、对话历史，以及上下文中的任何文件，一起打包。所有这些内容作为一个请求发送给 API。

Claude Code 拥有的一切信息都被打包进一个 API 请求。在服务器端，文本会在到达模型之前先被分词。

不过，模型从来不会以纯文本的形式看到这些内容。服务器上发生的第一件事是分词（tokenization）：文本被切成一个个片段，每个片段被映射为模型训练时所用固定词表中的一个整数。`const` 可能映射为 1978，`await` 可能映射为 4293。从这一步开始，**你的 prompt 就变成了一个整数数组**。

分词器把你的文本切成片段，并将每个片段映射为固定词表中的一个整数。上排每个片段对应下排的 token ID；图中 ID 仅为示意。

模型的工作是接收这个数组，并预测下一个会出现的 token 是什么。它的做法是为词表中的每一个 token 计算一个概率，再从概率最高的那些里挑选。在 "const x = await" 之后，一个训练良好的模型会给 "fetch" 分配很高的概率（非常可能），而给 "banana" 分配接近零的概率（几乎不可能）。

模型的预测其实是词表中每一个 token 的概率。排名第一的猜测和一个毫不相关的猜测之间，概率差距是巨大的。

真正把输入 token 转化为这些概率的，是权重（weights，也叫参数）：数十亿个数字，组织成巨大的矩阵。为了预测一个 token，模型会让你的输入经过这些矩阵（一长串矩阵乘法），并在最后读出概率。**模型"知道"的一切，都存在于这些权重之中**。

每个模型的权重都是在训练阶段确定的，等到你发送请求的时候，**它们是只读的**。你的 prompt、你的 CLAUDE.md，或者你的上下文，都不会改变它们。如果你遇到过"推理"（inference）这个词，它指的就是这件事：在训练结束、权重固定之后使用模型。

你的 prompt 进去，概率出来。中间的权重不会变化。

Claude 关于 TypeScript、流行框架，或任何其他通用编程知识的一切，都是在训练时被编码进这些权重里的。

你的 prompt 和上下文依然能引导预测的方向。把你的真实代码放在 Claude 面前就是一种引导，而且效果很好。但这并不会给权重本身增添任何东西。

如果某个库在模型训练时还不存在，它就不会出现在权重里。你可以把文档放进上下文，Claude 会去使用它，但那是**引导，而不是教学**。Claude 的响应只在这一次请求中受到影响，底层模型并没有真正"记住"任何东西。

当 Claude 自信满满地调用一个根本不存在的 API（也就是所谓的幻觉）时，那是权重根据训练时学到的模式生成了一段看似合理的 token 序列，而不是一次查找失败。

那么，切换模型到底改变了什么？它**替换的是处理你这次请求的那一套固定权重**。

模型不会一次性生成整个答案。它预测一个 token，把它拼接到序列末尾，然后重新跑一遍整个计算来得到下一个 token。一个 200 个 token 的回复，意味着权重被完整地过了 200 遍。这个循环正是你大部分等待时间（以及大部分输出成本）的来源。

序列每一步恰好增长一个 token。模型每次都要重新读取整个数组，才能预测接下来会出现什么。

模型设置决定的是哪一套权重来处理你的请求，同时也决定了每个输出 token 的成本。

它**不**决定的是**会生成多少个 token**。对于同一个 prompt，这个数字可以有很大差异，具体取决于 Claude 决定要做多少工作。

而这，恰恰就是 effort 所控制的东西。

#### effort 的工作原理

在 Claude Code 处理任务的过程中，它生成的 token 大致可以分为几类：

- **思考（Thinking）**：你在动作之前、动作之间看到的那些流式输出的推理内容。
- **工具调用（Tool calls）**：命名了某个工具（如 Read 或 Edit）及其参数的结构化代码块，Claude Code 随后会解析并执行它。
- **给你的文本（Text to you）**：计划、进度更新，以及结尾的总结。

这些其实都是同一个循环里产生的普通输出 token，按同样的价格计费。举例来说，思考 token 的生成方式和其他输出 token 完全一样，并且会在这一轮对话剩余的时间里一直留在上下文中。

等到 Claude 开始写代码时，它之前的推理内容已经成为了输入的一部分，就像它读过的一个文件一样。

Claude 的所有输出都是 token。思考、工具调用，以及给你的文本，都产自同一个循环。

那么 effort 到底改变了什么？effort 等级会**作为请求的一部分被发送给模型**，就紧挨在你的 prompt 旁边。模型在训练时就学会了如何在每个 effort 等级下行事，而这种习得的行为已经固化在了那些冻结的权重里。

当你的请求到达时，effort 只是模型要响应的又一项输入，就像它会响应你的 prompt 文本一样。它设定的是：在 Claude 认为任务完成之前，需要做到多彻底、多有把握。这个权衡会在每一轮都重新进行，而更高的确定性需要消耗更多的 token 才能达到。

同一个 prompt，两种 effort 等级。高 effort 路径为了达到更高把握的答案，生成的 token 数量大约是低 effort 路径的 7 倍。

在更高的 effort 等级下，Claude 通常会先制定一份计划，effort 等级会影响这份计划的深度和广度。但这份计划并非一成不变。随着 Claude 从它执行的动作中拿到结果，它会不断更新自己对"已经取得多少进展"以及"当前结果有多大把握"的判断。

当一个包含三个假设的排查计划在第一步就找到了 bug 时，"继续排查假设 2 和假设 3"可能就没有必要了。Claude 通常会明确说出这一点（例如"第一项检查就已经找到问题了，剩下的检查不再需要"），然后直接跳过。你在 Claude Code 中看到任务清单在运行过程中被重新调整时，看到的就是这种情况。

更高的 effort 确实会让 Claude 更倾向于反复核对，比如验证已经找到的答案，或者仍然去排查本可以跳过的那些假设。不过，它通常不会仅仅因为 effort 被调高，就在一个简单任务上人为地虚增用量。"过度思考"正是我们团队在模型训练中专门会去关注和抑制的问题，因为它会损害有效性。

#### 如何选择 effort 等级

对大多数任务而言，**使用模型的默认 effort 等级**就好。默认等级正是 Claude 将 token 用量控制在大多数人愿意为一项任务花费的水平上的那个点。

可以把 effort 想象成一个手动的覆盖开关，用来控制 Claude 工作的强度和时长。只有当你基于自己的领域或工作类型，对彻底程度或速度有明确的偏好时，才有意欣主动去调整它，并且把它当作一种整体性的偏好，而不是逐个任务去决定的事情。

一个来自 Opus 4.8 发布后的实践性提示：根据我们的测试，在同一个任务上，Opus 4.8 默认 effort 等级下产出的结果，要优于 Opus 4.7 默认 effort 等级下的结果，而消耗的 token 数量大致相同。

#### 当 Claude 做错时，该改什么

当 Claude 做错某件事时，你的第一反应不应该是去改某个设置，而应该是回头看看你给它的上下文。你的 prompt 是不是太模糊了？Claude 是不是连接了正确的工具？它是不是拥有恰当的 skill？

如果你正在为一个原本不需要那么高 effort 的任务调高 effort，那么真正该修的地方通常在上游：你的上下文、你的 CLAUDE.md，或者任务本身的范围界定。

但假设你已经给出了清晰的上下文，Claude 依然做错了。这时候该问自己的问题是：**它是没有** **试** **得足够狠，还是不够** **懂**？

**模型：问题本身太难**

当问题真正困难时——比如隐蔽的 bug、不熟悉的领域、架构决策——就该选更大的模型。当较小的模型无论你给多少上下文都会自信地给出错误答案时，你需要的正是更大的模型。

更大的模型也更擅长处理模糊性。而在较小的模型上，具体、能直接指导执行的指令才是成功的更优配方。

当工作是常规性的——你能精确描述的编辑、机械式的改动、关于已经在上下文里的代码的问题——就该选更小的模型。没有理由为任务用不到的能力付费。

如果 Claude 拥有了所有相关上下文、明显尽力去做了，却依然做错，那就是该换更大模型的信号。而如果你已经在用更大的模型，且这项工作持续都是常规性的，降级到小模型会提升速度，通常还能在不影响输出质量的前提下降低成本。

**effort：Claude 没有试得足够狠**

如果 Claude 做错是因为不够努力——跳过了某个文件、没有跑测试、没有反复核对自己的工作——那就该调高 effort 等级。这一点在你之前把 effort 设得低于模型默认值时最为相关。

#### 专才、专家与通才

我喜欢用这样的方式来理解这两个设置：Fable 是一位能处理几乎没人能解决的问题的专才，Opus 是专家，而 Sonnet 是一位非常出色的通才。effort 等级决定的是他们三人中的任何一位会在你的任务上花多少时间。

低 effort 下的 Opus，就像你花五分钟请教一位在你这类问题上经验深厚的专家。他们带来的知识是你的代码库里完全找不到的：见过的模式、知道该排查的坑，以及那种只有解决过大量类似问题才能积累出来的经验。但五分钟意味着快速浏览一遍你的代码，而不是逐个文件仔细过一遍。

高 effort 下的 Sonnet，则是那位有一整个下午时间的通才。他们非常擅长写代码，会读遍所有内容、跑各种检查、反复核对自己的工作，最终对你的具体代码建立起扎实的理解。

Fable 是那位在所有人都卡住时才会被叫来的专才。哪怕在低 effort 下，他们也能一眼看出别人都发现不了的问题。而那种洞察力，恰恰是你付出最多成本去换取的东西，所以值得把它留给真正需要的任务。

这几个设置里没有哪一个是"绝对更好"的。模型设置大致对应**能力有多强**；effort 设置大致对应**做事有多彻底**。大多数真实任务，两者都需要一些。

#### effort、模型与 token 消耗

那么模型选择、effort 和 token 消耗之间到底是怎么互动的？这取决于具体任务。

在同样的 effort 等级下处理常规工作时，大模型和小模型通常都能做对。大模型会因为额外的验证步骤消耗更多 token，且单价更高。这就是为什么在常规工作上降级到小模型，能在不损失质量的前提下真正省钱。

图中曲线仅为示意，展示的是一个足够简单、两个模型都能快速完成的单一任务，并不代表真实的基准测试数据。

而在更困难的多步骤工作上，情况会反过来。小模型不得不在自己能力的极限附近艰难推进，消耗大量迭代次数；而大模型能用更少的步骤达到同样的质量标准。

你为大模型的每个 token 付出了更高的单价，但在真正能拉伸小模型能力极限的任务上，整个任务的总成本反而可能更低。而更重要的是：大模型能完成小模型无论在哪个 effort 等级下都完成不了的任务。

这一点在 Fable 身上体现得最为明显。在长链条、多步骤的工作中，它领先得最远。在我们的测试中，它完成了 Opus 和 Sonnet 在任何 effort 等级下都无法企及的工作。它的单 token 成本也最高，这也是为什么值得把它留给真正需要它的工作。

图中曲线仅为示意，展示的是一个足够困难、能拉伸两个模型能力极限的单一任务，并不代表真实的基准测试数据。

上面两张图的关键点在于：effort 决定的是 Claude 愿意沿着这条曲线走多远，但这并不意味着 Claude 完成任务真的需要走那么远。

最后，effort 塑造的是 token 消耗的走向，但并不会给它设一个上限。系统里唯一真正的硬性上限是 [max_tokens](https://platform.claude.com/docs/en/build-with-claude/extended-thinking#max-tokens-and-context-window-size-with-extended-thinking)，它会在达到上限时截断正在流式输出的响应，但这是一个很粗糙的工具，主要和 API 开发者相关。像 [task budgets](https://platform.claude.com/docs/en/build-with-claude/task-budgets#task-budgets-are-advisory-not-enforced)（任务预算）这样更柔性的控制手段，或者直接在 prompt 里要求 Claude 保持简洁，会更有帮助。这些是模型被训练去遵循的指导原则（它会在接近上限时主动收尾），而不是一堵它会直接撞上去的墙。

effort 改变的是 Claude 做了多少工作。模型改变的是 Claude 知道什么。

当你对某个结果不满意时，先检查上下文，再去动任何一个设置：给 Claude 清晰的 prompt、正确的工具和 skill，以及一种能验证自己工作的方式。

如果 Claude 依然做错了，问问自己：是它不够懂，还是没有试得足够狠？不够懂是模型的问题，没试得足够狠是 effort 的问题。
