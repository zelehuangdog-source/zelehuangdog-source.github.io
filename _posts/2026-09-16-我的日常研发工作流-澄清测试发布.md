#### 摘要

1. **clarify**：谈完产品形态和流程之后不止步，继续去读代码仓库、线上数据、存储架构，判断这条流程背后的模型设计撑不撑得住，撑不住就把「砍流程还是换存储架构」交给用户决策。
2. **test-backend-full**：agent 本地把服务起起来直接调接口、用浏览器做端到端联调、按需写脚本造并发和数据 mock，一轮改动全方位测完。
3. **mt-deploy**：构建和发布走 CLI，灰度发布需要在页面上反复点击确认的那几步交给浏览器自动化。

#### 一、clarify · 流程谈完之后，去看模型撑不撑得住

现在做需求澄清、头脑风暴，大家盯的都是模型有没有理解用户的流程、诉求和边界。很少有人反过来问一句：**这个流程，我现有的数据模型和存储架构撑得住吗？**

传统开发流程里，大部分 PM 也不关注后端数据模型怎么实现。他们把流程定义出来之后，从需求评审一直到 RD 的技术方案设计，两边会反复沟通，而沟通里很大一部分内容，就是数据模型和产品流程之间的权衡。

clarify 里最核心的设计就是这个：**产品形态和流程沟通好之后，不是结束。** 下一步，它会去读代码仓库、查线上真实数据、看现有的存储架构，深度思考这条流程背后的模型设计到底支不支撑得了——撑不住就停下来，把「砍流程，还是换存储架构」交给用户决策。

#### 二、test-backend-full · 全方位、自动化地测一轮

有了 agent，测试这件事变得极度方便：

- **后端接口测试**：本地把服务起来，agent 直接 curl 调用
- **前端联调测试**：agent 用浏览器操控的方式做端到端验证
- **压力测试**：不需要任何专业工具，agent 本地写个脚本就能造出大量并发
- **数据 mock**：agent 读完代码和线上数据，mock 数据也不用我们操心

这个 skill 主要依赖两个东西：**JetBrains IDE 的 MCP**——它能自动帮你在本地把 Java 服务启动起来；**ego-lite**——一个给 agent 用的浏览器，方便做页面操控。

整体流程：

1. 根据工作区变更设计用例，并预留后门方便测试
2. 自动启动 Java 服务
3. 针对所有用例发起测试
4. 进行端到端联调测试
5. （可选）进行压力测试

#### 三、mt-deploy · 构建、发布与浏览器自动化

底层依赖两个 skill：后端走 **ee-plus**（Plus 平台），前端走 **ee-talos**（Talos 平台）。

**构建**：ee-plus 通过 CLI 发起构建、打包，拿到可发布的包。

**发布**：同样通过 CLI，用包 ID 加上发布项 ID、部署模板 ID，发起灰度发布任务，拿到任务地址。

规范的发布流程是灰度发布，灰度发布需要在页面上进行多次点击、确认，这一段就交给浏览器自动化：用 ego-browser 打开灰度任务页，点「执行检查并发布分组 批次N」→ 等检查点 → 勾人工检查项 → 点「确认」，一路推到 100% 全量。中途只有出现异常——失败机器、任务异常终态、页面点不动——才会**暂停并提醒**，其余情况自动往下推。
