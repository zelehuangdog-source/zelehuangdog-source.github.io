过去一年里，我们与商业零售行业的众多团队合作——零售商、电商平台、旅游、娱乐和电信公司——用 Claude 构建商业智能体（commerce agents）。

这些智能体已经投入生产，企业客户使用后看到了购物车金额的增长和商家运营效率的提升。它们的架构也很简单：Claude 运行在一个智能体循环（agent loop）里，配备一组技能（skills）、工具（tools）和一套完善的评测（eval）体系。

本文写给正在构建这类（或其他面向消费者的）智能体的工程师和工程管理者。第一部分讲架构——这是一次性的决策；第二部分讲延迟与成本；第三部分讲生产环境：记忆、安全、评测，以及如何在一个组织内扩展这项工作。

**01**

#### 架构

一个模型跑在标准智能体循环里，长尾功能用技能承载，工具对接你已有的系统。这个决策做一次就够了。

##### 什么是商业智能体？

我们把商业智能体定义为：简化在线商品目录上买卖行为的智能体。

有些智能体面向消费者：它们搜索、比价、找替代品、组装订单——可能是零售购物车、旅行行程、手机套餐变更，或者演出选座。有些智能体面向企业：它们回答销售相关的问题、执行促销和营销活动、管理库存和定价。

上面两个面板运行的是同一个智能体，工具和提示词完全相同，只有外壳（harness）不同。总耗时差不多，但用户第一次看到内容的时刻差别很大。

核心架构是一个模型跑在[标准智能体循环](https://www.anthropic.com/engineering/building-effective-agents)里：围绕目标推理、探索上下文、通过工具采取行动、通过技能学习流程、提出澄清问题、观察结果，直到目标完成。

它前面没有对对话做分流的意图路由器（intent router），后面也没有一组按领域拆分的子智能体。

##### 工程上下文

###### 用技能，而不是子智能体

商业智能体要覆盖众多品类和意图的广泛能力，这很容易让人想给每个领域配一个子智能体（subagent）。

实践证明这并不理想，因为一段商业对话是横跨多个意图、多个轮次的紧耦合会话，需要大量共享上下文。

在子智能体架构中，编排器（orchestrator）持有购物车或暂存的修改、用户偏好和对话历史。

每一次向子智能体的交接都是有损操作，往往影响子智能体回复的质量，进而影响整体回复。此外，每次交接还可能耗费数倍的 token，并增加数秒延迟。

各领域也很难干净地切开。一个退货流程可能同时需要订单历史、当前购物车和商品目录——按领域拆子智能体的做法，要么到处复制这些数据的访问权限，要么在任务中途交接。

而且随着模型越来越聪明，它们能处理更长的上下文、更多技能和工具，所以今天这些「拆分规则」所依赖的限制，每一代模型都会放松一些。

[智能体技能](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)反而能提供类似的按领域模块化和上下文控制，却没有「交接税」——因为技能指令加载进主智能体，而主智能体本来就持有全部历史。

在我们对多个企业部署的对比中，「单智能体 + 技能」在质量上始终优于「一个提示词包打天下」和「子智能体」两种设计，而且往往单任务成本和延迟更低。

子智能体真正有价值的场景，是编排器把它们当工具调用，处理狭窄或自包含、能从独立上下文窗口中受益的任务。

一个常见的生产例子是深度研究子智能体：它在自己的循环里搜索和阅读文档、写代码并运行、遍历数据模型、撞各种死胡同。所有工作都发生在子智能体内部，只有一份压缩后的答案返回给编排器。

另一个例外是已经拥有专属智能体的领域。如果你的药房或金融服务业务运行着一个带独立合规面的专用智能体，正确的做法可能是交接（hand-off）：让那个智能体接管任务，通过自己的循环直接与用户交互直到完成。

区别在于对话的所有权。交接让领域智能体成为用户的对话对象；委托（delegation）则保持编排者在场，领域智能体在同一次回复中进出，每次交互都有质量损耗。

###### 系统提示词还是技能：按使用频率决定

决定一组指令放系统提示词还是技能，主要看智能体需要它的频率。加载技能要花一个模型轮次，所以大多数轮次都需要的指令，应该放进系统提示词。

不过这也取决于你的流量分布，以及评测表现出的智能体行为。一个不错的起点是：与三分之一以上流量相关的指令（无论是上线前预判的还是生产中观察到的）放系统提示词，其余放技能。

如果某个技能可以从你已有的信号预测出来——比如用户来自哪个页面——我们建议在外壳层于首次模型调用之前直接注入，省掉加载技能的那一轮。

关键指令——安全与合规规则、品牌约束、过敏史等关键用户事实——永远放系统提示词。

对商业智能体来说，这意味着商品搜索放在提示词里，因为几乎每个会话都会用到；长尾功能则由技能承载。

在我们的[参考实现](https://github.com/anthropics/commerce-agents)里，购物智能体的提示词包含 grounding（回答依据）、购物车与结算语义、展示规则，其余由这些技能覆盖：search-discovery、purchase-research、planning-goals、customer-care、memory-personalization。

商家智能体同样如此拆分，技能为 performance-insights、catalog-listings、inventory-operations、pricing-promotions、marketing-campaigns，每个运营领域一个。

**在提示词里** *购物智能体*：Grounding、购物车与结算语义、展示规则、商品搜索。

**购物技能** *长尾功能*：search-discovery · purchase-research · planning-goals · customer-care · memory-personalization

**商家技能** *每个运营领域一个*：performance-insights · catalog-listings · inventory-operations · pricing-promotions · marketing-campaigns

##### 设计智能体工具

我们的《[为智能体写好工具](https://www.anthropic.com/engineering/writing-tools-for-agents)》一文讲了工具设计的通用原则。在商业场景里，最重要的是两点：

**智能体工具构建在你已有的核心系统和逻辑之上。**

一家商业公司已经有搜索与排序、购物车、偏好与画像存储、库存系统、促销与营销引擎、销售分析等系统，每个系统都沉淀了多年调优的逻辑，并且看到模型永远看不到的信号。

智能体的工具应该调用这些系统，而不是重新实现；工具边界就是系统逻辑的终点、模型判断力的起点。

例如，智能体调用 `search_products` 时，返回的结果应该已经排好序；它的工作是判断哪些结果符合用户目标、展示多少条、怎么呈现。

**工具结果就是上下文。**

返回模型推理需要的字段，其余丢掉。每条搜索结果都带图片 URL 是最常见的毛病。

必要时在工具内部重塑原始响应，包括在数据本身看不出来时附上下一步建议。

这对报错场景尤其重要——模型需要的是指令而不是错误码。比如加一句错误指令「查询库存时请带上商品 ID」，而不是笼统的 403。

###### UI 组件即工具

大多数商业智能体的回复是 UI 组件而非文字——商品轮播、行程、座位图或图表。这意味着智能体要输出的是 schema，而不是文本。

有些团队一开始让模型输出自定义标签、在客户端解析。界面一大就玩不转了，因为：

- 模型对你的标记语言的训练程度远不如对工具调用，嵌套组件一多，可靠性就下降。光靠提示词无法保证输出格式合法。
- 标签定义放在系统提示词里，每加一个组件都会撑大上下文，每次修改都可能在提示词的其他地方引入回归。
- 历史对话最终以一种只有你的解析器能读的格式存储，重新加载历史意味着要么在客户端重新解析原始消息，要么额外维护一份非模型 API 原生格式的副本。

经得起考验的做法是把每个 UI 组件做成工具。模型以带类型的参数调用 `present_products`、`present_itinerary` 或 `present_plan_comparison`；服务端校验并充实这次调用，发出一个事件；客户端负责渲染。

由于组件就是工具调用，它们天然以原生格式存在于 messages 数组里，重新加载旧对话时无需再解析。下面的示意图和[参考仓库](https://github.com/anthropics/commerce-agents)里有一个展示工具契约的例子。

代价是流式粒度。工具调用的每个顶层参数都会在服务端缓冲以做校验，所以即使开着流式，展示工具的子组件也是一段一段到达的。这会影响体感延迟。

要拿到 token 级流式，在工具定义上设置 `eager_input_streaming: true`，它会跳过缓冲，同时也就放弃了服务端的 schema 保证。

展示工具还让智能体知道屏幕上有什么。当顾客说「第一家酒店」或「左边往下数第三个」时，布局就在 messages 数组里，在最近一次展示调用的参数中。

要实现这一点，参数必须反映渲染后的布局，所以按 UI 的结构来组织参数——有序的行和轮播，而不是让客户端再重新排列的扁平列表。

**02**

#### 让它更快、更便宜

从端到端和体感两个层面压延迟，让缓存扛起成本。所有手段都不应该以牺牲智能为代价。

商业场景里延迟很重要，而面向消费者的界面是最不容忍延迟的。不过在智能体界面上，我们一贯看到真正拉动留存、参与度和购物车金额的，是结果的质量。

答案是否相关、任务是否真正完成，对这些指标的影响比边际的延迟收益大得多。

所以从两个层面压延迟。用好的工程把端到端延迟压到最低，同时压低体感延迟（看智能体干活的时间，读起来像进展）。

每个用户都有一个延迟预算，下面的技巧能把智能体控制在这个预算内，而且不牺牲智能。

##### 压缩任务完成延迟

任务完成延迟 = 各模型轮次的（最后 token 时间 + 工具处理时间）之和。由此得到三个抓手：更少轮次、更快工具、更快 token。这些抓手有时互相牵制，所以要最小化的是总和，而不是任何单项。

**更少轮次** 预加载可能的上下文、提升模型智能、让模型并行调用相互独立的工具。

**更快工具** 优化工具自身的后端，参数一到就开始执行。

**更快 token** 通过扫评测套件来选模型和配置。

###### 更少轮次

查询复杂度会增加轮次，而且通常不在你掌控之内。模型智能和相关上下文能帮智能体用更少轮次完成任务。我们在这方面的关键经验：

- **预加载可能的上下文。** 如果用户是从商品页打开助手，或商家是从营销活动面板打开的，把那个页面的数据放进会话上下文。对话多半与它有关，从上下文作答不花额外轮次。
- **提升模型智能。** 更聪明的模型能减少完成任务的总体轮次，因为它能更高效地规划和发起工具调用，这常常抵消它更慢的 token 生成。如果你的查询偏复杂，或生产数据显示每任务超过 5 轮左右，更快的模型往往不是更聪明的那一个。哪个更合适取决于你的流量，所以按下文「选模型」一节用扫测来定。
- **让模型并行调用相互独立的工具。** 商业场景经常需要并行做很多操作：搜多个商品、查多份政策文档、从多个销售数据源取数。并行工具调用确保多个独立查询不额外烧轮次。提示模型在同一轮内调用多个工具，并把结果以工具结果数组的形式放在一条 user 消息里返回（见[并行工具使用文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)）。

###### 更快工具

- **优化工具自身的后端。** 有时工具确实要扇出——比如商家智能体的「今日快照」查询，要分三次独立调用读销售、库存和活动状态。但我们更常看到工具边界成了拼凑后端缺失逻辑的地方：一个库存可用性检查，先调目录服务拿 SKU、按门店调库存服务、再调履约服务拿截止时间，然后在工具自己的代码里套替代规则和自提资格判断再作答。这个工具已经塞满了领域知识，规则一变就难保正确，而且它承载的逻辑本该放在上游系统。当你发现自己在工具里写这种逻辑，解法是做一个能直接回答该问题的后端接口，然后让智能体工具去调它。
- **尽早分发工具。** 工具参数和其他 token 一样流式输出，所以外壳可以在每个工具的参数凑齐时立刻执行它，并在模型还在流式生成其他并行工具或内容块时就处理结果。我们见过这把数秒的空档压到几百毫秒，[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview) 默认就这么做。为了最大化延迟收益，你应该提示模型最先发起最慢的那个调用。

##### 体感延迟

体感延迟是用户感觉屏幕有动静之前的时间。在面向消费者的场景里尤其关键，任何交易摩擦都会影响结算率和收入。两个技巧不动模型就能缩短它：

- **组件边形成边流式输出。** 一个渲染好的商业回复通常 500–700 个输出 token，不开流式就是转圈五秒以上。把展示工具的每个参数在流出的同时发给客户端，渐进式渲染页面。
- **展示工作过程。** 智能体收集上下文时，用平实的语言为每一步渲染一行简短进度（例如「正在找水边附近的酒店」）。你可以从工具现有参数构建（比如商品搜索的 query），或者给工具加一个 `user_facing_message` 参数，提示模型来写这行话。

*上面两个面板运行的是同一个智能体，工具和提示词完全相同，只有外壳不同。总耗时差不多，但用户第一次看到内容的时刻差别很大。*

##### 提示词缓存

提示词缓存是你最大的降本机会，商业流量恰好特别适合。缓存读取的成本是新鲜输入的十分之一；缓存写入有约 1.25 倍的溢价，但缓存前缀第二次使用就回本。在流量巨大的面向客户的应用里，你有一个独特机会：用最便宜的默认 5 分钟缓存过期，打出非常高的缓存命中率。

我们见过最好的商业部署跑在 90–99% 的缓存命中率上，这是从一开始就要设计进去的目标。经验还表明，在约 10 万 token 的规模下缓存读取还快 1.5–2 倍，token 越多加速越接近线性。

缓存基于前缀。一次请求会从缓存读到与上次请求第一个不同的字节，所以关键不只是上下文里有什么，还有它们的顺序。把请求想成三段，按变化频率排序：

- **全局段**：大部分系统提示词和工具定义，所有会话完全一致。这是你最热的缓存，规模够大时基本不会过期。跨轮次、跨会话保持字节级一致，并在其末尾放一个缓存断点（cache breakpoint）。
- **会话段**：每用户的上下文与对话历史，会话之间不同，会话内稳定。这一段放在全局段之后。
- **易变段**：会话内会变的东西，比如当前时间、当前页面。放到请求最末尾——要么作为最新 user 轮次里带标签的块，要么在支持[会话中系统消息](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)的模型上，作为 system 消息追加到 messages 数组。我们最常见到的错误是把时间戳或当前页放在系统提示词开头，每次请求都在悄悄打破缓存。

两个实现细节要记住。第一，技能应该作为工具结果加载，而不是追加到系统提示词。这样技能主体落在对话前缀里，随之被缓存。

第二，每轮把缓存断点往前滚：一次请求允许的断点数量有限，所以把最新的断点移到每条 user 轮次的末尾。这样每一轮都能从缓存读取累积的历史，包括搜索响应这类很长的工具结果。

##### 选模型和它的配置

[模型大小和 effort 设定](https://claude.com/blog/claude-model-and-effort-level-in-claude-code)本质是同一个权衡——智能对延迟和成本——两者都应该靠测量来选：

1. **定指标和底线。** 选出你业务赖以运转的质量指标（任务完成率、答案相关性、有据准确率），定一个评测分数下限，再定 p50/p99 延迟和成本预算。
2. **扫测。** 把整个评测套件在你考虑的每一个模型和 effort 档位上都跑一遍。我们建议商家智能体从 Opus 起步（任务偏分析），消费者智能体从 Sonnet 起步（延迟权重更大）。如果你有生产流量，按真实查询分布给结果加权。然后让数字说话。有时 Opus 5 在拉动购物车的任务上的提升能证明它相对 Sonnet 的差价值得，有时不值得。
3. **仔细读结果。** 两件事常常让团队意外。其一，提示词是针对某个模型调的，用一套提示词扫测，可能低估那些它不是为它写的模型。小模型通常需要当前模型能自己推断出来的指令，大模型则会一字不差地执行小模型本来会忽略的指令。在排除任何候选之前，先对每个候选的失败案例做几轮迭代，成本很低。其二，更智能的配置有时反而在延迟上获胜（最常见于 p90/p99），因为它的工具调用规划得更好，在最复杂的请求上需要的轮数更少。

按「每个完成任务的成本」而不是「每次模型调用成本」来衡量，因为一个需要更多轮次、或失败率更高的便宜模型并不便宜。当结果接近、且成本符合你的单任务经济模型和延迟要求时，选智能。质量才驱动采用和留存，也为接下来 6 个月模型变强留出空间。

**03**

#### 在生产中运行

记忆、安全、评测，以及跨组织扩展：让智能体穿过生产环境并站稳脚跟。

最后我们讲让智能体穿过生产环境的东西：记忆、安全、评测，以及跨组织扩展这项工作。

##### 跨会话存续的记忆

你与客户的关系和互动很重要。记忆让智能体从上一段对话结束的地方继续，而不是从零开始。三月份提过坚果过敏的顾客，六月不该再重复一遍；每周一都看同样三个营销活动的商家，不该每次都要报名字。长期记忆——那些应跨会话存续的事实——是一个需要你亲手构建的系统，它有三部分：事实怎么存、怎么写、怎么读。

###### 存储记忆

记忆属于你的系统，不属于模型。

当画像小、且智能体是唯一读者时，一个扁平的 markdown 画像文件够用。大多数生产级商业智能体都会超出这个规模，实际替代方案就是你已经在运营的数据库。一条事实是一条小的带类型记录：一个键（如 `shoe_size`、`default_store`、`preferred_report_cadence`）、一个短值、一个类别、以及它来自哪个会话。有些键你预先定好、每个用户都有；其余由抽取器发现。数据库随着存储增长仍可查询，让你能在特定属性上构建确定性行为，也能和你已有的用户数据做关联。

对商家侧智能体，记忆要按人而不是按账号建。商家登录常常是多个操作员共用的，所以每个操作员要有自己的画像，读取也必须尊重该操作员的权限：门店经理的智能体不应该回忆起大区经理说过的事实。

在商业领域，智能体记忆持有的是个人数据。值得记的事实往往正是受监管最严的那类，而各法域的规则不同。把记忆当作数据处理的设计问题，而不只是存储问题。实践中意味着四件事：

- **决定你愿意持有哪几类记忆。** 在写入路径上强制，每个保存都过一个校验器，而不是只靠提示词。
- **让用户能查看、更正、删除存储的内容。** 把删除接入你的账号注销和数据请求流程。
- **设定保留期。** 几年前的偏好很可能过时了，保留期有助于让记忆事实保持新鲜。
- **记忆应该是每个部署可独立开关的。** 这样无法承担这些义务的地区可以不开记忆运行。

###### 写入记忆

异步写记忆。每轮结束（或长会话中每隔几轮），一个独立的线程或进程读取对话，在存储中创建、更新或删除事实，并随着会话推进维护自己的工作上下文。

这不为对话增加任何延迟，而且在我们的内部商业记忆评测套件上，事实召回率高了 13%。

看似显然的替代方案——让智能体调用一个工具来保存事实——对延迟敏感的商业智能体来说是错误的。每次保存都是面向用户轮次内的一次工具调用；而且除非整个存储都在上下文里，一次保存需要先读才能更新或去重，这本身就是一轮。

它还在每一轮给智能体多加了一个决策，在我们的评测里，这种注意力的争夺表现为漏记。

分离出抽取器还让你能精准地为它写提示词。它只读用户和助手的文本，从不读工具结果，所以商品描述或评论不会变成关于用户的事实。它的提示词写明什么算事实——说过的尺码、饮食限制、履约偏好、商家常用的物化视图——什么不算，比如商品列表里的信息或一次性的细节。

###### 读取记忆

分三层读记忆。

**常驻上下文** 一小组固定事实每一轮都进上下文：几乎所有请求都依赖的那些，比如顾客的默认门店和履约偏好，或操作员的门店和角色。

**每轮预取** 与当前请求相关的事实每轮预取，用预加载技能的同一套信号：搜鞋就拉尺码和品牌偏好，问营销活动就拉操作员常用的指标。

**放在查询工具后面** 其余的一切放在一个查询工具后面。

由于记忆是每用户的上下文，全部放在会话段，即全局缓存断点之下。

##### 安全：执行在外壳层

提示词是安全行为的起点，但在商业场景里不能是安全被执行的地方。失败是资金上的、常常不可逆，而提示词规则离被跳过只差一次注入或一次坏样本。下面的每一条规则都用代码强制，消费者和商家两个智能体都适用，且只定义一次，让每个运行时共享。

###### 模型只做暂存；人或策略来执行

没有任何模型工具调用能直接动钱或改动业务。下单、支付、退款、改价、营销活动上线，全部终结于外壳控制的动作，而不是模型。

消费者侧这是结构性的：结算工具渲染带下单按钮的购物车，智能体调用的后端接口根本没有扣款方法。

商家侧，每个写工具产生一条带服务端生成 ID 的暂存变更，`apply_change` 只对已经通过真实界面批准的 ID 成功：操作员门户里的按钮、CLI 里的确认，或者智能体运行在 Managed Agents 上时平台自己的工具审批提示。

护栏在执行时按当前限额重查一遍，而不是暂存变更时的限额。无论哪个界面，形状都一样：模型最危险的动作是「提议」，批准则走你的业务对这类变更已经在用的制衡（maker-checker）流程。

###### 写和渲染只接受服务端签发的 ID

外壳为服务端交给模型的每个 ID 维护一份会话内记录，这份记录是任何写或渲染接受的唯一凭据。

购物车只接受本会话中服务端返回过的商品 ID，商家工具只接受智能体实际读过的 listing 和活动 ID。以其他任何方式出现的 ID——幻觉出来的、用户粘贴的、种在评论里的——在后端看到之前就被拒绝。

同一条规则也覆盖 UI。展示工具接受 ID，服务端自己去填商品、订单或变更记录，所以一张卡片只会渲染服务端自己填过的记录。

它也覆盖委托：商家分析子智能体只读数据，永远不向智能体可写的 ID 集合中添加任何 ID。

对费用、披露条款等受监管内容，模型选择对哪个商品做披露，服务端从已批准文案中提供每一个字。同样的费用字段也在商家智能体的保护名单上，所以买卖两侧都无法更改或改述它们，评测会逐字节检查渲染出的字符串。

###### 有上限的交易必须扛得住反复请求

大多数商业界面会限制一个用户能买多少件——用于票务配额、促销价或反欺诈——而智能体会以人类点按钮时从未有过的方式重试、换说法、并行化。

因此上限要按执行后的落点强制，如同写入之后那样，所以第二次「再加两件」无法叠加突破上限；同一会话的购物车写入串行化，让单轮内的并行工具调用无法合计突破上限。

商家变更同样按价格变动幅度、折扣深度、补货量、活动预算的上限检查，外加一份任何变更不得触碰的保护字段列表。规则可以泛化：对最终状态强制每一条限制，而不是对请求；并且按会话串行化写入。

###### 第三方内容要消毒

在商业场景里，大部分上下文是由不是你的人写的——卖家、评论者、竞争对手——所以每个后端读取都是不可信输入，过同一套消毒器。

每个由第三方撰写的工具结果——商品列表、评论、政策、卖家消息、存储的记忆——在模型看到之前，都要消毒并包进带固定标签的围栏（fence）里。

消毒器剥离控制字符和双向字符，移除任何模仿围栏标记的内容，拆解模仿对话轮次或工具调用的文本，并限制大小——目的是阻止一个恶意商品条目冒充系统或填满上下文。

提示词承载合约的另一半：围栏内的文本是用来汇报的素材，永远不是执行的依据。

##### 评测：发布一个非确定性系统

从一次小的提示词修改到一个新工具，任何东西都可能以难以预测的方式改变智能体行为，而且你正在发布的那次改动，往往不是引发回归的那次。评测是你在部署前发现这一切的方式。我们早前的博客《[智能体评测](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)》讲了通用做法，这一节讲商业智能体的具体之处。

**评测快照，而不是对话**

模型的 API 是无状态的，所以智能体的输出是系统提示词、工具和 messages 数组的函数。这意味着一段商业对话能到达的任何状态，都可以直接构造出来。创建评测用例，就是构造测试状态、追加测试用户消息、让智能体从这里开始运行。

然后评估结果：最终状态和渲染出的回复，包括最后一次写入的参数。大多数情况下，我们不建议评估智能体到达那里的路径，这类用例脆弱且限制性强。

模拟用户评测——第二个模型扮演用户、一个裁判给整段对话打分——作为测量工具很差。两个非确定性系统相互作用需要更大的样本、单次成本更高、更难评判、失败难以归因。它们适合用来发现覆盖缺口、给智能体做整体体感检查，所以用它们发现用例，然后把每个用例写成快照。

###### 在严苛条件下评测行为

大多数团队没有正确测试注入的状态。一个用例应该编码失败的前置条件，而不只是任务本身。如果某个行为只会在带多次工具调用的繁忙首轮之后、或会话早些时候出现矛盾之后才出现，那么从干净状态出发的用例在每种配置上都通过，提供不了任何有意义的数据。

我们观察到大多数套件里这种干净状态用例占比过高，所以确保你有一定比例的用例从冗长、混乱或自相矛盾的历史开始。

###### 覆盖不同类型的商业智能体评测

有效评测需要同时测期望行为和不期望行为。

每个正向用例都写它的反向用例：每个「应该服务」配一个「应该拒绝」，每个「应该直接做」配一个「应该先问」。缺失的反向用例是我们在评测套件里发现的最常见缺口。

评测以下几类：

- **核心请求**：构成你流量大头的那部分，这里失败影响大多数会话。包括简单查询、多约束请求、商品与套餐问题、多意图消息。对问题类，检查每个价格、库存、属性都能追溯到返回数据，并且数据缺失时智能体会如实说明而不是编造。
- **依赖上下文的请求**：如对屏幕上内容的指代、从早先轮次延续下来的约束、对现有购物车的写入。记忆评测也归入这一类：检查记忆被抽取、被检索到，并且改变了答案。
- **安全与品牌用例**：失败会损失金钱或信任。包括注入尝试、读取他人数据的尝试、逐字节检查的受监管话术。把注入拆成两种用例：用户注入（指令来自用户自己的消息）和数据面注入（指令种在商品名、评论或经工具结果到达的网页片段里）。
- **界面评测**：确保渲染了正确的组件、数量上限被遵守、面向用户的文本中没有内部标识符。也测试超时和空结果。
- **同时横跨多个能力的请求**。操作员问：「如果我降价 15%，库存够覆盖需求吗？」这是一个定价问题和库存问题的合体。正确答案是暂存降价并附上库存推演；错误答案是只做其中一半。按能力写的评测抓不住这个，因为每个只评自己那一半。为需要两个相邻能力一起完成的请求写用例，并评估答案的两半。

###### 与领域专家一起写评测，并用真实事故

与亲历失败的一线专家（SME）合作设计用例——产品、法务、商家运营、客户服务、品类管理的成员。真实故障是最好的评测，每个用户流程 50–100 条用例是不错的起点。

确保用例多样，如上所述。生产对话记录是寻找新用例的绝佳来源，尤其是棘手的那种。编码智能体擅长生成补充用例和对抗性变体。[参考仓库](https://github.com/anthropics/commerce-agents)包含一个 Claude Code 插件，内置用我们推荐方法构建的评测编写技能。

###### 在大组织内发布

在商业企业里，智能体由多个工程团队共建。搜索、结算、定价、营销技术、客服、目录平台各自拥有智能体依赖的系统，各自按自己的节奏发布，各自都想加或改一个工具、技能或提示词规则。

与服务不同，智能体没有保护其他部分的严格模块边界：定价团队做的一处修改，与结算共享同一个上下文窗口。

诱人的解法是把系统拆成许多子智能体，每个业务单元一个。如第一部分所述，出于质量原因我们不推荐。作为替代，我们概述降低多团队协作风险的流程：

- **所有权跟随系统。** 每个技能和工具有唯一的责任团队。例如定价团队拥有促销工具和定价技能，客服团队拥有订单和退货工具以及 customer-care 技能。共享提示词的公共部分由平台级唯一负责人拥有，领域特定部分由领域负责人拥有。
- **变更随用例一起发布，CI 运行为它挑选的一组用例。** 贡献一个技能的团队同时贡献它的用例，包括反向用例和针对相邻技能的边界用例。每个 PR 都跑全量套件太慢太贵，活不下去，所以要从中构建 CI 集。这个集由两部分组成：包含最高流量请求的核心集和每一条安全用例；再加上本次变更涉及的用例。对技能，是它自己的用例加上相邻技能的边界用例；对工具，是每一个调用它的用例；对共享提示词，是全量评测套件，因为所有东西都读系统提示词。我们建议对几次试验的通过率设门槛，并检查缓存命中率和每轮成本。每晚和每次发布前跑全量套件也是好实践。跨团队回归就在这些运行中被抓住。
- **智能体也应该进入发布日历。** 它是一个部署单元，一处坏改动会同时到达所有用户。提示词和技能变更先滚动到金丝雀用户群，保留一个无需部署就能单独关掉某个技能的开关，并在高峰期前冻结智能体，就像你冻结其他系统一样。

关于这套安排的人际面，参见《[构建高效的人机协作团队](https://claude.com/blog/building-effective-human-agent-teams)》。

#### 展望未来

本文讲的绝大部分内容与模型无关。工具调用的是你已经在运行的系统，技能编码的是你已经在遵循的流程，评测是你的产品需求文档写成了测试，外壳强制的是你对任何客户端都会强制的策略。模型会持续进步，更好的模型发布时，我们描述的架构把它当作一次配置变更加一轮评测扫测就能接纳。其他一切照常运转。

同样重要的是想清楚产品界面的路线图。架构会比聊天面板活得更久。同一个智能体可以工作在语音之上，可以在用户开口之前主动响应票价下降。对已经有评测和工具的团队来说，这些只是表现层的项目。更远处，你的店面流量将有一部分来自代替用户购物的智能体。让你自己的智能体守规矩的那套来源验证、暂存和批准规则，正是让你能安全地把工具开放给那些智能体的东西。

商业一直奖励把购买流程做到尽可能顺滑。智能体让这容易得多。查看[完整的参考实现](https://github.com/anthropics/commerce-agents)，包含消费者和商家两个智能体，以及零售、旅游、电信、娱乐的可运行示例。
