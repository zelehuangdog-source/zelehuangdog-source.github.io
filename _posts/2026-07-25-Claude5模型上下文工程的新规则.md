> **摘要**：随着 Claude 模型能力的跃升，过去为约束旧模型而积累的上下文工程"最佳实践"很多已经变成了"迷思"。Anthropic 在为 Claude Opus 5、Fable 5 等新一代模型优化时，删掉了 Claude Code 系统提示词的 80% 以上，编程评测却没有可测量的损失。核心转变是：从"给 Claude 定死规则"转向"让 Claude 用判断力"，从"堆砌示例"转向"设计接口"，从"一次性全塞进上下文"转向"渐进式披露（progressive disclosure）"，从"重复叮嘱"转向"简洁的工具描述"，从"简单规格文档"转向"丰富的引用（代码、测试、rubric）"。文章还给出了在自己的系统提示词、CLAUDE.md、Skills 中如何精简的具体建议。

我此前写过如何为最新一代 Claude 5 模型[编写提示词](https://x.com/trq212/status/2073100352921215386)，以及如何与它们迭代协作、逐步发现你真正想构建的东西。

但当你给 Claude 发一条消息时，这条提示词只是它所获得上下文的一小部分。你的大量上下文其实是从系统提示词（system prompt）、Skills、CLAUDE.md 文件、记忆（memory）以及其他来源中拼装出来的。我们把这件事称为[上下文工程（context engineering）](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)，它对你使用 Claude Code 或构建自己的 Agent 时产出的结果有着巨大影响。

与提示词不同，上下文是被广泛复用于许多次请求的，因此它无法像单条提示词那样具体。那么，在你并不知道用户的提示词会是什么的情况下，你该如何为 Claude 构建这些通用的提示与指引？

随着 Claude 自身能力的演进，这件事会难得出人意料。最近，我们注意到在为最新一代 Claude 模型编写提示词的方式上出现了一次很大的跃迁。对于 Claude Opus 5、Claude Fable 5 这类模型，我们删掉了 Claude Code 系统提示词的 80% 以上，而在我们的编程评测上没有任何可测量的损失。

以下是我们在为这一新类别模型编写提示词方面学到的经验，以及你可以如何利用它来更新自己的上下文工程。我们已经把这些最佳实践放进了 `claude doctor`，在 Claude Code 中使用 /doctor 命令即可对你的 skills 和 CLAUDE.md 文件做"合理瘦身"。

#### 为 Claude 松绑（Unhobbling Claude）

总体而言，我们发现自己过度约束了 Claude Code——无论是通过系统提示词，还是通过 CLAUDE.md 文件和 skills。

举个例子，当我们阅读自己内部使用 Claude Code 的对话记录时，会在同一次请求里看到好几条互相冲突的消息：比如系统提示词里说"酌情保留文档（leave documentation as appropriate）"，同时又说"不要添加注释（DO NOT add comments）"——我们的系统提示词、skills 和用户请求彼此打架。

一般来说，Claude 能够解读用户的意图从而得到正确答案，但在决定该怎么做之前，Claude 必须更费力地去权衡这些相互重叠、彼此冲突的消息。

而这些约束虽然曾经是为了避免最坏情况所必需的，但我们后来发现可以删掉其中很多条，转而让模型依靠周围的上下文和自身判断力去处理。

此外，Claude Code 现在拥有了多得多的工具。Claude 过去依赖 CLAUDE.md 作为记忆、信息与指引的来源。如今我们有了 memory、artifacts 和 skills，Claude 可以用它们来创造出在会话之间加载和共享上下文的新方式。

#### 昨与今（Then and now）

有不少过去的上下文工程"最佳实践"如今已经变成了迷思，包括：

**昨：给 Claude 定规则　今：让 Claude 用判断力（Give Claude rules → Let Claude use judgement）**　我们最初推出 Claude Code 时，需要确保 Claude 避免最坏情况，比如删掉文件。这意味着我们会给出特别强硬、但未必总是成立的指引。例如，我们过去在系统提示词里会说：

> 写代码时：默认不写注释。永远不要写多段落的 docstring 或多行注释块——最多一行简短说明。除非用户要求，否则不要创建规划、决策或分析类文档——从对话上下文出发，而不是从中间产物文件出发。

但对于某一部分提示词场景来说，这条指引会是错的。就文档而言，用户可能有自己的偏好，或者某些非常复杂的代码片段确实需要多行注释块。

尽管如此，对旧模型来说，如果没有这些护栏，Claude 写出的注释在很多情况下都会不对，我们不得不接受这个权衡取舍。但更新的模型判断力更好，即便没有明确规则，也能很好地处理这类决策。

在新的系统提示词里我们改成说：写出读起来像周围代码的代码——匹配它的注释密度、命名与惯用写法（idiom）。

**昨：给 Claude 示例　今：设计接口（Give Claude examples → Design interfaces）**　关于工具使用，头号规则曾经是给 Claude 提供如何使用它们的示例。而在我们最新的模型上，我们发现给出示例反而会把它们约束到某个特定的探索空间里。

与其使用示例，不如更多地思考你的工具、脚本和文件的设计——Claude 有哪些参数可用？这些参数如何能更有表达力？

例如，在 Todo 工具的例子里，仅仅把 status 列为一个枚举（在 pending、in_progress、completed 之间取值），就已经在暗示 Claude 该如何使用它。而"保持只有一项处于 in_progress"这条指令，则帮助定义了我们所期望的行为。

**昨：全部前置　今：使用渐进式披露（Put it all upfront → Use progressive disclosure）**

由于 Claude Code 聚焦于编程，我们的系统提示词里包含了如何做代码审查（code review）和验证（verification）的详细信息。这些信息并非总是需要，但当需要时，它们又是至关重要的。

自那以后，Claude Code 已经变得非常擅长使用渐进式披露——在恰当的时机加载恰当的上下文。例如，我们把验证和代码审查搬进了它们各自的 skills，让 Claude Code 可以按需选择性地调用。

但渐进式披露不仅仅适用于 skills，我们对工具也是这么做的。我们的一些工具是"延迟加载（deferred loading）"的，这意味着 Agent 必须先用 ToolSearch 搜索出它们的完整定义，然后才能使用。这让我们可以拥有更多工具（比如我们的 Task 工具），而这些工具在真正需要之前不会占用上下文。

同样的做法也可以应用到你自己的 CLAUDE.md 和 Skill.md 文件上。一个常见的迷思是：你想把这些文件做成一个囊括你可能遇到的所有已知实践的中央仓库，因为你担心 Claude 否则找不到它们。相反，[可以考虑构建一棵可以在恰当时机被加载的文件树](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)。

**昨：反复叮嘱　今：简洁的工具描述（Repeat yourself → Simple tool descriptions）**

早期的 Claude 模型有时需要重复的指令，或者更倾向于听从位于上下文窗口末尾的指令而非开头的指令。这意味着我们的系统提示词有时会在主体里引用工具，同时又在工具描述里放上指令。

我们发现可以删掉这些重复的示例，把"如何使用工具"的指令放进工具描述里，而不是放在系统提示词里。

**昨：把记忆放在 CLAUDE.md 文件里　今：自动记忆（Memory in CLAUDE.md files → Auto-memory）**

我们过去鼓励用户把东西保存到 Claude 的记忆里，方式是用 # 快捷键自动写入他们的 [CLAUDE.md](https://claude.md/)。如今，Claude 会自动保存那些与工作、与你本人相关的记忆。

**昨：简单规格　今：丰富引用（Simple specs → Rich references）**

在 plan 模式下，Claude Code 一直高度依赖带有计划的 markdown 文件。把这些计划存成文件，有助于 Claude 在需要时参考它们。另一个类似的最佳实践是把规格（specs）存进代码库，供 Claude 在跨越较长周期的项目中工作时参考。

但我们发现，Claude 能处理越来越复杂的引用。除了简单的 markdown 文件，Claude 还可以引用由我们新的 artifacts 功能创建的 HTML artifact。

你也可以以代码的形式给 Claude 提供引用。一份规格也可以是一套详尽的测试套件，或者是另一个代码库里 Claude 可能会移植过来的某个函数。

Rubric（评分标准）是引用的另一种形式。Rubric 让 Claude 能够尝试并验证你在某个特定领域里的品味（例如，什么样才算好的 API 设计），做法是使用[动态工作流（dynamic workflows）](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)并基于这些 rubric 启动验证者（verifier）Agent。

#### 把这些应用到你自己的上下文中

把这一切串起来，当你组装自己的上下文时，它看起来是怎样的？

**系统提示词（System Prompt）**　系统提示词与产品上下文紧密绑定。它告诉 Claude 它正运行在什么产品中、正在做什么。对于 Claude Code，你大概永远不需要去改动它；但如果你在构建自己的 Agent harness（框架），这里就是你应该投入大量精力的地方。

**CLAUDE.md**　让你的 CLAUDE.md 保持轻量，简要描述你的仓库是做什么的，但要把大部分 token 花在代码库里的"坑（gotchas）"上。例如，你可能把类型（types）统一组织在一个巨大的文件里、别处都不放。避免陈述那些 Claude 只要看一眼你的文件系统或仓库就能知道的"显而易见"的东西。

对于更多细节，使用渐进式披露。例如，如果你有若干条关于如何验证工作的独特指令，就创建一个验证 skill，并在你的 CLAUDE.md 里引用它。

**Skills**　把 skills 想成轻量的指南，让 Claude 在需要时能够找到信息。避免把它们做得过度约束，除非是在极其重要的领域。

对于较长的 skills，尽量多用渐进式披露——把它拆成多个文件、分开存放。

当 skills 编码的是那些专属于你、你的团队或你的产品的特定观点、知识或最佳实践时，效果最好。

**引用（References）**　你可以用 @ 提及（mention）文件，把它们作为引用包含进来。引用让 Claude 能够参考关于当前计划的深入信息。

这可能是规格文件、原型图（mockups），甚至是整个代码库。一般来说，你应该优先选择以代码形式存在的文件，因为它能以 Claude 非常熟悉的语言，给出清晰、高保真的指令。例如，一份设计的 HTML 原型，通常会比对设计的文字描述或一张截图产出更好的结果。

#### 试着做减法

在你的系统提示词、skills 和 CLAUDE.md 文件里，你可能需要像我们一样做减法。我们推出了一个新命令 `claude doctor`，它也能帮你自动完成这件事。想了解更多专门针对更先进模型编写提示词的细节，可以看看我们的 [Fable 实战指南（Fable field guide）](https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns)。
