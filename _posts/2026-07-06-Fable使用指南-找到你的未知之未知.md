和 Claude Fable 5 一起工作，一直在反复教给我一个古老的道理：地图不是疆域。

地图，也就是待完成工作的表征，是我给 Claude 的提示词、技能和上下文。疆域则是工作真正要发生的地方——代码库、真实世界，以及它实际的种种约束。

地图和疆域之间的差异，就是我所说的"未知（unknowns）"。当 Claude 遇到一个未知时,它需要基于对我意图的最佳猜测做出决策。要做的工作越多，Claude 可能遇到的未知也就越多。

Fable 是第一个让我感觉到工作质量瓶颈在于"我能否把自己的未知讲清楚"的模型。

重要的是，仅仅提前做规划并不总是够用。未知可能深藏在实现细节里，也可能这些未知本身就在提示你：你其实应该换一种完全不同的方式来解决这个问题。

我发现，和 Fable 一起工作是一个在实施之前、实施过程中、实施之后不断发现自己未知的迭代过程。

我做了一些[用于寻找未知的示例产物](https://thariqs.github.io/html-effectiveness/unknowns/)，但一定要回来建立起"什么时候该用它们"的直觉。

#### 认识你的未知

你的未知是什么？当我带着一个问题来找 Claude 时，我通常会把它拆成四类：

- **已知的已知（Known Knowns）**：本质上就是我提示词里写的内容。我告诉 agent 我想要什么？
- **已知的未知（Known Unknowns）**：我还没想清楚，但我知道自己没想清楚的部分。
- **未知的已知（Unknown Knowns）**：那些显而易见到我根本不会写下来，但只要看到就能认出来的东西。
- **未知的未知（Unknown Unknowns）**：那些我完全没考虑过的东西。我不了解哪些知识？我知不知道一件事到底能做到多好？

最优秀的 agentic coder 往往未知相对较少。看 [Boris](https://www.linkedin.com/in/bcherny) 或 [Jarred](https://www.linkedin.com/in/jarred-sumner-a8772425) 写提示词，很明显能看出他们对自己想要什么有非常细致的了解。他们对代码库和模型行为都有深度的同步认知。

但他们同样也会做出假设。从很多角度看，减少并规划自己的未知，正是 agentic coding 的**核心技能**。幸运的是，这项技能可以通过和 Claude 一起工作不断提升。

#### 帮 Claude 帮你

指挥 Claude 是一门精细的平衡艺术。如果你的指令太具体，Claude 会严格照做，哪怕转向一个不同的方案会更合适。如果你的指令太模糊，Claude 往往会基于行业最佳实践做出选择和假设，而这些未必适合你的任务。

当你没有把自己的未知考虑进去时，两头都会出问题：你不知道什么时候前方会布满障碍，也不知道什么时候前路清晰，但无论哪种情况你都希望 Claude 能灵活调整。

Claude 能帮你更快地发现自己的未知。它能极快地检索你的代码库和互联网，对大多数话题的了解也比普通人更多。它还能比人更快地从失败中迭代。

这个过程中最重要的一环，是给 Claude 提供关于你出发点的上下文。比如，告诉它你的思路进展到哪一步了；说明你对这个问题和代码库的经验水平；让它像思考伙伴一样和你一起工作。

我之前写过一篇关于[用 HTML 和 Claude 协作](https://x.com/trq212/status/2052809885763747935)的文章，在几乎所有这些场景里，HTML 产物都是可视化和呈现想法的最佳方式。

在这篇文章中，我会详细介绍一些我用来挖掘这些未知的模式。我不会每次都用上所有技巧，但这是一套很实用的工具集。

#### 实施前

#### 盲点扫描（Blind Spot Pass）

开始一项工作时，最有用的事情之一就是了解自己的盲点。比如，如果你要在代码库中一个陌生的部分写新功能，或者让 Claude 帮你处理不熟悉的工作（比如迭代一个设计方案），你很可能有大量的**未知的未知**。

你可能不知道该问什么问题、什么才算做得好、之前有过哪些历史工作、有哪些坑需要避开。

要做到这一点，你可以让 Claude 帮你找出你的未知的未知，并解释给你听。我喜欢直接用"盲点扫描（blindspot pass）"和"未知的未知（unknown unknowns）"这两个字面说法。告诉它你是谁、你了解什么，通常很重要。

**示例提示词：**

- "我在做一个新的 auth provider，但我对这个代码库的 auth 模块一无所知。你能帮我做一次盲点扫描，找出我相关的未知的未知，帮我更好地提示你吗？"
- "我不懂色彩分级（color grading）是什么，但我需要给这段视频调色。你能教我理解一下我关于色彩分级的未知的未知，好让我能更好地提示你吗？"

#### 头脑风暴与原型

当我在一个存在大量**未知的已知**的领域工作时——也就是那些我只有"看到才知道"的标准——我喜欢让 Claude 陪我一起头脑风暴、做原型。

在原型阶段尽早识别并说出这些未知的已知非常有价值，因为如果等到实施过程中才发现，代价（相对）会更高。一个需求或规格上的小改动，可能导致代码实现上天差地别，而且智能体要撤销之前的改动也会更困难。

比如，你可能只是想看看在某个界面上加一个按钮是什么效果，而不想真的去连后端路由或在前端维护额外的状态。

视觉设计对我来说就是那种很难用语言描述，但一看就知道自己想不想要的东西。在这种情况下，我会要求针对同一个产物给出多个不同的设计方案。

我几乎每次编码会话都会以一个探索或头脑风暴阶段开始。这有助于我一开始就带着明确的意图去界定项目范围。Claude 常常能找到我会错过的高价值方案，但有时候也会只见树木不见森林。头脑风暴能防止我把范围定得太窄或太宽。

**示例提示词：**

- "我想给这份数据做一个仪表盘，但我没有审美，也不知道能做成什么样。给我做一个 HTML 页面，展示 4 种风格迥异的设计方向，让我可以对着反应。"
- "在正式接线之前，先做一个单文件 HTML，用假数据模拟出新的编辑器工具栏。我想先对布局有个反应，再动真正的应用。"
- "我的问题大概是这样的：用户在完成 onboarding 之后就流失了。搜索一下代码库，头脑风暴出 10 个我们可以介入的地方，从最便宜到最有野心排序。我会告诉你哪些方案打动了我。"

#### 访谈式提问

在做完充分的头脑风暴之后，我很可能仍然存在一些未知。

这种情况下，我会让 Claude 就任何未知或模糊之处对我进行访谈式提问。让 Claude 采访你时，尽量给它提供关于你问题的上下文，好引导它提问的方向。以下是一些示例。

**示例提示词：**

- "一次只问我一个关于任何模糊之处的问题，优先问那些'我的回答会改变架构'的问题。"

#### 参考物

有时候你没办法把想要的东西详细描述出来。比如，你可能缺乏合适的语言来表达，或者这件事太复杂了，讲清楚要花很久时间。

这种情况下，最好的答案就是给一个参考物。虽然你可以提供图表、文档或图片，但最好的参考物是源代码。

如果你有一个库以某种特定方式实现了某个功能，或者有一个你非常喜欢的设计组件，直接把 Fable 指向那个文件夹，告诉它要找什么，即使它是用别的语言写的也没关系。

Claude Design 的工作方式也是这样。你不需要一定给它一个文件（当然你也可以那么做）。你可以把它指向一个你喜欢的网站上的某个模块，它会去读底层代码，而不只是截图。这能提供关于标记、结构以及组件实际构建方式的更丰富细节。

**示例提示词：**

- "vendor/rate-limiter 里的这个 Rust crate 实现了我想要的那种退避（backoff）行为。读一下它，然后在我们的 TypeScript API 客户端里用同样的语义重新实现一遍。"

#### 实施计划

当我觉得自己准备好要开始实施时，我通常会让 Claude 整理一份实施计划让我审阅，重点放在最可能发生变化的部分，比如数据模型、类型接口或 UX 流程的审查。这能让 Claude 把我可能真正需要调整的地方暴露出来。

**示例提示词：**

- "用 HTML 写一份实施计划，但把我最可能想调整的决策放在最前面：数据模型的变更、新的类型接口，以及任何面向用户的部分。把机械式的重构放在最下面，这部分我信得过你。"

#### 实施过程中

#### 实施笔记

一旦我对计划满意了，我会新开一个会话，把所有产物传给提示词。比如，我可能会传入一份规格文件和一个原型，让 agent 去实现它。

但事实是，不管你规划得多充分，总会有未知的未知潜伏在某处。agent 可能在工作过程中发现，由于代码中的某个边界情况，它需要采取不同的做法。

我会让 Claude Code 维护一份临时的 `implementation-notes.md`（或 `.html`）文件，把它做出的决策记录下来，方便我们从这次经验中学习，为下一次尝试做准备。

**示例提示词：**

- "维护一份 implementation-notes.md 文件。如果你遇到某个边界情况，被迫偏离原计划，就选保守的那个选项，把它记在'Deviations（偏离）'这一节下面，然后继续。"

#### 实施后

#### 汇报与讲解文档

交付一件事情最重要的环节之一，就是获得他人的认可和批准。在最终文档中构建汇报（pitch）和讲解（explainer）类产物，能帮助：

- 当评审者从和你一样的未知起点出发时，加快他们理解的速度
- 当专家想确认你是否考虑到了他们会预料到的未知和常见失败点时，加快审批速度

**示例提示词：**

- "把原型、规格文档和实施笔记打包成一份文档，让我可以直接丢进 Slack 去争取大家的认可。开头放上演示 GIF。"

#### 测验

经过一次长时间的工作会话后，Claude 完成的工作量可能远超我的想象。光是读代码 diff，只能给我一个很浅层的理解，因为很多行为其实取决于已有的代码路径。

在给我充分的上下文之后，让 Claude 对我进行一次关于这次改动的测验，能帮助我真正理解发生了什么。只有完美通过测验之后，我才会合并代码。

**示例提示词：**

- "我想确保自己完全理解这次改动发生的一切。给我一份关于这些改动的 HTML 报告，带上上下文、直觉、做了什么等内容，最后附一个我必须通过的测验。"

#### 这一切是如何汇聚到一起的：Fable 的发布

[Fable 的发布视频](https://x.com/ClaudeDevs/status/2064399512664526853)完全由 Claude Code 剪辑完成。这对我来说是一个全新的领域，我完全算不上专家。

所以我从自己已经知道的东西开始入手。我知道 Claude 可以用代码来剪辑和转录视频，但不确定它是否足够准确。于是我让 Claude 给我解释像 Whisper 这样的转录技术是如何工作的，以及我能不能用 ffmpeg 准确地剪掉"嗯""啊"这类语气词和长时间的停顿。

我希望 Claude 做一个和我说话节奏同步的 UI，但不确定这是否可行，于是我让 Claude 用 Remotion 加转录文本做一个原型视频，看看能不能做到。

最后，视频本身看起来有点发闷，我知道这是色彩分级（color grading）的问题，但我其实并不真正懂什么是色彩分级。我最初的尝试是让 Claude 做几个变体让我挑，但我意识到自己根本不知道色彩分级"好"是什么样子。所以我改为让 Claude 教我了解色彩分级，以此来发现我的未知。

你可以在[这里](https://x.com/trq212/status/2064826394589442448/video/1)看到更**深入的讲解**。

#### 让地图匹配疆域

模型越强，用对方法能做到的事情就越多。当一个长周期的任务最终结果不对时，很可能是你需要花更多时间去界定自己的未知，或者制定一份能让 Claude 在遇到未知时灵活应变的实施计划。

每一次讲解、头脑风暴、访谈、原型和参考，都是一种低成本的方式，能在代价变得高昂之前，让你发现自己原本不知道的东西。

所以，从让 Claude 帮你找到自己的未知开始你的下一个项目吧。
