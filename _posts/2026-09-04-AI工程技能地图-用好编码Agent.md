用好编码 Agent（coding agent），是一项关键的 AI 工程技能。你既能指挥它写代码，也能指挥它干数据分析、系统运维这类非编码的活；这项本事越强，你能做成的事就越多。

编码 Agent 迭代得飞快，这项技能也就跟着飞快变化——比其他几项顶层 AI 工程技能都快。闭源 Agent（比如 Claude Code、Codex、Cursor）和开源 Agent（比如 OpenCode、Pi）在 harness 和模型两个方向上都大步前进。所以，想跟上编码 Agent 的用法，就得持续实验、持续动手、持续学习。

我们访谈了几十位顶尖 AI 工程师，也复盘了自己团队使用编码 Agent 的经验，发现大家用 Agent 构建软件时遵循着一套相当一致的高层工作流。关键步骤有三个：

- **规划（Planning）**。包括 (i) 头脑风暴，可能涉及调研、实验，以及吃透现有代码库（如果有的话）；(ii) 写一份规格说明（spec），把需求、技术设计和架构固化下来，再据此生成执行计划。你也可以回头审一遍计划，追问其中的关键假设，检查有没有安全漏洞、过度设计（overengineering）等问题。
- **执行（Execution）**。动手构建、测试、验证，在 Agent 自主和人工监督之间找到合适的平衡。这包括 (i) 让 Agent 动手写软件，并给它校准好合适的自主程度；(ii) 用自动化检查或人工检查验证它的产出。
- **部署与监控（Deployment and monitoring）**。包括 (i) 部署，可以用 CI/CD 流水线把关，也可以额外再加一道人工卡点；(ii) 让 Agent 盯日志、把问题暴露出来，并提出和执行改进方案。

这套高层工作流，和编码 Agent 出现之前构建软件的流程差不多。区别在于，现在我们花在代码上的精力少得多，更多精力花在决定做什么、设计架构、写规格说明、验证产出上。

每一步占多长时间，项目之间差别很大，有些步骤也可以直接跳过。比如一个从零开始（greenfield）的原型，规格说明可能就是随手写的一段提示词；而一个已有大量用户的存量（brownfield）项目，规格说明就得花多得多的功夫去写、去验证。另外，这套流程高度迭代，老练的开发者知道什么时候该被后面的反馈拽回前面的步骤。比如验证没过，他们知道怎么指挥 Agent 重做、修错；监控发现了问题，他们知道怎么让 Agent 更新系统再重新部署。

想在这套流程里用好编码 Agent，关键技能有这几项：

- 驾驭工作流
- 放开 Agent 的自主性
- 审查产出
- 定制 Agent 及其运行环境
- 编码 Agent 的底层原理

**驾驭工作流。** 你知道这套流程里每一步该怎么走。这需要你判断每一步该投入多少人力、多少 Agent 的力气，以及什么时候该退回上一步迭代。它要求你深刻理解速度、成本、技术风险和人力投入之间的取舍，从而决定：前期该做多少调研和规划；哪些关键工作必须攥在人手里；架构怎么选；规划产物（比如规格说明）该写到多细；以及怎么把工作拆成一个个可验证的小步。

**放开 Agent 的自主性。** 把编码 Agent 用到流程的各个步骤时，你要选择给它多大的自主权：是盯着它一来一回地交互，还是把一大块工作直接甩给它？又该在什么时候给它定一个清晰的目标，让它一直循环到成功为止？此外，你还得帮 Agent 仔细管理上下文。随着构建推进到不同阶段，你要拿捏好什么时候把关键结论、用户反馈和假设——包括构建到一半发生变化的那些假设——沉淀下来，供 Agent 在后续环节使用。你还要决定什么时候把任务拆开、起一堆 Agent 并行跑——可以让人来编排，也可以让一个更高层的 Agent 去编排——以及怎么在多个并行会话之间分配自己的注意力。你也要懂得让 Agent 安全地跑：把权限和动作卡点设对，既让开发飞快推进，又把泄露、数据丢失之类的风险摁住。

**审查产出。** 编码 Agent 的产出是不确定的。我们事先并不知道它会冒出什么好点子，也不知道它会写出什么 bug。审查和验证产出是关键一步：它保证你拿到想要的结果，不对就及时把 Agent 掰回来。你要针对具体任务设计相应的测试和验证，该做行为验证就做行为验证，该做功能验证就做功能验证。你也可以测用户流程，比如让 Agent 截图，作为成功或失败的证据。至于定性的、行为层面的评估，可以用评估集（eval sets），也许再加上 LLM 作为裁判（LLM-as-a-judge）。

你还得决定这些测试有多少要自动化。有些工作流会把测试和验证全部自动化，这样 Agent 自己就能检查工作、知道自己有没有把任务做成。但你要审视这些测试，确认它们确实对准了你的目标，不对就得改。此外，你要用 Agent 式代码审查（agentic code review），跑 AI 驱动的安全和架构审计。当 AI 审查还不够用时，你要有判断力地在关键处插入人工审查——主要审代码的行为（偶尔也审代码本身）——同时继续探索怎么把这部分审查进一步自动化。最后，你要验证部署结果，并可以把监控和故障处理也交给 Agent 来运转。

**定制 Agent 及其运行环境。** 你能不能改造 Agent，以及它干活的环境，决定了它能不能高效拿到需要的上下文、用上该用的工具、把东西又快又对地建起来。你要会接入 Agent 技能（skills）、插件和 MCP 服务器。偶尔也要做减法，把不再需要的砍掉（比如新模型一出，某个旧技能就多余了）。你可以用 hooks 把开发流程里反复出现的环节自动化，比如自动触发代码审查或 CI/CD 流水线。你还要维护 Agent 干活的环境：更新常驻上下文（比如 AGENTS.md 或 CLAUDE.md），把代码库信息、关键架构假设、代码风格、数据访问模式写进去。你要懂得怎么在多个会话之间、多个并行 Agent 之间保持状态，怎么让 Agent 的经验随时间积累——比如跑跑事后复盘，记下哪些做法行、哪些不行。你还要建立统一的约定和结构，让 Agent 读得懂你的代码库，并时不时清理 Agent 攒下来的技术债。在团队里协作时，你还要考虑怎么在不同开发者的 Agent 之间协调上下文。

**编码 Agent 的底层原理。** 最后，为了全程都能做出好判断，你要真正理解编码 Agent 是怎么工作的：它怎么做代码库检索；怎么管理自己的上下文窗口；加工具调用、接 MCP 服务器这些操作会怎样影响上下文；Agent 和子 Agent（subagent）怎么交互；以及 Agent 本质上就是给一个大模型套上一层 harness。理解这些，Agent 对你就不再是个黑盒，你也能认出它的典型故障模式，比如把简单方案做复杂（overengineering）、因为没有明确的验证流程而失去严谨性、干到一半就停、以及可能毁掉文件或生产数据的危险动作。它还能帮你推断 Agent 处于什么状态，从而给它开出对的方子、喂对的上下文。盯着它跑的时候，这份理解也能让你更早发现它跑偏了、需要你介入。

我觉得社交媒体上关于怎么用编码 Agent 的说法，往往过于简化。举个例子：让 Agent 自主跑上几个小时、烧掉几百万乃至上千万 token，有时候确实有用。但就目前而言，超长周期任务的实用价值——尤其考虑到它的成本——被夸大了。实际情况是，绝大多数有效的编码 Agent 用法，都是一个复杂且高度迭代的过程；而能在关键时刻用高水平的判断力介入，效果会好得多。

用好编码 Agent 的技能，会让你成为一个高效的构建者。这也让你有能力去驾驭整个构建过程。关于这一点，我会在后续文章里展开。
