#### 一、背景：交互式编码智能体的天花板

六个月前，OpenAI 内部团队做了一个当时颇具争议的决定：项目仓库中**不允许任何人类手写代码**，所有代码必须由 Codex 生成。

为此他们从零开始重新设计了工程工作流：构建对智能体友好的仓库、大量投入自动化测试和护栏、把 Codex 当作正式的团队成员。这一切都奏效了，但很快遇到了**新的瓶颈：上下文切换**。

每位工程师同时打开几个 Codex 会话，分配任务、审查输出、引导智能体……实际操作中，大多数人能同时管理 3-5 个会话就已经是极限了。超出这个范围后，工程师会忘记哪个会话在做什么、在终端间反复跳转来纠偏、调试卡住的长任务。

**智能体很快，但系统瓶颈是人类注意力。** 他们实际上组建了一支能力极强的「初级工程师」团队，然后让人类工程师沦为微观管理者。这显然无法扩展。

---

#### 二、思维转变：从管理会话到管理可交付物

团队意识到他们优化的方向错了——围绕「编码会话」和「合并的 PR」来组织，而这些只是手段。软件工作流真正围绕的是**可交付物（deliverables）**：工单（issue）、任务（task）、里程碑（milestone）。

> 如果不再直接监督智能体，而是让它们**自己从任务看板拉取工作**，会怎样？

这个想法就是 Symphony 的起源。

---

#### 三、Symphony 的核心机制

##### 3.1 将任务追踪器变为控制平面

Symphony 的核心概念很简单：**每个打开的任务都应该被一个智能体接手并完成。**

- 每个 Linear 工单映射到一个**专属的智能体工作空间**
- Symphony 持续监视任务看板，确保每个活跃任务都有智能体在循环运行
- 如果智能体崩溃或停滞，Symphony 重启它
- 如果出现新工作，Symphony 自动接手

##### 3.2 用 Linear 作为状态机

整个工作流基于工单状态构建，Linear 充当状态机：

```
Todo → In Progress → Human Review → Merging → Done
```

- 有些工单产生多个跨仓库的 PR
- 有些是纯调研/分析，根本不碰代码库
- 工单可以代表更大粒度的工作单元

##### 3.3 复杂任务的编排

Symphony 可以编排复杂的特性和基础设施迁移：

1. **分析阶段**：智能体分析代码库、Slack、Notion，产出实施方案
2. **任务拆解**：智能体生成任务树，划分阶段并定义依赖关系
3. **并行执行**：智能体只开始处理未被阻塞的任务，自然以最优方式并行展开（DAG 调度）
4. **自主创建后续工作**：智能体在实施或审查中发现改进点时，自动提交新工单

##### 3.4 实际效果

- 部分团队的**落地 PR 数量提升了 500%**
- 编排器 7×24 运行，工程师可以从手机上随时添加任务
- 产品经理和设计师可以直接提交功能需求到 Symphony，无需克隆仓库或管理 Codex 会话
- Symphony 自动处理 CI 监视、rebase、冲突解决、重试 flaky check 等「最后一公里」工作

---

#### 四、探索性工作的爆发

当工程师不再花时间监督 Codex 会话时，**代码变更的经济性完全改变了**。每次变更的感知成本大幅下降，因为人类不再需要投入精力驱动实现本身。

这带来了行为上的深层变化：

- **投机性任务变得廉价**：尝试一个想法、探索一次重构、验证一个假设，只保留有希望的结果
- **参与者范围扩大**：产品经理和设计师可以直接提交功能请求
- **工程师聚焦高价值工作**：把时间花在最有趣、最需要判断力和专业能力的问题上

---

#### 五、代价与权衡

##### 5.1 失去了中途纠偏能力

从交互式引导智能体变为工单级别分配后，无法再在飞行中随时纠正方向。有时智能体产出完全偏离目标——但这些失败揭示了系统的空白，帮助团队使其更加健壮。

##### 5.2 应对措施

团队没有手动修补结果，而是：

- 添加**护栏和技能**让智能体下次能成功
- 新增能力：运行端到端测试、通过 Chrome DevTools 驱动应用、管理 QA 冒烟测试
- 显著改善了**文档质量**，明确了「好的输出长什么样」

##### 5.3 不适合 Symphony 的场景

- 模糊问题或需要强判断力和专业能力的工作
- 这些通常也是工程师最享受投入的任务

##### 5.4 从状态机到目标导向

早期版本将智能体视为严格状态机中的节点，只要求 Codex「实现任务」。这太局限了。

> **模型的力量来自其推理能力，给它们工具和上下文，让它们自由发挥。**

团队转向给智能体**目标（objectives）**而非严格的状态转换，就像好的管理者给下属分配目标而非微管步骤。

#### 六、Symphony 的技术架构

##### 6.1 核心：一个 SPEC.md 文件

Symphony 在技术上只是一个 `SPEC.md` 文件——定义问题和预期解决方案的规范文档。不是复杂的监督系统，而是给智能体高层级引导。

##### 6.2 关键组件

| 组件 | 职责 |
|------|------|
| **Workflow Loader** | 读取 `WORKFLOW.md`，解析 YAML 前置信息和 prompt 模板 |
| **Config Layer** | 暴露类型安全的配置 getter，处理默认值和环境变量 |
| **Issue Tracker Client** | 从 Linear 获取候选工单，标准化为稳定的 Issue 模型 |
| **Orchestrator** | 核心调度器，拥有轮询 tick、内存状态、分发/重试/停止/释放决策 |
| **Workspace Manager** | 将工单标识映射到工作空间路径，管理生命周期钩子 |
| **Agent Runner** | 创建工作空间、构建 prompt、启动 Codex app-server、流式转发事件 |

##### 6.3 WORKFLOW.md 契约

{% raw %}
```yaml
---
tracker:
  kind: linear
  api_key: $LINEAR_API_KEY
  project_slug: my-project
  active_states: [Todo, In Progress]
  terminal_states: [Done, Closed, Cancelled]
polling:
  interval_ms: 30000
workspace:
  root: /tmp/symphony_workspaces
agent:
  max_concurrent_agents: 10
codex:
  command: codex app-server
  turn_timeout_ms: 3600000
---

你正在处理一个 Linear 工单。
工单标题：{{ issue.title }}
工单描述：{{ issue.description }}
...
```
{% endraw %}

##### 6.4 编排状态机（内部状态）

```
Unclaimed → Claimed → Running → (成功退出) → 短延时重试检查
                   → (异常退出) → 指数退避重试
                   → RetryQueued → 重新分发或释放
```

##### 6.5 关键设计决策

- **工作空间隔离**：每个工单有独立的文件系统工作空间，智能体只在自己的工作空间内运行
- **动态配置热加载**：修改 `WORKFLOW.md` 无需重启，自动应用新配置
- **优先级调度**：按优先级升序 → 创建时间最早 → 标识符字典序排序
- **并发控制**：全局并发上限 + 按状态并发上限
- **停滞检测**：如果智能体长时间没有事件，自动终止并重试
- **Codex App Server 模式**：通过 JSON-RPC API 程序化地与 Codex 交互，比 CLI 或 tmux 更方便和可扩展

#### 七、Symphony 的演进历程

1. **V1**：一个 Codex 会话跑在 tmux 里，轮询 Linear 并为新任务产生子智能体。能用，但不够可靠
2. **V2**：集成到主项目仓库中，利用已有的智能体线束（harness）
3. **开源版**：提取为独立的 `SPEC.md`，让 Codex 用 Elixir 实现了参考实现
4. **多语言验证**：让 Codex 用 TypeScript、Go、Rust、Java、Python 分别实现，以此发现规范中的歧义并简化系统

> 选择 Elixir 是因为——当代码实际上是免费的时候，你终于可以**根据语言的优势来选择语言**了，比如 Elixir 出色的并发原语。

#### 八、核心洞察总结

1. **人类注意力是扩展交互式编码智能体的瓶颈**——管理多个并发会话导致上下文切换和生产力损失
2. **用任务追踪器作为控制平面**——将工作与人类监督解耦，智能体自主从看板拉取任务
3. **给智能体目标而非僵化指令**——`SPEC.md` 定义问题和预期解决方案，让智能体推理和使用工具来达成目标
4. **将隐性流程显性化**——开发工作流（签出代码、更新状态、附加 PR、录制视频等）过去是隐性的，现在记录在 `WORKFLOW.md` 中
5. **改变代码变更的经济性**——降低启动成本后，探索性工作和非工程师参与都大幅增加

---

#### 九、启示与思考

Symphony 不是一个产品，而是一个**参考实现**——OpenAI 鼓励开发者将自己喜欢的编码智能体指向 Symphony 的规范和仓库，构建适合自己环境的版本。

核心方法极其简洁：

> **对于每一个打开的任务，保证有一个智能体在自己的工作空间中运行。**

随着编码智能体在推理和遵循指令方面变得更强，瓶颈将从「写代码」转向「管理智能体工作」。Symphony 展示了一种优雅的解决方案：用已有的项目管理工具作为编排层，让智能体像团队成员一样从看板拉取工作、执行、交付。
