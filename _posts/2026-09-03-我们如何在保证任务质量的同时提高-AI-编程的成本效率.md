> **摘要**：GitHub Copilot 团队提出，衡量 AI 编程智能体（agent）的效率，不能只看单次工具调用的 token 数，而要看完整任务端到端的成本与质量。文章先用一个反例说明局部最优可能带来全局恶化——压缩 shell 输出的工具 RTK 反而让任务更贵，因为模型要花额外轮次找回被删掉的信息。随后介绍了四项已上线的优化：选择性压缩噪音输出（保留类源码内容并提供恢复路径）、去掉文件读取时的行号前缀（推理成本降约 5%）、用元提示循环加行为回归测试把 task 工具提示词压缩约一半、以及批量交付后台任务结果省去检索轮次。核心经验是：优化完成的任务而非单次调用，优化编排而不只是模型输出，且每项改动都必须在其真实运行的工作流中重新度量。

用 AI 编程智能体（agent）干活，产出质量固然重要，但真正的效率来自把活儿又快、又省、又带着恰当上下文地干完。

正因如此，单看单次交互的 token 数并不是一个有意义的效率指标。目标不该是"用更少的 token"，而是获取恰到好处的上下文来推进任务。一条精简的工具返回有时反而招来额外的调用：如果它省略了智能体需要的信息，任务会变得更慢、更贵。

所以我们要优化的是结果，而不是单次工具调用。本文检视了 GitHub Copilot 中的四项改动，把这一原则落到实处：

- 在减少重复输出的同时保留有用的上下文。
- 去掉对任务没有价值的格式。
- 在不改变有用行为的前提下缩短提示词（prompt）。
- 直接交付已完成的后台工作，省去额外的一次检索。

所有候选改动先在离线环境下用智能体编程基准测试（benchmark）评估，最有希望的再通过受控在线实验验证，最后才发布。文中的示例来自 GitHub Copilot CLI。其他多个 Copilot 产品（如 GitHub Copilot 应用和 Copilot 代码评审）使用同一底层 harness，也因这些改进变得更高效。

#### 局部指标的陷阱

人们常用"缩短每次工具调用的输出"来降低智能体成本。[RTK](https://www.rtk-ai.app/docs)（Rust Token Killer）就是这样一款工具：在智能体读取之前先压缩 shell 输出。我们用自家的智能体编程基准测试评估了它对 GitHub Copilot 的影响。

在我们的 harness 和基准配置下，RTK 确实缩短了一些响应，但当省略的文本重要时，模型有时会重新打开原始输出，或干脆重跑一遍命令，来找回它需要的东西。

这些补救步骤增加了轮次，也让更多上下文被带进后续对话。单次工具响应确实短了，但平均而言，任务消耗的 token 更多、耗时更长。我们在局部省下了 token，却在全局花得更多。

图 2：当缺失的细节迫使智能体重读输出、重跑命令、携带更多上下文时，一条更短的工具响应反而可能让整个任务更贵。

这一结论适用于我们测试的集成方式和工作负载，并不代表所有 RTK 配置或一般意义上的输出压缩。它恰恰说明"每次工具调用的 token 数"是个错误的目标函数。一项效率改动必须在完整任务上评估——从用户提出请求，到拿到最终结果。

更有用的问法是：哪些东西删掉之后，模型不需要返工？

#### 压缩噪音，保留有用信息

目标是缩短重复性输出，同时保留智能体完成任务所需的上下文，让它不必走回头路。

对基准运行的分析显示：安装、构建、测试和 lint 的输出常常充满重复噪音；而类源码的输出和任意命令的结果，更可能含有智能体需要的信息。基于这一分析，我们做了一个选择性输出压缩器，部分借鉴了 RTK 和类似思路。

原型在智能体编程基准测试和一批开源仓库上评估，覆盖了它们的构建、测试和 lint 体系。

早期版本过于激进。它们让模型返工或去读完整保存的原始输出，端到端成本不降反升，任务成功率也下降了。例如，我们最初压缩了 `git diff`，但基准任务显示智能体会重新打开原始输出去找回缺失信息，于是我们移除了这个过滤器。

这些早期失败催生了一条三段式策略：

1. **保留类源码和任意输出。** `cat`、`git diff`、`git show` 和任意脚本等命令的输出原样返回。
2. **重组搜索结果，不丢内容。** `grep` 等工具返回的匹配和文件列表可以更高效地分组，但每一条结果都保留。
3. **有选择地压缩重复噪音。** 只有当节省可观时，才压缩安装、构建、测试和进度类输出。

最终上线的版本是反复评估打磨出来的。它保守，不是因为我们的目标是做一个保守的压缩器，而是评估结果支持这样做。

输出被压缩后，智能体仍可通过一条直接的恢复路径取回完整的原始输出。

图 3：上线的压缩器保留类源码输出，无损地重组搜索结果，只压缩可预期的重复噪音，同时完整保留原始输出。

这条恢复路径既是安全机制，也是评估信号。我们会追踪智能体是否打开了保存的原始输出、重跑命令、重复探索、缩小搜索范围、或多花了轮次。恢复行为频繁出现，就说明压缩器删掉了有价值的东西。

在触发输出压缩的离线任务上，没有检测到统计显著的任务成功率回归，智能体也极少打开保存的原始输出。在线实验中，平均成本略有下降，追踪的各项质量指标没有发现实质性回归。

#### 先删格式，再删信息

一个干干净净的 token 优化来自 `view` 工具——智能体用它把文件内容读进上下文。

以前，`view` 在把文件内容呈现给模型之前，会给每一行加上行号前缀。早期的文件编辑工具用行号来定位修改位置，但现在的工具改为匹配周边代码，不再使用行号。尽管正常工作流已经用不到行号了，这个前缀却一直留着。

单个前缀很小，但乘以每一行、每一次文件读取，这些无用格式在整个会话中不断累积。所以，我们把它删了。

行号在 diff 和短代码片段中仍然有用。在这里它们是浪费，因为它们附着在每一次文件读取上，却服务不了当前的编辑工作流。

去掉之后，在离线智能体编程基准测试中，模型推理成本下降约 5%。成功率保持在预期的运行间波动范围内，编辑失败也没有增加。

随后我们在 Copilot CLI 用户中做了测试。在线实验使每用户日均模型推理成本下降约 3%，追踪的质量和满意度指标没有发现实质性回归。

对开发者来说，这意味着上下文窗口里有更多空间留给工作本身，而不是智能体用不上的格式。

这是最理想的改动：不需要给模型任何新指令、没有需要恢复的信息源、也没有新增任何决策点。文件内容原封不动地到达模型。

#### 压缩提示词，但不压缩意图

提示词承载着塑造智能体行为的指令，而且每一轮都要发给模型。只有当智能体保住开发者所依赖的行为时，缩短提示词才真正提升效率。

在 GitHub Copilot 中，task 工具用于启动专职智能体做并行工作。它的指引分散累积在工具描述、参数 schema、智能体定义、系统指令和配套工具中。

通过一个元提示（meta-prompting）循环——让 Copilot 迭代地改写自己的提示词——这份提示词缩短了约一半。Copilot 生成并打磨更小的候选版本，同时用针对性的行为测试校验我们想保留的要求。

第一次在线实验发现了一个离线评估漏掉的回归：元提示循环把原本谨慎的并行指引改写成了硬性调度策略，导致相互独立的自定义智能体被串行执行。

我们停掉了实验。在再次修改提示词之前，先为用户暴露出的这个行为补了一个回归评估。最终的修复只用一句话替换了原来的显式允许/禁止清单：

*独立智能体可以并行运行；注意副作用。*

这句话更短、限制更少；它把"是否并行运行子智能体"的选择交还给模型，而不是像之前那样靠显式指引兜底。有了它，新的行为测试通过了，既有的行为测试也全部保持通过。

提示词行为需要测试。没有测试覆盖的行为，会在缩短提示词时悄无声息地消失。

图 5：直到回归测试暴露出智能体被串行化、并用一句话修复恢复并行性之后，提示词压缩才算安全；由此带来的 token 节省在每一轮模型调用中反复兑现。

上线的提示词每轮移除约 1300 个 task 工具提示词 token，折合每会话总提示词 token 减少约 1.8%，每活跃小时归一化成本降低约 2.9%，在已测评估中未检测到质量回归。

#### 不多花一轮，直接交付完成的后台工作

智能体经常在后台跑独立工作，比如让一条长时间运行的 shell 命令和一个子智能体的调查并行进行。有了通知机制，智能体可以在那部分工作就绪之前继续干活，而不必花一次工具调用去干等。

如果智能体没有显式等待任何一个任务，harness 会在 shell 命令或子智能体完成时唤醒模型并通知它。

以前，这个通知里不含完成的结果，智能体还得再花一轮，去取回 Copilot 其实已经收到的输出。当多个任务几乎同时完成时，这种绕路还会重复发生。现在，Copilot 会把符合条件的完成通知批量合并，并以现有的工具结果格式直接交付已完成的结果。智能体拿着需要的信息继续推进，不用再花一轮去重新索要。对仍在运行中的工作做显式读取，行为保持不变。

图 6：以前，每次后台任务完成都可能唤醒一个只做检索的模型轮次。现在，harness 会批量合并符合条件的完成通知，以现有工具结果格式直接交付结果。

改动之前，每个完成的任务需要一次模型调用来请求结果，再一次来处理它。对上面展示的 shell 命令和子智能体来说，这意味着工作继续之前要花四次模型调用。

现在，harness 把两批完成合并、一并交付结果，一次模型调用就能处理两者。去掉这些检索绕路，也避免了把完整会话上下文在不必要的调用中反复搬运。

由于直接交付完整结果——不压缩、不摘要、不隐瞒任何内容——按 AI 积分（AI Credits）计量的平均 token 相关用量下降了约 2.3%。

#### 在真实上下文中度量每项改动

在一个 Copilot 工作流里省 token 的改动，换个工作流可能反而增加成本。

例如，一套更精简的文件工具指令在 Copilot 代码评审中取得了正面结果；但在 Copilot CLI 的在线实验中它反而推高了成本，于是我们没有发布。

与之相对，去掉行号前缀和选择性压缩输出这两项，在覆盖大量 Copilot 代码评审任务、使用生产模型的独立评估中，各自将每次评审的平均提示词 token 减少约 5%。追踪的评审质量指标没有发现实质性变化。

这些发现不同于此前 [Copilot 代码评审迁移到共享文件工具](https://github.blog/changelog/2026-06-25-copilot-code-review-analysis-depth-and-efficiency-updates/)的那次改动——那次迁移连同评审指令调优，把代码评审成本降低了约 20%。

每项改动都必须在它实际运行的工作流里度量。

#### 构建高效 AI 编程智能体的五条经验

1. **优化完成的任务，而不是单次工具调用。** 如果智能体要花更多轮次找回被删掉的东西，更短的输出并不更便宜。
2. **优化编排，而不只是模型输出。** 消灭那些 harness 本可以确定性完成、却让模型来做的轮次。
3. **按输出所代表的东西来决定压缩策略。** 精确内容要保留，优先无损变换，并度量智能体使用恢复路径的频率。
4. **重写提示词有时会有意想不到的后果。** 要验证预期的行为确实被保留。
5. **证据只对具体工作负载成立。** 在离线基准、在线实验、以及每一个发布这些改动的产品面上，都要重新评估。

这些改动没有一个让模型变得更聪明。它们只是删掉了模型本来就不必做的工作。
