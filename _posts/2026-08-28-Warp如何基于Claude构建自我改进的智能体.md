智能体需要可靠、有效地处理重复性任务。一个初版提示词（prompt）如果只能把任务做到 80% 的正确率，给用户的体验就是嘈杂而恼人的。Warp 是吃过这个苦头的，并把教训反哺进了产品策略，最终为全球近百万开发者打造出了更好的体验。

Warp 是一款 AI 驱动的终端和智能体开发环境，构建在 Claude Platform 之上。团队在他们的内部代码评审智能体上就撞上了这个"嘈杂体验"问题：工程师们抱怨这个智能体总是留下没什么用的评论，产出质量很低。

团队最初尝试的是权宜之计——根据观察到的代码评审失败案例手动改写提示词。这确实让输出更可用了，但没法规模化。完善 AGENTS.md 这类上下文文件也有帮助，但离彻底解决还差得远。

最终他们意识到，真正的问题在于：无论智能体是做什么的，人类给它的反馈通常在会话结束时就消失了，关键的上下文由此脱离了智能体循环（agentic loop）。他们的解法是一套基于 [Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)（智能体技能）的框架，用来打造自我改进的智能体——让反馈随时间不断累积复利，持续打磨和增强智能体的输出。

下面来看他们是如何在 Claude Platform 上用技能（skill）实现这一切的。

#### 建立在技能之上的智能体自我改进闭环

核心手法是一个使用[技能](https://support.claude.com/en/articles/12512176-what-are-skills)（skill）的自我改进闭环。技能本质上是把知识编码成文件，让指令不必直接塞进原始提示词里。Warp 演化出了一套由两个技能组成的自我改进智能体架构，中间夹着人类反馈。

**内层/基础技能**承载功能性领域知识和指令。比如有 PR（拉取请求）被打开时，Warp 的代码智能体就带着这套基础技能和上下文去执行评审。

**人类反馈**是自我改进闭环的关键一环。以代码评审为例，反馈可以简单到一个点赞，但越具体越好。

"人类可以确认'这条评论提得不错、有用'，"Warp 创始人 Zach Lloyd 解释道，"但人也可以详细说明为什么这次评审不好。比如'你建议重命名这个变量，但我们代码库的规范是这类全局变量要用这种命名方式'——这类具体信息能告诉智能体下次怎么做对。"

**外层/改进者技能**（improver skill）扮演的是一个观察者智能体，按计划定期运行，而不是每个任务跑一次。它拉取累积下来的人类反馈，对比"智能体当时建议了什么"和"人类实际怎么回应的"，然后对基础技能提出一个小的、聚焦的修改。

因为技能就是普通文件，智能体改起它们来非常擅长。这些修改可评审、可批准、可合并，能走正常的 PR/代码评审流程；一旦合并，内层技能的下一次运行就自动继承这次改进。

Warp 现在在整个开源仓库上跑这套模式，配置了规格编写（spec-writing）、代码评审、issue 分诊等多个智能体，每个都带着自己的自我改进闭环。

"基于文件的技能，是一种把知识编码给智能体、又不用把这些知识直接放进提示词的方式，智能体在工作过程中直接查就行，"Zach 说，"这套框架其实非常简单：一个承载领域知识的基础技能，再加一个负责打磨这个基础技能的改进者技能。简单，正是这个方法的精髓。"

#### 如何为智能体编写自我改进的技能

以下是 Warp 团队在为智能体循环编写自我改进技能方面千锤百炼出来的几条建议：

- **写原则，而不是写规则。** "构建技能时，要当作你是在给一个聪明人做指导，而不是在给计算机编程，"Zach 说，"比如'留意重复代码'这样的方向性指引，比穷举变量命名规则更能起到指导作用。"
- **解释为什么。** 给出规则背后的理由，智能体就能对问题进行推理，而不是机械照搬死板的指令——同样有助于更好的泛化。
- **让反馈给起来毫不费力。** 在人们本来就在工作的地方捕获反馈，比如直接在 PR 或 issue 上评论。而且这一步要自动化，不要额外的提交动作。"低摩擦是信号持续流入的保证，"Zach 指出，"如果反馈太麻烦，你既拿不到反馈，也就没法改进技能。"
- **保持技能小巧，用好渐进式披露。** [一份好的技能](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)文件不应该很大；它引用资源文件和脚本，而不是把所有东西一次性倒进上下文。
- **反馈质量重于数量，但数量也有帮助。** 一位资深工程师给出的少量、详细、领域特定的反馈，可能比大量走马观花的反馈更有价值，因为单纯的点赞/点踩说不出"为什么"。"哪怕样本量不大，只要反馈来自懂领域知识的人、又足够详细——这种智能体本来无从获得的知识——你就能拿到非常好的信号，"Zach 补充道，"当然，高质量信号的语料库越大越好。在 Warp，我们用一个闭环来管理整个开源仓库，几百人在贡献，我们在做几千次代码评审。"
- **在改进者技能上多下功夫。** 给改进者技能（观察者智能体）多投入是值得的，因为改进者技能在不同用例之间复用性很强。"除了领域知识那部分，这是一个相当可复用的机制——代码评审智能体的改进者技能，跟其他任何智能体的改进者技能差别不大。"

#### 闭环实战：Warp 的 issue 分诊智能体

[Warp 的 issue 分诊智能体](https://github.com/warpdotdev/warp-agents-demo-github-issue-triage)演示了这套自我改进智能体技能框架。只要有人在仓库提交新 issue（议题），模式就会被触发：GitHub Action 启动一个智能体，分析 issue 的复杂度和可行性、打上标签、给出修复方向建议。这个分诊智能体基于一个内层技能文件运行，文件里写着各标签的含义，以及在动手前该如何调研代码库。

拿一个样本 issue 来说：第一阶段的内层技能干得不错，但漏掉了一个标签——`ready to spec`（可以开始写规格了），这个标签的作用是告诉贡献者可以基于这个 issue 开始写产品和技术规格了。Warp 团队的一位维护者发现了这个遗漏，直接在 issue 上留了反馈——恰恰就在工作发生的地方。关键在于，他既说了自己期望什么，也解释了为什么这么期望：这样的反馈智能体之后才容易消化。

外层改进者技能作为定时运行的"更新分诊"智能体跑在 [Oz——Warp 的智能体编排平台](https://docs.warp.dev/)上。这个智能体先认证登录 GitHub，运行技能自带的 Python 脚本，拉取近期带有反馈的 issue，把它们汇总成一个 JSON 文件，再读回上下文。技能自带脚本这件事本身就是一条最佳实践：技能可以引用资源文件，而不必每次运行都现写代码。

接下来，智能体从维护者的评论中识别出具体的反馈信号，并提出了能覆盖这些信号的最小修改。它提交了一个 PR 去编辑内层技能，加上这样一条规则：当 issue 描述了一个真实存在的问题，即使具体的 UI 或 UX 形态还没定，也应该打上 `ready to spec` 标签。

因为整个更新就是一个技能文件，它会走正常的代码评审流程。这个 PR 附带说明，解释了是哪些信号触发了改动、改动改了什么。由人来评审、批准、合并，分诊技能的下一次运行就继承了新知识。这最后一步的人工环节闭合了整个循环，也让"什么真正被改掉"始终由人来掌控。

Warp 如今在自己的开源仓库上大规模运行的就是同一套机制：规格编写智能体、评审智能体、分诊智能体，各自带着自己的自我改进闭环。

任何智能体，无论它承担什么任务，只要你从一开始就给它内置这样一套闭环——捕获人类反馈信号、把信号转成技能更新——它就会随时间越变越好，从一个一次性的帮手，成长为在整个组织里持续复利的能力系统。

| Warp 团队的最佳实践 | |
|---|---|
| **你是不是把技能和记忆搞混了？** | 技能是程序性、稳定的——"怎么做成 X"，与具体运行无关，靠人有意识地修改。记忆是智能体在推理时自动写入的，永远处于变化之中。 |
| **你需要一个改进闭环，还是每个智能体一个？** | 折中：用一个模板化的基础闭环覆盖各智能体的共性，再叠加领域特定的配置。几个改进者可以各管一个智能体；上百个智能体就该共享。 |
| **反馈是错的怎么办？** | 假定它会是错的。别让智能体照单全收——给它上下文去做合理性检查，过滤谁的输入算数，并在过滤环节或最终评审环节保留人工把关。 |
| **你的领域可验证吗？** | 先把验证环境搭起来，再让智能体对着它调优：生成参考语料、拿输出跟参考比对、修复、循环。 |
| **如果领域不可验证呢？** | 凡是有标准答案（golden output）的地方，就用确定性的评估来对答案；必须用人类反馈的地方，把反馈者限定在领域专家范围内——不要敞开大门谁都能提。 |
| **怎么知道整个系统在变好？** | 跟踪人类本来就会盯着的全局指标——合并耗时、贡献者数量、成本——并把这些指标喂回给改进者智能体。部署节奏上采取爬、走、跑（crawl-walk-run）的渐进策略。 |
