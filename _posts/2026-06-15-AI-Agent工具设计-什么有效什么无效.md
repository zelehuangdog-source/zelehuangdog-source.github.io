> **摘要**：本文论证了大多数 AI 智能体（AI Agent）的失败根源不在于模型能力，而在于工具设计本身。文章系统地提出了五种有效的设计模式——单一职责工具、严格的 Schema 约束、定义边界的描述、结构化错误返回和幂等操作，以及五种常见反模式——未过滤的 API 薄封装、全量工具加载、静默部分成功、名称重叠和缺少确认闸门的破坏性操作。对于任何构建生产级 AI Agent 系统的开发者而言，这些模式提供了直接可落地的设计指导。

#### 引言

大多数 AI 智能体的失败看起来像是模型的错误：选错了工具、传了错误参数，或者错误处理没做好。但实际上，模型通常只是在使用它被赋予的接口。根本问题往往是工具设计本身。

模型只能基于工具接口暴露的信息进行推理：工具名称、描述、参数 Schema（模式）以及参数描述。这些细节决定了模型如何理解意图、规划行动和执行任务。当工具设计不清晰、不完整或结构松散时，失败就变得可预测而非偶然。

含糊的命名、模棱两可的说明、不一致的 Schema、薄弱的参数定义和拙劣的错误处理，都会增加失败的概率。更强的模型可以减少一些错误，但无法可靠地弥补有缺陷的接口。本文涵盖：

- 提高可靠性的工具设计实践
- 在演示中看似正常但在真实工作负载下崩溃的失败模式
- 在工具边界减少幻觉的 Schema 和错误设计

每种模式都配有其对应的失败案例，因为理解设计为何失败与知道用什么替代它同样重要。

#### 什么有效

##### 1. 一个工具，一个职责

在大多数 Agent 系统中，一个工具应该代表一个单一、清晰的操作。当一个工具通过 `action` 参数处理多种行为时，模型必须先弄清楚要调用哪种模式，然后才能解决实际任务。

对比多动作工具和专用单一职责工具，差异会更加清晰：

```python
# 避免：基于 action 的多行为工具
@tool
def manage_customer(
    action: str,
    customer_id: str | None = None,
    data: dict | None = None
):
    """
    action: create | get | update | delete | suspend
    """
    ...

# 推荐：单一职责工具
@tool
def create_customer(data: CustomerInput) -> Customer:
    """Create a new customer record."""
    ...

@tool
def get_customer(customer_id: str) -> Customer:
    """Retrieve a customer by ID."""
    ...

@tool
def suspend_customer(customer_id: str, reason: str) -> SuspensionResult:
    """Suspend a customer account."""
    ...
```

单一职责工具为模型提供了无歧义的函数，也为你提供了更清晰的错误处理和更容易的可观测性。

⚠️ 注意：这是一个有用的默认原则，而非普遍规则。某些领域——如 Shell、文件系统、浏览器或日历工具——可能更适合受约束的多动作接口，因为操作空间本身就是底层抽象的一部分。

##### 2. 让无效状态不可能存在的 Schema

在工具调用 Agent 中，模型通过推理你的 Schema 来构造工具调用参数。

- 松散的 Schema 意味着模型需要猜测约束
- 严格的 Schema 将这些约束编码进去，无需猜测

示例：

```python
from pydantic import BaseModel, Field
from enum import Enum

class Priority(str, Enum):
    LOW = "low"
    MEDIUM = "medium"
    HIGH = "high"

class CreateTaskInput(BaseModel):
    title: str = Field(
        description="Short, actionable task title. Use imperative form: 'Review PR', not 'PR Review'.",
        min_length=5,
        max_length=100
    )
    priority: Priority = Field(
        description="Task priority. Use HIGH only for blockers affecting other work.",
        default=Priority.MEDIUM
    )
    due_date: str = Field(
        description="Due date in ISO 8601 format: YYYY-MM-DD. Must be a future date.",
        pattern=r"^\d{4}-\d{2}-\d{2}$"
    )
```

枚举（Enum）对于具有少量有效值的字段特别有用，因为它们消除了一类"看似合理但实际无效"的输出。验证失败会在工具边界暴露，而不是变成隐晦的下游错误。

##### 3. 定义范围而非仅说明用途的描述

工具描述是面向模型的文档。它们需要做两件事：解释何时使用该工具，以及解释何时不应使用。大多数描述只做了第一件事。

```python
# 弱描述：只解释了做什么，没有说明何时不该用
"""Search for documents in the knowledge base."""

# 强描述：定义了用途、范围和边界
"""
Search the internal knowledge base for documents, policies, and reference material.
Use this when the user asks about company procedures, product specs, or documented workflows.
Do NOT use this for real-time data (prices, availability, current status) — use get_live_data() instead.
Returns up to 5 results ranked by relevance. If no results are returned, the information is not in the knowledge base.
"""
```

没有消歧义信息时，模型仅从工具名称推断范围，而这在规模化场景下往往是工具选择错误的可靠来源。一个好的工具定义不仅包括使用说明，还应包含与其他工具的清晰边界。

##### 4. 结构化的、可操作的错误返回

当工具失败时，模型读取错误并决定下一步做什么。未处理的异常或堆栈跟踪会产生基于噪声的后续行为。结构化错误给模型提供了可以据此分支的信息。

结构化错误不仅应该报告失败原因，还应该帮助 Agent 决定下一步该做什么。好的错误格式使重试行为变得明确，并给模型提供清晰的恢复路径：

```python
class ToolError(BaseModel):
    error_code: str       # 机器可读，供模型分支判断
    message: str          # 人类可读描述
    recoverable: bool     # Agent 是否可以重试？
    suggested_action: str # Agent 下一步应该做什么

# 记录未找到：可重试
return ToolError(
    error_code="RECORD_NOT_FOUND",
    message="No user record found with ID 'usr_123'.",
    recoverable=True,
    suggested_action="Use list_users() to get valid user IDs before calling get_user()."
)

# 配额超限：不可重试
return ToolError(
    error_code="QUOTA_EXCEEDED",
    message="API quota for this tool has been reached for today.",
    recoverable=False,
    suggested_action="Notify the user and stop. Do not retry this tool today."
)
```

`recoverable` 标志和 `suggested_action` 字段是改变 Agent 行为的关键。没有它们，模型会对不可重试的错误进行重试，或者放弃本可恢复的操作。

##### 5. 幂等的状态变更操作

每个改变状态的工具——创建记录、发送消息、转账——都必须能够安全地被调用两次。实际中，Agent 会重试，网络会失败，LLM 循环可能因为没有收到第一次调用的确认而发起第二次调用。

防止重复副作用的简单方法是为每个写操作要求一个幂等键（Idempotency Key）：

```python
@tool
def send_email(
    to: str,
    subject: str,
    body: str,
    idempotency_key: str = Field(
        description="Unique key for this send operation. Use a hash of recipient + subject + timestamp. "
                    "Same key on retry returns the original result without re-sending."
    )
) -> dict:
    """Send an email. Idempotent: the same idempotency_key will not trigger a second send."""
    existing = idempotency_store.get(idempotency_key)
    if existing:
        return existing
    result = email_service.send(to=to, subject=subject, body=body)
    idempotency_store.set(idempotency_key, result, ttl=86400)
    return result
```

没有幂等性保证，瞬时故障很容易转化为重复操作。

#### 什么无效

##### 1. 未经筛选的 API 薄封装

将 Agent 指向一个 REST API 并直接将其暴露为工具，是最常见的捷径，也是最常见的生产故障来源。为开发者构建的 API 暴露的细节往往远超 Agent 的实际需求。响应中包含数百个字段，即使只有少数几个是相关的。它们依赖分页，使用不透明的内部 ID（几乎没有上下文含义），并返回需要深度领域知识才能解读的错误码。

专门构建的封装层在内部处理分页，只投射 Agent 需要的字段，并将 API 错误映射为上文讨论的结构化 `ToolError` 格式。Agent 永远不需要构造 API 路径或管理分页；它接收的是可以推理的类型化对象。

也就是说，过度封装同样有害。如果每个端点都变成一个独立的、狭窄定义的工具，没有共享结构，工具表面就会变得碎片化，模型更难导航。目标不是最大化抽象，而是构建一致的、对 Agent 友好的抽象层。

##### 2. 将所有工具加载到每个上下文中

随着工具目录规模增大，准确率会下降。LongFuncEval（2025 年一项关于长上下文中工具调用性能的研究）发现，即使在具有 128K 上下文窗口的模型中，随着工具目录规模的增加，性能也会显著下降。将所有工具加载到每个系统提示词中，会在任何任务内容处理之前就消耗掉 Token 预算，使问题雪上加霜。

动态工具加载可以解决这两个问题。确定当前步骤需要哪些工具，只加载那些：

```python
STEP_TOOL_MAP = {
    "research": ["search_documents", "search_web", "get_url_content"],
    "write":    ["create_document", "update_document", "format_text"],
    "send":     ["send_email", "post_to_slack", "create_calendar_event"],
}

def get_tools_for_step(step_type: str, available_tools: list) -> list:
    relevant_names = STEP_TOOL_MAP.get(step_type, [])
    return [t for t in available_tools if t.name in relevant_names]
```

在每一步只暴露一小部分相关的工具子集——而非全量工具集——通常可以提高选择准确性并降低每次调用的 Token 成本。

##### 3. 静默的部分成功

当工具只完成了请求工作的一部分，却返回了看起来完全成功的响应时，部分成功就成了问题。Agent 会在系统状态不完整或具有误导性的认知下继续执行。

这通常发生在工具抑制内部失败、只返回成功部分结果的时候：

```python
# 这个版本会静默误导 Agent
@tool
def bulk_create_tasks(tasks: list) -> dict:
    created = []
    for task in tasks:
        try:
            result = task_api.create(task)
            created.append(result.id)
        except Exception:
            pass  # 静默失败：这是 Bug
    return {"created": created}

# 这个版本让部分成功变得显式
@tool
def bulk_create_tasks(tasks: list) -> BulkCreateResult:
    created, failed = [], []
    for task in tasks:
        try:
            created.append(task_api.create(task).id)
        except TaskCreationError as e:
            failed.append({"input": task.title, "reason": str(e)})
    return BulkCreateResult(
        created_ids=created,
        failed_items=failed,
        success=len(failed) == 0,
        partial_success=len(created) > 0 and len(failed) > 0
    )
```

`partial_success` 标志给模型提供了可以据此分支的信息：重试失败的项、将部分结果展示给用户，或终止工作流。

##### 4. 重叠的工具名称与描述

当两个工具做类似的事情时，模型在每次调用时都要推理该用哪个。这种推理消耗 Token 并引入错误。一些常见例子：

- `search_documents` 和 `find_documents` 用途相同
- `get_user` 和 `fetch_user_profile` 差异不明确
- `create_task`、`add_task` 和 `new_task` 是同一操作的三个工具

在这些情况下，仅仅重命名不是解决方案。每个工具都需要一个无需参照工具集中其他工具就能描述清楚的用途。如果一个描述需要"不同于 X，这个是……"才能理解，那就是设计问题。工具蔓延——太多范围重叠的工具——是企业部署中 Agent 行为不可靠的根源。

##### 5. 缺少确认闸门的破坏性操作

任何执行不可逆操作的工具——删除记录、给真实用户发消息、执行金融交易——都需要结构性的两步确认，而不是提示词中的"你确定吗？"。分阶段的方法引入了一个显式的确认边界，降低了意外或未授权执行的风险。

最安全的模式是将暂存与执行分离，并在两步之间要求一个短生命周期的确认令牌（Confirmation Token）：

```python
@tool
def stage_deletion(record_ids: list[str], reason: str) -> StagedDeletion:
    """Stage records for deletion. Does NOT delete anything.
    Returns a confirmation token that expires in 60 seconds.
    Call confirm_deletion() with this token to proceed."""
    token = generate_deletion_token(record_ids)
    staged_deletions[token] = {"ids": record_ids, "expires": now() + 60}
    return StagedDeletion(token=token, records_to_delete=len(record_ids), expires_in_seconds=60)

@tool
def confirm_deletion(token: str) -> DeletionResult:
    """Execute a staged deletion. IRREVERSIBLE. Confirm only after explicit user approval."""
    staged = staged_deletions.get(token)
    if not staged or staged["expires"] < now():
        raise ValueError("Token invalid or expired. Stage the deletion again.")
    # proceed
```

两次独立的工具调用意味着模型无法在单次推理步骤中完成破坏性操作——而这正是关键所在。

⚠️ 注意：然而在许多系统中，两步安全流程本身往往并不充分。即使使用了暂存和确认，仍然需要额外的安全措施——如短生命周期的一次性令牌、严格的会话绑定和重放保护——以防止令牌重用、泄露或跨会话执行绕过预期的安全边界。

#### AI Agent 工具设计决策一览

每一行代表 AI Agent 工具设计中的一个关键决策：

| 设计领域 | 有效做法 | 无效做法 |
|---------|---------|---------|
| 工具范围 | 每个工具单一职责 | 基于 action 参数的工具，如 `manage_database(action="create")` |
| Schema | 严格：枚举、验证器、类型化字段 | 松散：自由字符串、无类型字典 |
| 描述 | 包含范围边界和"何时不该用" | 仅覆盖正常路径 |
| 写操作 | 带幂等键的幂等操作 | 发射即遗忘，无重试安全保障 |
| 错误返回 | 结构化：error_code、recoverable、suggested_action | 未处理的异常或无类型字符串 |
| 工具数量 | 按步骤动态加载 | 所有工具加载到每个上下文 |
| API 封装 | 面向 Agent 的专建封装层 | 未经筛选的 API 暴露 |
| 部分成功 | 返回中包含显式的 partial_success 字段 | 静默吞掉异常 |
| 破坏性操作 | 两步：暂存 + 确认 | 单次调用即删除/发送/执行 |
| 工具重叠 | 语义清晰，部署前审计 | 相似名称和描述相互竞争 |
