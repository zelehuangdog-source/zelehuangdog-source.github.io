#### 构建优秀的垂直领域 Agent

如何构建一个在某个领域真正表现出色的 Agent——一个客户因为它「更好」而选择它的 Agent？

过去一年，基础已经标准化了：Agent 就是围绕模型的一个 while 循环，不断调用工具直到任务完成。给它一个文件系统、一个 shell，让它通过这些完成大部分工作。你可以在一个下午写出来，大多数人也确实这样做了。每个人都能构建 Agent——这真的没那么难，正如我接下来会阐述的，它也没那么深奥。把一个好 Agent 和一个玩具区分开的不是聪明，而是对你所在领域的深刻理解，以及在少数关键位置做些枯燥而细致工作的耐心。

我花了将近一年时间构建 Shortcut Agent，它被广泛认为是最准确的电子表格 Agent——部署在全球四大多策略对冲基金中的三家，在那里犯错的代价很高，没有人会"看在努力的份上"打分。我们没有微软或 Anthropic 的渠道分发能力。我们拥有的是 Agent 更准确，而在这个领域，这就是客户选择我们的唯一最有说服力的理由。所以 Agent 性能是我每天都在思考的问题。

而我不断遇到的空白是：关于构建 Agent 的文章很多，但关于构建**好的** Agent 的很少。看看这个领域在工具数量这样基础的问题上分歧有多大——Codex 和 Claude Code 各自配备了约 30 个工具；Pi 只有 7 个。当主流 Agent 在最基本的设计问题上相差 4 倍时，这是一个信号：没有公认的原则。所以我在分享我的原则，来自一年的构建实战，希望为每个编写自己 Agent 的人揭开这个过程的面纱。

核心论断是：**一个好的 Agent 是对其任务分布的忠实压缩**。本文的其余部分只是解释这句话的含义，以及它迫使你构建什么。

#### 上下文即分层缓存

假设你不拥有运行环境，也没有训练模型。那么你能设计的只有三样东西——系统提示词（system prompt）、工具（tools）和制品（skills、精选文档、参考资料）——它们本质上是同一样东西：Agent 的**上下文**。

所以这个问题很容易陈述。在模型固定的情况下，准确率是上下文质量的函数：臃肿的上下文埋没信号，缺失的上下文迫使猜测，两者都会损害准确率。而准确率就是你在卖的东西——这个关系不是线性的，一个得分 99% 的任务价值是 95% 的 10 倍。

但你的用户不会带来均匀分布的问题。他们带来的是一条长尾：

```
  频率
     |
     | ████
     | ████
     | ████
     | ████
     | ████
     | ████
     | ████
     | ████
     | ████
     | ████ ▓▓▓▓
     | ████ ▓▓▓▓ ░░░░ ░░░░ ░░░░ ░░░░ ░░░░ ░░░░ ░░░░
     +----------------------------------------------------> 任务多样性

   ████  日常高频任务         每次会话的主体
   ▓▓▓▓  关键但不频繁         每次会话出现几次
   ░░░░  长尾任务             每种都很少见——但种类很多，
                             而且每种都必须能处理
```

Agent 必须处理所有这些。但它不可能在上下文中同时持有所有东西的并集——那就是"提示词臃肿"的失败模式。所以真正的目标比"让所有东西可用"更尖锐：**最小化每个任务的上下文开销，在任务分布上取平均值**。

这恰好是 CPU 面临的问题。一个程序可能触及 GB 级的数据，但紧挨处理器的存储空间很小——所以计算机将内存按层级堆叠：一个小而即时的缓存（L1），更大但更慢的层级在下面（L2、L3），然后是主存和磁盘。它之所以有效，是因为访问模式同样是长尾的：把热数据放在快速层，只为罕见的数据去访问慢速层。"缓存未命中"（cache miss）就是你需要的东西不在快速层，你必须付出代价从更慢的层获取——这正是你在常见路径上要避免的开销。

Agent 应该具有相同的结构。将你的上下文构建为 L1 / L2 / L3：

```
       +---------------------------------------------+
  L1   |  常驻 - 小而即时                              |
       |  覆盖 80%。存在于系统提示词中。               |
       +---------------------------------------------+
                  |  未命中 -> 一次廉价调用
                  v
       +---------------------------------------------+
  L2   |  按需加载 - 精选的英文规范文档                 |
       |  覆盖接下来的 ~15%。一步发现即可加载。        |
       +---------------------------------------------+
                  |  未命中 -> 读取 skill，然后搜索
                  v
       +---------------------------------------------+
  L3   |  兜底出口 - 原始 API 全集                     |
       |  覆盖长尾。3-6 次 grep 调用即可挖掘到。       |
       +---------------------------------------------+
```

几乎每一项优化都是在**信息压缩**与**发现速度**之间做权衡。把某个东西放在 L1，它是即时的，但不管用不用都要在每个任务上花费 token。把它推到 L3，在需要之前零成本——但一旦需要就要花好几次工具调用才能找到。你的工作是将每个能力放在**在分布上总成本最小**的层级。这就是全部技艺。让我用我最熟悉的领域来具体说明。

#### 题外话：一个工具，而非三十个

在讨论层级之前，先说底层基础设施。我即将描述的每一个电子表格能力——每次读取、每次写入、每次精选查找——都是在**单个工具**下执行的代码。

```typescript
async function execute() {
  const data = await sheet.getCellRange("Sheet1!A1:D200");
  // ...读取、计算、写入...
}
```

Agent 编写代码；代码调用我们的函数；函数操作表格。没有 read_range 工具，没有 write_range 工具，没有 make_chart 工具。只有一个工具，API 存在于代码内部。

为什么？因为**模型准确率随着工具数量增加而下降**。这在我们自己的实验中一直如此。你添加的每个工具都意味着提示词中更多的 schema、更多的混淆面、更多选错工具的方式——尤其是当工具之间职责重叠时。一个 `execute_code` 工具将所有决策折叠为一个——写代码——并让模型用编程语言的全部表达力来组合能力，而不是将僵硬的工具调用拼接在一起（关于这一点将在以后的文章中详述）。

这对层级很重要，因为它意味着所有三个缓存层级都可以从同一个地方到达：模型总是在写代码，L1/L2/L3 只是它知道可以调用哪些函数，以及找到它们需要花多少功夫。

#### L1——日常高频：读写单元格

这是 80%。如果读写单元格区域做得不好，其他一切都不重要。所以这里是我们投入了不成比例的巨大努力的地方。看看一个 `getCellRange` 实际上做了什么。

##### 读取一个区域是一种压缩行为

读取一个 200 行的收入表：

```
公式用 F1、F2 等缩写。

A2:North | B2:1200 | C2:9.99 | D2:11988(F1)
A3:South | B3:840  | C3:9.99 | D3:8391.6(F1)
A4:West  | B4:1500 | C4:9.99 | D4:14985(F1)
... (196 more rows, each one line) ...

=F1 -> =RC[-2]*RC[-1]

--- 样式模式 ---
D2:D201: 200 cells (numbers)
  → numberFormat:#,##0.00, font.color:#1A7F37
A2:A201: 200 cells (text)
  → font.bold:true

--- 上方单元格的上下文 ---
A1:Region | B1:Units | C1:Price | D1:Revenue
```

这里发生了三件事。

**第一，公式别名化。** 一个 500 行的列 `=A2*B2`、`=A3*B3`……是 500 个几乎相同的公式。我们将每个公式归一化为 R1C1 形式——所以 `=A2*B2` 和 `=A3*B3` 都变成 `=RC[-2]*RC[-1]`——计算模式出现次数，任何出现超过十次的模式都折叠为一个短别名如 F1。模型看到 F1 重复加上一行图例，而不是 500 个公式。大量 token 节省，零信息损失。

**第二，免费的行列上下文。** 当你读取 C5:E20 时，那些裸数字意味着什么？我们向左扫描找行标签，向上扫描找表头行（通过投票选择哪一行有最多文本单元格来确定表头），然后附加上去，这样模型免费获得 `Region | Q1 | Q2` 和 `North America | …`，永远不需要猜测一堆数字代表什么。

**第三，样式压缩。** 格式也是信息——一个加粗红色、`0.00%` 数字格式的单元格在告诉你某些东西——但列出每个单元格的完整样式会淹没数值。所以我们按相同样式对单元格分组，将每组折叠为其连续区域，每组打印一行：区域、单元格数量和简洁描述。

六百个公式变成了一行图例。四百个带样式的单元格变成了两行。模型从未明确请求的表头行就在底部。这就是整个表格，无损地，只用了原始转储的一小部分 token。每一条都是压缩与发现的权衡，在常见情况下取得了决定性胜利。

##### 写入单元格：告诉模型它实际改变了什么，以及什么看起来不对

写入比看起来更难，因为单次 `execute_code` 调用可以改变数百个单元格，Agent 需要知道发生了什么而不用重新读取整个表格。所以代码运行后，我们返回一个结构化的变更 diff——同样重要的是，我们对其进行压缩和分类。

代码：

```typescript
async function execute() {
  const rows = await sheet.getCellRange("Sheet1!A2:C201");
  for (let i = 0; i < rows.length; i++) {
    const r = i + 2;
    await sheet.setCell(`D${r}`, `=B${r}*C${r}`);
  }
}
```

返回的 diff：

```
--- 单元格变更摘要 ---
(显示格式化后的显示值。∅ = 未定义/空。)

  无问题的变更：共 199 个单元格
    Sheet1!Row 2 (D): 1 cells
      → D2: ∅ -> 11,988 [=B2*C2]
    Sheet1!Row 3 (D): 1 cells
      → D3: ∅ -> 8,391.6 [=B3*C3]
    ... (采样行) ...
    Sheet1!Row 201 (D): 1 cells
      → D201: ∅ -> 4,995 [=B201*C201]
    ... 另有 189 行

  需要审查的单元格：
    必须修复: INVALID_FORMULA: 共 1 个单元格
      Sheet1!Row 57 (D): 1 cells
        → D57: ∅ -> #REF! [=B57*C57]
```

两种压缩在起作用。

**第一，diff 是分组和采样的，而非全量转储。** 变更的单元格按工作表和行分组，每行显示为列范围加计数（`Row 2 (D): 1 cells`），每组只打印确定性采样的单元格和行，其余用"… 另有 N 行"汇总。两百次写入变成少量，Agent 仍然知道总数。

**第二，diff 是分类的。** 干净的写入归入"无问题的变更"。任何看起来可疑的——无效公式如 `#REF!`、未标记的硬编码数字、隐藏在公式内的硬编码数字、不合理的超大百分比——被拉到"需要审查的单元格"部分，最严重的标记为「必须修复」。那个第 57 行的 `#REF!` 在两百个绿色 diff 的墙中很容易被忽略；在这里它被带标签地置顶展示。反馈循环不是"这是变化了什么"，而是"**这是变化了什么，这是你可能做错的部分**"——Agent 自身编辑的内置 linter。

**L1 一句话总结：** 频率曲线陡峭部分的操作获得了特征工程化的、token 压缩的、带后果报告的包装器，永久存在于提示词中。构建它们代价高昂，但你还是要构建，因为 Agent 在每个任务上都要付出这个成本。

#### L2——精选的英文文档，按需加载

你不可能把所有东西都放在 L1。条件格式、数据透视表、图表、数据验证、复制/移动语义——每个都很重要，每个在一次会话中出现几次，每个都有足够大的面积使得写在系统提示词中会让每个不用它的任务变得臃肿。这就是经典的 L2。

所以我们编写了精选的英文能力规范文档，按需获取，就像 skill 的 md 文件一样。模型从代码内部调用：

```typescript
console.log(general.getConditionalFormattingInfo());
console.log(general.getPivotTableInfo());
console.log(general.getChartInfo());
console.log(general.getDataValidationInfo());
console.log(general.getAPIInfo("addSpanAt"));   // 按名称查任何单个函数
```

这些不是类型签名的转储。它们是手写的散文——每个几百行——描述完成任务的规范方式，包括原始 API 永远不会告诉你的知识。以数据透视表规范为例。它不仅列出方法；它教你整个操作配方，按正确顺序：

```typescript
const pt = sheet.originalSheet.pivotTables.add("SalesPivot", "SalesData", 0, 0, ...);
pt.suspendLayout();
pt.add("Region",  "Region",        rowField);
pt.add("Quarter", "Quarter",       columnField);
pt.add("Amount",  "Sum of Amount", valueField, 8);   // 8 = sum
pt.resumeLayout();
```

它还内化了那些你原本只能通过反复失败才能学到的东西：你必须在批量修改前后使用 `suspendLayout()`/`resumeLayout()`，否则表格会在每次调用时重建；值字段的聚合必须作为原始整数传递（8 表示求和），因为友好的枚举在运行时不存在。这些都不是古怪的坑——它是正确操作透视表的实际形态，由已经付过学费的人写下来一次。

**关键属性：在任务需要之前零 token 成本。** 一个从不碰透视表的任务永远不会为透视表文档付费。一次 `console.log` 就是全部发现成本——单次缓存未命中，快速送达。

##### 同样的思路，用于可执行工具

L2 不仅用于文档。我们对延迟加载的工具——web_search、web_crawl、create_website 等——应用了完全相同的模式。它们的 schema 不在提示词中。取而代之的是一个元工具墙：

```typescript
get_tool_info("web_search")   → 返回 schema，标记为"已获取"
execute_tool("web_search", …) → 除非你先获取过它，否则拒绝执行
```

已获取工具的集合，字面意义上就是一个会话级缓存。模型加载一次 schema，从此它就是常驻的。同样的压缩与发现权衡，同样的解决方案：保持提示词小，在你实际需要能力时付一步未命中的代价。这和 Claude 上的延迟工具（deferred tools）是同一个思路，但我们不被锁定在某个供应商的工具加载特性上来获得这种行为。

#### L3——原始全集，以及映射它的 skill

然后是长尾：那个我们从未包装过、也从未为其编写规范的晦涩功能。你无法预料它——按定义就是如此。但 Agent 仍然必须能够到达那里，否则它会碰壁并任务失败。具体来说，这些请求会落到这里：

- "在每行添加一个迷你图（sparkline）来总结其趋势"——sparkline 是一个真实存在但很少被触及的 API 面。
- "将图表的副轴设为对数刻度，只重新着色第三个系列"——一个深三层的图表属性，没有精选规范会去覆盖。
- "从这个单元格插入一个超链接到那个命名区域，并将这些形状分组"——绘图/形状/超链接的角落，之前没人问过。

所以 L3 是完整的原始 API——整个 Office.js 表面（Excel 插件）或整个 SpreadJS 表面（Shortcut web），转储到磁盘。它是一个机器生成的参考，有 7 万行长。它包含一切。它也完全不适合作为提示词上下文——你永远不会把它粘贴进去。

**诀窍：你给它一个 skill——一个简短的地图，教它如何用 bash 来挖掘这本全集：**

```bash
# 来自 advanced-api SKILL.md —— 推荐的工作流程
grep -n '"charts.add"' api-reference.json -A 5   # 查找一个方法
grep -n '"pivots\.' api-reference.json | head     # 列出一个命名空间
grep -n '"ChartConfig"' api-reference.json -A 10  # 解析一个类型
grep -n '"isEnum": true' api-reference.json -B2 -A10  # 枚举所有枚举
```

这个 skill 大约 100 行。它说：这是结构，这是每个方法和类型条目的形状，这是针对每种问题的 grep 配方。有了它，Agent 从"我读不了的数万行"变成"找到我需要的签名的 3-6 次 grep"。这就是 L3 的访问成本——真实存在，但有界，而且只有到达这么深的罕见任务才需要付出。

系统提示词明确告知了这个兜底出口，这样模型知道路径存在以及何时走它：

> API 层级——有 2 个级别的 API 能力。包装 API：便利函数；部分直接列出，其他通过 `getAPIInfo(...)` 获取。绝不猜测——完整阅读文档。原始 API：当包装 API 不能满足需求时使用……如果包装 API 做不到，就用原始 API——不要妥协。

最后一句就是 L3 的全部意义。Agent 永远不应该被卡住。它可以在 L1 未命中，降到 L2，如果精选规范也沉默，就下沉到原始全集，仍然能在合理的调用次数内找到答案。

#### 提示词预算的实际分配

值得看看 token 花在了哪里，因为层级直接体现在系统提示词的形状中。

提示词的大部分是 L1——大约几百行。核心读写操作、`execute_code` 的约定、关键类型以及 Agent 在几乎每个任务中使用的那几个方法，加上执行和安全准则。这是每次调用都常驻的部分，所以也是我们最努力保持紧凑的部分。

L2 是顶部的薄薄一层——大约 50 行。它不是规范本身；而是一个精选的"经过认证"的方法允许列表和指示器，告诉 Agent `getXInfo(...)` 规范存在以及何时去获取它们。规范的实际内容在 `console.log` 拉取之前不会进入提示词。

L3 本质上是 5 行，skill.md 的名称和描述，以及散落在其他地方的引用。原始参考——7 万行——完全存在于磁盘上，永远不会触及提示词。常驻的只是简短的 skill 文件和 API 层级部分中指向它的一行。

所以预算镜像了频率曲线：大部分提示词花在 80% 的情况上，一点用于标示 15%，几乎没有用于长尾——这恰好是缓存层级框架所预测的分配。

#### 这个配方，移植到你的领域

电子表格只是我的例子。这个结构可以转移到任何领域。那些系统提示词和精选规范中的压缩实际上是对你的用户分布和他们所做任务的编码——而你，在你的领域中，比任何人都更了解那个分布。所以你的工作归结为三个问题：

**1. 你把什么包装进 L1？** 频率曲线陡峭部分的日常高频操作。让它们在 token 效率和速度上做到极致，让它们报告后果。在这里投入不成比例的努力——Agent 在每个任务上都要付出这个成本。

**2. 你把什么延迟到 L2？** 重要但不频繁的能力。将它们写成精选的、英文的、包含踩坑经验的规范文档，一步发现即可到达。编码规范的操作配方和约束，而不仅仅是签名。

**3. 你的兜底出口（L3）是什么？** 原始、完整的底层基础——加上一个教 Agent 如何挖掘它的 skill。它不需要符合人体工学。它必须可达、完整，并且在有限步骤内可以找到。Agent 必须能够——并且将会——最终找到正确的信息。

把这三个位置安排对了，你就构建了一个 Agent：在常见情况下快速，在偶尔的情况下有能力，在罕见的情况下也永不真正卡住——同时保持上下文足够小以让模型保持敏锐。

#### 层级不会消失——它在移动

最后一个观察。什么算 L1 不是固定的；它随模型能力漂移。

早期、弱小的模型需要微小的、单一用途的工具和所有东西都拼写出来。今天的模型可以一次性吸收更大的 L2 规范，并在更多原始 L3 细节上进行推理而不会崩溃。所以随着模型改进，昨天的 L3 变成明天的 L2，昨天的 L2 折叠进 L1。Agent 的职责向外扩展；层级向下滑动一个级别。

但层级本身永远不会消失——因为上下文相对于你可能放入其中的所有东西将永远是稀缺的，噪音将永远损害准确率。没有任何模型大到"在正确的时间把正确的东西放在它面前"不再重要。

更大的上下文窗口诱惑人们粘贴更多东西进去。更好的直觉是 CPU 几十年前就确立的那个：**摘要放在缓存里，细节按需加载，原始基础作为最后手段**。像构建内存层级一样构建你的 Agent 上下文，准确率自然随之而来。
