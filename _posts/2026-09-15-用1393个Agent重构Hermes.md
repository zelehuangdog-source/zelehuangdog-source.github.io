> **摘要**：Nous Research 创始人 Teknium 让日常使用的 Hermes Agent 去清理一个超过一百万行非测试 Python 代码的仓库，主任务跑了约 19 个有效小时、派出 1,393 个子 agent，并发峰值 218 个，最终把代码量削减 34.4%，`gateway/run.py` 从 34,847 行降到 5,512 行。模型成本约 1.93 万美元，而手工完成这项工作的估算成本是 15 万到 180 万美元、耗时 2 个月到 2 年。文章也如实记录了代价与翻车点：中途 token 过期导致任务中断、worker 误删外部插件依赖的 public 名称、自动改写引入 65 处异常处理回归，以及拆分文件带来的模块数和 import 依赖上升。核心经验是让 agent 把每次协作中学到的流程和纠正沉淀成可复用的 skill，再分享给整个团队——下一次重构可以直接从这一次的经验起步。

或者说：如何用 1.9 万美元的 token 换出 180 万美元的价值

---

*一句话总结：Hermes Agent 自主啃完了大约一百万行毫不起眼的清理工作，把 Teknium 和团队解放出来，继续给用户推新功能。*

我们迟迟没有对 Hermes（我们的开源 agent）做一次彻底清理，因为那意味着要把工程师从开发功能和修 bug 中抽调出来。到 9 月，这个仓库的非测试 Python 代码已经超过一百万行，光是 `gateway/run.py` 就有 34,847 行。我想要更小的文件、可共用的辅助函数，以及在出问题时不用再啃那些巨型函数。

9 月 2 日，我让我平时用的那个 Hermes agent 来做这次清理。主任务跑了大约 19 个有效小时，派出了 1,393 个子 agent，并发峰值达到 218 个。经历一次重启、一个接续会话，再加上两轮社区 review 和修复，我在 9 月 4 日合并了[那个 PR](https://github.com/NousResearch/hermes-agent/pull/102117)，非测试 Python 源码减少了 34.4%。

模型成本估算下来，主任务约 19,300 美元，算上后续几个会话大约 2.5 万美元，其中不包含人工 review 的时间。而我们粗略估算，如果让一个小团队手工做这件事，需要 2 个月到 2 年，成本在 15 万到 180 万美元之间。在还有其他东西要交付的情况下，我们实在排不出这个资源。

我每天都用 Hermes Agent 来开发 Hermes Agent。我们一起修 bug、review 改动，Hermes 会记下哪些做法有效；当我纠正它的思路，或者它自己摸索出解决新问题的正确路径时，它会更新自己的 skill。到我提出这次重构时，它已经学会了我的习惯做法和标准，并且能把这套东西用在一个大得多的任务上：

> *我要一大批以精简为目标的 PR，或者一个大的整合 PR 也行。我要代码行数大幅下降，整体至少降 30%。我要把那些「上帝文件」拆开。我要全面的精简。我要把可复用的 helper 和方法统一起来。我要少一些 if-if-if-if-if-if-else 式的分支路由。我要代码可读性更高。我要整个代码库、以及各部分之间的关联更容易理解。我要优雅。我要把多余的、臃肿的垃圾代码清理掉。所有这些都要彻底做完。不许找借口。不许停下来等我决策。全部做完，做完之后给我一个或一组 PR。*

我用了 `/goal`——它会给 Hermes 一个常驻目标，让它在本来要停下来的时候继续往下做。

#### 真正的自我改进

我的 `hermes-agent-dev` skill 是从我在这个仓库的日常工作中长出来的。每当我们敲定一套流程，或者我纠正了一个错误，Hermes 都会（自动）察觉到，并把可复用的经验存下来。日积月累，它攒下了关于怎么准备 PR、该避开哪些走捷径的做法、以及如何验证改动的各种说明。[Skill](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills) 就是一批可读的 Markdown 文档，需要时还会带上参考文件和脚本，agent 可以在后续任务里加载它们。Hermes 会在工作中自己编写和修订这些 skill。

现在这版 `hermes-agent-dev` 里，针对检查失败有一条这样的指示：

> *在干净环境里用 `origin/main` 的 HEAD 复现一下，确认这个问题是不是本来就存在*

也就是说，在未改动的代码上跑一遍失败的测试，判断问题是不是你的改动引入的。重构过程中 Hermes 用的也是同类对比方法：它先立了一个冻结的基线，在合并各个 worker 的改动时拿失败项跟基线对照。

我会把这个 skill 发给我们所有工程师。他们可以装进自己的 Hermes 环境里，让自己的 agent 用上我在这些会话里沉淀出来的流程和纠正。这样他们不用重跑一遍那些会话，也能拿到成果，而且他们的 agent 在用的过程中还能继续调整这个 skill。

#### 重构是怎么跑起来的

编排者（orchestrator）先度量代码库，把它切成 36 个互不重叠的分组。它结合我的目标和累积下来的指导，直接写好了书面任务说明，我不需要再逐个向 worker 交代。

worker 用的是 git worktree——各自独立的代码检出，改起来不会互相覆盖文件。它们拿到的任务说明里写清楚了三件事：要精简哪些代码、必须保持不变的是哪些接口、提交前要跑哪些检查。

有些 worker 又把自己的任务再往下分。整棵树在最上层那个 agent 之下延展了三层；而最上层这个 agent 自己不动源码，只做协调：写任务说明和脚本、读 worker 的报告、合并分支、跑检查。

Hermes 在一台 i7、64 GB 内存的台式机上，用一个 Python 进程来协调这些 agent。它们的工具跑在本地子进程里，推理则由远端的 Claude Fable 5.1 完成。

这个 agent 会拿特定接口跟原代码做核对。比如，某个工具的 JSON schema 必须完全一致；某个 CLI 命令的 `--help` 输出可以逐字节比对。此外，worker 每完成一个通过验证的步骤就必须提交一次。

跑了大约五十分钟，服务商的认证 token 过期，由此引发的一连串失败把整个任务打断了。好在 worker 的提交和任务说明都还在。我另开了一个 Hermes 会话来诊断这次失败、整理出一份交接说明，再把它交给恢复后的会话。Hermes 于是把 worker 派回去检查自己已保存的改动、修补没做完的抽取，然后继续往下做。

对于 `gateway/run.py` 这个最大的文件，worker 把消息分发、流式处理、RPC 和生命周期管理拆成了不同模块。在其他地方，它们合并了重复的 helper，并把按名称写的长 `if/elif` 判断链换成了分派表。

review 阶段发现，有些 public 名称因为仓库内找不到调用方，被 worker 删掉了，但外部插件是可能 import 它们的。另外，一次针对 `suppress()` 调用的自动改写，顺带改变了大约 65 处的异常处理。这些都是真实回归，而现有测试没测出来。我们在合并前用两轮社区 review 把它们修掉了，[合并之后又跟进修复了一些](https://github.com/NousResearch/hermes-agent/issues/103563)。

#### 代码是不是更好用了？

PR 里前后对比的度量数据，显示了代码改动的幅度：

| 指标 | 重构前 | 重构后 |
| --- | --- | --- |
| 非测试 Python 代码行数（所有目录） | 1,063,826 | 698,363 |
| 超过 5,000 行的文件 | 37 | 6 |
| 超过 300 行的函数 | 192 | 2 |
| 最长的 `if/elif` 链 | 92 个分支 | 9 |
| `gateway/run.py` | 34,847 行 | 5,512 |

对人来说更好导航的代码，对 agent 是不是也更好用？把一个函数拆开，函数定义本身是变短了，但 agent 可能得跟着调用跳到别的文件里去。我们针对这个问题做了一部分验证：在重构前后两个版本里，模拟查找同样的 4,000 个符号。每次查找先定位定义，读一个 60 行的窗口；只有当定义超出这个窗口时，才继续按 2,000 行的窗口读下去。

每次查找平均返回的 token 数从 2,218 降到 993。需要再读一个窗口的查找次数从 628 降到 184。原先要读几万个 token 才能看清的几个函数，现在几千个 token 就够了。

需要说明的是，这里量的只是查找成本，并没有测 agent 实际完成工程任务的表现。而且查找 token 数的中位数其实上升了：注释和 docstring 变少之后，同样行数的窗口里代码更密。平均值下降，是因为那些超大函数定义被削得小了很多。

代价也有。拆文件让模块数量和 import 依赖变多了，有些入口的 import 时间变长。这次重构让一个个零件更好读了，但并没有解决它们之间所有的耦合，仍有 6 个文件超过 5,000 行。

[基准测试数据](https://gist.github.com/teknium1/a7adb797243d6355c76abc9cae88838b)里包含了查找结果，以及依赖和运行时的度量。

#### 经验教训

同时跑几百个 worker，也暴露出 Hermes 自身可以改进的地方。比如，不同 worktree 里的 worker 各自启动了大约 30 份 Pyright（Python 语言服务器），吃掉了约 8.7 GB 内存。后续一个改动让所有 worktree 共用一个服务器，并加了实时检查，确认每个 worktree 依然能收到诊断信息。我们还减少了重复的 HTTP transport，修掉了那些让已结束的 agent 留在内存里的引用。

我们还改了未来 worker 会收到的任务说明和检查项。现在仓库里有了关于文件大小、函数复杂度、以及新行为该放在哪里的指引，并按领域拆开，这样 worker 在需要的时候能拿到对应的规则。我们还加了一项检查，用来标出被删掉的 public 名称，并为 review 补了测试。

我的 Hermes skill 也自动吸收了这次重构的经验，我可以分享给团队。而这一切只花了我们估算的手工成本和时间的大约 1%。

这是 Hermes 对团队来说堪称超能力的一个绝佳例子：和 Hermes 一起把问题解决掉，让它记录下你们学到的东西，再让这份经验能被下一个任务、下一位工程师用上。下次我们再动重构，我的 Hermes 和用上了更新版 skill 的工程师，可以直接从这次的经验起步。
