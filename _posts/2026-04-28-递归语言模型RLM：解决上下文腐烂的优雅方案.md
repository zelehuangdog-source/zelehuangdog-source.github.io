MIT 的研究人员最近提出了一个巧妙的方案，解决了现代大语言模型最大的局限性之一：**上下文腐烂（Context Rot）**。

#### 什么是上下文腐烂？

你把一份 200 页的文档粘贴到 ChatGPT 里，问一个简单的问题，返回的答案却是错的——尽管信息就在第 53 页。

你并没有超出上下文窗口。模型只是因为要处理的内容太多，推理能力变差了。

他们提出的优雅修复方案叫做**递归语言模型（Recursive Language Models）**。结果非常惊人，而核心思想却出奇地直观。

让我们一步步来理解。

---

#### 问题本质：上下文腐烂是推理失败，而非窗口不够

一个标称 100 万 token 上下文窗口的模型，在处理 5 万 token 的文档时仍然可能输出垃圾——原因和能塞进多少文本毫无关系。

前沿模型在「大海捞针」基准测试中表现优异。你在一堆填充文本中藏一句奇怪的话，问模型那句话的内容，模型能找到。

但那个测试衡量的是**在一堆 token 中的检索能力**，而不是**跨这些 token 的推理能力**。

前沿模型能通过大海捞针测试。但当你要求它们在成千上万条埋藏的条目中进行计数、分类或推理时，性能就崩溃了。

你自己可能也注意到了：
- 长时间的 Claude Code 会话变得迟钝
- 冗长的 ChatGPT 对话需要更多重复提示
- 模型并没有在幻觉，它只是随着上下文增长而变「笨」了

---

#### 解决方案：递归语言模型（RLMs）

核心思想很简单：

**不要强迫模型一次性处理所有内容，而是让它把上下文拆成小块，递归处理。**

关键转变是**以上下文为中心的分解**：
- Agent 框架基于人类设计的步骤来分解任务
- RLM 让模型**自己分解上下文**

模型变成了一个分析数据集的程序员，而不是临考抱佛脚的学生。

---

#### RLM 的工作原理

##### 1. 将查询与上下文分离

在普通的 LLM 调用中，查询和完整上下文一起塞进同一个 prompt。你希望模型看到的一切都必须在生成开始前放进那个单一的 prompt 窗口。

RLM 打破了这个假设。上下文存在于 prompt 之外——放在一个运行时内存槽中——而根模型只看到问题和一组工具。

类比 Jupyter Notebook：你把一个 DataFrame 加载到名为 `df` 的变量中，之后每个单元格都引用 `df`，而无需重新上传 CSV。

RLM 借用了完全相同的心智模型。那份 200 页的文档变成了一个变量（假设叫 `ctx`），存在于一个 REPL 环境中，模型通过工具调用与之交互。

##### 2. 模型获得工具

根模型无法直接读取 `ctx`，所以整个设计的成败取决于它用来探查该变量的工具。论文给了模型四个工具，它们一起覆盖了数据分析师会用到的所有访问模式：

- **Peek（窥探）**：查看上下文的前 2000 个字符，了解结构
- **Grep（正则搜索）**：用正则表达式过滤相关行
- **Partition（分区）**：将上下文分割成更小的块
- **Recursive Call（递归调用）**：在这些块上递归调用自身

##### 3. 策略从任务中涌现

Agent 框架传统上会硬编码分解方式。人类预先选好步骤、顺序和回退策略，模型只是扮演人类已经编排好的角色。

RLM 做的恰好相反。根模型根据它在探索过程中发现的内容来决定如何拆分问题。

它可能先 grep，再 partition；也可能先 peek，再 summarize。它自己摸索出策略，而不是遵循人类设计的工作流。

---

#### 一个具体的例子

假设你有 5000 条客户支持工单，你问："在用户 12345、67890 和 11111 中，有多少问题是关于账单的？"

**普通 LLM** 收到全部 5000 条工单，试图扫描所有内容，然后在计数时出错。

**RLM** 的处理方式不同：

1. **Peek 查看结构**："每行包含 日期、用户ID、问题"
2. **Grep 目标用户**，将 5000 行缩减到 50 行
3. **发起递归调用**："将每条分类为'账单'或'其他'"
4. **返回最终结果**

整个过程中，根模型的上下文始终保持很小。没有腐烂。

---

#### 为什么这很重要

- **无上下文腐烂**：无论文档多大，准确率都能保持
- **无限上下文**：1000 万 token？多分几次区就行
- **可解释**：能清楚看到模型做了什么
- **成本高效**：多个小调用比一次巨大的 API 调用更划算
- **面向未来**：随着 LLM 的进步，RLM 自动跟着进步

---

#### 总结

RLM 将上下文视为**待编程探索的数据**。

模型结合了代码执行和语言推理。这不是摘要，不是僵化的 Agent，而是模型根据它发现的内容来决定如何分解问题。
