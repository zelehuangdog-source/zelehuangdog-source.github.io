#### 摘要

Martin Fowler 在本文中提出了一个深刻的观点：代码始终服务于两个相互交织的目的——**给机器的指令**和**问题领域的概念模型**。随着 LLM 将代码生成迅速商品化，机械地编写指令不再是核心价值，真正重要的是第二个方面：通过代码构建和打磨精确的**领域词汇表**。

文章的核心论点包括：

1. **代码即词汇**：好的代码库本质上是领域词汇的精确表达，开发者的核心工作是将业务领域语言翻译为技术结构。
2. **词汇需要迭代发现**：正确的抽象不会凭空出现，而是通过 TDD、与领域专家的紧密协作、以及持续重构逐步浮现。
3. **认知债务是 LLM 时代最大的风险**：LLM 能以极快的速度生成看似合理的代码，但如果团队对背后的概念模型缺乏理解，代码库就在积累"认知债务"——有词汇无理解。
4. **好的代码本身就是最好的 LLM 上下文**：具有稳定抽象和清晰语义的代码结构，比任何精心设计的提示词都更能约束和引导 LLM 产出可靠的结果。

对开发者而言，编码的未来不是更快地写更多代码，而是构建更好的概念模型、更精准的词汇、更坚实的代码基础——让人类和 LLM 都能在其上高效工作。

#### 什么是代码？

代码是什么？从高层来看，这个问题的答案似乎显而易见。代码是开发者编写的东西：用编程语言表达的指令，告诉机器该做什么。多年来，写代码意味着逐字逐句地敲出来。进步的衡量标准是代码的生产、编译、测试和部署效率。借助现代 LLM，我们不再需要逐字敲出每一行代码。大量可执行代码现在可以从高层描述中生成。这引出了一个更深层的问题：如果生产代码变得更廉价，代码中还有什么是有价值的？

#### 代码的两个方面

代码始终服务于两个截然不同但又相互交织的目的。

第一，代码是给机器的一组指令。它指导计算、移动数据、与存储交互、协调执行。在 LLM 时代，这是正在被商品化的部分。

第二，代码是问题领域的概念模型。这就是"设计"方面。一个设计良好的代码库不仅包含给机器的指令，还包含供人类和工具进行推理的概念。

我们称之为"编码"的活动，正是这两个方面交汇的地方。我们在塑造用于理解系统的概念、名称、边界和关系。

#### 概念模型与词汇

使概念模型显式化是编码更深层的方面，它由系统要解决的领域和用例驱动。每个领域都有既定的流程、实践，更重要的是——共享词汇。这个词汇正是概念模型变得可见的地方。

词汇通常被理解为在特定语言或学科中使用的一组词语。我之所以能写这篇文章，是因为我掌握英语词汇。读者之所以能读懂，是因为他们与我共享这些词汇。

但要理解这篇文章，仅仅懂英语是不够的。这篇文章是关于软件开发的。软件开发是一个广泛而成熟的领域，有自己的专业词汇。当我使用"抽象"这个词时，我不仅仅是在用一个普通的词。我指的是一个特定的软件开发概念，有着自己的含义、历史和深层意味。一个不熟悉软件开发的读者可能在表面理解这个词，但会错失它在此语境下的深层含义。这些具有自己既定词汇的成熟领域被称为"领域"（domain）。

这在所有严肃的领域中都是如此。沟通依赖于共享词汇。无论我们是与人、框架还是 LLM 沟通，我们使用的词语必须映射到接收方能够理解并据此行动的概念。

#### 代码中的词汇

一个设计良好的代码库是某种词汇的表达。代码中的词汇从何而来？这正是软件开发独特本质真正闪耀的地方。软件开发工作在多个领域的交汇处。一端是银行、金融、零售、库存、医疗、保险等业务领域，另一端是 Web、基础设施、AI、数据工程等技术领域。

做 Web 开发的人需要深入理解 Web 架构、Web 方法的语义、GET 的通用缓存特性以及这些语义的深层含义。不懂这些的人无法很好地架构复杂系统。在其他领域也是如此。词汇不仅仅是标签的集合，它承载着含义、约束和设计后果。

以零售领域为例。当我们为零售编写代码时，我们谈论客户、产品、订单、发货、支付等。当我们为零售领域做 Web 开发时，代码包含将零售领域映射到 Web 领域的概念。例如，Catalog（商品目录）是一个资源，我们可以用 GET、POST、PUT、DELETE 等 HTTP 方法对它进行操作。编写代码的人需要同时熟悉这两套词汇。

**为一个领域编码，从根本上说是一种翻译行为。** 开发者将领域词汇映射到技术领域的词汇上。在这个过程中，借助编程语言提供的构造，一套新的词汇也在被构建。有诸如日志、仓储、法定人数、事务等概念，也有像"金额"这样的特定概念。概念变成类型，关系变成接口，规则变成不变式，工作流变成组合。

变量的精确命名、方法的边界划分、类的层次结构，都是一步步发现的。正确的抽象往往不是一开始就显而易见的；它只有在你不断地根据现实世界的约束来塑造和重构代码时才会显现。用得好的话，代码会慢慢变成领域本身的一种可读的、高度精确的表达。

对于技术领域，我们通常会找到提供基础实现模式的框架和库。**框架和库是被编码化的词汇。** 它们捕获了最常见的使用模式。这就是为什么像 Spring Framework 这样的生态系统存在——用于构建涉及 Web、集成和相关关注点的企业应用。不同的编程语言带来各自的风格，以及反映在其框架和库中的特定设计约束。

#### 限界上下文与本地词汇

当一个领域拥有稳定、重复出现且语义广泛共享的结构时，框架运作良好。但像"在线零售"或"证券交易所"这样的领域则不同。它们不仅仅是技术栈。没有通用高层框架的主要原因是：**词汇在该领域的所有实例之间不够稳定。** 试图寻找通用抽象的努力，要么变得过于泛化而失去实用价值，要么过于主观而无法广泛应用。越接近核心业务模型，抽象就越需要在本地发现。这就是为什么领域驱动设计（DDD）中**限界上下文**的概念如此重要。限界上下文标记了特定词汇和模型有效的边界。同一个词在不同上下文中可能意味着不同的东西，每个上下文都需要自己的抽象、规则和语言。

我们如何构建这些本地抽象和词汇？大量的词汇是通过迭代的编码和反思会话来构建的。像 TDD 这样的技术非常适合这种词汇的迭代开发。它们通过在模型和行为之间强制持续反馈，帮助我们发现正确的名称、正确的抽象和正确的边界。

编码不能孤立进行。领域专家、用户和开发者之间必须有紧密的协作。这种协作对于构建这些本地抽象和词汇是必不可少的。

这与敏捷软件开发的经验教训直接相关。对个体和互动、客户协作、可工作软件和响应变化的强调，不仅仅是流程建议，而是通过反馈来发现和完善词汇的一种方式。

领域驱动设计通过**通用语言**（ubiquitous language）的概念使这一点更加明确：一种由开发者和领域专家共同开发、并不断通过可工作软件来验证的共享语言。

#### 编程语言作为思维工具

通过代码构建词汇需要积极参与编写和重塑代码，而不仅仅是被动审查生成的代码。深入思考代码的行为，往往只有在我们主动编写代码时才会发生。**编程语言及其构造和约束本身就成为了思维工具。** 不同编程语言提供的设计约束帮助塑造我们的思维。Go 的通道和轻量级线程、Java 的面向对象模型、Rust 的所有权模型——都推动我们以特定方式看待结构、边界和权衡取舍。从这个意义上说，编程语言不仅帮助我们表达设计，它们还帮助我们发现设计。

我最近必须为异步编程示例设计一个自定义的 Future 实现。Future API 的一个重要方面是设计组合操作，使其能够表达一系列动作：

```java
var future1 = action1();
future1.thenCompose(val1 -> action2(val1))
       .thenCompose(val2 -> action3(val2))
```

掌握函数式编程的概念和词汇对于良好实现这个 API 至关重要。不了解这些概念会导致笨拙的实现和使用。

有时候，编程语言的语法可能过于冗长，掩盖了解决方案的底层结构。例如，最近在为我的工作坊开发快照隔离实现时，用纯英文描述核心需求有些模糊，而用 Java 代码又过于冗长。像 TLA+ 这样更受约束的形式化规范会有所帮助。但即使编写一页伪形式化规范也有很大帮助：

```
Begin(T, coord):
  R(T) := HLC(coord).now()
  writeSet(T) := {}

Read(T, N, key):
    N.HLC.tick(R(T))
    return latest committed version of key with ts <= R(T)

Write(T, N, key, value):
    N.HLC.tick(R(T))
    if LatestCommittedVersion(key).ts > R(T):
        abort T
    place provisional intent for (key, value)
    writeSet(T) := writeSet(T) union {key}
```

这个伪形式化规范帮助我厘清了思路，并成为后续讨论、实现和通过测试进行验证的良好基础。

#### 与 LLM 协作

将"编码视为词汇构建"对 LLM 有重要意义。LLM 是从大量文本和代码语料中训练出来的。它们学习了名称、API、库、框架、习惯用法、设计模式和实现结构之间反复出现的关联。当它们看到 Controller、Repository、Reducer、ConsensusModule 或 TransactionLog 这样的词时，这些名称不仅仅是标签，它们携带着与已知代码结构和预期行为的关联。

这就是为什么在与 LLM 协作时词汇很重要。如果我们的提示使用模糊或不一致的语言，模型就不得不猜测我们意图中的设计。如果我们的代码库使用不清晰的名称和不一致的概念，模型就缺少可以遵循的稳定结构。但当词汇精确、一致并体现在代码中时，LLM 就能更可靠地将我们的意图映射到有用的实现。

#### 认知债务

这也解释了 LLM 辅助编码的一个特定危险：**认知债务**。当词汇、抽象和结构被使用，而与之共事的人并未充分理解其含义时，认知债务就会累积。LLM 放大了这一风险，因为它们能以极快的速度生成大量看似合理的代码。生成的代码可能包含控制器、仓储、Reducer、工厂、事务、调度器或其他看起来很熟悉的结构。代码可能能编译通过，甚至可能通过基本测试。但如果团队不理解这些结构背后的概念模型，代码库就在没有共享理解的情况下获得了词汇。

**问题不在于 LLM 生成了代码。问题在于代码引入词汇的速度快于开发者建立理解的速度。** 这个差距正是认知债务的主要来源之一。

#### 代码作为共享概念模型

正如我们在《与 LLM 一起设计抽象》中所讨论的，编写代码有两个深度交织的活动：**发现抽象**和**应用抽象**。发现抽象是我们构建词汇的过程。一旦建立了强大的词汇，它就代表了一个共享的概念模型。一旦这个模型存在，编码的大部分工作就变成使用这个概念模型来构建用例。这正是优秀的库和优秀的基础代码大放异彩的地方。这是我们试图隐藏编程语言和环境的复杂性、为我们构建的词汇提供越来越接近英语的界面的部分。一种典型的方式是构建 DSL（领域特定语言），使得使用这些词汇或抽象变得简单且接近自然语言。

LLM 在这方面表现出色。它们为你的抽象词汇提供自然语言接口。最棒的是，如果你的抽象词汇背后有可执行代码，它本身就是 LLM 纠正错误的优秀护栏。好的抽象、可执行行为、测试、类型和不变式都有助于约束模型，使其输出更有用。

我们可以用词汇来构建外部 DSL。LLM 作为外部 DSL 之上的自然语言接口运作得非常好。我一直在使用 LLM 配合 PlantUML 等工具并取得了巨大成功。这并不令人意外，因为 LLM 在设计上最擅长映射词汇。

从这个意义上说，**强大的基础代码在 LLM 时代变得更加重要**。一旦系统的词汇已经成型，编码就不再是生产原始语法，而更多是使用一套成熟的概念语言来构建可靠的软件。

#### 代码本身作为约束和上下文

关于上下文工程和约束工程的大量讨论，将代码视为黑盒，认为正确生成代码的责任应由外部管理——通过在提示中提供正确的上下文，或通过规范、测试、静态验证等构建正确的约束，确保代码结构合理且按预期工作。

然而，**结构良好、抽象形成了定义明确词汇的代码本身，就是约束和上下文中最重要的部分。** 我一再看到，设计良好的代码能与 LLM 配合得非常好。更重要的是，当代码建立在具有清晰语义的稳定抽象之上时，你可以自由选择使用任何 LLM 模型，而不必过于担心提示的准确性。代码结构和配套测试本身就提供了使 LLM 输出可靠且有用的上下文和约束。

#### 结论

编码的角色并没有消失，但它正在改变。

随着 LLM 使代码生成变得更廉价，机械地编写指令的行为不再是核心。更重要的是使概念模型显式化、发现正确的词汇，并通过迭代、领域专业知识和反馈来完善这些词汇。这也是为什么编程语言继续深刻地重要。我们不应该是生成代码的被动审查者。编写代码的行为本身就是我们思维的一部分。

**代码仍然是给机器的指令。但它也是一种理解的模型。在 LLM 时代，这第二个角色变得更加重要。编码的未来不仅仅是更快地编写更多代码，而是构建更好的概念模型、更好的词汇和更好的基础，让人类和 LLM 都能在其上工作。**
